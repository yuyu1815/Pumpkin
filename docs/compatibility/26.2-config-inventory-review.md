## Findings

### INV-T1 / P1: transmute の material 数と multiplier が公式26.2と一致しない

- **場所 / symbol**: `crates/pumpkin-inventory/src/crafting/crafting_screen_handler.rs:208-260` の `recipe_matches`、`crates/pumpkin-data/src/generated/recipes.rs:8994-9002`、`assets/datapacks/26_2/data/minecraft/recipe/map_cloning.json:1-12`。
- **到達条件**:
  - `CraftingTransmute` が選ばれ、occupied slot が厳密に `2` 個のときだけ現状分岐に入る。
  - input/material の順序は今回の修正で検査されるが、material は `second_stack.item_count` の値で倍率計算される。
- **公式26.2との比較**:
  - 公式 JSON は `input=filled_map`、`material=map`、`material_count.min=1/max=8`、`add_material_count_to_result=true`。
  - 公式26.2 JAR の `net.minecraft.world.item.crafting.TransmuteRecipe` bytecode は、occupied な material slot を1個ずつ数え、`materialCount` boundsを検査し、`computeResultSize(materialCount)` で `result.count + materialCount` を計算する。`assemble` も input stackの component patchを result templateへ適用する。
  - したがって、filled map 1個 + blank map 8個を8 occupied slotに置く公式入力は、現状では occupied count `9` のため preview が出ない。逆に blank map stack count `8`を1 slotに置いたケースでは、現状は `1 + 8 = 9`を作るが、公式 bytecodeの material 数え上げはそのslotを1個として扱うため、同じ意味ではない。
- **期待値 vs 現状**:
  - 期待: material slot数が `1..=8` の valid inputを受理し、result数を base `1 + material slot数` とする。
  - 現状: occupied slot数を必ず2に限定し、単一material stackの item countを倍率に流用する。
- **最小修正**:
  1. codegen の `CraftingTransmute` modelに少なくとも `material_count` bounds と `add_material_count_to_result` を保持させる。
  2. matcherを「input 1 slot + material 1..8 occupied slots」にし、material item stack countではなく material occupied slot数を検査・加算する。
  3. `on_take_item` は input 1個と各material slot 1個を消費する。全transmuteへ map専用の推測分岐を残さない。
- **最小テスト案 / expected**:
  - `filled_map(map_id=42)` + blank mapを1, 2, 8 slotに分散: result count `2, 3, 9`、component id `42`、material各slot消費。
  - blank map 8個を1 slotにstack: 公式 oracleの slot-count semanticsを固定し、item-count semanticsを採用しない。
  - filled_map + filled_map、map + map、material上限9 slot: preview empty、消費0。
- **判定**: 現在の `map_transmute_preserves_components_multiplier_and_requires_material` は `1+1` の1ケースだけなので、この欠陥を検出しない。**要修正**。

### INV-T2 / P1: remainder の identityは cake 1回では合うが、公式 recipe remainder 経路を再現していない

- **場所 / symbol**: `crates/pumpkin-inventory/src/crafting/crafting_screen_handler.rs:428-443` `ResultSlot::recipe_remainder`、`:499-521` `ResultSlot::on_take_item`。参照 `crates/pumpkin-data/src/generated/recipe_remainder.rs:4-15`。
- **一致している点**:
  - 26.2 generated mappingの7件は、`mushroom_stew/rabbit_stew/beetroot_soup/suspicious_stew -> bowl`、`milk_bucket -> bucket`、`potion/honey_bottle -> glass_bottle`で、今回の hard-code identityと一致する。
  - cakeの `AAA / BEB / CCC`（milk bucket 3、sugar 2、egg 1、wheat 3）では、result pickup時に各 milk bucketを1個消費し、3 bucketをgridへ戻す経路になる。1回の空grid fixtureについては公式保存則と整合する。
- **相違 / 到達条件**:
  - 公式26.2 JAR `net.minecraft.world.inventory.ResultSlot::onTake` は、recipeの `getRemainingItems` を呼び、remainderの item/componentが既存gridと同じならstack、空ならgridへ戻し、それ以外はplayer inventoryへ入れて満杯ならdropする。現状は item IDの global hard-codeだけで、recipe-specific/special recipeの `getRemainingItems` を呼ばない。
  - `on_take_item` は通常 pickupだけでなく `CraftingTableScreenHandler::quick_move` / `PlayerScreenHandler::quick_move` からも到達する。capacity不足時は `offer_or_drop_stack` → `PlayerInventory::offer` → `InventoryPlayer::drop_item` に到達するので、dropの外側経路自体はある。
  - closeは `CraftingTableScreenHandler::on_closed` / `PlayerScreenHandler::on_closed` → `default_on_closed`（cursor）→ `drop_inventory`（grid）→ `offer_or_drop_stack`である。cursor/gridとも、満杯ならdropされる設計だが、今回のtestは空inventoryのみ。
- **期待値 vs 現状**:
  - 期待: recipeの remainder listをslotごとに適用し、partial/full inventory、cursor占有、closeの順序を含め合計保存する。
  - 現状: 26.2 generated mappingにある単純容器は合うが、generic recipe semanticsと特殊 recipeを「全て合う」とは言えない。`recipe_remainder` moduleはfeature-gatedのままで、crafting handlerは公式generated helperもrecipe resultも利用していない。
- **最小修正**: `RecipeResult`またはmatch contextにper-slot remainderを持たせ、公式同様 recipe-specific `getRemainingItems`相当を呼ぶ。少なくとも generated remainderを item ID hard-codeではなく一箇所の26.2 data sourceから参照する。
- **最小テスト案 / expected**:
  - cakeを空、同種partial stack、全main inventory満杯で pickupし、`cursor + grid + inventory + drops = input remainder + output`を数える。満杯時は bucket `3`がdropへ移る。
  - cursorに既存 itemを置いた状態でresult pickup、closeを実行し、cursor交換・grid remainder・close returnを別々に検査する。
  - potion/honey/stew各1レシピ、creative/non-creative双方を検査する。
- **creative境界**: 公式 `ResultSlot::onTake` bytecodeにも crafting resultのcreative特別分岐はなく、現状 `ResultSlot`が `is_creative`を参照しないこと自体は直ちに仕様違反とは断定しない。ただし本変更testは `DropRecorder::is_creative=false`のみで、creative実playerの cursor/remainder/drop は**未確認**。
- **判定**: cakeの狭い正常経路は merge可の根拠になるが、generic remainderとしては**未確認 / 要追加テスト**。

### INV-T3 / P1: test expectedが実装の限定分岐に合わせられており、公式 oracleの範囲を検証していない

- `docs/compatibility/26.2-inventory-remainders.md` の test `cake_pickup_returns_bucket_remainders_and_close_returns_cursor` は、現行 `crates/pumpkin-inventory/src/player/player_screen_handler.rs` では `run_cake_pickup_remainder(true)`だけを呼ぶ。2x2 player screenへ3x3 cakeを置かないfixture修正は妥当だが、player 2x2境界を検査したtestではない。
- `map_transmute_preserves_components_multiplier_and_requires_material` の expected `2` は JSONの base 1 + material 1と実装分岐が一致するだけで、公式 `material_count 1..8` の `3` / `9`、複数occupied slot、stacked materialの差を判定していない。
- 先行gateに記録された `cargo test --locked -p pumpkin-inventory -- --nocapture` の `32 passed / 0 failed` は既存記録として読むが、今回のレビューではcargoを再実行していない。その数値は公式26.2 differential proofではない。
- **判定**: 期待値を実装へ合わせただけと断定する直接証拠はないが、現testだけではそれを排除できない。公式JAR bytecodeから導いたINV-T1のケースを追加するまで、inventory互換を承認しない。

### INV-T4 / P1（隣接する既存経路）: stale closeが別windowを閉じてcursor/gridを返す

- **場所 / symbol**: `crates/pumpkin/src/net/java/mod.rs:1220-1223`、`crates/pumpkin/src/net/java/play/close_container.rs:5-7`、`Player::on_handled_screen_closed`。
- **到達条件**: `SCloseContainer.window_id`をdecodeした後、値を捨てて無条件に`player.on_handled_screen_closed()`を呼ぶ。AをcloseしてBをopenした直後の遅延A close、または不正window idで発火する。
- **期待値 vs 現状**: 期待は packet window id == current handler sync id のときだけclose。現状は現在handlerをcloseし、cursor/gridのreturn/dropを実行し得る。
- **最小修正**: `handle_close_container`へwindow idを渡し、`current_screen_handler.sync_id()`と比較して不一致なら無操作＋authoritative resync。通常player inventory id `0`の扱いを公式26.2 protocolと合わせる。
- **判定**: 最新remainder変更そのものではないが、依頼された close/cursor空間の経路にある正式コード欠陥。**要修正または別blockerとして追跡**。

### CFG-T1 / P1: resource-pack `Downloaded=4` を terminal と扱い、公式26.2の `isTerminal` と逆

- **場所 / symbol**: `crates/pumpkin/src/net/java/pending.rs:537-610` `PendingConnection::handle_resource_pack_response`、同 `crates/pumpkin/src/net/java/config/resource_pack.rs:5-99` `JavaClient::handle_resource_pack_response`。
- **公式根拠**: 公式26.2 JAR `net.minecraft.network.protocol.common.ServerboundResourcePackPacket$Action.isTerminal()` bytecodeは `ACCEPTED` と `DOWNLOADED`だけをfalse、それ以外をtrueにする。
- **到達条件**: pending resource-pack phaseでclientが response result `4 (Downloaded)`を送る。
- **期待値 vs 現状**:
  - 期待: `Accepted=3` と `Downloaded=4` は pendingのまま。`Successfully loaded=0`で configuration taskを完了し、Known Packsを送る。
  - 現状: `Downloaded | DownloadSuccess | Discarded | Unknown`を同一armで`send_known_packs`へ進める。clientが続けて `DownloadSuccess=0`を送ると phaseは`AwaitingKnownPacks`なので、正常な後続responseを「resource pack response without a pending ...」として拒否する。
- **最小修正**: `Downloaded`を`Accepted`と同じ待機armに移し、terminal matrixを公式 enumに合わせる。`DownloadSuccess`だけを正常完了としてKnown Packsへ進める。
- **最小テスト案 / expected**:
  - phase `AwaitingResourcePack`で `Accepted`: phase不変、Known Packs未送信。
  - `Downloaded`: phase不変、後続`DownloadSuccess`: `AwaitingKnownPacks`へ一度だけ遷移。
  - `DownloadSuccess`: Known Packs request 1回。
  - duplicate terminal response: phase guardで拒否し、二重Known Packsを送らない。
- **判定**: 正常download成功の確認を、途中のDownloadedで成功と誤認している。**要修正**。

### CFG-T2 / P1: Known Packsの任意selectionを受理するが、registry selection semanticsを無視する

- **場所 / symbol**: `crates/pumpkin/src/net/java/pending.rs:440-453`、`crates/pumpkin/src/net/java/login/known_packs.rs:5-30`。受信codec `crates/pumpkin-protocol/src/java/server/config/known_packs.rs:10-34`。
- **公式根拠**: 公式26.2 JAR `net.minecraft.server.network.config.SynchronizeRegistriesTask.handleResponse` は、client listがrequest listと `List.equals` ならrequested packsのSetでregistryを送る。不一致（subset、任意pack、順序違い、未知packを含む）は空Setでregistryを送るが、configuration自体はFinishへ進む。
- **到達条件**: phase `AwaitingKnownPacks`で、有効な count `0..64`・bounded string packetを送る。
- **期待値 vs 現状**:
  - 現状はbodyをdecodeしてtrailing bytesを拒否するphase/framing guardは正しいが、`known_packs`を捨て、`handle_known_packs`が常に全registry entryを送る。
  - そのため任意selectionでもstuckはしない一方、公式の「一致時のみknown pack registryを利用し、不一致時は空Setで同期」の意味と異なる。
- **最小修正**: request listをphase stateへ保存し、受信listを順序込みで比較し、registry serializerへ選択Setを渡す。不一致でもFinishへ進む公式動作は維持する。known packの単なるvalidity（count/string）とsemantic matchを分離する。
- **最小テスト案 / expected**:
  - exact list: registry dataはrequested pack set、Finish送信。
  - empty/subset/unknown/order違い: registry dataはempty set、Finish送信、stuckしない。
  - duplicate packet: phaseが`AwaitingFinishAck`になった後に再受信し、reject。
- **判定**: docsの「legal subsetを受け、semantic compareしない」は公式26.2実装とは一致しない。**要修正**。

### CFG-T3 / P1: future reconfigurationのphaseだけ追加され、受信dispatcherとsenderがない

- **場所 / symbol**:
  - `crates/pumpkin/src/net/java/mod.rs:80-103` `ConfigurationPhase`、`JavaClient::configuration_phase`。
  - `crates/pumpkin/src/net/java/play/configuration_acknowledged.rs:7-30`。
  - `crates/pumpkin-protocol/src/java/client/play/start_configuration.rs` の `CStartConfiguration`。
  - `crates/pumpkin/src/entity/player.rs:2512-2518` `process_inbound_packets` はplayer後段を常に `JavaClient::handle_play_packet`へ渡す。
- **到達条件**: 現在は`CStartConfiguration`のsend call siteがなく、`ReconfigurationAwaitingAck`へstoreするproduction callerもないため通常未到達。将来senderが`CStartConfiguration`を送り、clientがPlay `configuration_acknowledged`を返すと到達する。
- **期待値 vs 現状**: 期待は Play → reconfiguration ack → Config packet dispatcher → Known Packs/Registry/Tags/Finish → Play の一連のstateful transition。現状ack handlerはphaseを`AwaitingKnownPacks`、coarse stateを`Config`にするが、以後のserverbound Config packetを読むJavaClient側のdispatcherがない。player inbound loopはPlay parserを継続するため、Known Packs requestを受けてもphase handlerへ到達せずstuck/誤packet処理になる。
- **追加欠陥**: `crates/pumpkin-protocol/src/java/server/play/configuration_acknowledged.rs::SConfigurationAcknowledged::read` はpayloadを消費・empty検査せず、`mod.rs:1395-1397` callerも`payload.is_empty()`を確認しない。reconfiguration pending中なら任意trailing body付きackをphase transitionさせる。
- **最小修正**:
  1. senderを一箇所に限定し、送信直前に`Play -> ReconfigurationAwaitingAck`へCAS/guard付き遷移。
  2. JavaClient inbound loopをcoarse `ConnectionState`で分岐し、Config用packet decoder/handlerを実装する。既存Pendingとphase transitionを共有する。
  3. `SConfigurationAcknowledged` bodyがemptyであることをdispatch側またはcodec側で検査する。
- **最小テスト案 / expected**: senderなしではreserved/unreachableを明記。senderを追加する時点で、`CStartConfiguration`受信→empty ack→Known Packs exact/subset→Finish ack→Play、途中のPlay packet/Config packet混在、trailing ack、duplicate ack、disconnect各ケースをstateful testする。
- **判定**: unsolicited ackをPlayから勝手にConfigへ落とさない外側guardは改善しているが、reconfiguration互換を実装済みとは言えない。**未確認ではなく、現在は未実装経路として要修正**。

### CFG-T4 / P1（future caller向け）: JavaClient configuration duplicate pathがPendingとstatus policy不一致

- **場所 / symbol**: `crates/pumpkin/src/net/java/config/resource_pack.rs:10-86`、`crates/pumpkin/src/net/java/config/known_packs.rs:5-116`。
- **相違**:
  - `JavaClient::handle_resource_pack_response`も`Downloaded`を即`send_known_packs`へ進める。
  - `force`を`Declined`/`DownloadFail`のacceptance policyに使わず、invalid/reload/failもPending pathと別の扱いにしている。
  - 現時点のgrepではこれらJavaClient config handlersに通常のincoming callerはなく、initial configurationはPendingConnectionが処理している。そのため直ちにinitial接続へ発火するとは断定しないが、CFG-T3のfuture reconfiguration senderが追加されたときに二重policyとなる。
- **最小修正**: resource-pack status matrixを共通pure functionへ集約し、Pending/JavaClientの両方が同じphase transition、force policy、UUID policyを使う。
- **判定**: 現在の実到達範囲は未確認、future merge blocker。
