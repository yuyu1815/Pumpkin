# 26.2 直前修正 独立 read-only review

対象: Java Edition 26.2 / protocol `776` / world data version `4903`

判定: **追加修正必須**。`LoadedData::Error` を `ProtoChunk` へ降格しない主経路は確認できたが、load failure の DAG cancellation が直接の影響ノードだけで止まり、キャンセルした前段ノードの後続ノードを `drop_node` が再解放するため、失敗 chunk を間接的に必要とする generation task が再実行され得る。inventory 側は、追加テストが実処理の partial shift-click 経路に入っており、今回の狭い通常 recipe fixture では増殖を反証できている。ただし、その結論を remainder/component/special recipe 全体へ一般化してはいけない。

## Findings

### F-1 [P1 / 修正必須] LoadFailure が DAG の後続 task を誤って解放する

**場所 / シンボル**

- `crates/pumpkin-world/src/chunk_system/schedule.rs:972` `GenerationSchedule::drop_node`
- `crates/pumpkin-world/src/chunk_system/schedule.rs:1018` `GenerationSchedule::cancel_tasks_affected_by_load_failure`
- `crates/pumpkin-world/src/chunk_system/schedule.rs:1047` `GenerationSchedule::receive_chunk`
- `crates/pumpkin-world/src/chunk_system/chunk_state.rs:136-170`
  - `StagedChunkEnum::{get_read_radius,get_direct_dependencies}`
- `crates/pumpkin-world/src/chunk_system/schedule.rs:1492-1530`
  - generation task dispatch前の read-area pre-validation

**具体的な入力と呼出し経路**

1. chunk `A` の Empty-stage IO read が `LoadedData::Error` になり、
   `worker_logic.rs:199-204` から `RecvChunk::LoadFailure { pos: A, error }` が送られる。
2. 隣接 chunk `B` が Full まで要求され、`B` の stage chain に `Surface -> Carvers` が存在する。
3. `B:Surface` は `get_read_radius() == 1` なので、`cancel_tasks_affected_by_load_failure(A)` の `affected` に入る。
4. しかし `B:Carvers` は `get_read_radius() == 0` なので、`B != A` なら `affected` に入らない。
5. `receive_chunk(LoadFailure)` は失敗 holder の tasks を `drop_node` で削除する。その過程、または `cancel_tasks_affected_by_load_failure` が `B:Surface` を削除する過程で、`drop_node` は削除 node の outgoing edge を辿り、後続 `B:Carvers` の `in_degree` を減らす。`in_degree == 0` になると queue に積む。
6. `B:Carvers` は `B:Surface` の結果を受け取っていないのに、`schedule.rs:1495` の read-area check（radius 0、`B.chunk.is_some()`）を通り、`run_generation` へ進み得る。

このため「失敗 chunk を直接 read area に含む task は止める」という現在の cancellation だけでは、DAG の依存失敗を終端まで伝播できない。`Carvers` が `Noise`/古い stage の chunk に対して実行される、または `generation_cache` の stage invariant に到達して panic する可能性がある。これは単なる永久待機ではなく、失敗後に隣接 generation が不正に進む具体的な実行経路である。

**修正案**

- LoadFailure 時に、直接 read-area affected nodeだけでなく、そこから outgoing edge を辿る非 in-flight descendant を先に closure として収集し、全 descendant を terminal cancellation する。
- 収集後に holder task slot と `waiting_for_chunks` を消し、後続 node を queue に再投入しない cancellation helper を使う。通常の `drop_node` は依存が正常に完了した場合の `in_degree` 解放用なので、失敗伝播でそのまま使わない方が安全。
- in-flight node は強制停止せず、失敗 chunkを必要とする in-flight が通常の graph invariant 上存在しないことを test で固定する。もし存在し得るなら、generation result 側にも failure token を返して commit を無効化する。

**必要な test**

- `crates/pumpkin-world/src/chunk_system/tests.rs` に、`A` の load failure、`B` の `Surface -> Carvers` chainを構築する graph testを追加する。
- `B:Surface` を cancellation対象にした後、`B:Carvers` が queueに残らず graphから終端処理されることを assertする。
- 可能なら `receive_chunk(LoadFailure)`相当まで通し、`running_task_count`、`holder.tasks`、`waiting_for_chunks`、`queue`、`chunk_map[A].chunk`を確認する。

### F-2 [確認結果] LoadedData::Error は通常の worker 経路では空 chunk/save に流れない

**確認した経路**

- `crates/pumpkin-world/src/chunk_system/worker_logic.rs:112` `io_read_work`
  - `LoadedData::Loaded` は要求座標と payload座標を照合し、正常時だけ `process_loaded_chunk` → `RecvChunk::IO`。
  - `LoadedData::Missing` だけが `ProtoChunk::new` → `RecvChunk::IO(Chunk::Proto(...))`。
  - `LoadedData::Error` は `RecvChunk::LoadFailure`。
- `crates/pumpkin-world/src/chunk/io/file_manager.rs:272-302` `ChunkFileManager::fetch_chunks`
  - region serializer初期化エラーは `LoadedData::Error` を送る。
- `crates/pumpkin-world/src/chunk/format/anvil.rs:792-868` `AnvilChunkFile::get_chunks`
  - compression/NBT等の chunk entry errorは `LoadedData::Error((pos, err))`。
- `crates/pumpkin-world/src/chunk_system/schedule.rs:1047-1139` `receive_chunk`
  - LoadFailure branchは `holder.chunk = None` とし、`Chunk::Proto`/`Chunk::Level`を生成しない。
- `crates/pumpkin-world/src/chunk_system/schedule.rs:806-900`付近の `process_unload_queue`、`save_all_chunk`
  - failure holderは `chunk == None` なので save batchへ入らない。
- `crates/pumpkin-world/src/chunk_system/worker_logic.rs:214-265` `io_write_work`
  - LoadFailure自体を受け取る write channelはなく、失敗 payloadを保存する呼出しは確認できなかった。

したがって、通常の Anvil region read/parse/decompression errorについて、今回の分離後も「Error → 空 Proto → generation → dirty/save」という直接経路は見つからなかった。元資料の主張のうち、この部分は妥当である。

### F-3 [確認結果 / 未検証] waiter・channel は通常の current FileIO 実装では各座標1結果になるが、実処理 test がない

`io_read_work` は従来の batch channelをやめ、`worker_logic.rs:151-161`で各 `pos`について capacity `1`の channelを作り、`fetch_chunks`完了後に1件を待つ。現行 `ChunkFileManager`では、次の結果になる。

- current `ChunkSerializerLazyLoader::read_from_disk` はOSのNotFoundを `S::default()` に変換し、`AnvilChunkFile::get_chunks` はregion/slot内の未登録entryを明示的な `LoadedData::Missing(pos)` として送る。
- `get_serializer` が generic な `ChunkNotExist` error を返して早期returnする実装では channel close になり、workerの `unwrap_or(LoadedData::Missing(pos))` がMissingを補う。ただし current Anvil readのNotFoundはこの枝ではなくdefault serializerへ進む。
- region serializer初期化 error: Errorが1件送られる。
- entry parse/decompression error: Errorが1件送られる。
- valid entry: Loadedが1件送られる。

region-open errorをbatch先頭1件だけに送る `file_manager.rs:282-285` の契約に対し、workerが一座標ずつfetchするため、同じbatchの残り座標が永久に待つ旧経路は解消されている。current `AnvilChunkFile`/`Linear`/`Pump` の `get_chunks` は receiverが生きている限り各 requested coordinateを送る実装であり、region/slot absentも通常は明示Missingになる。通常のIO errorについて waiterが永久待機する直接経路は確認できなかった。

ただし、`io_read_work`の `t_recv.recv().await.unwrap_or(LoadedData::Missing(pos))` は「fetch_chunksが意図せず結果なしでreturnした」ケースまでMissingにする。現行実装で region absent を表す意図的な無送信と、serializer task panic/将来実装の契約違反を区別できない。後者ならworker task自体がpanicしてschedulerにterminal resultが届かず、shutdown待ちの5秒上限まで `running_task_count` が残る可能性がある。このケースは現在の通常実装からは再現確認できず、契約上の防御不足として未確定に留める。

**必要な test**

- TempDirの実Anvil fixtureで、同一regionの正常entry、slot absent、malformed compression/NBT、region header errorを `io_read_work`経由で確認する。
- requested座標ごとに結果が1件、LoadFailureの座標が正確、schedulerの `running_task_count` が0になることを数える。
- batch（最低2〜16座標）でregion-open errorを起こし、全座標にterminal outcomeが出ることを確認する。

### F-4 [確認結果] error文字列の無制限保持・LoadFailure直後の自動retry stormは見つからない。ただし明示的再入場にはbackoff/quarantineがない

- `LoadedChunkOutcome::Error`は`String`化され、`RecvChunk::LoadFailure`とlog処理を通過した後、holderに保持されない。
- `ChunkSerializerLazyLoader::get_or_try_init`はread errorを成功値としてcacheしないため、error mapが蓄積する実装ではない。
- `LoadFailure` branchは失敗holderのtaskを消すが、同じ`target_stage`を保持する。現行 `LevelChannel`の同一状態からは自動的に同じtaskを再作成しないため、受信直後の無限retryは見つからない。
- playerがunload→再入場する、または明示的なlevel transitionを繰り返すと、同じ破損entryを再読する。retry回数、quarantine、cooldownはないため、複数回の再入場を外部から連続させればIO/log stormになり得る。これは現在の変更が直ちに作る無限loopとは断定しないが、運用上の未解決事項である。

最小の後続案は、failure holderにlast failure / retry gateを持たせるか、上位APIで明示retryをrate-limitすること。ただし structured error/quarantine policyは今回の最小修正の外側であり、先にF-1の依存 cancellationを直すべきである。

### F-6 [確認結果] recipe outputと残りdrop/resultの二重計上は、狭いfixtureでは実際に検査できている

partial stack fixtureの数値は以下の通り。

- 初期: main inventoryのoak planks `62`、recipe preview oak planks `4`（previewは所有済み合計に含めない）。
- 搬送: existing stackへ`2`を受け入れ、残り`2`を`DropRecorder::drop_item`へ渡す。
- 最終: inventory `64` + drop `2` + cursor `0` + result `empty` = 操作前所有 `62` + recipe output `4`。
- `assert_all_main_stacks_within_limit`でmain inventory各stackがmax以下。
- full inventoryでは inventory/drop変化なし、材料oak log `1`とresult preview `4`を保持。
- ingredient `2`の repeated caseでは既存QuickMove内部反復により output `4 * 2 = 8`、2回目の再QuickMoveはno-op。

`owned_output_total`がresult previewを除外するのは正しい。previewを含めると操作前から未取得の4個を所有済みとして二重計上するためである。その代わり、各testはresult slot、grid、cursor、dropを個別にassertしており、今回の経路で「inventory + drop + result」を同じoutputとして残すことは検査できている。

なお、`DropRecorder`はworld entityのtick/pickup/persistenceを再現しないtest doubleである。drop callbackに渡されたcountを保存則へ入れる検査としては十分だが、実world drop lifecycleまでは未検証である。

### API caller追跡の要点

- `RecvChunk`の生成は主に`worker_logic::io_read_work`と`run_generation`。
- `RecvChunk`の消費は`GenerationSchedule::work`内の`recv_chunk` drain / timeout箇所から`receive_chunk`へ集約される（`schedule.rs:1364,1390,1650,1699,1725`付近）。
- `LoadedData`のchunk saver callerはworker、entity saver callerは`level.rs`に別途存在する。entity saverの`Missing | Error`統合は、今回のworld chunk corruption修正の対象経路とは別である。
- save側は`process_unload_queue`と`save_all_chunk`がholderの`chunk`を起点にbatchを作るため、LoadFailureで`chunk=None`にする設計自体は原本上書き防止になっている。

## Recommended Next Steps

1. **最小の必須修正: F-1のfailure propagationを直す。** `drop_node`による通常のin-degree解放をLoadFailure cancellationに直接流用せず、失敗前段のtransitive descendantsをqueueへ解放しないterminal cancellationにする。
2. `crates/pumpkin-world/src/chunk_system/tests.rs`へ、`A load failure -> B Surface canceled -> B Carvers must not run`を固定するgraph testを追加する。`in_degree`だけでなく、queue、holder task slot、waiting set、current stageを確認する。
3. TempDir Anvil fixtureで、合法正常entry / absent slot / malformed compression or NBT / malformed region headerを`io_read_work`からscheduler受領まで通す。終了条件は、各requestが1件のterminal outcome、`running_task_count == 0`、failure holderの`chunk == None`、region bytes unchanged。
4. channel closeとMissingの契約を明示する。現行FileIO実装のregion absentをMissingとする必要があるため、少なくとも「意図的なabsent」と「unexpected early close/panic」を同じ`unwrap_or(Missing)`に隠さないintegration testまたはAPI契約を追加する。
5. inventoryは**このINV-01 fixtureについてはmerge可能な反証**と扱う。production inventory logicを「直した」とは報告しない。remainder/component/transmute/special/dynamic/recipe-bookをINV-03として別test群に分離する。
6. 実client確認が可能になった場合のみ、partial stackのGUI traceとdrop/result/cursor final stateをvanilla 26.2と比較する。今回のtest doubleはdrop callbackまでであり、vanilla完全互換の証明ではない。

**最終判断:** 現状態は **追加修正必須**。理由はF-1のDAG cancellationが、破損chunkを直接参照しない後続stageを`drop_node`経由で再開させる具体的なgeneration pathを残しているため。inventory側の最小後続タスクは、現行通常recipe fixtureの限定を維持し、remainder/component等を別INV-03検証へ持ち越すことである。
