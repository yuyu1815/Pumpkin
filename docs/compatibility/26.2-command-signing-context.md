# 26.2 signed-command execution context (minimum seam)

## Scope

This change carries the already verified signed-command argument result into the
existing command executor. It does not redesign the command framework or create
a second parser. `CommandDispatcher::execute_with_signing_context` consumes the
existing `ParsingResult` once; the signed packet is never reparsed after the
`PlayerCommandSendEvent` check.

## Official 26.2 placement

Read-only static evidence was taken from the repository-external
`C:/Temp/minecraft-26_2-inner.jar` and existing `javap` artifacts:

- `C:/Temp/javap-ServerGamePacketListenerImpl.txt:4502-4565` parses once,
  creates `CommandSigningContext.SignedArguments`, maps the same parse result,
  and calls `Commands.performCommand`.
- `C:/Temp/javap-ServerGamePacketListenerImpl.txt:4567-4661` resolves each
  entry by parsed argument name, verifies the parsed raw value, and uses
  `Map.put`; a duplicate therefore selects the last value for the consumer.
- `C:/Temp/.../CommandSigningContext.java` exposes only
  `getArgument(String) -> PlayerChatMessage`.
- Existing `javap-signable-parse` evidence identifies `MessageArgument` as the
  production `SignedArgument` consumer. Its argument name is the lookup key;
  the parsed range supplies the original value. Recipient display is applied
  later by the message/chat output path, not by signature lookup.

The Rust seam mirrors only the part Pumpkin can safely consume now:
`CommandSigningContext::resolve(name)` returns either an authenticated
`Signed` value (raw value, node identity, signature bytes) or an explicit
`Unsigned` value. It never represents an unsigned value as signed. Duplicate
entries replace the map value only after the packet-entry verification path has
accepted them. The raw value is copied from `SignableArgument::raw_value`, not
from a typed parse result.

## Production connection

- `crates/pumpkin/src/net/java/play/chat_command.rs` builds the context after
  ACK, parse, name-set, permission, and signature policy checks. Secure entries
  become `Signed`; reports-disabled/no-session legal entries become `Unsigned`.
- The existing `/msg` executor is the minimum message consumer. It checks the
  resolved `message` argument against the already parsed name/node/raw range
  before using the parsed message for the existing recipient-display path.
  Event command mutation is still rejected, so a signature cannot be reused for
  a different command.
- The existing `Player::send_message`/disguised output path does **not** yet
  emit a signed `CPlayerChatMessage` for command arguments. Therefore this
  change proves context delivery and raw/name/node binding, but does not claim
  signed recipient display or full vanilla `MessageArgument.resolve` output
  compatibility.
