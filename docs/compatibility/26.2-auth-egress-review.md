# 26.2 signed-command auth / egress 独立 read-only review

## Findings

### 判定: 要修正（merge 不可）

安全側の reject と egress の単一 owner 化は確認できるが、公式 client/server と完全互換とは判定しない。重大な未解決は auth の実行時再parse、no-signable policy、ACK の順序/並行性、`try_kick` の disconnect race である。vanilla client round-trip はこの review では実施していない。

### Blocker A — 認証済み command と実行 command が一致しない（TOCTOU）

- `crates/pumpkin/src/net/java/play/chat_command.rs::JavaClient::handle_signed_chat_command` は `packet.command` を parse して raw argument を署名検証する。
- その後 `SChatCommand { command: &packet.command }` を作るが、`execute_chat_command` は `PlayerCommandSendEvent` 後の `event.command` を `dispatcher.handle_command` へ渡し、別の parse を実行する。
- 従って、署名済み `/demo safe` に event handler が `/op` または別の command を代入すると、署名は元 command のまま別 command が実行される。command registry/source の変更も検証と execution の間に入り得る。
- 公式 `C:/Temp/javap-ServerGamePacketListenerImpl.txt` の `performSignedChatCommand` (4502–4567) は parse result を signing context で map した後、同じ ParseResults を `Commands.performCommand` (offset 44–71) へ渡し、再parseしていない。

**最小反証 test:** signed packet の `packet.command="/demo safe"` を固定し、`PlayerCommandSendEvent` handler が `event.command="op"` に変更する fixture を作る。RSA/ACK/chain が成功しても executor が `op` を受けないこと、または変更を reject することを assert する。

**最小修正:** 認証済み parse result をそのまま execution へ渡す。既存 event の command mutation を残すなら、mutation 後に raw command/signature/name-set を再検証し、不一致時は execute せず reject する。署名成功後に通常 `handle_chat_command` を呼ぶだけでは直らない。

### Blocker B — no-signable signed command が secure session 必須になっている

- 現在の `handle_signed_chat_command` は `signable=[]` かつ `argument_signatures=[]` でも `chat_session.session_id != nil`、public key、certificate signature、expiry を要求し、さらに `verify_signed_command_and_commit` の sidecar state を要求する。
- `handle_chat_session_update` (`crates/pumpkin/src/net/java/play/chat_message.rs`) は `allow_chat_reports=false` なら session/state を install しない。その policy 下で no-signable `SChatCommandSigned` は実行不能になる。
- 公式 bytecode では `handleSignedChatCommand` が ACK (`unpackAndApplyLastSeen`) の後に `tryHandleChat(..., true, ...)` を呼ぶ。`collectSignedArguments` (primary artifact 4567–4661) は argument entries と parsed signable list が共に空なら `Map` を返し、`Decoder.unpack` を呼ばずに execution へ進む。これは secure argument signature が不要な command の合法境界である。
- したがって「signed packet は常に valid chat session 必須」とする現 docs の記述は、公式の no-signable/unsigned 境界より強い。安全な reject ではあるが完全互換ではない。

**最小反証 test:** `allow_chat_reports=false`、session UUID/key/state 未 install、parser の signable list empty、packet entries empty、valid ACK を用意し、ordinary command が一回だけ実行されることを確認する。別 test で signable list non-empty + entries empty は reject する。

**最小修正:** no-signable path を signed-argument decoder から分離し、ACK policy だけを適用して通常 permission path へ渡す。secure session/chain を要求する範囲は signable argument がある場合に限定する。プロジェクトとして常時 reject を選ぶなら、compatibility blocker として docs/contract に明記し vanilla compatibility claim を出さない。

### Blocker C — ACK の適用順と task ordering が公式/packet order と異なる

- 公式は `handleSignedChatCommand -> unpackAndApplyLastSeen -> tryHandleChat`。つまり ACK validation/apply が parse、argument name matching、signature verification より前である (`javap-ServerGamePacketListenerImpl.txt` 4480–4502, 4790)。
- Pumpkin は `handle_signed_chat_command` で parse、signable extraction、unknown/duplicate/missing set、session gateを先に行い、`verify_signed_command_and_commit` で初めて ACK preview を行う。invalid parse/name-set/session では valid ACK も適用されない。これは atomic policy としては安全だが、official order との互換差である。
- 実 caller では `crates/pumpkin/src/net/java/mod.rs::handle_play_packet` が `SChatAck` を同期的に `handle_chat_ack` へ渡す一方、`SChatCommandSigned` は `server.spawn_task` へ渡す。`crates/pumpkin/src/net/java/play/chat_ack.rs::handle_chat_ack` は `signature_cache.last_seen_validator` を直接変更し、`chat_lifecycle` を取得しない。従って signed task と後続/先行 ACK task の scheduling が packet arrival order を変え得る。

**最小反証 test:** 同じ player に signed command と `SChatAck` を連続投入し、signed handler を barrier で遅延させる。wire order が `signed -> ack` のときに ACK window、command execution、next index が `ack -> signed` 相当へ並び替わらないことを assert する。

**最小修正:** ACK、ordinary signed chat、signed command、session update を同一 `chat_lifecycle`/single inbound queue で順序化する。公式順序を採るなら signed command は先に ACK preview/apply、contract の atomic rollback を採るならその意図と差分を fixture/decision として固定する。現在の ACK direct caller を lock 外のままにしない。

### Blocker D — N-entry atomic commit は安全だが vanilla state semantics ではない

`crates/pumpkin/src/net/chat/state.rs::verify_and_commit_entries` は validator と inbound state を clone し、全 signature が成功した後だけ `cache.last_seen_validator` と `next_index` を一括 commit する。途中の signature failure は元 cursor/cacheを commitせず `broken=true` にする。single shared helper を N 回呼んで部分 commitする実装ではなく、この点は安全である。

ただし primary source は同じ動作ではない。

- 公式 ACK は signature/parse より先に validatorへ apply される。
- 公式 `SignedMessageChain$Decoder.unpack` は timestamp を更新してから RSA verifyし、valid entry ごとに `nextLink.advance()` する (`C:/Temp/javap-chat-chain-player.txt` 62–183)。N=2 の後半が失敗すれば、前半の chain advancement は rollback されない。
- 公式 `collectSignedArguments` は全 entry を packet entry order で処理し、最後に parsed args の missing checkをする。Pumpkin は name set を先に全検査するため、missing/duplicate/unknown を signature検証前に reject する。

これは部分 commitを防ぐ security policyとしては妥当だが、vanilla state transition と同一ではない。「safe reject = complete compatibility」と扱わないこと。exact compatibility を要求する場合は blocker、atomic project policy を採る場合は intentional divergence として acceptance contract に格上げすること。

### Blocker E — duplicate entry の reject は公式と異なる

`validate_signed_command_arguments` は duplicate name を即時 reject し、chain を broken にする。公式 `collectSignedArguments` は entryごとに `getArgument(name)` と `Decoder.unpack` を行い、mapへの `put` で同名 keyを上書きするだけで duplicate check がない。したがって、署名が各 packet-entry order/link index に対して有効なら、公式は duplicate entry を通し得る。

この reject は安全側だが、official behavior の証明ではない。missing/unknown と duplicate を同じ contract IDにせず、意図的に reject するなら互換差として記録する。

**最小 test:** N=1 parsed arg `message` に同名 entryを2つ、link index `i`/`i+1` 用の独立 valid signatureで送る。Pumpkin policy が rejectすることは確認済みだが、公式 static behaviorとの差を `deferred`/`policy_divergence` として fixtureへ記録する。

### Blocker F — `try_kick` は enqueue 直後に cancel するため disconnect frame が失われ得る

- `crates/pumpkin/src/net/java/mod.rs::JavaClient::try_kick` は disconnect packetを `enqueue_encoded(..., force_main_queue=true)` した直後に `self.close()` する。
- writer (`start_outgoing_packet_task`) は `packet_receiver.recv()` と `close_token.cancelled()` を select しているため、cancel branch が先に選ばれると disconnect packetを frame/write/flush せずに queue Drop へ送る。
- 実 caller は `crates/pumpkin/src/net/java/config/resource_pack.rs:67,75,90` の同期 `try_kick`。今回の `kick_flushes_disconnect_before_close` test は `kick_explicit(...).await` のみで、実際の `try_kick` race をカバーしていない。
- frame/write/flush failure 後に writerが `close_token.cancel()`、deferredをclear、loop exitする部分は後続処理を続けず、Dropが `Err(())` を返すため方向性は正しい。ただし disconnect-now ordering は未証明。

**最小反証 test:** writer taskを起動し、`try_kick` を反復実行して peer側で disconnect packet ID/frameを待つ。`pending_bytes==0` だけでなく、受信した frame が disconnect packetであることを assertする。

**最小修正:** async callerは `kick_explicit(..., true).await` に統一するか、writer queue内に「flush完了後 close」を表す close-after-completion itemを置く。enqueue後の即時 `close()` は順序保証にならない。

### Egress の確認結果（blockerでない部分）

- `OutgoingPacket::Drop` は `Err(())` と pending bytes解放を一度だけ担当し、writerは frame/write/flush 全成功後だけ `complete_success()` (`Ok(())`) を呼ぶ。正常 flush後の packet Drop は completion senderを消費済みなので二重通知しない。
- `start_reconfiguration` と `send_packet_now_data_inner` は `Ok(Ok(()))`/`Ok(())` のみを成功とみなし、sender close、frame/write/flush error、cancelを失敗として closeする実装になっている。
- public wrapper (`send_packet`, `send_packet_now_data`, typed wrapper) は completion結果を呼び出し側へ返さず捨てるが、inner側で failure時 closeするため、現時点で成功扱いに反転する caller は確認できなかった。呼び出し側が成功/失敗を必要とする APIなら `EgressCompletion` を返す別途修正が必要。
- `try_reserve_pending_bytes` の `checked_add` overflow は `Err(usize::MAX)` へ落ちる。release underflow は所有権不整合として panicを維持しており、これは invariantを壊さないための意図として許容する。

### Fixture / UTF-16 の判定

- `tools/compat-26_2/chat-fixtures/signed-command-independent.json` は Rust implementationから署名を生成していない test-only RSA/SPKI fixture。Node self-check は vectors `5`、arguments `6`、public DER `294` bytes、signature `256` bytes x6、canonical hash/RSA `6/6`、exit `0`。
- 現在の `crates/pumpkin/src/net/chat/signature.rs` の fixture unit test接続は canonical/hash/RSAの known-answerを固定するが、handler、ACK transaction、N-entry state commit、permission、vanilla runtimeを証明しない。
- `crates/pumpkin-protocol/src/java/server/play/chat_command_signed.rs` の read path は `get_str_bounded_borrowed(16)`。実装 (`crates/pumpkin-protocol/src/ser/mod.rs`) は先に最大UTF-8 byte数を `16*3` で抑え、最終的には `encode_utf16().nth(16)` で Java `readUtf(16)` 相当の UTF-16 code unit数を検査する。16 UTF-8 bytesと誤解している証拠はない。Unicode境界（8 BMP、8 supplementary/16 UTF-16 units、17 units、48 UTF-8 bytes超）は protocol testを追加すべき。
- packet writerの `SChatCommandSigned::write_packet_data` は entry nameの16 UTF-16上限とsignature 256 bytesを明示検査しない。ただしこれは serverbound inbound read boundaryではなく、known-answer encoder/test helperの契約欠落として扱う。

## Recommended Next Steps

1. **merge blockerを先に直す:** signed executionを元の parse resultへ結合する、または event mutationを署名再検証なしで許さない。`/demo safe -> eventでop` の最小 testを追加する。
2. **policy境界を決める:** no-signable signed commandを reports-disabled/no-sessionでも公式通り許すか、常時rejectを明示的な非互換 policyにする。no-signableとsignable-empty-entryを別 testにする。
3. **inbound orderingを一本化:** `SChatAck` direct mutationを`chat_lifecycle`またはsingle inbound queueへ移し、signed/ordinary chat/session updateとpacket arrival orderを保つ。ACK-firstを採用するかatomic policyをcompat contractに明記する。
4. **state semanticsを文書化/fixture化:** N=2後半失敗時のACK、cache、next_index、brokenの期待値を official mode と atomic mode のどちらかで固定する。safe rejectだけでpassにしない。
5. **egress:** `try_kick`を実 caller込みで flush-before-closeにする。`kick_explicit` testとは別に `try_kick` の disconnect packet ID受信 testを追加する。completion結果を必要とするAPI callerには `EgressCompletion`を返す。
6. **fixture:** independent KATのRust unit接続は維持し、次に handler/state integration（valid N=1/N=2、raw mutation、unknown/missing/duplicate、replay、ACK invalid、permission failure）を固定する。Java UTF-16 name length境界を追加し、fixtureは引き続き `vanilla runtime capture: false` と表記する。
7. 上記を確認するまで内部判定は **要修正**。公式 client未実施、runtime compatibility未主張、merge可へ変更しない。

## 2026-09 final must-fix follow-up

- **A resolved in source:** `JavaClient::handle_signed_chat_command` now keeps and executes the authenticated `ParsingResult`; `PlayerCommandSendEvent` mutation is rejected instead of reparsing a replacement command. The signed packet branch runs this authentication inline before the next inbound packet is handled.
- **ACK ordering tightened:** `handle_chat_ack` now shares `Player::chat_lifecycle` with signed authentication. This preserves Pumpkin's atomic reject/commit policy; it does not claim vanilla's ACK-first side effect order.
- **F resolved in source/test:** `try_kick` waits for the `OutgoingPacket` completion before canceling the writer, and `try_kick_flushes_disconnect_frame_before_close` received the disconnect frame on the production loopback TCP writer path.
- **N2 coverage added:** `signed_command_fixture_exercises_n2_atomicity_and_no_signable_ack` uses the independent RSA fixture through `verify_signed_command_and_commit`; valid N=2 advances `41 -> 43`, an invalid second signature leaves `next_index=41` and marks the chain broken, and zero-entry ACK-only verification leaves the index at `41`.
- **Residual compatibility limits are explicit:** official static order is ACK-before-parse/auth while Pumpkin intentionally uses atomic preview/commit; duplicate-entry behavior is not runtime-confirmed; reports-disabled signed packets still require the validated session in the secure signed path. These are not described as compatibility-complete merely because they reject safely. Offline ordinary unsigned `SChatCommand` remains governed by `allow_chat_reports=false` and is separate from signed attribution.
- **Current security merge judgment:** the reviewed must-fix root causes are addressed and tested; vanilla runtime compatibility remains **not claimed**. The old read-only “merge不可” snapshot above is historical, not the final gate result.
