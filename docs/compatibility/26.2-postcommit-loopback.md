# 26.2 post-commit config / inventory binary TCP loopback regression

## Findings

### 判定

- 対象は Java Edition `26.2` / protocol `776`、repository 外の既存 debug binary `C:/Temp/pumpkin-target-26_2-next/debug/pumpkin.exe`。
- binary の実 SHA-256 は期待値と一致した。`233,683,456` bytes、SHA-256 `1fac8aa55dc83f4757b95d0f4f1fe0ac39895128935da7fd40a207900215dc5f`。
- binary source の記録上の対応先は `89d47265b60f2d61564064dc2b626f4a5a654777` (`89d47265b`)。この担当では build、cargo、rustup、Rust source の変更を行っていない。binary を上書きしていない。
- fresh isolated run に対する status、strict-play、Known Packs fallback 3種、既存 configuration negative 2種は、各 harness exit `0` で TCP pass となった。
- **server の graceful shutdown は未達**。`stop\n` を redirected stdin へ送ったが、server exit は `3221225725` (`0xC00000FD`, Windows stack overflow)。従って lifecycle gate を含む全面 pass は主張しない。port は閉じ、server process は残っていない。
- vanilla client acceptance、registry/chunk/NBT の意味論、inventory UI/click、resource-pack実ダウンロード、reconfiguration は未確認・未実装のままである。

### 実 TCP run

最終の採用 run は `C:/Temp/pumpkin-26_2-config-inventory-tcp-regression-25576`、bind は `127.0.0.1:25576` のみ。新規 `pumpkin.toml` はこの run directory にだけ作成した。

```toml
[networking.java]
enabled = true
address = "127.0.0.1:25576"
online_mode = false
encryption = false

[networking.bedrock]
enabled = false

[telemetry]
enabled = false
```

`server.stdout.log` は `2,255` bytes、SHA-256 `3d37ee2bab89148c6524ff62ebc6804279af0290874c23f92e305cda6bfd3a03`。`server.stderr.log` は `48` bytes、SHA-256 `30cc22ad1db45fe1280a98f1ae1c7ebd45674c45b967a977b12c02c38fd63f3c`。stdout は `Server is now running`、3接続の join/leave、`Stopping the server`、`Starting save.`、`Starting worlds` までを含み、`Completed save!` と `The server has stopped.` には到達しなかった。

| 接続 / harness | exit | 主な観測 |
|---|---:|---|
| `--mode status` | `0` | `protocol=776`, `status_pong=pass`, version `1.7.2-26.2` |
| `--mode login --strict-play --known-packs-case empty` / `compat_empty` | `0` | `first_playable_strict`, `configuration_packets=35`, `play_packets=5818`, `position_syncs=1`, `teleport_confirms_sent=[1]`, `first_chunk.section_data_bytes=19472`, `keepalives_replied=1` |
| `--mode login --strict-play --known-packs-case legal_subset` / `compat_subset` | `0` | `first_playable_strict`, `play_packets=13727`, position/teleport/chunk envelope/keep-alive 全 pass |
| `--mode login --strict-play --known-packs-case unknown` / `compat_unknown` | `0` | `first_playable_strict`, `play_packets=17294`, position/teleport/chunk envelope/keep-alive 全 pass |
| `--mode config-regression --case early_finish_ack` / `compat_early` | `0` | 期待 disconnect: `Received finish configuration acknowledgment before finish configuration` |
| `--mode config-regression --case duplicate_known_packs` / `compat_duplicate` | `0` | 期待 disconnect: `Received known packs without a pending server request` |

3つの strict 接続は独立 TCP connection とした。`known_packs_request` は全て `[{namespace: "minecraft", id: "core", version: "26.2"}]` の1件だったため、実 TCP の `legal_subset` は空集合（1件リストの proper subset）になった。`unknown` は core に `{namespace: "example", id: "unknown", version: "1"}` を追加した。いずれも wire-valid な fallback selection として server が Registry Data / Update Tags / Finish Configuration を送り、empty Finish ack 後に正常 Play へ進んだ。非空 subset の形状は harness unit fixture で別途検証したが、今回の fresh server request には2件以上の Known Pack がなく、実 TCPで非空 proper subsetは作れなかった。

strict-play の成功は synthetic protocol peer から実 Pumpkin process への受理・遷移である。`Join Game` envelope、Player Position と teleport confirmation、first chunk の外側 envelope、Keep Alive echoを検査しただけであり、`registry_data`、`update_tags`、chunk section palette/block state/biome/light、block-entity NBTの意味論は opaque のままにした。

### 既存 negative と duplicate phase

- early Finish は server の `select_known_packs` packet (`packet_id=14`) を観測した後、serverの `finish_configuration` (`packet_id=3`) より前に空 ackを送った。serverは phase違反理由を含む Configuration disconnectを返した。server Finish前の送信であることを socket read 順序で確認した。
- duplicate Known Packs は最初の Known Packs response送信後、Registry Data response (`packet_id=7`) を1 frame以上観測してから、同じ空 responseを2回目として送った。serverは `Received known packs without a pending server request` で disconnectした。
- duplicate caseでは server が既に queue した Registry Data / Finish Configuration を disconnect前に送ることがある。Finish frameの観測だけを正常 phase遷移とは判定せず、最終 disconnect reasonを判定根拠にした。最大の実観測 decoded configuration payload は `169,866` bytesで、既存上限内だった。

### resource pack synthetic fixture

実 resource-pack URLを有効にした起動、外部通信、Java client downloadは行っていない。`tools/compat-26_2/protocol776_harness.py` に次を追加した。

- `synthetic_resource_pack_ack_fixture()` — UUID + status VarInt の local wire fixtureを作る。
- `parse_resource_pack_ack_fixture()` — UUID、status、trailing bytesだけを構造検証し、`download_observed=False`を返す。

`test_resource_pack_ack_fixture_is_local_structure_only` は status `0`, `3`, `4`, `7`, `99` と trailing byte rejectionを検証する。これは `DownloadSuccess` / `Accepted` / `Downloaded`等の packet envelope確認であり、clientのHTTP download、hash検証、pack展開、適用、実client acceptanceの証拠ではない。

### inventory の扱い

今回の synthetic TCP peer は inventory screen、crafting click、map transmute、remainder/drop、close windowを送っていない。従って対象 binaryが inventory source commitを含むことの hash/build correspondence は記録したが、inventory runtime TCP acceptanceは主張しない。checkpointに記録済みの inventory package `32 passed / 0 failed` は既存 evidenceとして参照できるが、今回 cargo禁止のため再実行していない。

### 初回試行と再実行

最初の `25573` run は接続間の quiescenceを設けず連続実行したため、strict 3接続が `VarInt exceeds five bytes` または `truncated NBT compound name` で exit `1` になった。negative 2件は exit `0` だった。これは採用 evidenceにせず、接続終了処理の待機を追加した `25576` fresh runを採用した。`25576` では strict 3件と negative 2件が全て exit `0`。この差異は binary互換 passへ昇格せず、接続終了/負荷時の再現性注意として残す。
