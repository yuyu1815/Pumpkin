# 26.2 reconfiguration TCP stability / wire narrow gate

- 対象: Java Edition `26.2`, protocol `776`, world data version `4903`
- 目的: `Play -> Configuration -> Play` flake の失敗情報を増やし、Configuration の critical wire 検証を狭く強化する
- 所有書込み: `tools/compat-26_2/`、`crates/pumpkin/tests/java_reconfiguration_tcp.rs`、`crates/pumpkin/tests/protocol776_reconfiguration_client.py`、本書
- Cargo: **この担当では実行禁止のため未実行**
- stage/commit: **未実施**

## Findings

### 結論

今回の作業で正式 vanilla client の互換性、実 Pumpkin の再試験、または timeout flake の根因を確定したとは扱わない。直前 handoff に記録された一回の失敗は次の値だった。

```text
Rust real-TCP test: exit 101
failure: 20 s Play baseline timeout
state=Play, pending_bytes=24, closed=true
```

その後、同じ gate が pass した記録はあるが、`pending_bytes=24` と `closed=true` になった future/task の厳密な因果順序、child の EOF、server reader の close reason、harness の最終 JSON の関係を同時に保存していなかった。従って、**flake は handoff 記録上観測済み、根因は未確定**である。単純な timeout 延長は行っていない。

### 最有力仮説（未確定）

1. 初回 Play の Join Game/chunk/position/keep-alive が server writer queue と harness の read loop の境界に残った。
2. Rust test が `ConnectionState::Play` と `pending_bytes == 0` を見た時点と、synthetic peer が strict baseline の keep-alive を返信し readiness を通知した時点が一致していなかった。
3. その間に Java reader/writer future が EOF/close を処理し、Rust 側は `Play` を観測しつつ `closed=true` を観測した可能性がある。
4. 旧 test-only adapter は Configuration reader の known ID set に**全 Play clientbound ID**を union し、state collision を `opaque` として通せた。これは queued Play frame の race を隠すため、wire failure の可視性を下げていた。

上記は順序仮説であって、実サーバーの同一条件 repeat と child/server の close-reason traceなしに根因確定とはしない。

## Wire changes

### 1. Configuration critical packet の explicit decode

`tools/compat-26_2/protocol776_harness.py` に `ConfigurationCriticalTracker` と次の minimum envelope parser を追加した。

| packet | packet ID source | 検証範囲 |
|---|---:|---|
| Update Enabled Features (optional in 776 path) | `assets/packet/26_2_packets.json` の configuration/clientbound | present時のcounted String list、重複、trailing bytes。protocol 776 のPumpkin pathでは省略可能 |
| Select Known Packs | 同上 | 既存 tuple/count/string decoder、request 1回 |
| Registry Data | 同上 (`registry_data=7`) | registry String、entry count、entry String、has-data boolean、anonymous NBT envelope、entry duplicate、trailing bytes |
| Update Tags | 同上 (`update_tags=13`) | category/tag/entry の counted bounds、String、non-negative VarInt IDs、category/tag duplicate、trailing bytes |
| Finish Configuration | 同上 (`finish_configuration=3`) | empty body、critical packet の順序、exactly-once |
| Keep Alive / Ping / Disconnect | 同上 | fixed-size payload または reason String の end-boundary |

Registry Data の NBT は root tag/type と compound/list/scalar の byte boundary/depth/array boundsを読むだけで、registry key、entry component、NBT値の意味を解釈しない。Update Tags の numeric IDsも意味を主張せず、wire上の VarInt/count と重複だけを検査する。

ローカル安全上限は protocol semantic maximum の主張ではない。

- Registry Data entries: `65,536`
- Update Tags categories: `64`
- tags/category: `8,192`
- IDs/tag: `65,536`
- total packet data: 既存 `8 MiB`
- frame: 既存 `2 MiB`
- VarInt: 既存 `5 bytes`

根拠は packet ID map と既存 repository codec の field order である。参照した既存 codec は `crates/pumpkin-protocol/src/java/client/config/registry_data.rs::CRegistryData`、`update_tags.rs::CUpdateTags`、`known_packs.rs::CKnownPacks`。公式 vanilla client の semantic acceptance をこの parser から主張しない。

### 2. unknown / needs_review の分離

- 26.2 mapping に無い Configuration clientbound ID: **hard fail**。
- mapping にはあるが今回 decode 対象外の packet: `needs_review_configuration` としてイベントに記録する。互換性 pass の根拠にしない。
- normal Rust assertion は `needs_review` 件数 `0` を要求する。
- 旧 `opaque_configuration` の一括扱いは critical path から除去した。
- Play payload は Join Game、Player Position、first chunk envelope、keep-alive/ping以外を理解したとは主張しない。既知 Play ID の全 union による Configuration 側の隠蔽は test adapter から除去し、state collision/unknown IDを fail にする。

### 3. readiness / diagnostics

Python harness は strict initial Play baseline（Join Game、position、teleport confirmation、first chunk envelope、keep-alive reply）完了後に JSON-lines diagnostic file へ `play_baseline_ready` を書く。各 cycle について次を sequence 番号付きで記録する。

- `harness_started`
- `play_baseline_ready`
- `start_configuration_observed`
- `configuration_finished`（Registry Data 数、Update Tags 数、needs_review 数）
- `returned_play_keepalive`
- `harness_result` または `harness_failed`（stderr の failure と同じ根拠を補助）

Rust `java_reconfiguration_tcp.rs` は、従来の `ConnectionState::Play` / `last_packet_time` / `pending_bytes == 0` だけで trigger せず、child が diagnostic file に対応する readiness event を出すまで待つ。cycle 2 は `returned_play_keepalive` を待ち、cycle 1 の readiness を再利用しない。baseline timeout の panic は `state`、`last_packet_time`、`pending_bytes`、`closed`、child stdout/stderr、diagnostic traceを一緒に出す。

これは timeout を延長する変更ではない。initial handshake/keep-alive/readiness の future ordering を同じ観測点に揃える変更である。

### 公式 schema の境界

`assets/packet/26_2_packets.json` は packet state/direction/ID の local repository assetであり、全 field semantic の公式 client acceptance oracleではない。Registry Data/Update Tags の field orderは既存 Pumpkin protocol codec と既存 compatibility auditに照合した。未知 gameplay payloadについては「理解した」「clientが受理した」と記録しない。

### Critical判定の意味

`stateful_reconfiguration_pass` は、required critical packetの wire envelope、counted bounds、順序、empty ack、同一接続のPlay keep-alive、および Rust側のPlayer/World/entity/inventory保存を満たす synthetic-peer gateである。Update Enabled Features は protocol 776 の実送信経路で省略されるため、存在時だけ検証し、必須packetとは数えない。Registry entry NBT value、tag meaning、resource pack、chunk section、gameplay payload、vanilla rendering/acceptanceのpassではない。
