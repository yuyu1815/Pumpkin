# 26.1 基盤 → 26.2 server 比較契約

- 目的: 26.1の機械可読データ／toolを比較基盤として使い、26.2差分に基づく**条件付き許容**を定義する。
- 最終対象: PumpkinのJava 26.2 server（protocol `776`、world data `4903`）。26.1 server、26.1 bot、Via変換経路を最終対象へ昇格しない。
- 契約の原則: `wire framing / 同一形状の操作` と `packet ID / registry / semantic` を別証拠にする。26.1から学べることを26.2一次証拠の代りにしない。
- 書込み所有: 本ファイルのみ。担当1 tools、担当2 delta、正式コード、generated sourceは変更していない。

## Findings

### 1. 証拠レーンと判定語

| lane | 証拠 | 使える主張 | 使えない主張 |
|---|---|---|---|
| L0: source catalog | pinned commitのREADME、実ファイル、schema、license、blob SHA | dataset/toolが実在し、どの範囲を読めるか | 26.2の互換、vanilla受理、server semantic |
| L1: 26.1 structural | `minecraft-data` protocol/schema、node-minecraft-protocol/MCProtocolLibのcodec、mineflayerの操作model | VarInt/frame、state machineの形、同一操作の入力表現、数量/順序fixtureの雛形 | 26.2 packet ID、registry payload、component/recipe意味、vanilla結果 |
| L2: 26.2 primary | 26.2 official metadata/JAR hash、`assets/packet/26_2_packets.json`、26.2 assets/datapack/generated source、26.2 protocol code | version/protocol、packet ID/field、registry/item/block/recipe source、26.2 wire候補 | clientが実際に受理したこと、実serverの最終状態 |
| L3: controlled synthetic | isolated loopback/in-process peer、固定seed/world、opaqueでないdecode、fixture結果 | Pumpkinのframe/state/codec、入力拒否、限定されたhandler invariant | vanilla clientの画面・完全gameplay、real traceの代り |
| L4: real trace | 許諾済みvanilla 26.2 client/server、同一初期状態、redacted packet/log/state | client acceptance、合法packet順、結果状態、実時間/tick相関 | 未取得traceの内容、別初期状態への一般化、秘密を含むraw再配布 |

判定値は `pass`、`fail`、`needs_review`、`not_run` の4値に限定する。`unknown`、未decode、opaque、証拠不足は成功へ暗黙変換せず `needs_review`（安全境界やdecode不能で実行継続不可なら `fail`）とする。

### 2. 26.1から学べる層と26.2一次証拠必須層

#### 26.1基盤から条件付きで再利用できるもの

- frame envelope: length VarInt、compressionの外側構造、bounded read、state/direction分離のテスト形。
- 同一形状の操作: handshake → status/login/configuration/playという段階、Known Packsが namespace/id/version listであるという**形**、keep-aliveのechoという操作形、inventory clickやblock/entity actionのシナリオ表。
- data fixtureの構造: item/block name、stack count、recipe input/result、entity UUIDと一時runtime ID、tick/order/eventのログ形式。
- bot/codec APIの補助: 26.1で合法操作を作るgenerator、packet encode/decodeのround-trip、schema coverage、negative inputのfixture。

#### 26.2一次証拠なしには採用しないもの

- packet ID、stateごとのpacket名、field順、registry ID、item/block/entity/component numeric ID。
- 26.2 Registry Data、Known Packsの実 tuple、Update Tags、dimension NBT、chunk/level NBT。
- recipe result quantity、remainder、component inheritance/transmute、stack limit、semantic event。
- movement/attack/reach/LOS、permission、chat signing、tick scheduler、entity transfer、world saveのserver意味。
- 26.1 toolの「接続できた」「botが動いた」を26.2 client acceptanceへ変換すること。

26.1の`protocol=775`と26.2の`protocol=776`は別版である。特定IDが偶然同じでも、state・field・registry・semanticの一致を意味しない。26.2 serverのpacket mappingは既存 `assets/packet/26_2_packets.json`、generated audit、26.2一次資料で再確認する。

### 3. 比較対象の canonical record

各 scenario は次の record を一つ持つ。raw secretや個人情報は保存せず、必要ならアクセス制御された外部一時領域に分離する。

```text
scenario_id
version_lane                 # 26.1_fixture / 26.2_synthetic / 26.2_real / via_26.2_to_26.1
source_pins                  # data/tool commit, blob SHA, package, license
server_commit
protocol_version/world_data_version
initial_state_hash
initial_state_canonical
input_kind                   # legal_client / synthetic / replay / malformed
normalized_packet_trace
semantic_events
ordered_tick_events
final_state_hash
final_state_canonical
invariants
redaction_profile
trace_artifacts              # metadata only; no fabricated hash
result                       # pass/fail/needs_review/not_run
failure_reason
```

#### initial state

必須項目:

- version lane、protocol、world data version、server/tool commit、data pins。
- 固定 seedの**hashまたはfixture ID**、dimension、world border、game mode、permission、difficulty、simulation/view distance。
- player UUID、名前は必要最小限にし、entity mapping、position/rotation、health/hunger/effects、inventory全slot、cursor、container/window id/revision。
- 参照する block/entity/item/recipe/registry/component の canonical IDsと初期値。

初期状態は入力 traceより後に生成してはならない。期待値は観測後に後付けせず、fixture契約に先に固定する。外部world/JARが未取得なら `initial_state_hash`を捏造せず `needs_review` とする。

#### final state

必須項目:

- player/entityの位置、rotation、health、effects、inventory、cursor、container、permission。
- block state、block entity NBT/component、recipe input/result/remainder、world time、scheduled tick queue、drop/item entity。
- disconnect/reject理由、server decision、event cancel、mutationの有無。

canonicalizationでは UUID/entity runtime ID、window ID、teleport ID、timestamp、random seed、absolute coordinatesなどを許可されたmappingで正規化する。ただしpacket順、tick内順序、count、NBT/component key/value、registry key、recipe quantityを消してはならない。

### 4. stable entity mapping

- primary identityはfixtureで発行した stable logical ID（例 `player:p1`, `mob:target-a`, `item:drop-1`）。
- UUIDはreal traceではredaction mapを持つ。runtime entity IDはrunごとの値なので、`run_id + direction + raw_id -> logical_id`をログし、比較キーにraw IDを直接使わない。
- mappingは最初のspawn/login/transferで確定し、途中で再割当しない。未解決・重複UUID・同一logical entityの二重spawnは `fail`。
- cross-dimension比較では source detach、destination add、tracker pairing、remove/spawn eventを logical IDで比較する。
- 26.1 bot/MCProtocolLibが扱うentity IDを26.2のstable identityとみなさない。26.2側の一次spawn/registry/semantic eventが必要。

### 5. tick と ordered events

各 event に最低限 `logical_tick`、`within_tick_order`、`source`、`action`、`before_hash`、`after_hash`を付ける。

- packet orderとtick orderを別フィールドにする。arrival timestampだけで順序を決めない。
- 同一tickの scheduled block/fluid/entity events、neighbor update、inventory mutation、entity spawn/remove、packet sendを順序付きで記録する。
- `OrderedTick.priority`、sub-tick/order key、sequence/transaction revisionを落とさない。並列workerのcompletion orderをvanilla orderと混同しない。
- comparisonは少なくとも `(logical_tick, within_tick_order, event_kind, stable_entity/block key)` を比較する。順序差がsemantic stateを変えないと証明されていない限り、packet count一致だけでpassしない。
- 26.1のtick/event modelはfixture schemaとして利用できるが、26.2のserver scheduler semanticsの証明にはならない。26.2 serverで実測・一次仕様照合が必要。

### 6. recipe quantity invariant

各 recipe/craft scenario で、item typeとcomponent identityを含む単位を定義し、次の保存則を評価する。

```text
consumed_ingredients
+ input_remainders
+ output_to_inventory
+ output_to_cursor
+ output_to_result_slot
+ dropped_output
+ explicitly_destroyed_by_semantics
= expected_recipe_quantity
```

- `expected_recipe_quantity`はrecipe serializer/result count、必要craft回数、vanilla 26.2一次資料またはreal oracleから**事前に**決める。
- 同じitem名でもcomponent/NBTが異なるstackは別単位。recipe remainder、transmute input/material、suspicious stew effect、map/book/bundle等を数量だけで同一視しない。
- inventory slot max、item max stack、container capacity、partial shift-click、cursor、dropを別項目にする。
- `consumed > expected`、出力の二重計上、remainder欠落、component消失、unknown serializerは `fail`または `needs_review`。26.1 `recipes.json`の形だけで26.2 craft passにしない。

### 7. packet / state comparison contract

| 比較項目 | 26.1基盤で参照可 | 26.2 passに必要な一次証拠 |
|---|---|---|
| outer frame / VarInt / zlib boundary | schemaとcodec testの形 | 26.2 decoder/encoder code、targeted synthetic、必要ならreal trace |
| state transitionの段階 | 26.1のstate model | 26.2 packet map、server state、client acceptance |
| packet ID/name | **不可**（候補表のみ） | 26.2 packet JSON/generated/official protocol。偶然一致は差分証拠にしない |
| packet field order/type | 26.1のshape fixtureのみ | 26.2 field schema＋decode/encode＋real acceptanceまたは明示的一次資料 |
| Registry Data/Tags/known packs | tuple/listの形だけ | 26.2 registry key、entry、NBT type/value、pack tuple、ordering |
| block/item/entity IDs | logical-name fixture | 26.2 assets/generated/remapとwire payload |
| recipe quantity | invariantの実装枠 | 26.2 recipe source/result/remainder/componentとoracle |
| semantic event/final state | event record schema | 同一initial stateで26.2 server/oracleの結果 |

### 8. trace種別と秘密情報除去

#### synthetic

- in-processまたはloopbackの自作peer、固定fixture、改変packet、malformed packetを `input_kind=synthetic` とする。
- synthetic peerが受けた/送ったことは `real_client_compatibility` ではない。opaque payloadを読んでいない場合、対象fieldの結果は `needs_review`。
- packet replayは session/encryption/compression/known-packs/registry stateを再生成する。raw byte再送をreal-client証拠にしない。

#### real

- 許諾済みJava 26.2 vanilla clientまたは公式 serverとの同一初期状態比較だけを `input_kind=real` とする。
- client log、server log、packet trace、final stateを同じ `scenario_id`で結び、version、Java major、tool/server commit、exit codeを記録する。
- 実trace未取得なら、hash、packet count、画面受理、実プレイ成功を推測・捏造しない。artifact pathだけ記録し、hash欄は空または `not_recorded` にする。

#### redaction

必ず除去または置換するもの:

- access token、session/refresh token、Microsoft/Mojang account情報、server secret、proxy secret、Velocity/Bungee/Vine forwarding secret、private key、chat session private material。
- 接続先の公開不要なIP/hostname、個人UUID/name（fixture logical IDへ写像）、認証コード、署名payloadの再利用可能な秘密部分。

保持してよいもの:

- version、protocol、state、direction、packet name/id（26.2根拠がある場合）、field type、count、順序、正規化後のhash、reject reason、public artifact URL、commit/blob SHA、license。
- signatureは検証結果と長さだけを基本とし、再利用可能なraw secret/signature chainを公開しない。

redactionでwire semanticを壊した場合は `redacted_non_comparable` として `needs_review`。秘密除去後のログをreal traceと呼ぶための変換表を保存する。

### 9. 26.2差分による条件付き許容

26.1基盤の再利用は、シナリオ単位で次の全条件を満たした場合だけ `conditionally_accepted` とする。

1. 26.1 source/tool pinとlicenseが記録済み。
2. 26.2のversion/protocol/対象packetまたはdata pathが一次資料で確認済み。
3. packet ID/field、registry/component/recipe semanticの26.2側差分が列挙済み。
4. initial stateを同一canonical recordで作り、stable entity mappingが解決済み。
5. final state、ordered event、quantity invariantの期待値が事前固定され、比較結果が得られた。
6. syntheticかrealか、Via変換経由かをtrace metadataで分離している。
7. unknown/opaque/未取得artifactがpass条件に混入していない。

条件のいずれかが欠ける場合:

- framingだけ一致: `structural_pass`（full compatibilityではない）。
- 26.1 fixtureだけで26.2 packet/registry未確認: `needs_review`。
- 26.2一次 evidenceと比較してinvariant違反: `fail`。
- malformed入力を拒否できずmutation/allocation/desyncへ到達: `fail`。
- real traceがなくclient acceptanceを語る: `not_run`または`needs_review`。

### 10. Via変換経由の別契約

`assets/viabackwards/data/mappings-26.2to26.1.nbt`、ViaVersion/ViaProxy等を使う場合は `version_lane=via_26.2_to_26.1` とする。

- 変換前の26.2 packet/state/registryと変換後の26.1 packet/stateを別々に記録する。
- ID remap、field add/remove、registry substitution、component loss、synthetic/real clientのendpointを比較する。
- 変換層を通った26.1 botの成功は、vanilla 26.2 clientがPumpkin 26.2 serverを直接受理した証拠ではない。
- translation-specific semantic invariantを満たさない限り、操作を「互換」と昇格しない。変換できない／合成した／落とした情報は明示し、`needs_review`または`fail`とする。

## Recommended Next Steps

1. `scenario_id`、initial/final canonical record、stable entity mapping、quantity invariant、ordered event schemaを先にfixtureレビューし、後から期待値を変更しない。
2. 26.1 data/toolを `26.1-source-catalog.md`のcommit/blob SHAで固定し、26.2 sideは`assets/packet/26_2_packets.json`とgenerated/source pathを別pinにする。
3. まず `INV-01`（partial shift-click）、`BLK-01`（dig start/finish/permission）、`PLY-ATTACK/INTERACT`（reach/LOS）をsyntheticで契約化し、次に同一初期状態のvanilla 26.2 oracleへ進む。
4. packet ID、registry、component、recipe semanticの未確認は `needs_review` のまま保持する。26.1 data countや同名packetの一致だけで `pass`にしない。
5. Via変換を使う場合は別laneでbefore/afterを保存し、変換を通らないvanilla 26.2 client比較を別途要求する。
6. 後続報告には出典URL、実確認版、commit/blob SHA、推奨採用範囲、拒否条件、実行コマンド、終了コード、数値、未確認事項、変更パスを必ず記載する。
