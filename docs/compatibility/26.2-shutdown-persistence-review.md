# 26.2 shutdown entity persistence independent review

- 対象: Java Edition `26.2`, protocol `776`
- レビュー対象: `802353e33` (`fix(world): make 26.2 shutdown entity save stack-safe`)
- 開始 HEAD: `802353e33a4a2f79b9e2bb72745a605143301222`
- 判定: **must-fix。exit `0` と stack overflow 回避は確認できても、非 resident entity を「既に保存済み」とみなす保存互換は証明されず、静的にデータ消失経路が残る。完成主張はしない。**
- 作業範囲: 本レビューでは production Rust code は変更していない。既存の `.pi/` 未追跡物、user world、既存 run は変更・stage していない。

## Findings

### F-01 (P1): new spawn を保存済みと誤認できる（静的確定）

`crates/pumpkin/src/world/mod.rs::World::add_entity_silent` (`5242`)、`spawn_entity_non_save` (`5211`) は、entity の現在 chunk が `Level::loaded_entity_chunks` に resident か、過去の entity snapshot が存在するかを確認せず `World::entities` に追加する。plugin/API、structure entity、raid、natural spawn、各種 projectile/item などの caller がこの入口を使う。

`World::shutdown -> save_entity` (`578`, `617`) は `Level::get_entity_chunk_sync` (`623`) が `None` の場合、保存処理も load も行わず `return` する。従って、次の状態では entity NBT が一度も entity file に追加されない。

1. entity が非 resident chunk に spawn される、または load/eviction の境界で map から外れる。
2. entity が `World::entities` に live のまま残る。
3. shutdown で `get_entity_chunk_sync == None` になる。
4. warning の後、entity index が clear され、`Level::shutdown` が終了する。

これは「前回 eviction で書いた snapshot がある」という前提を必要としない新規 entity の反例である。`World::save` (`7230`) にも同じ `save_entity` が使われるため、shutdown 限定でない。

### F-02 (P1): eviction の last snapshot と live state の間に境界移動 race がある（静的確定）

`World::remove_entities_in_chunks` (`5290`) は最初の filter で `entity.get_entity().chunk_pos.load()` を読み、entity を `World::entities` から除去した後 (`5300` 前後)、`save_entity` は別の読み取りで `block_pos` (`622`) を読み直す。`Entity::set_pos` (`crates/pumpkin/src/entity/mod.rs::1302`) は `pos` → `block_pos` → `chunk_pos` の順に atomic fields を更新し、selection と serialization の間に同時 tick/teleport が入るロックまたは version check がない。

そのため、evict 対象の旧 `chunk_pos` を見て removal list に入った entity が、保存時には新しい `block_pos` にいる場合、新 chunk が非 resident なら `save_entity` が skip する。旧 loaded entity chunk の NBT は load 時に `mem::take` (`World::spawn_world_entity_chunks`, `4768`) で消費済みなので、旧 chunk に fallback snapshot はない。新しい live state、UUID/type/position/custom NBT の全体が失われ得る。

逆方向の stale read（`block_pos` が旧、`chunk_pos` が新）も owner/index の不整合を示し、chunk ownership を resident 判定だけで推定する根拠を弱める。

### F-03 (P1): `None` は saved / pending / missing / load error を区別しない（静的確定）

`Level::get_entity_chunk_sync` は `loaded_entity_chunks` map の在否しか返さない。`None` には少なくとも以下が混在する。

- 正常 eviction 後、eviction writer が既に disk へ snapshot を確定した状態
- entity chunk load がまだ pending の状態
- missing entity file から `spawn_entity_generation` 待ちの状態
- entity file の parse/I/O error から generation 待ちの状態
- new spawn により一度も snapshot が存在しない状態

特に `Level::receive_entity_chunks` (`709`–`778`) は `LoadedData::Missing(pos) | LoadedData::Error((pos, _))` (`748`) を同じ空 chunk generation queueへ流す。entity-specific loader は corrupt/error と missing を分離しない。したがって `None` を「既に保存済み」と読むことは storage state の証拠にならない。

### F-04 (P1): shutdown stack fix の根因証拠は「同じ entity を捨てて回避した」可能性を排除していない

`802353e33` は `World::shutdown` (`576`–`588`) の snapshot/clear を bounded にし、`save_entity` (`617`–`641`) で resident chunk だけを保存する。既存 validation log では warning が多数出ている。既存の isolated run `C:/Temp/pumpkin-26_2-shutdown-investigation-login-disconnect-fix2/server.stdout.log` は、`13:46:51` に **36件**（entity `51,55,57,...153`）の `Skipping entity ... in evicted chunk ...` を出した後、server exit `0`、`Completed save!`、`The server has stopped.` に到達している。

これは process lifecycle と stack overflow の改善の証拠であり、UUID/type/position/NBT の reload 一致の証拠ではない。warning 対象を実際に捨てたまま正常終了した可能性があり、`exit 0` は保存互換を保証しない。

### 全 `World::save_entity` caller の追跡結果

| caller | path/symbol | 非 resident 時の意味 |
|---|---|---|
| shutdown | `crates/pumpkin/src/world/mod.rs::World::shutdown` | `None` を保存済みとみなし skip。今回の must-fix |
| eviction | `World::remove_entities_in_chunks` | 現在の code では同じ skip。boundary race で eviction caller 自体が live state を落とし得る |
| manual/autosave/plugin save | `World::save` | shutdown 以外にも同じ skip が適用される |

`World::save_entity` の旧実装は全 caller で `Level::get_entity_chunk(...).await` を行っていた。802353e33 は stack overflow を避けるため、その load を全 caller から消し、resident-only 判定へ変えた。よって root cause が「async load の再入」であっても、保存経路を正しく所有管理した証拠にはならない。

## Recommended Next Steps

1. **最優先の狭い追補:** `World::save_entity` の戻り値を `SavedResident | NeedsLoad | Removed | LoadFailed` のように区別し、`World::shutdown` では `NeedsLoad` を「保存済み」と扱わない。Level 側に、chunk-system/task drain 後に一つずつ entity chunk を load してから save する bounded shutdown queue を追加する。entity saver の `Missing` と `Error` は必ず別結果にし、`Error` は既存 file を空 chunk で上書きしない。
2. **eviction owner fix:** `remove_entities_in_chunks` の selection/save を同じ chunk ownership/version snapshotで線形化する。`Entity::set_pos` の `block_pos`/`chunk_pos` の不一致を検出したら entity を removal list から戻し、target chunk を確定してから save する。非 resident targetを黙って drop しない。
3. **new spawn contract:** `add_entity_silent` が resident ownership または明示的な pending-save lease を取得しない限り、live-only entity を登録しない。外部 spawn の非 resident case は bounded load/queue で保存可能になってから `World::entities` に publish する。
4. **回帰 test:** freeze → save/stop → 新 process/reload を専用 TempDir で実行し、UUID/type/position/必要 NBT を exact 比較する。最低3ケース（resident normal、eviction境界移動、new spawn）、加えて missing/error を原 file hash とともに検査する。
5. `World::save`、eviction caller、shutdown callerを別々に testし、shutdown exit `0` のみを pass にしない。実装後は専用 target、incremental `0`、debug `0`、jobs `2`、`--locked` で局所 check/test を再実行する。

## Limits / conclusion

- **保存保証の証拠:** resident chunkへの `write_nbt` + `mark_dirty(true)`、Level shutdownの entity-saver barrier、既存 runの exit `0`/停止完了は確認済み。専用 target の `cargo check --locked -p pumpkin` も exit `0`。
- **保存保証の限界:** 非 resident chunkでの live entity、new spawn、boundary move、pending/error loadについて、現在のコードには「disk snapshotが存在する」証拠がなく、reload一致も未確認。warning件数を bounded にすることは保存成功ではない。freeze → stop → 新 process/reload の UUID/type/position/必要 NBT test は未実施。
- **結論:** `802353e33` は stack overflow回避としては有効そうだが、resident-only skipを保存済み判定として採用したことはデータ保全上未証明であり、P1 must-fix。production修正・regression test・完成主張は次の追補まで保留する。
