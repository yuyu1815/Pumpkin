# 26.2 block-digging authority (BLK-01)

## Findings

BLK-01 was confirmed by static control-flow comparison. Before this change,
Pumpkin's Java `FinishedDigging` path checked only reach and then called
`World::break_block`; it did not require a matching server-side start, matching
`mining_pos`, elapsed progress, height, or `may_build` before block mutation.
The existing `StartedDigging` path already handled item `can_mine`, creative
instant break, mining state setup, block-damage event, and sequence recording.

## Official 26.2 conditions

`ServerGamePacketListenerImpl.handlePlayerAction` delegates block actions to
`ServerPlayerGameMode.handleBlockBreakAction(pos, action, direction, maxY,
sequence)`, then calls `ackBlockChangesUpTo(sequence)` after the delegate
returns. Thus sequence acknowledgement is prediction ordering, not a
permission or completion proof.

`ServerPlayerGameMode.handleBlockBreakAction` applies the interaction-range
check (`isWithinBlockInteractionRange(pos, 1.0)`) and rejects `pos.y > maxY`
before action-specific logic. The vanilla block-break path does not use a
separate lower-height check in this method.

- **START (`START_DESTROY_BLOCK`)**: spawn protection and `mayInteract` are
  checked. Creative/`instabuild` calls `destroyAndAck` immediately; it does not
  require a later STOP. For other modes, `blockActionRestricted` is checked,
  current destroy progress is calculated, progress `>= 1.0` is instant-broken,
  otherwise the server records `destroyPos` and `destroyProgressStart`.
- **STOP (`STOP_DESTROY_BLOCK`)**: the requested position must equal the
  server's `destroyPos`; the current block must not be air; and
  `destroyProgress * (elapsedTicks + 1) >= 0.7` destroys the block. Below that
  threshold vanilla schedules delayed destruction rather than breaking at
  once. Therefore a STOP-only packet is not *automatically* a vanilla
  violation as a general statement, but it cannot pass the normal position/
  state gate without a matching start state. Creative clients normally do not
  send STOP after an instant START.
- **ABORT (`ABORT_DESTROY_BLOCK`)**: clears the destroying state and sends
  progress cleanup. A position mismatch is logged/cleaned; it does not destroy
  a block. It is still subject to the common reach/height gate.
- **Adventure**: `Player.blockActionRestricted` returns restricted for
  Adventure/Spectator. Spectator is always denied. Adventure may proceed only
  when `mayBuild` is true or the main-hand item's
  `canBreakBlockInAdventureMode(BlockInWorld)` predicate matches. The official
  predicate can include block ids, state properties, block-entity NBT, and
  component matchers.

## Local state and dependency boundary

- `Player::may_build()` reads `Abilities.allow_modify_world`. The current
  gamemode setup makes this true for Survival/Creative and false for
  Adventure/Spectator.
- `CanBreakImpl` exists in `crates/pumpkin-data`, but it intentionally stores
  the predicate as raw NBT. The 26.2 protocol codec currently consumes the
  wire predicate entries and stores an empty raw list. There is no existing
  evaluator that can safely implement the official Adventure predicate in the
  two requested source owners. Reimplementing that item/feature evaluator in
  the network handler would duplicate the item owner and risk allowing a
  predicate that does not match block state/NBT.
- This patch therefore fails closed on `!may_build` at the mutation boundary.
  Adventure `can_break`/`can_place_on` support remains a separate item/data
  owner task; it is not falsely claimed as implemented here.

## Minimal changes

### `crates/pumpkin/src/net/java/play/player_action.rs`

`JavaClient::handle_player_action` now:

1. rejects START/ABORT above the world top before block-damage/abort effects;
2. rejects START when `may_build` is false, before block-damage hooks;
3. on FINISH, requires `mining == true`, exact `mining_pos`, non-negative
   elapsed ticks, finite server-calculated break speed, and vanilla-tolerant
   progress `speed * (elapsed + 1) >= 0.7`;
4. rejects FINISH above the world top or with `may_build == false` before
   `World::break_block` and all break/drop/stat/tool side effects;
5. on every rejected FINISH, calls the existing `Player::stop_mining`, sends
   the authoritative `CBlockUpdate`, and records the packet sequence. This
   prevents a client-predicted air block from becoming a persistent ghost;
6. keeps the existing delayed ACK design: `update_sequence` still coalesces
   the max sequence and `Player::process_inbound_packets` sends the ACK after
   authoritative block updates are flushed.

The private `can_finish_digging` function is the actual handler predicate, not
an alternate mining implementation. Its focused tests cover start absence,
position mismatch, and the 0.7 tick/swing timing boundary.

### `crates/pumpkin/src/block/registry.rs`

`BlockRegistry::place_block` now rejects `!player.may_build()` before world
lookup, placement events, block-state mutation, block-entity application, or
item decrement. This closes the shared placement mutation boundary without
changing attack/item behavior. Existing Adventure/Spectator denial remains a
fail-closed result until the item owner's `can_place_on` predicate evaluator
exists.

## Current must-fix correction

The follow-up implementation now owns the missing state transitions instead of rejecting them:

- `Player` has separate active and delayed-destroy state. Java STOP below the official `0.7`
  threshold transfers the matching target to delayed destroy; `Player::tick` continues the same
  server-side progress and performs the authoritative break at `>= 1.0`.
- A mismatched Java STOP only resynchronizes the requested position and sequence. It does not
  clear the active target. ABORT, air, permission rejection, target replacement, and world
  transfer clear both active and delayed state through `stop_mining`; `change_world_chunks` is
  the common old-world cleanup boundary for all production callers.
- The shared tick rejects non-finite/negative speed and checked-subtraction failure rather than
  continuing with invalid progress. Bedrock target replacement and `may_build` mutation guards
  use the same cleanup boundary.

## Follow-up proposal

The item/data owner should preserve and evaluate the 26.2 `can_break` and
`can_place_on` predicate list (block set, properties, NBT, and component
matchers) in the existing component path, then expose one shared predicate
check to the Java interaction handlers. Until that exists, fail-closed
Adventure mutation is safer than accepting every block or inventing a partial
predicate matcher in `player_action.rs`.
