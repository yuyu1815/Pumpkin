# 26.1 比較検証データ基盤（26.2 最終互換対象）

## Findings

- **最終互換対象は Java 26.2 / protocol 776 / world data version 4903 のまま**である。26.1 / protocol 775 は、既存ツール・機械可読データを使うための比較専用 namespace であり、サーバーを 26.1 へダウングレードしない。
- `tools/compat-data/` に、依存なし Python の薄い adapter、固定 manifest、26.1/26.2 の分離済み summary、synthetic fixture、unit test を追加した。正式 Rust、assets、既存 `tools/compat-26_2/` harness は変更していない。
- PrismarineJS `minecraft-data` は **pinned commit** `20a0b0142d99d9a069aa8fec98512ec082b4f0a3` から実取得して検証した。logical namespace と physical source はともに `26.1`（共有別版ディレクトリの推測なし）。`version.json` は protocol `775` / 104 bytes / SHA-256 `cced5b9e15eaa84c15b229fe7d861894dc29ec21210a03ff3a1ba4da606dee10`、実 schema `protocol.json` は 336,715 bytes / SHA-256 `88bad867681214bfea6c59c9a705da4cc269f8131e9d3495bd03916275e7fa08`。さらに items 1,506 entries / 189,396 bytes、blocks 1,168 / 860,277 bytes、recipes top-level 887 / 404,729 bytesを同じ pin で検証した。rawは `tools/compat-data/.cache/` のignored cache-onlyで、remote `master`/HEAD を golden data にはしていない。
- `protocol.json` は `tools/compat-data/.cache/` へ pinned fetch後に利用可能で、`schema-list` が実際の mapperから state/direction/name/packet_idを抽出する。これは parser生成・26.2 decode成功・vanilla受理を意味しない。`loginPacket.json`、JAR、pcap、実 trace、26.1 registry/known-packs/world schema は今回の committed scopeに含めていない。
- 26.2 側は既存 `assets/packet/26_2_packets.json` を source として使用し、256 packet entries、SHA-256 `430b5955...5c1d4d` を検証した。公式 26.2 metadata も immutable package URL から取得し、SHA-256 `b4ada813...aaad5c` を manifest に記録したが、JAR/assets は repo に保存していない。
- 26.1 summary は 9 state/direction 組で 257 entries、26.2 summary は 9 組で 256 entries。26.1 の handshaking/serverbound に id `254` の entry があるため、単純な件数一致を合格条件にしていない。
- 観測 fixture はすべて `observed: false` の synthetic contract であり、実機 client/server trace ではない。実機 trace なしで「完全互換」「finding再現済み」とは判定しない。

manifest にある hash は未取得値のプレースホルダーではない。上記は今回実際に GET/読込して確認した値で、ignored cacheのraw artifactを `validate_local` でも再計算する。再取得時は必ず同じ pinned URL と SHA-256 を照合し、不一致なら使用せず fail する。`minecraft-data` upstream READMEのdata-origin caveatと同pinのroot LICENSE/NOTICE不在を踏まえ、repository-level MITをper-file dataへ拡張せず、`THIRD_PARTY_NOTICES.md` と `LICENSE-minecraft-data.txt` に記録した。

### 2. 再現可能コマンド

リポジトリルートで実行する。

```text
py -3.11 tools/compat-data/compat_data.py fetch
# exit 0（今回確認: version 104、protocol 336715、items 189396、blocks 860277、
# recipes 404729、index 852、26.2 metadata 51781 bytes。全7 URLが manifest hash と一致）

py -3.11 tools/compat-data/compat_data.py verify
# exit 0
# compat-data verify: OK (26.1 comparison namespace, 26.2 final namespace)

py -3.11 -m unittest discover -s tools/compat-data -p "test_*.py" -v
# exit 0, Ran 16 tests ... OK

py -3.11 tools/compat-data/compat_data.py schema-list --state play --direction serverbound
# exit 0, JSON count=69。packet_id=62 は name=spectate_entity、source_state=play
```

`fetch` の出力先は `tools/compat-data/.cache/` で、同ディレクトリの `.gitignore` により repo の golden data にならない。raw license/provenanceがsource依存のため、取得後も配布コピーを作らない。取得先を remote HEAD に変更する操作や、hashを更新して失敗を隠す操作は禁止する。大量 install、cargo/npm install、server起動、JAR/pcapのrepo保存は不要である。

### 3. 26.1/26.2 を接続する形式

他担当は `fixtures/trace-contract.json` の形で、少なくとも次を各 observation に保持する。

```json
{
  "scenario_id": "BLK-01",
  "observed": false,
  "source": {
    "minecraft_version": "26.2",
    "protocol": 776,
    "role": "final_target_contract"
  },
  "target": {"minecraft_version": "26.2", "protocol": 776},
  "state": "play",
  "direction": "serverbound",
  "initial_state": {
    "world": "fixed synthetic block",
    "player_position": "fixed",
    "gamemode": "survival",
    "may_build": true
  },
  "expected": {
    "invariant": "break/drop/event requires valid start, progress, reach, permission",
    "source": "26.2-validation-strategy.md BLK-01",
    "oracle_required": true
  },
  "classification": "exact"
}
```

実 trace を接続する場合は `observed: true` とし、`initial_state_hash`、normalised packet sequence、decision、final state hash、採取 tool/version を追加する。`source` と `target` の version/protocol、`state`、`direction`、初期状態、期待値の由来を省略しない。`expected` は trace 後の後付け値ではなく、独立した fixture/仕様または vanilla oracle の出典を記す。

### 4. 差分分類と「素通りしてよい」リスト

`compat_data.py classify` は入力の `allow: true` を信用せず、次の分類を計算する。

| 分類 | allow 条件 | 今回の扱い |
|---|---|---|
| `exact` | source/target とも 26.2 / 776 で、契約上の比較結果が一致 | 条件成立時のみ allow |
| `allowed_version_delta` | 現在 verified/enabled rule は **0件**。ID 62 の名前差候補は具体 artifact の source系が一致しないため proposed/disabled。将来有効化する場合も source/target、state/direction、ID、before/after metadata の preservation を要求 | 今回は allow しない。payload schema、server acceptance、gameplay result、persistent state には適用しない |
| `known_implementation_gap` | 既知だが Pumpkin/vanilla 差を埋める実装不足 | allow しない。修正または別検証が必要 |
| `unknown` | 由来・分類不能、想定外の差分 | allow しない |
| `error` | version/protocol 欠落・不一致、state/direction 不正、入力契約不備 | allow しない |

従って、26.1 の packet 名が 26.2 と違うことを理由に、payload や gameplay を自動合格にはしない。`26.1 / 775` を `26.2 / 776` の wire parser、vanilla oracle、最終 server compatibility の代用にしない。

現在の ID 62 候補を同じ入力で classify すると、rule が `proposed/disabled` のため exit code `1`、`allow:false`、`disposition:needs_review` になる。将来 `verified` に昇格する場合の追加契約は `before_metadata` / `after_metadata` の両方で、`packet_id`、opaque payload識別子、順序、field数、数量、presence が実際に等しいこと（変更は `packet_name` のみ）である。これは入力された metadata の差分照合であり、wire bytes、decode/encode round-trip、server decision を独立検証する trace verifier ではない。

`classification: unknown`、version 欠落、`26.1` と protocol `776` の不一致などは exit code `1` で `allow: false`。不明差分を「素通りしてもいいリスト」へ追加する場合は、まず source hash、差分の state/direction/wire identity、payload非該当、期待値の由来を manifest に固定し、unit test を追加する。

### 5. 既存監査との対応

synthetic scenario は `docs/compatibility/audits/26.2-validation-strategy.md` の次の契約をそのまま実験入力へ落とした。

- `INV-01`: recipe result 部分 shift-click。総量保存を inventory/drop/result/cursor で確認する。
- `BLK-01`: StartedDigging → FinishedDigging、progress/reach/permission を満たさない mutation を拒否する。
- `PLY-ATTACK-INTERACT`: reach、LOS、same-world、dead/removed、spectator を分離する。

これは「候補を実機で再現した」ことを意味しない。既存監査が記す通り、vanilla client、同一初期状態、実 server decision、最終 state の比較が完了するまで finding の真偽は未確定である。

## Recommended Next Steps

1. 他担当は `synthetic-scenarios.json` を入力契約として使い、実機 trace を採取できたケースだけ `observed: true` の別 fixture として追加する。既存 synthetic fixture を observed に書き換えない。
2. 26.1 source を使う担当は、必ず `manifest.json` の source id と hash を参照し、26.2 の最終判定へ接続するときに `target=(26.2, 776)` を明示する。
3. payload/schema、registry/component、server decision、world/inventory/entity final state の差分は `allowed_version_delta` ではなく、`exact` または未確定分類として扱う。unknown/version欠落は常に fail-closed とする。
4. vanilla 26.2 oracle を使える段階で、同一初期状態を用いて INV-01、BLK-01、PLY-ATTACK-INTERACT の順に trace/decision/final-state を記録する。今回の基盤は server を起動しない。
5. 26.2 mapping の再生成や正式 Rust/assets の変更は別担当の所有範囲で行う。この基盤は read-only input と比較判定の adapter に留める。
