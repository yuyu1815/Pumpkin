# Minecraft Java 26.2 Play -> Configuration -> Play reconfiguration

- Target: Java Edition `26.2`, protocol `776`, world data version `4903`
- Scope: stateful Java reconfiguration after the player has already entered Play.
- Status: source implementation reviewed, local state/codec tests passed, and a fresh initial-login loopback passed against the rebuilt source binary. No reconfiguration runtime trigger or vanilla-client acceptance is claimed.

## Findings

### CFG-T3 transition contract

The guarded sender is `JavaClient::start_reconfiguration` in
`crates/pumpkin/src/net/java/mod.rs`. It only succeeds for a configuration-capable
version whose coarse state is `Play`, and atomically claims
`ConfigurationPhase::Play -> ReconfigurationAwaitingAck` before sending
`CStartConfiguration`. A second concurrent or repeated caller returns `false` and
cannot send another start packet.

The existing repository search found no production reconfiguration sender call
site. The new method is therefore a narrow future-facing API rather than a
test-only hook. It does not create a new player, entity, inventory, world, or
connection; the existing `JavaClient`/`Player` remain attached.

The inbound path is owned by the existing Java packet reader task in
`JavaClient::progress_player_packets`:

1. while Play, an empty serverbound `configuration_acknowledged` body is decoded;
2. `handle_configuration_acknowledged` claims
   `ReconfigurationAwaitingAck -> AwaitingKnownPacks`, changes only the coarse
   connection state to Configuration, and invokes the shared `send_known_packs`;
3. while Configuration, `handle_configuration_packet` decodes the existing
   Configuration serverbound packets and routes Known Packs/resource-pack/keepalive
   responses through the existing `net/java/config/` handlers;
4. the shared Known Packs handler serializes Registry Data, Update Tags, and
   Finish Configuration, and records `AwaitingFinishAck` before sending Finish;
5. an empty Finish Configuration acknowledgment is admitted once by
   `handle_reconfiguration_finish`; after the existing `can_not_join` admission
   check it atomically claims `AwaitingFinishAck -> Play`.

A duplicate configuration acknowledgment, duplicate finish acknowledgment, wrong
phase, or trailing bytes is rejected/kicked without a second Play transition.
The Finish path does not return `PacketHandlerResult::ReadyToPlay`, so the initial
join/spawn path is not invoked a second time.

### Official 26.2 packet schema used

No new Start Configuration or acknowledgment codec was necessary. The repository
already had the official empty-body codecs:

- clientbound Play `start_configuration`: packet id `118` in
  `assets/packet/26_2_packets.json`, `CStartConfiguration` with an empty body;
- serverbound Play `configuration_acknowledged`: packet id `16`,
  `SConfigurationAcknowledged` with an empty body;
- serverbound Configuration `finish_configuration`: packet id `3`,
  `SAcknowledgeFinishConfig` with an empty body;
- serverbound Configuration `select_known_packs`: packet id `7`, existing bounded
  `(namespace, id, version)` entries.

The 26.2 mapping also defines clientbound and serverbound Configuration
`keep_alive` as packet id `4` with a big-endian `Long`. The clientbound codec was
missing from the local protocol tree, so the minimal official-schema addition is
`crates/pumpkin-protocol/src/java/client/config/keep_alive.rs`; it only writes
that `i64` body and is exported from the existing config module. The serverbound
codec was already present and is reused.

## Migration / Investigation Notes

### Queue and state timing

Reconfiguration packets are handled in the existing async network-reader task
once the state changes, rather than being put into the Play tick queue. This keeps
Known Packs, Registry Data, Tags, Finish, and Finish acknowledgment ordered behind
the empty Play acknowledgment. Play packets already queued before the transition
remain on the existing player queue; no new queue or player tick is created.
After the transition, chat, movement, teleport, inventory, entity, and other Play
handlers are not selected for Configuration packets.

The existing `Player` and `JavaClient` continue to own the same entity ID,
position, inventory, screen handler, chat/session state, and tracked entities.
The reconfiguration Finish path changes only connection/configuration phase; it
never calls `Server::add_player`, `World::spawn_java_player`, or any initial join
constructor.

### Keepalive, chat, teleport, and disconnect behavior

- The existing keepalive timer remains active. It selects the Play clientbound
  keepalive while coarse state is Play (including the short period before the
  client acknowledges Start Configuration), and the Configuration clientbound
  keepalive after the acknowledgment. Both use the existing pending-ID timeout
  accounting.
- Configuration serverbound keepalive responses are routed to
  `JavaClient::handle_config_keep_alive`; unexpected IDs remain ignored by the
  existing handler.
- Chat, movement, teleport, inventory, and entity packet IDs are not routed by the
  Configuration dispatcher. A disconnect/EOF exits the existing reader loop and
  does not advance the phase; no new player cleanup or spawn path is triggered by
  reconfiguration.
- Existing packet-rate limiting and `close_token` handling run before/around the
  state-aware dispatcher, preserving the current kick and stop behavior.

## Validation Limits

- No production caller currently requests reconfiguration, so no live server
  trigger or socket-backed Play -> Configuration -> Play runtime run is claimed.
  A user command or ad-hoc trigger was not added; the next test hook should invoke
  `start_reconfiguration` from an existing server-owned lifecycle/event seam.
- The rebuilt source binary was exercised only through a fresh initial-login
  localhost run at `127.0.0.1:25577`: status and strict-play harness each exited
  `0`, with `protocol=776`, `configuration_packets=35`, `known_pack_reply=true`,
  `position_syncs=1`, `teleport_confirms_sent=[1]`, `keepalives_replied=1`, and
  `result=first_playable_strict`. The server accepted `stop\n` but exited with
  Windows `3221225725` (`0xC00000FD`, stack overflow), so graceful lifecycle pass
  is not claimed; the port closed and no process remained.
- `docs/compatibility/26.2-postcommit-loopback.md` is explicitly prior evidence
  from the old source `89d47265b`; it is not evidence for this rebuilt
  CFG-T3 runtime. No vanilla client was used.
- The test exercises the real transition helpers, but not a socket-backed client
  with an official Java client. Packet framing and body fields are covered by
  existing protocol codecs and the new Configuration keepalive round-trip test.
- Registry payload equivalence with the official per-entry Known Pack ownership
  data remains the documented full-payload fallback limitation from CFG-T2.
