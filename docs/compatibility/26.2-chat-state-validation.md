# 26.2 secure chat state validation

## Findings

This task connects the committed stateless 26.2 canonical-byte/RSA helper to the
serverbound Java chat-message validation path without changing signed commands,
world construction, packet dispatch, configuration, or `Player`/`ChatSession`
struct definitions.

The production validation order is:

1. secure policy and session presence/expiry checks;
2. preview `LastSeenMessagesValidator` on a clone, including offset/20-bit ack
   application and the 26.2 Java signed-byte checksum;
3. preview inbound chain link (`sender`, session UUID, expected index) and
   timestamp ordering;
4. canonical 26.2 body construction and RSA PKCS#1 v1.5/SHA-256 verification;
5. only after all checks succeed, commit the cloned ack validator and inbound
   chain state;
6. return to the existing handler, which may then broadcast.

An invalid signature, replay/index mismatch, or old timestamp does not consume
ack state; it marks the inbound chain broken, matching the official fail-closed
chain policy. Missing session, expired key, unknown ack, and checksum mismatch
are rejected transactionally. Unsigned chat remains accepted only on the
existing reports-disabled policy path; it is never promoted to secure
attribution.

## Migration / Investigation Notes

### Sidecar state and atomicity

`ChatSession` currently has no inbound next-index/last-timestamp fields, and its
`messages_sent` counter is outbound state. The new sidecar is keyed by player
UUID and stores only the validated session UUID, next inbound index, and last accepted wire timestamp in epoch milliseconds plus sticky broken
state. Session replacement resets this sidecar to index zero only after the
existing certificate verification succeeds.

The state transaction holds the sidecar lock while it clones and previews the
player's ack validator, computes canonical bytes, and verifies RSA. On failure,
no original validator, sidecar index, or timestamp is written. On success, both
are committed together from their previews. The implementation intentionally
uses the current packet's ordered acknowledged signatures as canonical
`last_seen`; it does not reuse `MessageCache::last_seen`.

The checksum is the 26.2 `LastSeenMessages.computeChecksum` interpretation:
Java signed-byte `Arrays.hashCode` for each 256-byte signature, then the Java
31-fold list hash, with a zero result changed to one. A wire checksum of zero is
kept as the official bypass, but RSA verification is still mandatory.

### Production connection status

Connected now:

- secure chat message session presence and expiry gate;
- sender/session/expected inbound index binding;
- wire-millisecond timestamp ordering and sticky chain-break state;
- current-packet ack preview and checksum;
- canonical 26.2 bytes and RSA/SHA-256 verification;
- success-only ack/chain mutation before the existing broadcast call;
- separate validation gates for missing-session, unsigned, expired,
  invalid-signature, replay, and out-of-order/checksum cases. The existing
  `ChatError` API maps missing/default session to its legacy `UnsignedChat`
  variant and maps cryptographic/ack failures to `ChatValidationFailed`; a
  later error-taxonomy owner can split those public disconnect variants without
  changing this transaction.

Not connected by this task:

- `World::broadcast_secure_player_chat` still constructs its outbound
  `PlayerChatMessage` using its pre-existing outbound/nil-session behavior;
  changing it is explicitly outside this owner boundary and is a follow-up for
  the world owner.
- signed command argument signatures and removal of signed-command fallback;
- session certificate refresh, vanilla runtime/client round trips, and report UI
  behavior;
- changes to the wire decoder or to `ChatSession` itself.

The fixture provenance remains unchanged: canonical order comes from static
inspection of the official 26.2 server JAR; RSA values are repository test-only
OpenSSL known-answer material, not Mojang fixtures. No runtime vanilla
compatibility claim is made here.

Review response: the sidecar now stores wire epoch milliseconds and a sticky
broken flag for replay/out-of-order/session/signature failures. Identical
validated session updates are idempotent, and `World::remove_player` clears the
UUID-owned state. These local tests do not verify signed-command arguments,
outbound secure attribution, or an independent official runtime chat fixture.
