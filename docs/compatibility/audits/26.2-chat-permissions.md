# Minecraft Java 26.2 chat / commands / permissions / player-auth 境界監査

- 対象: Java Edition 26.2 / protocol `776` / world data version `4903`
- 監査範囲: chat signing/session/ack、chat表示、command tree/parser/suggestion/permission、op/whitelist/ban、profile/UUID/secure profile、proxy forwarding trust boundary
- 境界: packet framing/compression/state本体は network 担当の監査範囲として重複させない。正式 Rust code/config は変更していない。
- 監査種別: **監査のみ**。出力所有: 本ファイルだけ。
- HEAD: `1ac447f2918b7dec7d19a5836fa3673d4fe3c9f5`
- vanilla 26.2 client、外部 server、server 起動、Cargo/rustup、重い download は未実施。

## Findings

### 1. P1 — secure chat が「署名の存在・長さ」を検査するだけで、本文署名を検証しない

**確度: 高（ソース上確定。server/client実往復は未実施）**

- 対象:
  - `crates/pumpkin/src/net/java/play/chat_message.rs:14-18` `JavaClient::handle_chat_message`
  - 同 `:108-179` `JavaClient::validate_chat_message`
  - 同 `:243-276` `JavaClient::validate_chat_session`
  - `crates/pumpkin/src/net/java/mod.rs:950-976` `SChatMessage` の decode/dispatch
  - `crates/pumpkin/src/world/mod.rs:1096-1147` `World::broadcast_secure_player_chat`
- 前提設定:
  - `basic.allow_chat_reports=true`、`networking.java.online_mode=true`、`encryption=true`。
  - `SPlayerSession` は Mojang public key により受理済みで、session expiry 内。
- 期待:
  - session update の証明だけでなく、各 chat message の署名が、現在の chat session public key と `content/timestamp/salt/last_seen` に対して有効か検証する。不正署名は broadcast 前に reject/kick する。
- 現状:
  - `validate_chat_message` は signature の `len()==256`、timestamp、session expiry、message count/ack、pending 数、任意 checksum を検査するが、`chat_session.public_key` で RSA 署名を verify する処理がない。
  - `validate_chat_session` は `session_id + expires_at + public_key` に対する Mojang key の RSA 検証を行うため、**session 証明と message 証明の実装が分離しており、後者が欠落**している。
  - 検証を通った入力は `broadcast_secure_player_chat` が受け取り、受信 signature をそのまま `PlayerChatMessage` と `CPlayerChatMessage` に流す (`world/mod.rs:1126-1129`、`net/chat/mod.rs:372-380`)。
  - `checksum == 0` は source comment どおり bypass 可能であり、checksum は署名の代替ではない。
- 影響:
  - P1。secure chat/reporting の sender authenticity と chain integrity が壊れる。攻撃者は任意 bytes の256-byte signatureを付けた本文を secure player chat として中継させられる可能性がある。command permission自体は後述の dispatcher が再検査するため、この finding単独で `/op` 実行権限が増えるとは断定しない。
- ローカル再現案（未実行、外部 server 禁止条件内）:
  1. `validate_chat_message` の fixture に、受理済み session、現在時刻、正しい ack window、`[0u8;256]` の署名、checksum `0` を与える。
  2. 期待は RSA 検証エラー、現状は `Ok(())`。その後の broadcast が signature を保持することを pure/unit fixture で確認する。
  3. 正しい client署名、期限切れ、長さ255/257、ack window不正を別ケースにする。
- 修正パス:
  - 26.2 の signed-body wire canonicalization を `SChatMessage`/chat command 共通 helper にし、session public keyで署名検証してから event/broadcastへ進む。
  - signed message の replay/session-id/message-index policyを一箇所に集約し、検証済み署名だけを `MessageCache` に登録する。

### 2. P1 — signed command の署名・ack・timestamp・argument signatureを無視して通常 commandとして実行する

**確度: 高（ソース上確定）**

- 対象:
  - `crates/pumpkin-protocol/src/java/server/play/chat_command_signed.rs:12-21` `SChatCommandSigned` の fields（timestamp、salt、argument signatures、message count、ack、checksum）
  - `crates/pumpkin/src/net/java/mod.rs:930-949` `SChatCommandSigned` 到達経路
  - `crates/pumpkin/src/net/java/play/chat_command.rs:5-35` `JavaClient::handle_chat_command`
  - `crates/pumpkin/src/net/java/play/chat_message.rs:14-18` slash chat shortcut
- 期待:
  - signed command の command body/argument signature、secure-chat chain、timestamp、ack、checksumを検証し、失敗時は実行しない。
- 現状:
  - `mod.rs:933-934` は packet 全体を decodeした後、`signed.command.to_string()` だけを取り出す。その他の signed fields は検証されず、`SChatCommand` に詰め替えて `handle_chat_command` へ渡される。
  - `handle_chat_command` は spam check、plugin event、dispatcher実行のみ。ここで signed metadataを再検査しない。
  - `SChatMessage` の本文が `/` で始まる場合は、secure-chat の `validate_chat_message` より前 (`chat_message.rs:14-18`) に command として実行される。
- 期待 vs 現状の権限境界:
  - dispatcher側の `requires(PERMISSION)` と `Player::has_permission` は実行時に残っているため、signed command欠落だけで一般 player が op commandを実行できる証拠はない。
  - ただし secure chat の command attribution/reporting、署名済み argument の真正性、session chainは保証されない。`/op` などは permission failureになるべきで、署名不正でも同じ command parserへ到達する点が問題。
- ローカル再現案（未実行）:
  - `SChatCommandSigned` に timestamp過去、zero/garbage argument signature、invalid ack/checksumを与え、`handle_chat_command` に到達しないことを期待する。現状は command stringだけが同じになる。
  - permission level `Zero` と `Four` の player fixtureを分け、署名検証修正後も dispatcher permissionが維持されることを確認する。
- 修正パス:
  - signed chat command専用 validatorを作り、通常 chatと同じ session/ack/checksum stateを利用する。parse fallbackで signed packetを unsigned commandへ降格させない。
  - slash shortcut は protocol versionごとの意図を確認し、secure modeでは署名済み command経路に限定する。offline/`allow_chat_reports=false` は意図的な unsigned限界として分離する。

### 3. P1 — BungeeCord forwarded IPを受け取るが login connection addressへ反映せず、IP ban境界がproxy IPになる

**確度: 高（ソース上確定。proxyを用いた実接続は未実施）**

- 対象:
  - `crates/pumpkin/src/net/proxy/bungeecord.rs:46-77` `bungeecord_login`
  - `crates/pumpkin/src/net/java/login/login_start.rs:53-66` Bungee login branch
  - `crates/pumpkin/src/net/java/login/encryption_response.rs:181-188`、`crates/pumpkin/src/net/java/pending.rs:416-428` `can_not_join` 呼出し
  - `crates/pumpkin/src/net/mod.rs:341-405` `can_not_join`
- 前提設定:
  - `networking.proxy.enabled=true`、`proxy.bungeecord.enabled=true`。BungeeGuard相当の `proxy.bungeecord.secret` を設定している正規構成でも発生する。
- 現状:
  - `bungeecord_login` は forwarded host の2番目のfieldを `ip` としてparseし、UUID/profileとともに返す。
  - callerは `Ok((_ip, profile))` (`login_start.rs:60`) として `_ip` を破棄し、`self.address`を更新しない。
  - `can_not_join` は `address.ip()` で banned IP (`net/mod.rs:395-405`) を判定するため、Bungee経由では実 client IPではなく backend TCP peer/proxy IPを判定する。
  - `ban-ip` の live player path (`command/commands/banip.rs:38-44`) も `player.client.address().ip()` を保存するので、正規 proxy下では全員同じproxy IPをbanする結果になる。
- 期待 vs 現状:
  - 期待: proxyが認証済みであることを確認した上で、forwarded IPを pre-login event、IP ban、ログ scrub、ban enforcementの canonical client addressにする。proxy address自体を使う用途とは分離する。
  - 現状: Bungeeのみ Velocity/Vine と異なり `self.address = new_address` 相当がない。profile UUID/whitelist/player banは forwarded profileで判定されるが、IP banだけ別 identityになる。
- 影響:
  - P1。IP ban enforcementの不一致、proxy配下のIP banが効かない/過剰に全員へ効く。player UUID ban/whitelistの直接判定は別に動く。
- ローカル再現案（未実行）:
  1. `bungeecord_login` に client socket `10.0.0.1` と forwarded IP `192.0.2.10` を渡し、返却 `IpAddr` が `192.0.2.10` になる既存 unit pathを利用する。
  2. caller相当で `_ip`を捨てた場合の `can_not_join` に、banned IP `192.0.2.10` と `10.0.0.1` を別登録し、どちらが拒否されるかを fixtureで確認する。
  3. BungeeGuard secret missing/mismatchは既存 `bungeecord.rs` tests (`MissingToken`/`InvalidToken`)を維持する。
- 修正パス:
  - `PendingConnection` に proxy-verified client address と socket peer addressを分離して保持し、Bungee成功時も verified addressを `can_not_join`/pre-login/ban policyへ渡す。
  - forwarded addressを信頼する条件は secret/BungeeGuard等の認証成功後だけとし、secret空のBungee構成は「direct spoof可能な意図的限界」と明示して安全な設定を促す。

### 4. P2 — offline UUIDがMinecraft互換の `OfflinePlayer:<name>` UUID v3でなく、SHA-256(name)先頭16 bytes

**確度: 高（コード比較で確定。offline identityの意図的非認証限界とは別の互換性バグ）**

- 対象:
  - `crates/pumpkin/src/net/mod.rs:74-76` `offline_uuid`
  - `crates/pumpkin/src/net/java/login/login_start.rs:73-77` offline login
  - `crates/pumpkin/src/command/argument_types/game_profile.rs:83-103` offline profile resolution
  - 比較対象: `crates/pumpkin-protocol/src/java/server/login/login_start.rs:45-50` の `Uuid::new_v3(nil, "OfflinePlayer:{name}")`
  - 既存資料: `docs/compatibility/26.2-connection.md:61-62` は v3 と記録しているが、現 sourceとは不一致。
- 期待:
  - Java offline modeの既存 ops/whitelist/ban/user-cache と同じ `UUID.nameUUIDFromBytes("OfflinePlayer:" + name)` 相当を使う。
- 現状:
  - `offline_uuid` は `Sha256::digest(username)[..16]` をUUID化し、prefixもversion/variantの整形もない。
  - offline login、offline command target解決、Bungee fallbackがこの値を共有するため、Pumpkin内では一貫するが、vanilla/Paper系の `ops.json`、`whitelist.json`、`banned-players.json` とIDが一致しない。
- 影響:
  - P2。offline modeの意図的な「usernameを証明できない」限界によるなりすまし可能性とは別に、既存管理ファイルとの互換性が壊れる。正規設定で権限が不意に付かない/ban・whitelistが一致しない。
  - offline modeで名前を知るだけでその名前として接続できること自体は、online authenticationを無効化した設定の意図的限界であり、本findingの権限昇格としては数えない。
- ローカル再現案（未実行）:
  - 固定 name `Steve` について、`Uuid::new_v3(Uuid::nil(), b"OfflinePlayer:Steve")` と `offline_uuid("Steve")` を比較する。期待は一致、現状は不一致。
  - 同じ nameで login profile、GameProfileArgumentType、ops/whitelist entryの lookupが同じになること、およびvanilla形式entryとの不一致をpure testで固定する。
- 修正パス:
  - `offline_uuid`をprotocol parserと同じv3 algorithmへ統一し、既存データ移行方針（旧SHA UUIDを保持するか再生成するか）を明示する。
  - online modeでは client supplied UUIDを信頼せず、既存 `encryption_response.rs:68-126` の session authentication経路だけを identity sourceとする。

### 5. P2 — Bedrock command treeは全 commandを `Any` として送信し、permission-filtered treeになっていない

**確度: 高（送信コード上確定。server execution bypassは未確認だが dispatcher path上は防止される）**

- 対象:
  - `crates/pumpkin/src/command/client_suggestions.rs:154-226` `send_bedrock_commands_packet`
  - `crates/pumpkin/src/command/client_suggestions.rs:154-205` の root command列挙
  - `crates/pumpkin/src/command/context/command_source.rs:174-225` `CommandSender::has_permission`
  - `crates/pumpkin/src/entity/player.rs:6194-6208` `Player::has_permission`
  - Java比較: `client_suggestions.rs:35-92` は root childについて `requirements.evaluate(source)` を行い、restricted bitを設定する。
- 前提:
  - Bedrock playerがjoinまたはpermission level変更し、`send_bedrock_commands_packet`を受ける。
- 現状:
  - Bedrock `CommandData.permission_level` は常に `CommandPermissionLevel::Any` (`:216`)。root commandも requirementで除外されず、overloadもrestricted permissionを反映しない。
  - Java treeは少なくともrootの requirementを評価し、nodeごとに `restricted` を設定する。
  - ただし実行時は `dispatcher.handle_command` → node requirement → `Player::has_permission` へ進むため、現コード読解だけでBedrock clientが権限 commandを実行できるとは言えない。
- 影響:
  - P2。権限漏えいではなく、非opへの command tree/UI/補完の過剰露出、client-side command availabilityの非互換。高権限 command名や引数構造の情報露出も最小限発生する。
- ローカル再現案（未実行）:
  - permission level `Zero`/`Four`で生成された Bedrock available-commands packetを比較し、`ban/op/stop`等が同じ `Any`で送られることを確認する。
  - 同じplayerで直接 dispatcher executeを行い、permission failureが維持されることを確認する。client tree filteringとserver authorizationを別テストにする。
- 修正パス:
  - Javaと同じ `requirements.evaluate(source)` を root/node/overloadへ適用し、Bedrockの正式な permission level/restricted表現へ変換する。
  - 送信treeを絞っても、execution側の permission checkは必ず残す。

## 正常・意図的限界として確認した経路

### Chat/session/ack

- `validate_chat_session` (`net/java/play/chat_message.rs:243-276`) は expiry と Mojang public keyによる session certificate signature を検証する。`player.gameprofile.id`もsignableへ含めるため、別UUIDのsession certificateをそのまま流用する経路は確認できなかった。
- `SChatAck` (`net/java/play/chat_ack.rs:5-48`) は負値と `LastSeenMessagesValidator::apply_offset` を検査し、失敗時は chat validation failed で切断する。ack window state自体は存在するが、P1-1/P1-2の本文・command署名検証とは別問題。
- `MessageCache` (`entity/player.rs:7403-7510`) はlast-seen/full-cache/pending countを管理し、送信側にもpending上限がある。ただしsigned messageの暗号学的validityを保証するものではない。
- `allow_chat_reports=false` 時に `PlayerChatMessage::system` と system/disguised chatへ切り替えることは、secure reportを要求しない意図的設定限界。これをP1の欠陥とは数えない。
- `allow_chat_reports=true` の設定validationは `pumpkin-config/src/lib.rs:125-130` 付近で `online_mode=true` を要求する。Mojang public keys取得がserver起動後background taskで行われ、空key時に正規sessionをrejectし得る点は可用性の未確認事項として残す。

### Command parsing / suggestions / permissions

- `handle_chat_command` (`net/java/play/chat_command.rs:5-35`) は command spam、plugin cancellation、dispatcherを通す。dispatcherのnode `requires(PERMISSION)`、`CommandSender::has_permission`、`Player::has_permission`を経るため、client command treeの露出とserver authorizationは分離されている。
- Java command suggestions (`net/java/play/command_suggestion.rs:5-31`) は player command sourceでdispatcher suggestionを呼ぶため、suggestion providerのserver-side contextは権限主体を持つ。入力に空白がない場合に早期returnするため root `/`の補完互換は未確認だが、権限 bypassとは判定しない。
- `op.rs`、`deop.rs`、`whitelist.rs`、`ban.rs`、`banip.rs` の built-in permissionは原則 `PermissionDefault::Op(Three)`。`CommandSender::Console/Rcon`が全permissionを持つのは管理経路として意図的。RCON bind/password hardeningは本監査の外部境界として未検証。
- player permission levelはjoin時 `ops.json` UUIDから初期化 (`entity/player.rs:777-789`)し、`op/deop` は runtime levelとcommand treeを更新する。stale session/cacheの再接続挙動は未テスト。
- whitelist enforcement (`net/mod.rs:374-391`) は op UUIDを例外扱いし、player banを先に判定する。Bungee IPだけはFinding 3のため address identityが不一致。

### Profile / UUID / proxy

- online modeの通常経路は `handle_login_start`で profileを仮作成し、encryption response後 `authentication::authenticate` (`login/encryption_response.rs:191-242`) の hasJoined responseでGameProfileを置き換える。default configは online/encryptionとも有効。
- `pumpkin-config/src/lib.rs:119-123` は online mode時に encryption必須をassertするため、`online_mode=true,encryption=false` という設定を「正しく有効にした状態」とは扱わない。このinvalid configを起動時に拒否するguardは存在する。
- `login_start.rs:73-106` の offline branchがclient UUIDを使わず名前からUUIDを作る設計自体は妥当だが、algorithmはFinding 4のとおり互換でない。
- Velocity (`net/proxy/velocity.rs:112-160`) はHMAC-SHA256 secretを検証し、profile/addressを返す。Vine (`net/proxy/vine.rs:143-227`) はEd25519、timestamp drift `30s`、challenge nonceを検証する。Bungee (`bungeecord.rs:74-116`) もsecret設定時はtoken missing/mismatch/duplicateを拒否する。
- Velocityは `velocity_login` が発行した plugin transaction idを responseで照合しない（`velocity.rs:51-53` TODO）。HMACと同一PendingConnectionがあるため直ちにprofile偽装と断定せず、P2 hardening/未確認として扱う。Vineもmessage id自体ではなくnonce/signatureで境界を守る。

## Recommended Next Steps

1. **P1-1/P1-2:** signed chat messageとsigned commandのcanonical payload/crypto verificationを一つのchat-auth helperへ集約し、本文broadcast、argument signature、ack/checksum、timestamp/session expiryを実行前に検査する。既存 permission dispatcherはその後段として残す。

## P0/P1/P2 集計（最大5件）

2. **P1:** signed commandのtimestamp/salt/argument signature/ack/checksumを無視し、command文字列だけを実行経路へ渡す。slash chatはvalidation前にcommand化される。

## 既知 / 未確認

### 既知・意図的限界

- `online_mode=false` は username/UUIDの暗号学的認証をしない。whitelist/op/banを名前だけで守れるとは主張しない。
- `allow_chat_reports=false` は unsigned/system chatへ切り替える意図的設定であり、secure reportingの証拠ではない。
- proxy enabledでsecret未設定のBungee forwardingは direct connection/spoofを防ぐ設定にならない。安全なproxy構成ではBungeeGuard secret、Velocity secret、またはVine public key/secretを設定する。
- Console/RCONが全 permission を持つ設計は管理経路として意図的。RCON exposure/passwordは今回の詳細範囲外。
- 26.2 vanilla clientのsecure chat表示、signed command rejection、Bedrock tree rendering、proxy client IP表示は未確認。

### 未確認事項

- chat messageの26.2 canonical signature bytesをvanilla client/JARで照合していない。P1はverify call site欠落の静的所見であり、暗号化方式のwire詳細を新規推測していない。
- invalid signed commandがsecure chat report UIでどう表示されるか、正常 clientがslash chat shortcutをどのversionで送るか未確認。
- Bungee forwarded IP修正後に、pre-login event、ban command、disconnect理由、proxy chain（proxy behind proxy）がどの addressを期待するか未確認。
- `allow_banned_players` と `allowed_actions` の profile action semantics、custom auth/profile URLの信頼性、Mojang public keys background fetch失敗時の再試行は本findingから除外した。現状は主に可用性/設定信頼の問題で、権限 bypassの確定証拠ではない。
- Velocity plugin responseのtransaction id未照合は `velocity.rs:52` のTODOとして確認したが、HMAC secretとPendingConnection単位の応答処理があるため、P1のprofile偽装とは判定せずP2 hardening/未確認に留めた。
