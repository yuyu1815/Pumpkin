# Minecraft Java 26.2 / protocol 776 接続・protocol 境界監査

- 監査対象: Java Edition 26.2 / protocol `776`
- 監査範囲: `crates/pumpkin-protocol/src/java`、`crates/pumpkin/src/net/java`
- 対象機能: handshake / status / login / configuration / compression / encryption / state transitions / disconnect / packet bounds
- 監査種別: **監査のみ**。正式コード、config、他 docs、`.pi` は変更していない。
- 監査時点の HEAD: `1ac447f2918b7dec7d19a5836fa3673d4fe3c9f5`
- 結論: 26.2 の packet ID mapping と主要な正常系縦断は既存資料・コード上で整合する一方、serverbound の悪意ある入力に対する collection bounds、frame 完全性、configuration state guard に確実な監査残件がある。vanilla 26.2 client の実接続は本監査でも未実施。

## Findings

### 新規発見 1 — P1: serverbound の可変件数を `Vec::with_capacity` 前に制限していない

**確度: 高（ソース上確定。サーバー process を起動した再現は指示により未実施）**

- `crates/pumpkin-protocol/src/java/server/play/chat_command_signed.rs:32-34`
  - `SChatCommandSigned::read` が `arg_count = read.get_var_int()?.0 as usize` をそのまま `Vec::with_capacity(arg_count)` に渡す。
  - `arg_count` の上限、負値拒否、packet payload 残量に基づく上限がない。
- `crates/pumpkin-protocol/src/java/server/play/set_game_rule.rs:23-25`
  - `SSetGameRule::read` も `count = ... .0 as usize` → `Vec::with_capacity(count)` としている。
  - count の上限検査がない。
- 到達経路:
  - `crates/pumpkin/src/net/java/mod.rs:930-938` の `SChatCommandSigned::read`。
  - `crates/pumpkin/src/net/java/mod.rs:1349-1350` の `SSetGameRule::read`。
  - いずれも packet ID は 26.2 mapping に存在する serverbound Play packet で、permission 検査より前に decode が行われる。
- 最小入力:
  - Minecraft signed VarInt `-1` は `[FF FF FF FF 0F]`。これを argument/count に置くと、64-bit target ではほぼ `usize::MAX` の capacity 要求になる。
  - `set_game_rule` は packet body 5 bytes の count だけでも decode 入口へ到達する。
  - signed command は空 command string + timestamp 8 bytes + salt 8 bytes + 上記 count で、少なくとも 22 bytes の prefix で到達する。
- 期待 vs 現状:
  - 期待: packet payload の残量または仕様上限を超える count を `ReadingError::TooLarge` 等で拒否し、接続を切る。
  - 現状: `Vec::with_capacity` が巨大 allocation、capacity overflow panic、または allocator failure に到達し得る。`SChatCommandSigned` は fallback の前にこの処理を行う。
- 影響:
  - 外部の unauthenticated/connected client が、権限を必要とする処理の前に server task の panic/OOM/接続処理停止を誘発する可能性がある。複数接続からの反復で DoS になり得る。
- 最小テスト案:
  1. codec 単体で `-1`、`i32::MAX` の count を与え、allocation を行わず `Err` になることを確認。
  2. `JavaClient::handle_play_packet` 相当の decode に packet ID と最小 body を渡し、server process を起動せず reject を確認。
  3. 正常な signed command と通常の 1-entry gamerule を round-trip する回帰も追加。
- 修正所有パス / 依存:
  - 主所有: `crates/pumpkin-protocol/src/java/server/play/chat_command_signed.rs`、`set_game_rule.rs`。
  - 回帰到達確認: `crates/pumpkin/src/net/java/mod.rs`。
  - 依存: protocol の packet payload upper bound (`MAX_PACKET_DATA_SIZE`) と各 packet の仕様上限。正式な count 上限を決める際は 26.2 vanilla codec/上流仕様を別途照合する。

### 新規発見 2 — P1: TCP frame の truncated body と compressed stream の frame 完全性を decoder が保証しない

**確度: 高（uncompressed の premature EOF はソース上確定。compressed trailing/desynchronization の実 TCP 再現は未実施）**

- `crates/pumpkin-protocol/src/java/packet_decoder.rs:130-190`
  - `packet_len` 分の `Take` は作るが、`packet_id` と payload の read loop (`:171-180`) は `bytes_read == 0` で break するだけ。
  - uncompressed packet では、宣言した `packet_len` に対して必要 bytes が不足しても、`expected_packet_data_len` と実読込み長の一致を検査しない。短い `RawPacket` が返り得る。
  - compressed packet では、宣言された decompressed length (`:182-188`) は検査するが、zlib stream が packet body の末尾まで消費されたこと、trailing compressed bytes がないこと、bounded reader の残りがないことは検査しない。
- 到達する入力:
  - compression 無効、または `Data Length=0` の frame で、outer `Packet Length` を実 body より大きく宣言して TCP EOF/次 frame を送る。
  - compression 有効で、正しい zlib stream の後ろに packet body 内 trailing bytes を付ける、または宣言された decompressed length だけ出力して stream/trailing を残す。
- 期待 vs 現状:
  - 期待: frame body を宣言長どおり全消費し、早期 EOF、未消費 trailing bytes、zlib stream の終端不在を reject して connection を close/kick する。
  - 現状: uncompressed は `RawPacket` を返し得る。compressed は decompressed length 一致だけで通る経路があり、`BufReader<Take<...>>` の読み取り量に依存して次 frame 境界の不整合を残し得る。
- 影響:
  - malformed client input による packet desynchronization、後続 packet の誤 decode、誤 kick、接続処理の不安定化。trailing の扱いは読み取り chunk/BufReader read-ahead にも依存するため、直ちに全入力で再現すると断定しない。
- 最小テスト案:
  1. outer length を実 body より 1 byte 大きくした uncompressed frame を decoder に与え、`FailedDecompression`/malformed とし、`Ok(RawPacket)` にならないことを固定。
  2. compressed body に zlib stream + 1 byte / 大きな trailing を付け、次の正しい frame と連結して、第一 frame を reject し後続 frame を誤読しないことを確認。
  3. compressed stream の declared decompressed length より短い/長いケースを分離して検証。
- 修正所有パス / 依存:
  - `crates/pumpkin-protocol/src/java/packet_decoder.rs`。
  - `ZlibDecoder` の stream-end/remaining-body 検証方法、`Take` の完全消費、既存の `MAX_PACKET_SIZE` / `MAX_PACKET_DATA_SIZE` 境界に依存。

### 新規発見 3 — P1: Login → Configuration の `finish_configuration` を順序外でも Play へ昇格できる

**確度: 高（状態変数と分岐が直接確認できる。実 server に malicious frame を送る試験は未実施）**

- `crates/pumpkin/src/net/java/pending.rs:399-428`
  - `handle_config_packet` は `SAcknowledgeFinishConfig::to_id(version)` (`:413`) を受けると、server が `CFinishConfig` を送信済みか、client の `SKnownPacks` を受信済みか、resource-pack 応答待ちかを確認せず、`:418` で `ConnectionState::Play` を store し `ReadyToPlay` を返す。
  - `SKnownPacks::to_id(version)` (`:426-428`) も payload を decode せず、受信順を状態として記録しない。
- 到達する入力:
  - Login Acknowledged 後、serverbound configuration `finish_configuration` (26.2 ID `3`) を空 body で先に送る。
  - または `select_known_packs` (26.2 serverbound ID `7`) を server の select-known-packs 送信前/任意 body で送る。
- 期待 vs 現状:
  - 期待: server が要求した configuration packet sequence (`select_known_packs` → registry/tags → `finish_configuration`) に沿わない packet は reject/kick し、Play へ遷移しない。
  - 現状: `finish_configuration` 単独で Play へ遷移可能。既に送信 queue/stream に残る configuration packet と、以後 `JavaClient` が Play queue で受ける packet の state が不一致になり得る。
- 影響:
  - malicious client の protocol state bypass、configuration packet と Play packet の境界混乱、実装が期待する registry/configuration 初期化を飛ばした参加。vanilla client がこの順序外入力を送るとは主張しない。
- 既存 codec との関係:
  - `crates/pumpkin-protocol/src/java/server/config/known_packs.rs:15-33` の `SKnownPacks::read` には count `0..=64` と各 String の bounded decode が既にある。しかし pending handler がこれを呼んでいない。
- 最小テスト案:
  1. `PendingConnection::handle_config_packet` の stateful test で、Known Packs 未受信の Finish Ack を `Stop`/error とする。
  2. 正常 sequence だけが `ReadyToPlay` を返すことを確認。
  3. `SKnownPacks::read` を実際に呼び、count 64 超、negative count、truncated String を reject する。
- 修正所有パス / 依存:
  - 主所有: `crates/pumpkin/src/net/java/pending.rs`。
  - packet decode 依存: `crates/pumpkin-protocol/src/java/server/config/known_packs.rs`。
  - resource pack enabled 時の許容 sequence と 26.2 vanilla state machine の照合が必要。

### 新規発見 4 — P2: Play の `configuration_acknowledged` を server initiation なしで Config に変更する

**確度: 高（未実装の sender と unconditional store を確認。client-visible full effect は未実施）**

- `crates/pumpkin/src/net/java/play/configuration_acknowledged.rs:6-12`
  - `JavaClient::handle_configuration_acknowledged` は packet を受けるだけで、server が `CStartConfiguration` を送ったか、reconfiguration pending flag があるかを検査せず `ConnectionState::Config` に変更する。
- `crates/pumpkin/src/net/java/mod.rs:1364-1366`
  - Play の `SConfigurationAcknowledged` ID に対して payload を読むことなく上記 handler を呼ぶ。
- `crates/pumpkin-protocol/src/java/client/play/start_configuration.rs:8-14` には `CStartConfiguration` codec はあるが、本監査の grep では server 側の送信 call site を確認できなかった。
- 到達する入力: 通常 Play 中に serverbound `configuration_acknowledged` (26.2 ID `16`) の空 bodyを送る。
- 期待 vs 現状:
  - 期待: server-issued Start Configuration の後だけ Config へ移り、完了 sequence を tracking する。未要求 packet は rejectする。
  - 現状: 任意 client が state を Config に変更できる。`JavaClient::handle_play_packet` 自体はその後も Play handler queue で処理されるため、`connection_state` と packet dispatcher の意味が分離する。disconnect packet 種別や plugin/extension 側の Config 判定も変わり得る。
- 影響: malicious/buggy client の state confusion、誤 disconnect type、将来 reconfiguration 機能追加時の bypass。現時点で vanilla client の通常 reconfiguration failure と確定してはいけない。
- 最小テスト案:
  1. pending flag なしの `SConfigurationAcknowledged` が state を変更しない/接続を閉じることを確認。
  2. `CStartConfiguration` 送信 → ack → Config packet sequence → finish ack の往復を、実 client なしの local packet/state test で固定。
  3. `connection_state` と inbound dispatcher の責務を同じ state machine で検証。
- 修正所有パス / 依存:
  - `crates/pumpkin/src/net/java/play/configuration_acknowledged.rs`、`crates/pumpkin/src/net/java/mod.rs`。
  - `CStartConfiguration` の送信主体、configuration packet dispatcher/reconfiguration design が依存。

## Recommended Next Steps

1. **P1 / 最優先:** `SChatCommandSigned::read` と `SSetGameRule::read` に checked count conversion、payload-aware upper bound、allocation前の reject を追加し、negative/huge count 回帰を protocol crate の局所 test で固定する。
2. **P1:** decoder に exact body consumption、premature EOF、zlib stream end/trailing bytes の test を追加し、`TCPNetworkDecoder` の frame boundary contract を明文化する。
3. **P1:** PendingConnection に configuration phase flags/expected packet sequence を持たせ、Known Packs payloadを decodeしてから `Finish Configuration` を送る/受ける順序を検査する。resource-pack enabled/disabled の両方を別テストにする。
4. **P2:** Play reconfiguration は `CStartConfiguration` の server send、ack pending state、Config → Play return sequenceを一体で設計する。未要求 `configuration_acknowledged` は受理しない。
5. vanilla 26.2 client の Java 25 loopback 接続を、上記 codec/state 修正と分離して実施し、client log、configuration order、clean disconnect、online-mode/encryption を別 evidence として保存する。

## 最重要発見（P0/P1/P2、最大5件）

1. **P1** `SChatCommandSigned::read` / `SSetGameRule::read` の unchecked count が、最小 serverbound payload から巨大 allocation/capacity panic に到達し得る。
2. **P1** `TCPNetworkDecoder::get_raw_packet` が uncompressed premature EOF を `RawPacket` として返し得て、compressed body の exact stream/body consumptionも保証していない。
3. **P1** `PendingConnection::handle_config_packet` が `finish_configuration` を Known Packs/Finish送信順序なしで Playへ昇格させる。
4. **P2** Play `configuration_acknowledged` が server-issued `CStartConfiguration`/pending stateなしで `ConnectionState::Config` を変更する。
5. **P2** `SKnownPacks::read` の既存 bound が `pending.rs` の handlerから呼ばれず、malformed Known Packs payloadを無視して registry/tags送信へ進む。
