# Java 26.2 / protocol 776 仮説検証戦略

## Findings

- 前回の監査所見は、現時点では **静的な候補または仮説** であり、真の不具合・実害・vanilla非互換と同一視しない。監査文書自身も、P0/P1の大半が実機、vanilla client、悪意wire入力、再起動による再現ではないと明記している。
- プレイヤーの行動履歴 packet をWebで集めることは、packet名、field、state遷移、通常の送信順を調べる材料にはなる。ただし、公開pcapだけで `行動 → packet列 → server判定 → world/inventory/entity結果` を精度よく証明するのは難しい。公開pcapは対象version、compression/encryption、Known Packs/registry、初期world、UUID/entity ID、tick境界、random seed、latency/timingが不明または異なるためである。
- より強い方法は、**同一初期状態を作ったvanilla 26.2をoracleとする差分検証**である。Pumpkinとvanilla serverを同じJava 25、同じ初期world/player/inventory/registry状態にし、同じ意味の合法操作を行い、packet列だけでなく最終状態と中間判定を比較する。合法client操作と、許諾したlocal lab内の改変/replay入力を二系統に分ける。
- wireだけでは不十分である。最低限、次を同時に記録する。
  - inbound/outbound packet: state、direction、packet id/name、decode結果、受信時刻とtick/sequence
  - server decision: accept/reject、reject理由、permission/reach/LOS/phase、event cancel
  - 結果: inventory/cursor/drop総量、block/world state、entity health/position/tracker、NBT/component
  - 検証用の初期状態と設定: version、registry/known-packs、seed、dimension、gamemode、permission、player/entity対応表
- 反証可能な基準を先に固定する。例えば、INV-01なら「1回のrecipe入力消費に対する output の総量保存」、BLK-01なら「開始状態・経過時間・権限を満たさないFinishedDiggingはmutationしない」、PLY-ATTACKなら「reach外/壁越し/別world targetはdamage/event side effectを発生させない」。期待値は比較対象の結果を見てから後付けせず、packet traceを採取する担当と独立したfixture/仕様表から決める。

### 最初に行う3シナリオ

1. **INV-01: crafting result の部分 shift-click**
   - 初期状態: recipe result 4個、player inventoryは同種stackに2個分だけ空き、他slotは埋める。
   - 行動: vanilla clientで結果slotをshift-click。別系統で同じ `SClickSlot` を許諾済みloopbackから再生する。
   - 観測: click mode/slot/revision/changed-slot hash、ingredient消費、inventory増加、drop、result slot残量、cursor、全stack/component。
   - 反証: `input消費数 × recipe semantics = inventory + drop + result + cursor` が成立し、vanilla/Pumpkinの差分がないこと。vanilla clientがこの厳密な部分stack状態を生成しないなら、「静的な増殖候補」として仮説を弱める。
   - 根拠: `docs/compatibility/audits/26.2-inventory.md` の `INV-01`、`crates/pumpkin-inventory/src/player/player_screen_handler.rs`、`crafting/crafting_screen_handler.rs`。

2. **BLK-01: block break の開始・完了・権限**
   - 初期状態: 固定座標のsolid block、同じplayer位置、同じtool/gamemode。合法操作ではclientの通常dig sequenceを使う。
   - 行動: `StartedDigging →（必要tick）→ FinishedDigging`、別位置、即時Finishedのみ、Adventure/Spectatorまたは `may_build=false` を分ける。sequence ACKも記録する。
   - 観測: `SPlayerAction`列、sequence、mining target/progress、reach、block state、drop/event、ACK。改変入力は必ずlocal isolated labだけで送る。
   - 反証: vanillaと同じ条件でのみbreakが起き、開始なし/早すぎ/位置不一致/権限なしではmutation・drop・eventが起きないこと。ACKの有無はmutation検証の代替にしない。
   - 根拠: `docs/compatibility/audits/26.2-blocks-ticks.md` の `BLK-01`、`crates/pumpkin/src/net/java/play/player_action.rs`、`crates/pumpkin/src/block/registry.rs`。

3. **PLY-ATTACK/INTERACT: reach・LOS・target lifecycle**
   - 初期状態: 同一worldのtargetを、合法距離、reach外、壁越し、dead/removed、spectator、別worldに配置する。
   - 行動: vanilla clientの攻撃/interactionを合法ケースで採取し、local labでtarget idだけを差し替えた改変packetを別ケースにする。
   - 観測: `SAttack`/`SInteract`、target entity id、距離/視線判定、plugin event、damage/knockback/interaction副作用、entity tracker。
   - 反証: vanillaと同じ合法ケースだけが副作用を持ち、invalid targetはevent/damage前に拒否されること。target idが存在することだけを「攻撃可能」の証拠にしない。
   - 根拠: `docs/compatibility/audits/26.2-player-entities.md` の `P1-2`、`crates/pumpkin/src/net/java/play/attack.rs`、`interact.rs`、`crates/pumpkin/src/entity/player.rs`。

Movement (`PLY-MOVE`) と tick (`TICK-01`) は重要だが、物理・timing・thread数の正規化が重く、最初の3件の後に回す。movementを始める場合も、まずfinite/delta/teleport/vehicleの判定だけを小さく比較する。

## Migration / Investigation Notes

### 推奨する検証構成

1. **Static candidate**: auditのsymbol/call pathから「どの入力がどのmutationに到達するか」をfixture表にする。ここでは「不具合」と確定しない。
2. **Protocol/code照合**: Minecraft Wikiの26.2/776、公式metadata/JAR、必要に応じてBurger/Via mappingsを使い、packet field/state/registryを照合する。ID一致だけでsemantic一致とはしない。
3. **最小再現**: まず純粋なcodec/state/handler fixture、次に許諾済みloopback/in-process peer。受理・拒否・副作用を数値化する。
4. **Vanilla differential**: 公式vanilla 26.2 serverをoracleとして、同じ初期world/player状態と意味的に同じ操作を実施する。Pumpkinとvanilla双方で client trace、server decision、final stateを採取する。
5. **Regression**: 反証基準をtestへ固定し、合法ケースと改変/replayケースを別テストとして回帰化する。最終的にも「対象シナリオの一致」と報告し、「完全互換」とは主張しない。

### packet capture/replayの境界

- 本番認証を弱めない。online-mode/encryptionを無効化して公開serverへ接続する方法は採らず、local isolated offline lab、許諾済みclient/server instrumentation、またはendpoint直前のログを使う。
- Java本番通信はlogin後に暗号化され得る。圧縮、frame境界、replay時のtimestamp/salt/ack/session、registry/known-packs状態も変わるため、公開pcapのbyte列をそのまま再送して証拠にしない。
- 合法client経路では「通常のpacket順とclient acceptance」を測る。改変/replay経路では「どのvalidation前にmutationへ到達するか」を測る。後者の拒否をvanilla clientの通常仕様と混同しない。
- captureの正規化対象は UUID、entity ID、window/sync ID、timestamp、teleport ID、random seed、absolute position、packet arrival time。正規化し過ぎて順序、tick内順序、count、NBT/component差分を消さない。
- 比較は3層に分ける。(a) wire envelope/packet sequence、(b) semantic events/判定、(c) persistent/game state。wireが異なっても意味が同じ場合と、wireが同じでも結果が異なる場合を区別する。

## Recommended Next Steps

1. 最初の小タスクは実装ではなく、**INV-01/BLK-01/PLY-ATTACKの3行動シナリオ契約表**を作ること。各行に初期状態、合法packet列、改変packet列、期待decision、world/inventory/entity invariant、正規化規則、反証条件を1つずつ書く。
2. その契約表を使い、次の段階で公式JAR/vanilla clientをユーザーが許諾・用意できるlocal isolated labに置く。最小構成は Java 25、公式Java client利用権、公式server JAR、同一固定world、loopback capture/instrumentation、EULA同意。今回は起動しない。
3. 取得したtraceの保存形式を `scenario_id / initial_state_hash / normalized_packet_trace / decisions / final_state_hash / tool-version` とし、UUID/entityID/timestamp等の差分を正規化する。raw traceは別保管し、正規化後だけをdiffする。
