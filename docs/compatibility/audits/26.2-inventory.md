### INV-01 — crafting result の部分 shift-click が増殖する [P0]

- **場所 / シンボル**
  - `crates/pumpkin-inventory/src/player/player_screen_handler.rs:149-239` — `PlayerScreenHandler::quick_move`
  - `crates/pumpkin-inventory/src/crafting/crafting_screen_handler.rs:409-425` — `ResultSlot::refill_output` / result生成
  - `crates/pumpkin-inventory/src/crafting/crafting_screen_handler.rs:442-451` — `ResultSlot::on_take_item`
  - 共通移動: `crates/pumpkin-inventory/src/screen_handler.rs:686-766` — `ScreenHandler::insert_item`
- **到達入力 / 状態**
  1. crafting result slot `0` に count `>1` の結果（例: planks `4`）がある。
  2. player inventory は満杯に近く、同種 stack にだけ少量の空きがある（例: planks `62`、空き `2`、他に空slotなし）。
  3. client が shift-click (`SClickSlot.mode=QuickMove`, slot `0`) を送る。
- **コード上の遷移**
  - `insert_item` は既存 stack に2個だけ入れ、ローカル `slot_stack` を残り2個にする。
  - `slot.set_stack(stack.clone())` は `ResultSlot::set_stack` に入り、渡された残り stack を保存せず `refill_output()` で元の結果4個を再生成する。
  - その後 `on_take_item` が各ingredientを1個だけ消費する。
  - `on_quick_move_crafted` が再度outputをrefillし、元の `stack`（残り2個）は `player.drop_item` に渡される。
  - `quick_move` は `stack_prev.item_count - stack.item_count` を taken量とみなすが、result slot側は再び4個を表示する。
- **期待値 vs 現状**
  - 期待: 1 craft分の結果だけが移動し、搬送できない残りは正しく扱う。ingredient消費量とoutput生成量は一致する。
  - 現状: inventoryに2個追加、dropに2個、result slotに4個残存、ingredientは1回分だけ消費、という経路があり、1回の4個レシピから合計8個相当になる。
- **影響**: 実アイテム増殖。通常の空slotがある場合は発火しにくいが、満杯inventory + stack partial roomで再現可能性が高い。
- **確度**: 高（関数の値の流れだけで成立。vanilla client実機は未確認）。
- **再現テスト案**
  - 3x3 crafting tableで planks 4個レシピを用意。
  - player inventoryを同種62個のstackと他の非空stackで埋め、空きは2個だけにする。
  - result slotをshift-clickし、入力ingredient数、既存stack数、result表示、drop数を操作前後で合計比較する。
  - `quick_move_result_partial_stack_does_not_duplicate` を result slotの単体/handler testとして追加。
- **修正パス**: result slotのtake/quick-moveを「実際に受け入れられたoutput量」と「craft回数」に分離し、部分搬送時にresultを無条件に全量refillしない。result outputを通常slotのように部分setする設計は避け、vanillaのcraft-on-take semanticsに合わせる。

### INV-02 — state-id / changed-slot hash を検証せず stale click を適用 [P1]

- **場所 / シンボル**
  - `crates/pumpkin/src/entity/player.rs:5773-6172` — `Player::on_slot_click`
  - `crates/pumpkin-protocol/src/java/server/play/click_container.rs:14-23` — `SClickSlot::{revision,array_of_changed_slots,carried_item}`
  - `crates/pumpkin-inventory/src/screen_handler.rs:323-345` — `set_received_hash` / `set_received_cursor_hash`
  - `crates/pumpkin-inventory/src/screen_handler.rs:1310-1312` — `ScreenHandlerBehaviour::next_revision`
- **到達入力 / 状態**
  - clientが古い `revision`、または実際のslot/cursorと一致しない `OptionalItemStackHash` を含む `SClickSlot`を送る。
  - `Player::on_slot_click`は `not_in_sync` を計算するが、拒否・事前resyncせず、`screen_handler.on_slot_click(...)`を常に実行する。
  - client supplied hashは操作後の `set_received_hash` / `set_received_cursor_hash` でtracking stateに記録される。
- **期待値 vs 現状**
  - 期待: revisionまたは送信済みslot/cursor stateが一致しない操作は適用せず、server authoritative stateを再送する。
  - 現状: stale操作を現在のserver slotに対して実行し、最後に mismatchなら `update_to_client()`する。changed hash自体を操作前にserver stateと照合していない。
- **影響**: clientが意図したslot状態と異なる操作が通る。高速クリック、同時plugin更新、再接続/画面再open直後にclient UIが跳ねる、誤ったstackを拾う/置く、cursor表示だけが遅れる可能性がある。直ちにserver-side増殖と断定はしないが、protocolのtransaction保証を満たさない。
- **追加のrevision問題**: `next_revision` は `fetch_and(32767) & 32767` で0..32767にmaskされる。長時間のcontainer更新でvanillaのstate-id単調増加前提とずれる可能性がある。境界値の実client受理は未確認。
- **確度**: 高（stale packetを適用する分岐は確定）。増殖への直接到達は未確認。
- **再現テスト案**
  - handlerのrevisionを進めた後、古いrevisionと古いhashで同じslotを再送し、server inventoryが変化しないことを期待する。
  - cursor hashだけ不一致、slot hashだけ不一致、arrayに範囲外/負のslotを入れたケースを分ける。
  - revision `32766 -> 32767 -> 0` 境界をmodel testで固定し、26.2 packetのclientbound state-idとして受理されるか実clientで確認する。
- **修正パス**: `SClickSlot`のrevisionと変更slot/cursor hashを、操作前のtracked stateに対して検証し、不一致なら操作を中止してfull content/cursorを再送する。revisionのmaskは公式26.2 server semanticsと照合してから撤去/置換する。

### INV-03 — crafting remainder、item component、transmute validationの欠落 [P1]

#### 3-a. recipe remainderが消える

- **場所**: `crates/pumpkin-inventory/src/crafting/crafting_screen_handler.rs:442-451`。
- `ResultSlot::on_take_item` は全input slotから無条件に `remove_stack_specific(i, 1)`するだけで、remainderをplayer inventoryへ戻さない。
- 既存の生成helper `crates/pumpkin-data/src/generated/recipe_remainder.rs:4-15::get_recipe_remainder_id` は存在するが、crafting経路から参照されていない（検索結果はcrafter/furnace系のみ）。
- **具体例**: `crates/pumpkin-data/src/generated/recipes.rs:1801-1804` の cake recipeは milk bucketを使う。craftするとbucketがgridから消え、vanillaの空bucket相当のremainderが失われる可能性がある。
- **期待**: ingredient 1個を消費し、recipe remainderを対応slotまたはplayer inventoryへ戻す。満杯時のdropも含めて合計数を保存する。

#### 3-b. result outputがinput componentを保持しない

- **場所**: `crafting_screen_handler.rs:409-425::ResultSlot::refill_output`。
- `RecipeResult { item_id,count }`から `ItemStack::new(matched.count,item)`を作るだけで、input component/custom dataをコピーしない。
- **具体例**: generated recipesには `CraftingTransmute` の map cloning (`recipes.rs:8994-9002`, filled_map + map -> filled_map) がある。resultは新規のbare `filled_map`になり、map id等のcomponent/dataを失う可能性が高い。bundle/shulker dyeでも入力component保持の設計がない。

#### 3-c. transmuteがinput/materialの組合せを検証しない

- **場所**: `crafting_screen_handler.rs:203-224::recipe_matches`。
- `count == 2`の後、各non-empty slotが `material`または`input`のどちらかにmatchすれば成功する。
- **到達例**: black bundle + black bundle、またはblack dye + black dyeの2slotでも条件を通り、bundle + dyeの組合せを要求するtransmute recipeを生成する。
- **期待**: inputを1個、materialを1個、かつ各ingredientが対応component条件を満たすこと。

#### 3-d. recipe-bookのuse-maxがitem max stackを超える

- **場所**: `crates/pumpkin/src/net/java/play/place_recipe.rs:163-233::handle_place_recipe`、`recipe_helper.rs:16-48::take_n_ingredient` / `compute_biggest_craftable`。
- `compute_biggest_craftable`は最大64まで数え、itemのmax stack/slot maxを考慮しない。`take_n_ingredient`は1slotへcount個をまとめる。
- transmuteのbundle等、max stack 1のingredientでrecipe-book `use_max_items=true`を使うと、gridにcount>1のunstackable stackを作り得る。
- **確度**: remainder欠落とtransmute条件は高。component保持とrecipe-book overstackはコード経路上高いが、26.2実clientのpacket/recipe-book表示は未確認。
- **再現テスト案**
  - milk bucket cake、honey bottle系、map cloning、bundle dyeをそれぞれ「grid投入→左クリック→grid/result/inventory合計・component」を比較。
  - transmuteはinput/input、material/material、input/materialを3ケースに分ける。
  - recipe-book use-maxでmax-stack-1 ingredientを投入し、各grid stack countがitem/slot max以下か確認。
- **修正パス**: recipe match結果を「output stack + per-slot remainder + component transform」として返す。recipe remainder registryをcraftingでも再利用し、transmute/special recipeは入力componentを明示的に移送/変換する。recipe-book helperはitem max、slot max、ingredientごとの必要数で上限を計算する。

### INV-04 — generic hopperのshift-clickが `rows * 9` 固定 [P1]

- **場所 / シンボル**
  - `crates/pumpkin-inventory/src/generic_container_screen_handler.rs:218-245::GenericContainerScreenHandler::quick_move`
  - `add_inventory_slots`は `rows * columns` でslotを作る（同ファイル:155-166）。
  - `create_hopper`は `rows=1, columns=5`（同ファイル:91-105）。
- **到達入力 / 状態**
  - hopperを開き、container slotまたはplayer inventory slotをshift-clickする。
- **期待値 vs 現状**
  - 期待: container範囲は0..5、player範囲は5..全slot。
  - 現状:境界・挿入範囲に `rows * 9 == 9`を使用する。実slot配置のcontainer 5枠と一致しない。
  - hopperのplayer slot 5..8をcontainer側として扱い、player slot 9以降からの移動先範囲0..9にはhopper以外のplayer slot 5..8も混入する。
- **影響**: hopperへの搬入漏れ、誤slotへの移動、shift-click連打時のclient/server表示不一致。経路によってはitem loss/残留の回収が遅れる。直接増殖はコード上確定しない。
- **確度**: 高。
- **再現テスト案**: hopperの5枠とplayer screen slots 5,8,9,10に識別可能なitemを置き、container→player、player→containerを各方向でshift-click。最終inventoryと全slot packetを比較する。
- **修正パス**: `container_slot_count = self.inventory.size()`または`rows * columns`を唯一の境界値にして、quick_move・behaviour.container_slots・packet validationを同一値から組み立てる。

### INV-05 — equipment / close lifecycleの同期不足 [P1]

#### 5-a. 通常GUIのmain/off-hand変更がequipment broadcastされない

- **場所**
  - `crates/pumpkin-inventory/src/screen_handler.rs:1077-1118` — normal pickupはarmor slot `(5..9)`だけequipment changeを通知。
  - 同ファイルの`Swap`処理（`internal_on_slot_click`内の`SlotActionType::Swap`分岐、約1150行以降）は`PlayerInventory::set_stack` / `source_slot.set_stack`を直接実行し、equipment changeを通知しない。
  - `crates/pumpkin/src/net/java/play/set_creative_slot.rs:37-75` はarmorとselected hotbarだけをbroadcastし、screen slot `45`のoff-handを扱わない。
- **到達入力**: E inventoryでselected hotbarまたはoff-handへpickup/number-key swap、またはcreativeでoffhand slot `45`へitemをセットする。
- **期待値 vs 現状**: server inventoryは変わるが、他player向けheld/equipment packetを同一操作で送る経路がない。本人のslot表示と他clientの手/装備表示が分岐し得る。
- **確度**: 高（broadcast呼び出しがない）。実clientの表示受理は未確認。

#### 5-b. 既存 hand-swap修正の適用範囲

- **既知・既存変更**: `crates/pumpkin/src/entity/player.rs:4987-5018::Player::swap_item` は selected hotbar `0..=8` と off-hand `40`の`CSetPlayerInventory`を明示送信し、equipment broadcastと`sync_inventory_to_client`を維持している。`26.2-progress.md`記載の既存testはslot mapping/server stateを確認済み。
- **残る確認事項**: `sync_inventory_to_client` (`player.rs:1463-1466`) は`player_screen_handler`だけを更新する。containerを開いたままF-key swapした場合、active container handlerのplayer slots・state-idとの整合は`CSetPlayerInventory`が26.2 clientでどう反映されるか未確認。既存testはactive container/real client packet acceptanceを証明しない。

#### 5-c. close packetのwindow idを捨てる

- **場所**: `crates/pumpkin/src/net/java/mod.rs:1189-1192` は`SCloseContainer`をreadするだけでwindow idを検査せず、`crates/pumpkin/src/net/java/play/close_container.rs:5-6::handle_close_container`が無条件に`Player::on_handled_screen_closed()`を呼ぶ。
- **到達入力**: container Aを閉じてBを開いた直後など、遅延したAのclose packet、または不正なwindow idのclose packet。
- **期待値 vs 現状**: 現在のhandlerのsync idと一致した場合だけ閉じる。
- **影響**: 現在のcontainerを意図せず閉じ、cursor/grid itemをdrop/returnしてclient UIとserver handlerがずれる。item loss/二重returnの実機再現は未確認だが、lifecycle guard欠落は確定。
- **確度**: 高（window id未使用）。
- **修正パス**: close packetのwindow idを`on_handled_screen_closed(expected_sync_id)`で検証し、外部containerだけをcloseする。通常GUI/active handlerのequipment更新はslot mutationの共通callbackへ集約する。

### 追加のP2 / 未優先事項

1. `crates/pumpkin-inventory/src/player/player_screen_handler.rs:63-64::is_in_hotbar` はprotocol上hotbar `36..=44`なのに`45`（off-hand）を含む。現在repo内の呼び出しは検索上なく、直ちに到達する影響は未確認。
2. `ScreenHandler::copy_shared_slots` (`screen_handler.rs:394-429`) は同じ`ComparableInventory`をtableへinsertする際、player inventoryのslot mappingを1件ずつ上書きするため、再open/close後に全共有slotのtrackingを復元できない。再open時のfull syncが多くを隠すが、close直後の差分同期で過不足packetが出る候補。
3. `set_creative_slot` (`set_creative_slot.rs:13-14,77-79`) は負値全てをdrop扱いし、protocolで許されるdrop sentinel以外を拒否しない。通常権限ではcreative限定だが、入力validationとして不足。
4. `Inventory::count` (`crates/pumpkin-inventory/src/inventory/inventory.rs:28-38`) は合計を`u8`で保持する。複数slotの合計が255を超えるとrelease/debug条件によりwrap/panicの境界があり、count用途に使うとstack limit判定を壊し得る。
5. `PlayerInventory::insert_stack` / `add_stack_to_slot` (`player_inventory.rs:175-221,303-333`) は明示slotへ渡したstackと既存stackのitem/component一致を検査しない。ただし通常server経路は`-1`または事前にroomを選ぶため、client直接入力からの到達は未確認。
6. `Slot::insert_stack_count` (`slot.rs:186-214`) は既存stack countがslot maxを越えた不正状態でu8 subtractionが成立しない可能性がある。creative入力はitem maxまでは制限するが、slot max/既存壊れ状態の回復方針は未確認。

### 実装上「確認できた」正常経路 / 既知修正

- player screen slot mappingはコード上、result `0`、crafting `1..4`、armor `5..8`、main `9..35`、hotbar `36..44`、off-hand `45`で一貫している（`player_screen_handler.rs:8-20,93-111`）。ただしgeneric hopperはINV-04の別問題。
- `PlayerInventory::OFF_HAND_SLOT == 40`、selected hotbar `0..=8`のdirect inventory mappingと、player screen上のoff-hand `45`を混同しないようにする必要がある。
- 既存hand-swap修正は監査中に変更していない。既存記録の通り、local testはslot mapping/server-side交換を確認するが、vanilla 26.2 clientのUI・packet受理・再接続後保存は未確認。
