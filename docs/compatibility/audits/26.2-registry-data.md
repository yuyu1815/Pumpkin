- 対象: Java Edition 26.2 / protocol `776` / world data `4903`

### 整合している範囲（根拠あり）

1. **ID 表**
   - `assets/blocks.json`: block `1,196` 件、ID `0..1195`、重複 `0`、欠番 `0`。
   - `assets/items.json`: item `1,537` 件、ID `0..1536`、重複 `0`、欠番 `0`。
   - `assets/entities.json`: entity `158` 件、ID `0..157`、重複 `0`、欠番 `0`。
   - `assets/data_component.json`: component `111` 件、ID `0..110`、重複 `0`、欠番 `0`。generated `DataComponent` も `CustomData=0` から `ShulkerColor=110`。
   - これは ID 全置換の根拠ではない。wire/version remap は `item_id_remap.rs`、`entity_id_remap.rs`、`data_component_type_id_remap.rs` の既存経路を別途検証する。

2. **26.2 registry source と generated 静的 registry の件数**
   - `SYNCED_REGISTRIES` は `29` registry。
   - source JSON 件数と generated `REGISTRY_V_26_2` の比較は、`worldgen/biome=66`, `trim_pattern=18`, `dimension_type=4`, `damage_type=51`, `enchantment=43`, `dialog=3`, `world_clock=2` 等を含め **397 source entries と generated entries が一致**。例外は codegen が仕様上注入する `chat_type.raw` の `+1`（source `7` → generated `8`）。
   - registry entry name は codegen の sorted JSON stem から `minecraft:<name>` として生成される。`worldgen/biome` は source/generated とも filename lexicographic order で `66` 件。
   - これは NBT tag type/value と client acceptance の証明ではない。

3. **tags**
   - `assets/datapacks/26_2/data/minecraft/tags` は `796` JSON、tag value object `0`、hash reference `419`、parse error `0`。空 tag は `9`。
   - `tools/pumpkin-codegen/src/tag.rs` は namespace/category を走査し、tag reference を再帰解決する。`CUpdateTags` は `RegistryKey::NETWORK_KEYS` と version remap を通して送信する。
   - 現入力に optional tag object (`{"id":...,"required":false}`) は無かったため、その仕様の意味保持は未確認。

4. **datapack/codegen 境界**
   - `crates/pumpkin-world/build.rs:23` は vanilla pack として `../../assets/datapacks/26_2` を埋め込み、container pack は sorted load order で後勝ち。
   - `tools/pumpkin-codegen/src/main.rs:70-145` は生成先を `crates/pumpkin-data/src/generated` に固定し、generated header は手編集禁止。今回 codegen 再実行はしていない（共有 generated file を変更しないため）。

## Recommended Next Steps

1. **最優先: R3 の三者比較を実装**。公式 JAR（既存 hash のもの）から registry/codec の一覧と data schema を抽出し、`SYNCED_REGISTRIES` → `REGISTRY_V_26_2` → actual `CRegistryData` bytes を比較する。raw NBT の tag type、entry ordering、duplicate、trailing byte を検査し、成功条件を `missing=0, extra=0, mismatch=0` とする。
2. **R1 を recipe fixture で固定**。suspicious stew result components、crafting transmute quantity/component inheritance、special recipe serializer を client recipe-book と server craft result の両方で確認する。正式コード変更は別担当・別タスクで行い、この監査では生成物を直接編集しない。
3. **R2 の dimension model/fallback comparator** を追加。source JSON、generated model、fallback NBT、Registry Data raw NBT の 4-way compare。特に Nether scalar spawn-light `7` と `default_clock/has_ender_dragon_fight/cardinal_light/skybox` を必須キーにする。
4. **R4 の component value loss を定量化**。ID 表はすでに contiguous なので置換せず、source `items.json` の non-empty component と generated default の差分だけを出す。firework、potion、book、map、crossbow、bundle/container、suspicious stew を最小 fixture にする。
5. **R5 の実 client boundary**。Known Packs の全 tuple、Feature Flags、Registry Data、Update Tags、Finish Configuration の順序と payload を capture する。既存 strict harness の `known_pack_reply=true` や `play_frame_observed` を semantic pass に昇格させない。
6. vanilla 26.2 client が利用可能になるまで、`real_client_compatibility` と「registry identical」の宣言は未確認のまま維持する。cargo build/test/server 起動は次の実装担当の許可された検証でのみ実施する。
