# 26.2 プレイヤー移動・entity lifecycle・戦闘 監査

- 対象: Java Edition 26.2 / protocol `776` / world data version `4903`
- 監査範囲: `crates/pumpkin/src/entity/**`、`crates/pumpkin/src/world/entity_tracker.rs`、`crates/pumpkin/src/world/mod.rs` の player/entity lifecycle、関連 Java play packet handler
- 境界: inventory/block 処理は経路確認のみ。protocol/world crate、generated packet、server設定、正式 Rust source は変更していない。
- 判定: **完全互換・安全な server-authoritative movement・dimension lifecycle は未達。** 以下はソース監査で確定できる重要事項で、Cargo test、server 起動、vanilla client 接続は実施していない。
- 所有書込み: 本ファイルのみ。

## Findings

### P1-1 [新規] クライアント移動を無条件に位置へ反映し、衝突・速度・落下の server-side 検証がない

- **対象シンボル/行**
  - `crates/pumpkin/src/net/java/play/player_position.rs:46-184` `JavaClient::handle_position`
  - 同 `:187-359` `JavaClient::handle_position_rotation`
  - `crates/pumpkin/src/net/java/play/move_vehicle.rs:5-31` `JavaClient::handle_move_vehicle`
  - `crates/pumpkin/src/entity/mod.rs:2310-2354` `Entity::move_entity`（mob/entity の collision 経路）
  - `crates/pumpkin/src/entity/living.rs:1404-1406` `LivingEntity::tick_movement` の `// TODO: Gliding`
- **到達条件**
  - client が `PlayerPosition` または `PlayerPositionRotation` を `has_client_loaded()` 後に送る。teleport confirmation 待ち、vehicle搭乗中、movement lock 中を除けば、event が cancel されない限り実行される。
  - 通常のプレイヤーは `LivingEntity::tick` で `travel`/`Entity::move_entity` を実行せず、handler が `entity.set_pos(pos)` を直接呼ぶ。
- **期待**
  - 26.2 vanilla 相当では、受信 delta の妥当性、world border/座標上限、ブロック collision、loaded chunk、vehicle権限、必要な速度・飛行状態を server 側で検証し、不正なら位置を戻す/teleport する。落下距離・on-ground・fall damage は認証された移動結果から更新される。
- **現状**
  - `set_pos` で server state を先に client 座標へ置き、`chunker::update_position`、fall、他 client への delta broadcast を行う。collision はその後の `tick_block_collisions` による suffocation/damage の検出に限定され、移動を衝突面で解決しない。
  - source に `// TODO: Warn when player moves to quickly` (`player_position.rs:124,280`) が残る。`Entity::move_entity` の衝突解決は caller が player なら `return` (`entity/mod.rs:2310` 付近) するため、player handler からは使われない。
  - vehicle packet は `move_vehicle.rs:12-22` で packet 座標を vehicle と player の両方へ直接 `set_pos` し、距離検証、finite 検証、teleport confirmation 待ちを行わない。
- **根拠**
  - `player_position.rs:103`/`:251` の `set_pos(pos)`、`player_position.rs:124`/`:280` の速度検証 TODO、`move_vehicle.rs:12-22` の直接更新。
  - `LivingEntity::tick` (`living.rs:3358-3370`) は player を `is_player` 分岐で travel から除外し、velocity friction/collision callback のみ実行する。
- **確度**: 高（実行経路をコードで追跡可能）。
- **影響**: P1。壁抜け、speed/fly/vertical teleport、落下距離の偽装、chunk/entity tracking 更新の不整合、対人戦闘・保護領域の回避につながる。通常の client は使わない経路でも、悪意ある client/packet peer では再現可能。
- **ローカル再現/回帰テスト案**（未実行）
  1. 既存 handler の unit fixture で solid block の中/反対側へ 10 block の position packet を渡し、期待値が collision 解決または corrective teleport になることを確認する。
  2. 前 tick から `+100`、`+1e9`、`y=-2e7/2e7`、vehicle搭乗中の `SMoveVehicle` を入力し、position、chunk tickets、fall distance、broadcast packet を検査する。
  3. `on_ground=true` のまま上方へ移動する packet と airborne elytra/flying packet を分け、jump/fall damage が一度だけ発生することを確認する。
- **修正パス**
  - player/vehicle 用の共通 `validate_movement` を作り、全座標 `is_finite`、world border、許容 delta/速度、teleport ack、vehicle ownership を先に検査する。
  - `old_pos -> requested_pos` の swept AABB collision 解決を player にも適用し、受理後の delta だけで `fall_distance`、`on_ground`、chunk watcher を更新する。推測値で即 kick せず vanilla の corrective teleport/警告方針を別途固定する。

### P1-2 [新規] entity attack/interact に reach、line-of-sight、hitability 検証がない

- **対象シンボル/行**
  - `crates/pumpkin/src/net/java/play/attack.rs:5-58` `JavaClient::handle_attack`
  - `crates/pumpkin/src/net/java/play/interact.rs:6-133` `JavaClient::handle_interact`
  - `crates/pumpkin/src/entity/player.rs:1170-1410` `Player::attack`
  - 比較用の既存 helper: `crates/pumpkin/src/entity/mod.rs:3447-3456` `Entity::has_line_of_sight`
- **到達条件**
  - client が存在する entity id を `SAttack`、または `SInteract` の target として送る。target が同じ world の `get_player_by_id`/`get_entity_by_id` で見つかれば処理される。
- **期待**
  - attack/interact は target の alive/can-hit、同一 world、攻撃者からの entity reach、必要な視線/遮蔽と action/hand を server 側で検証する。target が遠い/壁越し/非攻撃対象なら無効化する。
- **現状**
  - `handle_attack` は entity id を解決後、creative protection と victim health だけを確認して `player.attack(&target)` (`attack.rs:43-55`) する。距離、AABB hit、視線、`can_hit()` の検査がない。
  - `handle_interact` も同じ target 解決後、spectator camera を除き、`PlayerInteractEntityEvent` の後に `event.target.interact`/item registry を呼ぶ。距離/視線検証はない。
  - `Player::attack` は damage、knockback、sweep、Fire Aspect、耐久、exhaustion を実行するため、呼出し前の検証欠落がそのまま gameplay/security 境界になる。
- **根拠**: `attack.rs:20-55` と `interact.rs:31-133` の分岐に distance/raycast/can_hit が存在しない。projectile/AI 等には既存 raycast helper があるため、実装能力が全くないことが理由ではない。
- **確度**: 高。
- **影響**: P1。任意の loaded entity/player を遠距離から攻撃し、entity interaction の副作用（trade、乗車、item use 等）を遠隔で発生させられる可能性がある。PVP、mob、plugin event の前提を破る。
- **ローカル再現/回帰テスト案**（未実行）
  - attacker を target から `4.5` block 超、壁の反対側、別 chunk に配置し、`SAttack` と `SInteract` を直接 handler に渡す。damage/interaction event/knockback が 0 で、invalid attack の kick 方針が仕様化されることを確認する。
  - target が `can_hit=false`、dead、spectator、removed の各ケースを分ける。
- **修正パス**
  - `Player::can_interact_with_entity` 相当の共通関数を作り、target AABB 最近点または vanilla の entity interaction range、same-world/alive/can_hit、視線/raycast を検査する。
  - attack と interact の両 handler が共通 validator を通り、validator 後にだけ plugin event と `Player::attack`/`interact` を呼ぶ。inventory/block 操作そのものは別担当の境界として残す。

### P1-3 [新規] dimension transfer が player/entity tracker と world 所有権を一貫して更新しない

- **対象シンボル/行**
  - `crates/pumpkin/src/world/mod.rs:4493-4502` `World::respawn_player` の cross-dimension 分岐
  - `crates/pumpkin/src/entity/player.rs:3841-3900` `Player::teleport_world`
  - `crates/pumpkin/src/entity/mod.rs:3394-3428` `Entity::teleport`
  - `crates/pumpkin/src/entity/mod.rs:2435-2455` portal transfer caller
  - `crates/pumpkin/src/world/entity_tracker.rs:472-509,542-639`
- **到達条件**
  - cross-dimension respawn、plugin/API の `Player::teleport_world`、または non-player entity が portal processor の destination を得た場合。
- **期待**
  - source world から entity/player を detach し、destination の live entity list、`world` reference、`EntityTracker`、chunk watcher/pairing を順序付きで更新する。destination watcher には spawn、source watcher には remove を一度ずつ送る。
- **現状**
  - player の cross-dimension respawn は `self.remove_player(player, false).await` で source tracker から外した後、`destination.players.rcu(...push...)` (`world/mod.rs:4495-4501`) に直接追加する。しかし `destination.add_player`、`destination.entity_tracker.add_entity`、`pair_new_player_with_tracked_entities` を呼ばない。
  - `Player::teleport_world` も source remove 後に `new_world.players.rcu(...push...)` (`player.rs:3876-3888`) を行い、同じ tracker 登録欠落がある。
  - non-player portal path (`entity/mod.rs:2452`) は `entity_arc.teleport(..., dest_world)` を呼ぶが、`Entity::teleport` は position/packet broadcast のみで、引数 `world` を `set_world` に反映せず、source entity listから除去してdestinationへ追加もしない。player は `EntityBase for Player::teleport` (`player.rs:6677-6705`) が async `teleport_world` に分岐するため経路が異なる。
- **根拠**
  - 正常 spawn の `World::add_player` (`world/mod.rs:5082-5090`) は players list と tracker add を同時に行い、初期 join は `pair_new_player_with_tracked_entities` (`world/mod.rs:3448-3450`) を呼ぶ。
  - transfer 分岐にはその呼出しがなく、non-player `Entity::teleport` に `self.world.store(...)` がない。
- **確度**: 高。
- **影響**: P1。dimension 移動後の player/entity が destination の `entity_map` にいない、他プレイヤーに見えない、tracking-based damage/status/equipment packet が届かない、source world の tick/list に残った non-player entity が destination 座標で処理される可能性がある。死亡→別 dimension respawn と portal を分けて発生する。
- **ローカル再現/回帰テスト案**（未実行）
  1. 2つの World fixture に player を移動し、移動前後で `source.entity_tracker.has_entity_with_id(id)`/`destination...`、players list、`entity.world`、seen_by を比較する。
  2. mob/item を Nether portal transition に通し、source/destination entity list、world pointer、tick world、tracker map、spawn/remove packet を確認する。
  3. cross-dimension respawn 後に destination player が既存 entity を見て、既存 player が respawn player を見られることを packet/event fixture で確認する。
- **修正パス**
  - transfer を一つの lifecycle helper に集約し、source tracker/player listからdetach → chunk ticket reset → entity world変更 → destination list/tracker add → pairing → packet/teleport confirmation の順序を明示する。
  - `add_player` をそのまま使う場合は login-only side effect と重複しないよう分離した `add_player_after_transfer` を検討する。non-player も source `World::remove_entity` の removal semantics（discard扱いにしない）と destination spawn/tracker 登録を持つ専用処理が必要。

## 正常または部分確認できた経路

- **spawn/initial tracking**: `World::add_player` (`world/mod.rs:5082-5090`) は player list と tracker add を行う。初期 spawn の `send_world_info` (`world/mod.rs:4118-4160`) と `pair_new_player_with_tracked_entities` (`world/mod.rs:3448-3450`) は存在する。ただし vanilla clientでの受理は未確認。
- **teleport confirmation**: `Player::request_teleport` (`player.rs:3993-4049`) は Java の `awaiting_teleport=(id,position)` を設定してから packet を enqueue。`handle_confirm_teleport` (`confirm_teleport.rs:5-48`) は正しい id のみ解除し、wrong/not-teleporting を kick する。confirm前の position packet は `player_position.rs:67-76,207-216` で無視される。ID race/多重 teleportの実client traceは未確認。
- **NaN/inf**: `handle_position` は NaN のみ kick (`player_position.rs:84-94`)、`handle_position_rotation` は全座標/yaw/pitchの `is_finite()` (`:226-238`)。しかし position-only の `+inf/-inf` は reject せず `clamp` (`:95-100`) され、`SMoveVehicle` (`move_vehicle.rs:12-22`) は finite検査自体がない。これは P1-1 の入力検証欠落に含めた。
- **collision/fall/swim**: entity/mob向け `Entity::move_entity` (`entity/mod.rs:2310-2354`)、block collision/suffocation、fluid state、fall damage (`living.rs:1816-1910`) は存在する。playerの受信移動は同じ collision solverを通らないため、完全互換とは判定しない。`Player::update_swimming` (`player.rs:2079-2100`) と pose update (`:2139-2165`) は存在するが、client authoritative positionの水中判定は未実測。
- **velocity**: `Entity::apply_knockback`、`velocity_dirty` coalescing、`LivingEntity::tick` の送信は存在する (`living.rs:3358-3380`、`entity/mod.rs` の velocity fields)。playerは travelをskipして frictionのみ (`living.rs:3361-3370`) なので、受信位置と knockback velocity の reconciliation は未完成。
- **death/health/hunger/effects**: `LivingEntity::damage_with_context` (`living.rs:2919-3320`) は invulnerability、fire/resistance/armor/shield、hurt cooldown、absorption、health、death eventを処理し、`LivingEntity::on_death` は一度だけ death state を立てる。effect add/remove/tick (`living.rs:942-1180,2287-2326`)、hunger tick (`player.rs:2823`)、Java respawn request (`client_command.rs:7-48`) も存在する。ただし respawn の完全な client sync は P2-5、damage source/attack reachはP1-2を参照。
- **disconnect cleanup**: Java/Bedrock main loop は `player.remove().await` → server listing/data save (`crates/pumpkin/src/lib.rs:613-616,719-721`) を呼ぶ。`Player::remove` (`player.rs:1031-1090`) は搭乗中 vehicleから `remove_passenger_on_disconnect` し、`World::remove_player`/tracker/chunk ticketsを掃除する。この範囲では player が vehicle に乗っている場合の基本 cleanup 欠落は確認しなかった。passengerを持つ特殊な player/vehicle plugin構成、task cancellation中の二重removeは未実測。
- **lock/await**: `respawn_player` は `calculate_respawn_point().await` 前に長期 Mutex guardを保持しない構造で、cross-world transferも source remove/unload と destination publishを段階化している。ただし cross-world tracker登録欠落は P1-3。parallel world tick (`world/mod.rs:1481-1600`) と Rayon内の plugin/entity処理は、全 lock orderを静的完全証明したものではない。
