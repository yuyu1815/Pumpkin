# Minecraft Java 26.2 ブロック設置・破壊／物理／redstone・tick 監査（並列ロジック監査 5/8）

- 対象: Java Edition 26.2 / protocol `776` / world data version `4903`
- 監査範囲: `crates/pumpkin/src/world`、`crates/pumpkin/src/block`、`crates/pumpkin/src/block/entities`、Java play packet handler のブロック操作呼出し
- 対象経路: block breaking/placing、sequence ack、gamemode/reach/permission、neighbor updates、scheduled/random ticks、fluids、redstone/piston、block entity lifecycle
- 境界: inventory の数量計算・保存基盤そのものは別担当。ここでは設置・破壊 handler が inventory/item registry に渡す境界だけ確認した。
- 判定: **完全互換は未達。静的読解で、P1 3件、P2 2件の代表欠陥を確定/高確度で記録する。正式 Rust source は変更していない。**
- 所有書込み: 本ファイルのみ。
- 実行制約: `cargo`、`rustup`、server 起動、vanilla client、重い download は実施していない。

### BLK-01: Java block mutation の server-authoritative 検証不足（P1）

#### 対象シンボル／呼出し経路

- `crates/pumpkin/src/net/java/play/player_action.rs:185-237` `JavaClient::handle_player_action`
  - `Status::FinishedDigging` は `can_interact_with_block_at` の reach だけ確認して、`player.mining`、`mining_pos`、`start_mining_time`、経過 progress を確認しない。
  - コメントにも `:186` `// TODO: do validation` が残る。
  - `world.break_block(&location, Some(player), ...)` は `:208-216` で直接呼ばれる。
- 同ファイル `:73-75`
  - block break の入口で creative だけを特別扱いし、Adventure/Spectator または ability の `allow_modify_world` を一般 gate として確認しない。
- `crates/pumpkin/src/block/registry.rs:610-790` `BlockRegistry::place_block`
  - `:622` は Spectator/Adventure を拒否するが、`player.may_build()` (`crates/pumpkin/src/entity/player.rs:4085-4087`) を呼ばない。
  - 最終変更は `:790` `world.set_block_state(..., BlockFlags::NOTIFY_ALL)`。
- `crates/pumpkin/src/net/java/play/use_item_on.rs:256-274` `run_is_block_place`
  - `SUseItemOn` → `BlockRegistry::place_block` → block state変更 → caller が inventory/item境界で decrement/sync する経路を確認。
- sequence:
  - `player_action.rs:274-281` `JavaClient::update_sequence` は受信した最大 sequence を atomic に保持するだけ。
  - `crates/pumpkin/src/entity/player.rs:2484-2495` `Player::process_inbound_packets` の**次 tick 冒頭**で `swap(-1)` し、`CAcknowledgeBlockChange` を送る。

#### 入力／状態

1. Survival の client が `SPlayerAction(Status::FinishedDigging)` を、開始 packetなし、別位置で開始した後、または必要時間未経過で送る。
2. Adventure/Spectator 相当の player、または server-side abilities の `allow_modify_world=false` 状態が Java block handler に到達する。
3. 通常の `SUseItemOn` で block item を置く。place 側は gamemode の2値だけを拒否し、`may_build` を見ない。

#### 期待 vs 現状

- 期待:
  - reach に加えて、対象が現在の server-side mining target と一致し、経過 tick が `calc_block_breaking` の必要量を満たす場合だけ破壊する。
  - Adventure/Spectator および `allow_modify_world=false` は、break/place の双方で mutation 前に拒否する。
  - client の sequence ACK は prediction の同期用であり、権限・完了条件の検証とは独立する。
- 現状:
  - `FinishedDigging` は reach後に対象 stateを取得し、そのまま `break_block` を呼ぶ。`player.mining`/`mining_pos`/elapsed の条件はない。`continue_mining` (`crates/pumpkin/src/entity/player.rs:2868-2897`) にある progress 計算は通常 tick表示・Bedrock完了処理には使われるが、Java FinishedDigging の gate ではない。
  - break handler に `may_build`/Adventure/Spectator の明示拒否がない。通常 item の `ItemBehaviour::can_mine` デフォルトも `true` (`crates/pumpkin/src/item/mod.rs:64-66`) で、gamemode制御を代替しない。
  - place handler は Spectator/Adventureを拒否するが、server-side `Abilities.allow_modify_world` を確認せず、`may_build` を使う comparator等の個別 block use と mutation入口の挙動が分離している。
  - sequence は最大値を一つだけ保存し、次の `Player::process_inbound_packets` まで ACK しない。既存コメントは prediction順序のための意図的遅延と説明しており、ACK欠落を新規欠陥とは判定しない。ただし ACK があることは、上記 mutation 検証が行われた証拠ではない。

#### 影響／確度／出典

- 影響: P1。悪意ある Java peer が block hardness/progress を待たずに破壊でき、Adventure/Spectator または `may_build=false` の権限境界も block mutation handler で迂回し得る。drop/event/tool durability/advancement は破壊後に走るため、plugin eventを含めた server state の前提も崩れる。
- 確度: **高（制御フロー静的確定）**。実 client packet trace、server起動、実際の破壊再現は未実施。
- 26.2根拠: 既存 `docs/compatibility/26.2-progress.md` の protocol `776`、`docs/compatibility/26.2-gameplay-audit.md` の block break/place 未実client検証という限界を再利用。現行 `assets/packet/26_2_packets.json` に基づく generated handler の sequence fieldを前提にし、packet schemaを推測していない。

#### 再現／テスト案（未実行）

1. handler fixtureで `FinishedDigging` のみを solid block に渡す。期待: state unchanged、`BlockBreakEvent`/loot/`broken`未発火、sequence ACKのみ。
2. `StartedDigging` と `FinishedDigging` を別位置・0 tick経過・必要 tick未満で渡す。期待: `mining_pos`一致かつ必要 progress未達なら破壊しない。
3. Survival/Adventure/Spectator と `allow_modify_world=true/false` を分け、break/place各々で state、event、item decrement、ACKを比較する。
4. invalid actionでも、次 tickの `CAcknowledgeBlockChange` が prediction同期用に一回だけ送られ、権限判定とは独立していることを検査する。

#### 修正パス／依存

- `JavaClient::handle_player_action` に common `validate_block_break` を導入し、gamemode/`may_build`、target一致、経過progress、現在block state、reachを mutation 前に固定する。Javaの通常 clientが送る FinishedDigging順序だけを信頼しない。
- `BlockRegistry::place_block` の最初に `player.may_build()` を確認し、block-specific `normal_use` と placement mutationの境界を一貫させる。
- 依存: block placement item decrement/sync は inventory担当と調整するが、validator自体は `crates/pumpkin/src/net/java/play` と `crates/pumpkin/src/block/registry.rs` の範囲で閉じられる。実装時は protocol/generated packet を編集しない。

### BE-01: pending block entity NBT が削除されず、破壊・置換後に復活する（P1）

#### 対象シンボル／行

- `crates/pumpkin/src/world/mod.rs:6415-6448` `World::get_block_entity`
  - `:6425-6434` は `chunk.pending_block_entities.get(block_pos).cloned()`。
  - `:6444-6447` で live mapへ insertするが、pending mapから removeしていない。
- `crates/pumpkin/src/world/mod.rs:6564-6580` `World::remove_block_entity`
  - live `block_entities` mapからだけ removeする。`chunk.pending_block_entities`からの削除がない。
  - live entityが無かった場合は `removed=false` で、chunk dirtyも立たない。
- `crates/pumpkin/src/world/mod.rs:629-650` `World::save_block_entities`
  - live mapにある entityを pending mapへ書き戻すが、live mapに無い古い pending entryを掃除しない。
- `crates/pumpkin/src/world/mod.rs:5402-5410` `World::set_block_state`
  - block typeが変わる時、old block entityを `get_block_entity` で起こして `remove_block_entity` するため、この stale pending経路を踏む。
- `crates/pumpkin/src/block/registry.rs:1144-1173` `BlockRegistry::on_placed`
  - 新 block entity typeなら `get_block_entity(position).is_none()` の場合だけ create/addする。

#### 入力／状態

- region/chunkから chest等の block entity NBT が `pending_block_entities` に残っているが、live mapには未ロード。
- その位置の blockを破壊する、または別の block entity block（例: furnace）へ置換する。
- chunk unload/save後、同じ位置を再読込みする。

#### 期待 vs 現状

- 期待: block entityが破壊/置換された時、live object・pending NBT・custom dataが同一 transactionで消える。別 block typeを置いた時は、その typeの新規 BEだけが作られる。
- 現状:
  1. `set_block_state` が old BEを検出するため `get_block_entity` を呼ぶ。
  2. `get_block_entity` は pending NBTを cloneして liveへinsertするが、pendingは残す。
  3. `remove_block_entity` は liveだけ削除し、古い pending NBTを残す。
  4. 新 blockの `on_placed` が `get_block_entity` を再度呼ぶと、古い pending NBTから chest等を復元し、`is_none()` が falseになるため furnace等の新BE作成を抑止できる。
  5. live mapが空になる unloadでは `save_block_entities` が古い pendingを消さず、再load時に古いBEが復活する。
- これは inventoryの保存計算の問題ではなく、world block mutationとBE pending/live lifecycleの境界である。

#### 影響／確度／出典

- 影響: P1。破壊した containerが再起動/再chunk loadで復活する、または chestを壊して同位置へ furnace等を置いた際に block stateとBE typeが不一致になる。container内容の二重化・消失、comparator出力、redstone、screen handlerの誤動作につながる。
- 確度: **高（静的に clone/insert/remove の不整合が確定）**。実 Anvil unload/reloadは未実施。
- 出典: 既存 `docs/compatibility/audits/26.2-world-storage.md` は chunk persistenceを別担当として扱うが、今回の BE lifecycle は `crates/pumpkin/src/world` の gameplay-owned path。前段の `844e2871e` block entity resume修正済み範囲とも別で、今回の stale pending削除欠落を新規として扱う。

#### 再現／テスト案（未実行）

1. TempDir/fixture chunkの pending NBTへ chestを1件入れ、live mapを空にする。
2. chest stateを air、続けて furnaceへ変更し、`get_block_entity(pos)`の resource location、pending map、live mapを各段階で確認する。
3. chestを破壊→save_block_entities→chunk unload/reloadし、BEが再生成されないことを確認する。
4. live未ロード、liveロード済み、custom dataあり、block entity type変更の4ケースを分ける。

#### 修正パス／依存

- `remove_block_entity` が live mapと同時に chunk pending map、`custom_block_entity_data` を削除し、live未ロードでも stale entryを消して dirtyにする。
- `get_block_entity` を「起床時にpendingからremoveしてliveへ移す」契約へ揃える場合は、save/unload側の二重化を避けるため `save_block_entities` の snapshot/flushを同時に見直す。
- `set_block_state` の old/new block entity type変更を一つの lifecycle helperへ集約する。依存は world/block entityのみで、inventory内容のシリアライズ仕様変更は別担当。

### TICK-01: scheduled tick callback を全体順なしで並列実行する（P1）

#### 対象シンボル／行

- `crates/pumpkin/src/world/mod.rs:1925-2016` `World::tick_chunks`
  - `:1934` で `Level::get_tick_data` を取得。
  - scheduled block tick `:1942-1957`、fluid tick `:1964-1974`、random tick `:1982-2016` をそれぞれ `par_chunks(BATCH_SIZE)` で並列実行。
- `crates/pumpkin-world/src/level.rs:602-603` は block/fluid scheduled ticksを `sort_unstable()` する。
- `crates/pumpkin-world/src/tick/mod.rs:68-106` `OrderedTick` は priority/sub_tick_orderで順序を表す。
- `crates/pumpkin-world/src/tick/scheduler.rs:64-72` は schedule時に global `sub_tick_order`を保持する。

#### 入力／状態

- 同一 tickに隣接する repeater/comparator/observer/redstone wire/piston、または互いに同じ水・lava流路を更新する scheduled tickが複数ある。
- `get_tick_data`の並びは優先度・sub-tick順に整列済みでも、32件ごとの別batchが別 Rayon workerで同時に callbackを実行する。

#### 期待 vs 現状

- 期待: scheduled tickの priorityとsub-tick orderを保った server tick順で、前のcallbackの block state変更が後のcallbackの入力になる。
- 現状: sort後に `par_chunks`。batch内だけはloop順だが、batch間の実行順はworker scheduling依存。各 callbackは `World::set_block_state`、`update_neighbors`、次tick scheduleを行えるため、単なる読み取り並列ではない。
- 例:
  - repeater/observer/pistonが隣接して同一tickにstateを読むと、片方が変更前、片方が変更後を読む可能性がある。
  - fluid callbackが隣接位置を書き換える間に、別fluid callbackが旧stateを読む可能性がある。
  - redstone wireの `update_power_strength` は `NOTIFY_LISTENERS`でstateを変更し、その後neighbor callbackを明示的に走らせるため、callback順が出力波形へ影響する。

#### 影響／確度／出典

- 影響: P1。redstone回路、piston timing、fluid spreadがtickごとに非決定的になり、同じ入力で回路が異なる結果を出す。再現がCPU thread schedulingに依存し、保存/packet traceだけでは原因を追いにくい。
- 確度: **高（並列 callbackとmutating APIの組合せは静的確定）**。実際の複数worker raceは未実行。
- 26.2/既存解析: protocol/world versionは `docs/compatibility/26.2-progress.md` の既存値を使用。今回、公式JAR/world downloadはしていない。existing sourceの `OrderedTick` priority/sub-orderを新規推測せず、その保持がcallback executionで崩れる点だけを監査した。

#### 再現／テスト案（未実行）

1. 固定 seedの小さな world fixtureで、同じ tickに2つ以上の隣接 repeater/observer/pistonを scheduleする。
2. Rayon thread数を1と複数で変え、tickごとの block state、scheduled queue、neighbor event順、block event packetを比較する。
3. fluidでは水源・lava・障害物を隣接させ、各tickの state mapを順序ログ付きで比較する。
4. 合格条件は priority/sub_tick_orderを保った一つのlogical tick sequenceで、worker数に依存しないこと。

#### 修正パス／依存

- vanilla互換を優先する最小修正は、scheduled block/fluid tick callbackをpriority/sub_tick_order順に単一logical executorで処理すること。random tickは独立性を検証したうえで並列化を分離する。
- 並列化を残す場合は read-only phaseとmutation/event commit phaseを分け、neighbor update・schedule・state writeを順序付きcommit queueへ送る必要がある。
- 依存: `pumpkin-world`のscheduler API、`crates/pumpkin/src/world/mod.rs`のtick orchestration、各redstone/fluid callback。正式変更は別タスク。

### TICK-02: scheduled block/fluid tick が非 active loaded chunkでも進む（P2）

#### 対象シンボル／行

- `crates/pumpkin-world/src/level.rs:518-605` `Level::get_tick_data`
  - `:531-578` の random tick生成は引数 `active_chunks` を走査。
  - `:580-600` の scheduled tick処理は `self.chunks_with_scheduled_ticks.iter()` を全走査し、`active_chunks`とのintersectionを行わない。
- `crates/pumpkin-world/src/level.rs:940-990` `schedule_block_tick` / `schedule_fluid_tick`
  - loaded chunkなら activeかどうかに関係なく schedulerへ追加し、`:963`/`:990` で `chunks_with_scheduled_ticks`へ登録。
- `crates/pumpkin/src/world/mod.rs:1930-1934` は `active_chunks`をLevelへ渡すが、scheduled側の非active filteringはない。

#### 入力／状態

- playerのsimulation/ticking範囲外だが、view/load範囲内のchunkに repeater、observer、piston、water/lavaのscheduled tickが残る。
- chunkは `loaded_chunks` に存在し、`chunks_with_scheduled_ticks`にも登録されているが、`active_chunks`にはない。

#### 期待 vs 現状

- 期待: random tickだけでなく block/fluid scheduled tickも、serverの ticking/simulation対象 chunk policyに従う。非 active chunkは停止・延期し、active化時に残りdelayから再開する。
- 現状: `get_tick_data`が非activeでも `step_tick()`を呼び、そのtickを `World::tick_chunks`でcallback実行する。random tickとscheduled tickで対象範囲が異なる。
- 影響例: playerから遠い表示済み redstone が進み、water/lavaがsimulation distance外へ流れ、active化前に回路/地形が変わる。

#### 影響／確度／出典

- 影響: P2。simulation distance、chunk loader、redstone/fluidの時間経過がvanilla相当からずれ、遠隔装置の停止を前提にした設計と一致しない。
- 確度: **高（active引数をscheduled側で使わない分岐が静的確定）**。実際の view distance > simulation distance のserver runは未実施。
- 既知区分: 前段 gameplay/world docsは block placeや実worldを未検証と記録するが、この `active_chunks` と `chunks_with_scheduled_ticks` の不一致は本監査で初めて縦断確認した。

#### 再現／テスト案（未実行）

1. active chunk Aとloaded-only chunk Bをfixtureで作り、Bのrepeater/observer/fluidへdelay 1のtickを登録する。
2. `get_tick_data({A}, 3)`を呼び、Bのtickが取り出されない、または延期されることを期待値にする。
3. Bをactive化した後、元のremaining delayを保ったcallback実行とstate変化を検査する。

#### 修正パス／依存

- scheduled chunk collectionを`active_chunks.contains(pos)`で制限し、非active schedulerのoffset/delayを進めない。
- chunk unload・active化・save時のscheduler persistenceとsimulation-distance policyを同時に固定する必要がある。world storage担当のchunk tick NBT境界と依存する。

### PST-01: moving piston の pushed state が save/reload で失われる（P2）

#### 対象シンボル／行

- `crates/pumpkin/src/block/entities/piston.rs:15` `PistonBlockEntity::pushed_block_state`
- 同 `:202-247` `tick`/`finish`
  - animation完了時に `pushed_block_state`を最終block stateとして復元する。
- 同 `:256-275` `PistonBlockEntity::from_nbt`
  - `:261` `let pushed_block_state = Block::AIR.default_state;` 固定。
- 同 `:277-295` `write_nbt` / `chunk_data_nbt`
  - `:278`/`:287` に `// TODO: pushed_block_state`。stateをNBTへ保存していない。

  - moving piston BE生成時は、実際の `moved_state`/head stateを `pushed_block_state`へ渡しているため、通常のin-memory pathには情報がある。

#### 入力／状態

- pistonがblockを押している途中（`current_progress < 1.0`）にchunk save/unloadが発生する。
- chunk reloadでNBTから moving piston BEを復元する。

#### 期待 vs 現状

- 期待: moving pistonの facing、progress、extending/sourceに加えて、完了時に復元する pushed block stateを保持する。reload後も残りanimation完了で元のblockが現れる。

#### 影響／確度／出典

## 追跡確認した正常／部分正常経路

### Block placing

- `SUseItemOn` (`crates/pumpkin/src/net/java/play/use_item_on.rs:10-274`) は次の順で進む。
  1. `has_client_loaded`、reach、face、handを確認。
  2. spectatorはscreen handlerへのinteractだけを許す。
  3. block-specific `use_with_item` / `on_use`を先に呼ぶ。
  4. block itemなら `run_is_block_place`から `BlockRegistry::place_block`へ。
  5. place成功後、Java clientへ `CBlockUpdate`を送り、非creativeなら item decrement/syncをcaller側で行う。
- `BlockRegistry::place_block`には、replaceable/water source、world height、spawn protection、`can_place_at`、obstruction、`BlockCanBuildEvent`、`BlockPlaceEvent`、`set_block_state(NOTIFY_ALL)`、block entity item component適用がある。
- したがって placeの「全経路が未実装」という所見は採用しない。欠陥は `may_build` gateと、block handlerの最終validatorが別々である点に限定した。

### Block breaking

- `StartedDigging` (`player_action.rs:18-152`) はreach、BlockDamageEvent、item `can_mine`、creative即時破壊、または mining state/progress開始を処理する。
- `Player::tick` (`crates/pumpkin/src/entity/player.rs:2747-2788`) は server-side progressを更新し、Bedrockでは完了時に破壊する。
- Java `FinishedDigging`だけがこのprogress gateを再利用していないため、BLK-01を採用した。
- `World::break_block` (`crates/pumpkin/src/world/mod.rs:5512`) 自体は spawn protection、BlockBreakEvent、loot、waterlogged replacement、`set_block_state`、破壊粒子を持つ。world primitiveのdrop/event経路欠落とは判定していない。

### Sequence acknowledgement

- `SPlayerAction`/`SUseItemOn`/`SUseItem`受信時は handlerが `update_sequence`を呼ぶ。
- `packet_sequence`はmax sequence一つにcoalesceされ、Player tickの次回 inbound processing開始時に `CAcknowledgeBlockChange`へ変換される。
- 既存コメント（`player.rs:2487-2491`）は block update flush後にACKするための意図を示す。今回、sequence ACK自体の欠落は代表欠陥としない。
- 未確認: vanilla 26.2 clientが複数 sequenceを同一tickに送る実trace、invalid block prediction後の画面受理、ACK delayの実client体感。

### Reach / neighbor updates / physics

- reachは `Player::can_interact_with_block_at` (`crates/pumpkin/src/entity/player.rs:4072-4081`) のeye positionからblock AABBまでの距離で、creative `5.0`、その他 `4.5`にadditional `1.0`を加える。
- `World::set_block_state` (`crates/pumpkin/src/world/mod.rs:5365-5510`) は block entity replacement、on_placed/fluid、listener、`update_neighbors_at`、registry `prepare/update_neighbors`、POI、lightingを呼ぶ。
- `update_neighbors_at` (`world/mod.rs:6220-6269`) は6方向の BlockPhysics event、block/fluid neighbor callbackを行う。
- `BlockRegistry::update_neighbors` (`crates/pumpkin/src/block/registry.rs:1334-1340`) はneighbor shape replacementを行う。
- 代表的な「neighbor updateが全く呼ばれない」という欠陥は確定しなかった。ただしTICK-01のparallel scheduled callbackにより、redstone/fluid callbackの順序保証は別問題として残る。
