# 26.2 stateful Play -> Configuration -> Play TCP evidence

- Target: Java Edition `26.2`, protocol `776`, world data version `4903`
- Scope: one real in-process Pumpkin server, real Java TCP listener, real `World`, real `Player`/`JavaClient`, and two server-owned reconfiguration cycles on one connection.
- Status: **historical evidence from an earlier source revision; not a current-source gate result.** The current continuation reran the gate with strict collision/envelope diagnostics and did not obtain three consecutive passes. Vanilla client compatibility is not claimed.
- Production trigger: none. The only trigger is the existing public `JavaClient::start_reconfiguration()` call from the test.
- Production `crates/pumpkin/src/net/java/mod.rs`: not modified by this task.

### Real server and TCP setup

`java_reconfiguration_tcp.rs::java_reconfiguration_over_real_tcp_preserves_player_state`
creates an isolated `tempfile::TempDir` world and configures:

- Java bind: `127.0.0.1:0`; the test uses the actual OS-assigned loopback port from `TcpListener::local_addr()`.
- Bedrock, query, LAN broadcast, RCON, plugins, telemetry, online mode, and encryption: disabled.
- Java keep-alive interval: `1` second, only to bound the test's wait for the real Play keep-alive.
- World dimensions: overworld only.
- Server lifecycle: the test calls `stop_server()`, awaits the listener/task tracker, then calls the real `Server::shutdown()` API. No stdin command, RCON command, user command, or hidden production hook is used.
- Vanilla data: in-memory empty `VanillaData` lists; repository `data/`, `world/`, `.pi/`, logs, and user-owned files are not used or modified.

The Python dependency is explicit and local: `py -3` must be available, and the
subprocess path is the test-only
`crates/pumpkin/tests/protocol776_reconfiguration_client.py`. That adapter imports
and runs the existing `tools/compat-26_2/protocol776_harness.py`, which loads
`assets/packet/26_2_packets.json`; it does not implement a synthetic protocol
state machine or invent a Start Configuration packet.

### Normal connection and two cycles

The historical normal subprocess used username `compat_reconfig`, `--reconfiguration-cycles 2`,
and Known Packs case `exact`.

`java_reconfiguration_tcp.rs` waits for the server-owned `Arc<Player>` and for
real Play traffic to update `JavaClient::last_packet_time` while the outbound
queue drains. It then calls the same `JavaClient::start_reconfiguration()` twice,
with the following actual ordering:

1. first `start_reconfiguration()` returns `true`;
2. an immediate duplicate call returns `false`;
3. the client observes the real clientbound Play `start_configuration` packet and sends the empty Play `configuration_acknowledged` packet;
4. the existing Configuration path handles Known Packs, Registry Data, Update Tags, and Finish Configuration;
5. the client sends the empty Finish acknowledgment and observes a real Play keep-alive on the same TCP connection;
6. after that returned Play keep-alive, the same JavaClient is triggered for cycle two;
7. the same empty-ack / Known Packs / Registry Data / Update Tags / Finish / empty-Finish-ack / Play-keep-alive path completes again.

The parsed normal result asserted:

- `result = "stateful_reconfiguration_pass"`
- `cycles_completed = 2`
- `same_entity = true`
- `same_position = true`
- clientbound `start_configuration`: **2**
- serverbound empty `configuration_acknowledged`: **2**
- clientbound `finish_configuration`: **2**
- serverbound empty Finish acknowledgment: **2**
- duplicate Finish acknowledgment: **0**
- Join Game (`join_game` event): **1**, so no second initial Play join/spawn envelope was accepted.

The Rust-side assertions additionally compare, across both cycles:

- exact `Player::entity_id()`;
- exact server-side `Player::position()`;
- `Arc::ptr_eq` for the same `Arc<Player>` while it remains registered after cycle two;
- `Arc::ptr_eq` for the same `Arc<World>`;
- all 36 main inventory slots as `(item id, item count)` snapshots.

The pointer assertion is made before the harness closes its final socket. The
harness exits immediately after its final Play keep-alive, so normal disconnect
cleanup may remove the player from `Server::get_player_by_name()` before the
post-process assertions; that cleanup is not confused with a reconfiguration
rejoin.

### Mid-Configuration EOF negative

A second independent subprocess uses username `eof_reconfig` and
`--reconfiguration-case disconnect_during_config` with one cycle. After the
strict initial Play baseline, the test calls the same real
`JavaClient::start_reconfiguration()` once. The harness sends the empty Play
ack, then closes the same TCP socket during Configuration.

Assertions:

- harness exit code: `0`;
- result: `client_disconnected_during_configuration`;
- `server_disconnect = "client_eof"`;
- the retained JavaClient connection state is **not** `ConnectionState::Play`.

Thus the EOF path is not promoted to a successful reconfiguration return and
there is no observed invalid Play recovery after the mid-Configuration close.

### Queued Play packet handling (historical handoff note)

An earlier handoff used a test-only adapter that allowed all Play clientbound IDs
while reading Configuration and recorded collisions as opaque. That workaround
is no longer present in the current worktree: the adapter now uses the mapped
Configuration ID set only, so a Play/Configuration collision or unknown ID is a
hard failure. The readiness marker and queue-drain wait remain diagnostic
alignment aids; they do not prove the earlier `pending_bytes=24, closed=true`
observation's causal root.

## Validation Limits

- The client is a dependency-free synthetic protocol peer using the repository's existing harness; it is **not** the official vanilla Java 26.2 client.
- The test proves the real Pumpkin process-in-test accepted the bounded TCP exchange and preserved server-side player ownership/state. It does not prove vanilla client decode/acceptance.
- Registry Data, Update Tags, chunk section contents, NBT meaning, resource-pack download/application, online-mode authentication, encryption, gameplay compatibility, and official client rendering remain unverified.
- Inventory preservation is a server-side 36-main-slot snapshot; no inventory click/UI operation is part of this gate.
- Exactly-once Finish is observed as two clientbound Finish frames and two matching empty acknowledgments for two cycles, with no duplicate Finish event and no second Join Game. It does not replace the existing pure CAS/state tests.
- The test uses `Server::shutdown()` in-process and verifies its `Result` through the passing test; it is not a separate executable graceful-shutdown exit-code evidence run.
- The server bind port, temporary world path, generated server entity ID, and process thread IDs are intentionally nondeterministic. The final run did not retain a repository log or world artifact.
