# Minecraft Java 26.2 chat/auth の狭い実装計画

- 対象: Java Edition `26.2` / protocol `776` / world data version `4903`
- 出力所有: **本ファイルだけ**。正式 Rust code、config、inventory、既存 audit、fixture は変更していない。
- 目的: 前回の no output を繰り返さず、chat message の署名対象 bytes と最初の実装単位を固定する。全 chat/auth を一度に実装する計画ではない。
- 開始 HEAD: `1ac447f2918b7dec7d19a5836fa3673d4fe3c9f5`
- 判定: 現状は secure chat の署名長・時刻・session certificate・ack state の一部だけがあり、**message signature の暗号学的検証と正しい chain/link bytes は未実装**。signed command は署名 metadata を通常 command へ降格させる経路がある。

## Findings

### 1. 現在の到達経路と実欠落

#### 1.1 chat message

`crates/pumpkin/src/net/java/mod.rs::handle_play_packet` の `SChatMessage` 経路 (`:983-1007`) は packet をコピーして `JavaClient::handle_chat_message` へ送る。`crates/pumpkin/src/net/java/play/chat_message.rs` は次を行う。

- `handle_chat_message` (`:6`) は `/` で始まる本文を `validate_chat_message` より先に `handle_chat_command` へ分岐する。
- `validate_chat_message` (`:88`) は secure mode (`basic.allow_chat_reports=true`) で signature が存在し長さ `256`、timestamp、session expiry、message count、3-byte ack bitset、pending count `4096` 以下を確認する。
- `validate_chat_message` (`:174`) の checksum は `pumpkin_util::math::polynomial_rolling_hash(player.signature_cache.last_seen)` を比較するだけで、現在の packet の ack update から得た last-seen 集合を比較していない。
- `chat_session.public_key` に対する message signature の RSA verify call はない。`validate_chat_session` (`:243`) にある RSA 検証は、Mojang の public key で **session certificate** を検証する別処理である。
- 検証後の `World::broadcast_secure_player_chat` (`crates/pumpkin/src/world/mod.rs:1096-1147`) は `messages_sent` と `Uuid::nil()` を `SignedMessageLink` に使い、受信 packet の signature/body を broadcast する。これは受信 message の `session_id` と inbound chain index を署名対象へ戻す処理ではない。`messages_sent` は outbound broadcast count であり、受信 chain index の代替にしてはいけない。

従って、現状の secure path は「256 bytes らしい値を secure player chat として流す」可能性があり、署名の sender/session/index/content/timestamp/salt/last_seen binding を証明していない。既存 audit `docs/compatibility/audits/26.2-chat-permissions.md` の P1 所見を、26.2 公式 class の canonical bytes 確認で具体化した。

#### 1.2 signed command

`crates/pumpkin/src/net/java/mod.rs:961-979` は `SChatCommandSigned` を decode して `signed.command` だけを文字列化し、失敗時には通常 `SChatCommand::read` へ fallback する。timestamp、salt、argument signatures、ack/offset/checksum は `handle_chat_command` に渡らない。

`crates/pumpkin/src/net/java/play/chat_command.rs::handle_chat_command` は dispatcher の permission check は通るが、signed command の authenticity/chain/argument attribution は検証しない。したがって、これだけで一般 player の `/op` 権限が増えるとは断定しない一方、署名不正 packet が通常 command と同じ execution path へ降格するのは auth/reporting 欠落である。

`crates/pumpkin-protocol/src/java/server/play/chat_command_signed.rs::SChatCommandSigned` は wire fields を保持するが、現状の protocol count boundary test (`rejects_negative_signed_command_argument_count` 等) は cryptographic verification の証拠ではない。公式 26.2 `ArgumentSignatures` の上限は argument 数 `8`、名前長 `16`、各 signature `256` bytes である。現在の parser は remaining bytes に収まるかは見るが、公式の `8` 上限を同じ意味で固定していない。この parser hardening は第一タスクの範囲外に置く。

### 2. 26.2 の canonical signed-message bytes

公式 26.2 server JAR の inner artifact (`META-INF/versions/26.2/server-26.2.jar`) を実行せず、class bytecode/signature を静的解析した。対象 class は次の通り。

- `net.minecraft.network.chat.PlayerChatMessage`
- `net.minecraft.network.chat.SignedMessageLink`
- `net.minecraft.network.chat.SignedMessageBody`
- `net.minecraft.network.chat.LastSeenMessages`
- `net.minecraft.network.chat.SignedMessageChain`
- `net.minecraft.network.chat.RemoteChatSession`
- `net.minecraft.network.chat.LastSeenMessagesValidator`

公式 26.2 bytecode の `PlayerChatMessage.updateSignature` は次の順序で bytes を流す。

```text
int32_be(1)                                      // format/version marker
sender UUID: 16 bytes (most-significant, least-significant, big endian)
session UUID: 16 bytes (same UUID byte representation)
int32_be(link.index)
int64_be(salt)
int64_be(timeStamp.epochSecond)
int32_be(content UTF-8 byte length)
content UTF-8 bytes
int32_be(last_seen.entries.size)
for entry in last_seen.entries in order:
    entry.signature raw bytes (exactly 256 bytes)
```

重要な区別:

- packet の timestamp は `readInstant()`/wire long（現在の Pumpkin の `SChatMessage.timestamp: i64` は epoch milliseconds 相当）だが、署名対象は公式 class の `Instant.getEpochSecond()`。positive timestamp の実装では `timestamp / 1000` へ明示変換し、future/negative/overflow の policy は先に決める。millisecond bytes をそのまま署名してはいけない。
- content の長さは Java `String` 長や UTF-16 code unit 数ではなく、UTF-8 bytes の `int32_be`。
- last-seen は packet の raw 3-byte ack bitsetそのものではない。`LastSeenMessagesValidator.applyUpdate` で現在の tracked window に offset と bitset を適用し、acknowledged signature の順序付き集合を復元してから canonical body に入れる。
- signature は link の sender/session/index を含む。session UUID を `Uuid::nil()`、index を outbound `messages_sent`、または sender UUID だけで代用すると別 message の signature と一致しない。
- `SignedMessageBody` の順序は **salt → timestamp epoch seconds → UTF-8 length → content → last_seen count/signatures**。content-first、epoch milliseconds、VarInt length への置換は禁止。

公式 26.2 class の `LastSeenMessages.updateSignature` は `int32_be(count)` と各 256-byte signature を連結する。`SignedMessageLink.updateSignature` は sender UUID、session UUID、index の順で連結する。`PlayerChatMessage.updateSignature` は先頭 marker `int32_be(1)` を必ず含める。

### 3. session key / certificate / crypto の境界

`crates/pumpkin/src/net/java/play/chat_message.rs::validate_chat_session` の既存処理は、profile UUID、`expires_at.to_be_bytes()`、DER public key bytes を Mojang public key (`rsa::pkcs1v15`, `Sha1`) で verify する session certificate 検証である。これは維持する。

message signature は別の検証である。公式 26.2 `RemoteChatSession::createMessageDecoder` → `SignedMessageChain.decoder` → `PlayerChatMessage.verify` の構造は、session public key の signature validator で signed message を検証する。公式 `ProfilePublicKey.createSignatureValidator` の実装は `SHA256withRSA` である。したがって次の二つを混同しない。

| 対象 | 鍵 | 対象 bytes / algorithm | 現状 |
|---|---|---|---|
| session certificate | Mojang profile public key | profile UUID + expiry epoch-millis + encoded chat public key、RSA/SHA-1 検証経路 | `validate_chat_session` に存在 |
| chat message | 現在の player chat session public key | 上記 canonical link + body、RSA/SHA-256 (`SHA256withRSA`) | **未実装** |

既存 deps は最小実装に足りる。`crates/pumpkin/Cargo.toml` は `rsa.workspace`, `sha1.workspace`, `sha2.workspace`, `uuid.workspace` を既に持ち、`crates/pumpkin/src/net/java/play/mod.rs` は `rsa::pkcs1v15::{..., VerifyingKey}`、`rsa::signature::Verifier`、`sha1::Sha1` を使用している。追加 crypto crate を導入する計画にはしない。chat public key の DER/SPKI decode は既存 rsa の `pkcs8`/encoding API で実際の型を確認してから行う。

### 4. chain / timestamp / salt / ack / checksum

公式 26.2 `SignedMessageChain` は次の順序を取る。

1. player UUID と current session UUID で root link `(index=0)` を作る。
2. signature verify 前は link index/timestamp state を進めない。
3. timestamp が前回より古い (`isBefore`) 場合は `OUT_OF_ORDER_CHAT` とし chain を broken にする。equal timestamp はこの比較だけでは拒否しない。
4. signature verify が失敗した場合も chain を broken にする。
5. verify 成功後だけ timestamp と link を advance する。

現在の `ChatSession` (`crates/pumpkin/src/entity/player.rs:7213-7250`) は session UUID、expiry、public key、certificate signature、outbound `messages_sent/messages_received` を持つが、inbound signed chain の `next index` と `last timestamp` を持たない。`MessageCache`/`LastSeenMessagesValidator` (`:7310-7510`) は ack window を持つが、message signature verify と chain link を結び付けていない。

公式 26.2 `LastSeenMessages.Update` は wire で `VarInt offset + fixed 20-bit ack + byte checksum`。`Update.verifyChecksum` は checksum が `0` のとき bypass、非 zero のとき `applyUpdate` で得た acknowledged signatures の `LastSeenMessages.computeChecksum()` と比較する。各 `MessageSignature.checksum()` は Java `Arrays.hashCode(byte[256])` 相当で、list は rolling `31 * value + entryChecksum`、結果 byte が `0` なら `1` になる。

これは現 Pumpkin の `polynomial_rolling_hash(player.signature_cache.last_seen)` と異なる。`last_seen` の所有者・時点も current packet の acknowledged update と一致しない。さらに `pumpkin-util::math::java_array_hash` は Rust の `u8` を正値として加算しているが、Java `byte` の `Arrays.hashCode(byte[])` は signed byte の符号拡張を行うため、high-bit を含む signature では hash も一致しない可能性がある。checksum は signature verification の前段で純粋に復元し、成功時にだけ state commitする必要がある。現コードの ack validator は reject packet でも state を先に mutate し得るので、実装時は transaction/clone/rollback のいずれかを選ぶ。

### 5. offline unsigned が合法な条件

- `basic.allow_chat_reports=false` の場合、現在の `handle_chat_message` は secure validation を要求せず、`PlayerChatMessage::system` / disguised/system chat へ送る。この「unsigned chat を secure attribution として扱わない」経路は意図的な設定境界であり、P1 message-signature defect の反証にはしない。
- `online_mode=false` は username/profile を暗号学的に証明しない。`encryption=false` の offline 構成で unsigned chat/command を許可すること自体は設定上の合法な限界だが、username impersonation や op/ban identity の保証にはならない。
- `online_mode=true` かつ `allow_chat_reports=true` では、valid session certificate、未 expiry の session key、valid signed message、ack/chain policy が揃わない message を secure broadcast してはいけない。
- `allow_chat_reports=false` でも signed packet が到着することはあり得るが、signedness を権限昇格や secure report の証拠へ変換しない。通常 command の permission dispatcher は独立した authorization gate として残す。

### 6. 第一実装タスクの境界（70 turns 以内を想定）

第一タスクは **chat message の canonical body construction + known-answer verification helper/test だけ**に限定する。

含めるもの:

1. `SChatMessage` の message、wire timestamp、salt、復元済み last-seen signature、`SignedMessageLink` を受けて canonical bytes/stream を構築する pure helper。
2. `RsaPublicKey`/DER public key と 256-byte signature に対する RSA PKCS#1 v1.5 + SHA-256 verify の pure helper。
3. 正規署名 fixture `valid` と、同じ signature bytes を使った改竄 fixture `content_changed`、`salt_changed`、`timestamp_changed`、`session_changed`、`index_changed`、`last_seen_changed`、`wrong_key`、`zero_signature`。
4. helper の known-answer test。署名 verify の前に canonical bytes の exact equality/hash を検査し、crypto API の使い方だけで pass しないようにする。
5. この task では handler、world broadcast、session state、signed command、offline policy、permission dispatcher、packet decoder を変更しない。正式 code はこの調査回では read-only のままにする。

含めないもの:

- signed command の argument signature verification
- `LastSeenMessagesValidator` の state ownership/replay redesign
- `SChatCommandSigned` の通常 command への fallback 除去
- `/` chat shortcut の routing変更
- session certificate refresh、Mojang key fetch、proxy、RCON、permission tree
- vanilla client/server 実往復

| session | `00000000-0000-0000-0000-000000000002` |
| link index | `0` |

| wire timestamp | `1700000000000` ms; canonical `epochSecond=1700000000` (`0x6553f100`) |

| canonical byte length | `66` |
| canonical hex | `000000010000000000000000000000000000000100000000000000000000000000000002000000000102030405060708000000006553f10000000002686900000000` |

### 独立した正規署名 / 改竄 negative fixture の作り方

自己実装が自分の bytes を自分の signer で肯定するだけにならないよう、次の二層に分ける。

1. **外部 oracle 生成**: 固定 2048-bit RSA key pair を repository 外で一度だけ生成し、固定 private key で canonical bytes file を `openssl dgst -sha256 -sign key.pem -out valid.sig canonical.bin` する。signature は `256` bytes、public key は DER/SPKI として test input にする。private key は repository に保存しない。
2. **Rust known-answer**: public key、canonical bytes、固定 `valid.sig` を test fixture として読み、`valid` が `true` になることを確認する。test 実行時に private key、OpenSSL、ネットワーク、Mojang auth を要求しない。外部 oracle が作った signature bytes を固定し、実装側で再署名しない。
3. **negative は独立変異**: 同じ valid signatureに対して canonical bytes の一 byteだけ（content、salt、timestamp、sender/session UUID、index、last_seen signature）を変更し、全て reject。signature byte一 byte変更、別 public key、全 zero 256-byte signature、length `255/257` も reject。negative fixtureは「invalid signatureを別のRust signerで作る」のではなく、正規 bytes/signatureの一方を変える。
4. **chain state の後続 test**: invalid signature、out-of-order timestamp、expired key の後に index/timestamp/ack state が進まないこと、valid の後だけ indexが `+1` になることを別 test にする。第一 taskでは helper testまでに止める。
