# 26.2 CFG-T3 stateful TCP reconfiguration test-hook plan

- Target: Java Edition `26.2` / protocol `776` / world data version `4903`
- Scope: test-only orchestration and a dependency-free TCP harness for
  Play -> Configuration -> Play. This document does not add a user command,
  production caller, or Rust source change.
- Owned write paths for this task: `tools/compat-26_2/` and this document.
  `tools/compat-26_2/chat-fixtures/` is read-only for this task.
- Status: **harness preparation complete; server-triggered TCP evidence is not
  claimed because no production caller or test trigger has been run.**

## Findings

### Current Rust contract and the missing trigger

The existing source already contains the narrow sender and state guards:

- `crates/pumpkin/src/net/java/mod.rs::JavaClient::start_reconfiguration`
  checks configuration-state support and coarse `Play`, atomically claims
  `ConfigurationPhase::Play -> ReconfigurationAwaitingAck`, and sends the
  empty clientbound Play `start_configuration` packet.
- `crates/pumpkin/src/net/java/play/configuration_acknowledged.rs::JavaClient::handle_configuration_acknowledged`
  accepts only the claimed phase, checks the empty body in the reader path, and
  changes the coarse state to Configuration.
- `crates/pumpkin/src/net/java/mod.rs::JavaClient::handle_configuration_packet`
  owns the state-aware Configuration dispatcher and routes Known Packs,
  keep-alive, ping, and other existing Configuration handlers.
- `crates/pumpkin/src/net/java/config/known_packs.rs::JavaClient::handle_known_packs`
  sends Registry Data, Update Tags, and Finish Configuration through the shared
  serializer path.
- `crates/pumpkin/src/net/java/config/config_acknowledged.rs::JavaClient::handle_reconfiguration_finish`
  claims `AwaitingFinishAck -> Play` exactly once and does not return
  `PacketHandlerResult::ReadyToPlay`.

A repository search found no production call site for
`start_reconfiguration`. The sender is therefore not runtime-reachable from a
normal server run. The Python harness must wait for the real packet and must
not synthesize that packet or report success when the packet is absent.

### Existing server-owned test access

No `crates/pumpkin/tests/` socket integration test directory currently exists.
The existing TCP-capable server infrastructure is nevertheless sufficient for a
small test fixture:

- `crates/pumpkin/src/lib.rs::PumpkinServer::new` creates the real server and
  Java listener; `PumpkinServer::unified_listener_task` is the existing accept
  loop entry.
- `crates/pumpkin/src/server/mod.rs::Server::get_all_players` exposes the
  server-owned player list.
- `crates/pumpkin/src/net/mod.rs::ClientPlatform::java` exposes the existing
  Java client reference from a server-owned `Player`.
- `JavaClient::start_reconfiguration` is already `pub async`; the test can call
  it after finding the connected test player. No public command, console input,
  RCON action, or plugin command is needed.
- `crates/pumpkin/Cargo.toml` already has the required Tokio networking/runtime
  features, `pumpkin-protocol` as a normal dependency, and `tempfile` as a
  dev-dependency. No new dependency is required for the proposed test seam.

The preferred minimal Rust patch is therefore a test-only integration fixture,
not a production trigger:

```text
crates/pumpkin/tests/java_reconfiguration_tcp.rs
```

The fixture should start an isolated loopback server, connect one protocol-776
synthetic client, wait until the player is present, and invoke
`player.client.java().expect("Java player").start_reconfiguration().await`.
After the first cycle's Play keep-alive it invokes the same existing method a
second time. The fixture must retain the same `Arc<Player>` and assert that the
server did not call `Server::add_player` or `World::spawn_java_player` again.
If the current global server/ticker lifecycle makes an external integration
fixture unsafe, the equivalent test module may live beside
`PumpkinServer::unified_listener_task`; that is a fixture-placement decision,
not a reason to add a user-visible command.

### Stateful harness behavior prepared

`tools/compat-26_2/protocol776_harness.py` now has an opt-in
`--mode reconfiguration` path. It performs the following on one TCP connection:

1. Performs the ordinary Login prefix and initial Configuration using the
   existing Login/Configuration packet maps and codecs.
2. Establishes a strict initial Play baseline: Login/Join Game envelope,
   entity ID, Player Position, teleport confirmation, first chunk envelope, and
   one Play keep-alive echo.
3. Waits for an actual clientbound Play `start_configuration` frame. It does
   not send or invent a trigger. If no server-owned Rust seam sends that frame,
   the socket read times out and the run fails.
4. Checks the empty Play `configuration_acknowledged` response, then answers
   Configuration Known Packs, Configuration keep-alive/ping, and Finish using
   the existing bounded codecs.
5. After the empty Finish acknowledgment, requires another Play keep-alive on
   the same connection. A second Join Game is rejected. Any later Player
   Position is compared to the initial position.
6. Repeats the wait/respond/Finish/Play-keep-alive sequence for two cycles by
   default (`--reconfiguration-cycles 2`). The harness returns
   `same_entity=true`, `same_position=true`, and
   `cycles_completed=2` only after both real trigger packets and both return
   paths are observed.

Example command for the later, explicitly triggered gate:

```text
py tools/compat-26_2/protocol776_harness.py \
  --mode reconfiguration \
  --host 127.0.0.1 --port <isolated-port> --timeout 60 \
  --username compat_reconfig \
  --reconfiguration-cycles 2 \
  --known-packs-case exact
```

`--known-packs-case` remains a wire fixture only. `empty`, `legal_subset`, and
`unknown` are fallback-selection observations; `exact` is the ordered exact
selection. Registry payloads remain opaque and are not promoted to semantic
compatibility evidence.

### Packet mapping and bounds

Initial login and each later state use separate packet-ID dictionaries. Runtime
mapping is loaded from the existing
`assets/packet/26_2_packets.json`; `verify_critical_mapping` now additionally
checks:

- Play clientbound `start_configuration = 118`;
- Play serverbound `configuration_acknowledged = 16`;
- existing Configuration IDs for Known Packs, Finish, keep-alive, and ping.

The harness retains the existing safety limits without widening them:

- frame length: `MAX_PACKET_SIZE = 2,097,152` bytes;
- decompressed/data length: `MAX_PACKET_DATA_SIZE = 8,388,608` bytes;
- VarInt: at most `5` bytes;
- strings: at most `32,767` UTF-8 bytes;
- Known Packs count: `0..64`;
- NBT envelope skip depth and array bounds remain bounded;
- socket reads retain the caller-provided per-read timeout.

### Negative probes

The opt-in reconfiguration mode prepares these cases. They must be run on
independent connections and must not be combined with a normal two-cycle pass:

| Case | Injection point | Expected classification |
|---|---|---|
| `unsolicited_ack` | Play baseline, before any Start Configuration | Play disconnect; no Configuration transition |
| `duplicate_ack` | Immediately after the first valid Play acknowledgment | Configuration disconnect; no second ack admission |
| `trailing_ack` | First Play acknowledgment carries one extra byte | Play disconnect; empty-body guard rejects it |
| `early_finish` | After reconfiguration Known Packs request, before server Finish | Configuration disconnect; Finish phase is not claimed |
| `duplicate_finish` | Send Finish acknowledgment twice after one server Finish | Negative no-second-transition probe; no second Join Game/ReadyToPlay is accepted |
| `disconnect_during_config` | Close the same socket after Start/ack while in Configuration | Client EOF; no return-to-Play claim |

`duplicate_finish` is deliberately classified as a no-second-transition
observation rather than an assumed disconnect: once the first Finish
acknowledgment atomically returns the connection to Play, a second wire packet
is no longer a Configuration packet. The Rust pure state test must still prove
that `claim_finish` is exactly once, and the TCP result must not be called a
server rejection unless a real disconnect is observed.

The existing `config-regression` mode remains separate for initial-configuration
negative cases (`early_finish_ack` and `duplicate_known_packs`). It must not be
used as evidence for stateful Play reconfiguration.

### Evidence separation

The existing `docs/compatibility/26.2-reconfiguration.md` records source-level
state/codec tests and an initial-login loopback only. The older
`26.2-postcommit-loopback.md` uses a prior binary and initial Configuration
negative cases. Neither is stateful Play reconfiguration evidence. A future
normal result is valid only if it includes the actual Start Configuration frame,
empty ack, Configuration response order, Finish ack, same-connection Play
keep-alive, and the explicit Rust trigger/source binary identity.

## Recommended Next Steps

1. Add the test-only Rust fixture at the owner candidate above, or place the
   equivalent fixture beside the public `PumpkinServer` lifecycle if global
   shutdown state requires unit-test visibility. Keep the existing
   `start_reconfiguration` method as the only sender.

   initial strict Play baseline; trigger once after each returned Play
   keep-alive, for exactly two cycles.
3. Run the pure Rust state gate first, then the focused real TCP gate. Record
   packet IDs, per-state codec, frame/payload lengths, timeouts, entity ID,
   position, disconnect reason, server process exit code, and port cleanup.
4. Run the Python negative cases on fresh connections. Treat
   `duplicate_finish` as no-second-transition unless a real disconnect is
   observed, and treat client EOF during Configuration as a negative lifecycle
   observation rather than a success.
5. Do not promote a timeout, synthetic Start packet, initial-login loopback,
   pure helper test, or opaque Registry/Chunk payload observation to server
   reconfiguration success or vanilla-client compatibility.
