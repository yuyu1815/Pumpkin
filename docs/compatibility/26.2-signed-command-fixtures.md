# 26.2 signed-command 独立 known-answer fixture

## Findings

### 成果

`signed-command-independent.json` を追加した。正式 Rust code、protocol code、server/client
起動、stage、commit は変更していない。fixture は次を固定する。

- N=1: plain、quoted、greedy、Unicode の parser raw substring。
- N=2: quoted argument と greedy argument。packet entry order は `first`, `rest`、
  chain link index は `41`, `42`。
- 各 argument の raw UTF-8 hex、canonical bytes、canonical byte length、SHA-256、
  256-byte RSA/SHA-256 signature。
- test-only 2048-bit RSA public SPKI DER。private key は repository に保存していない。
- payload tamper、N=2 argument reorder、index mismatch、wrong public key の reject 期待。
- invalid ACK は signature fixture に混ぜず、既存 `last-seen-ack.json` の別 contract として
  参照する。

fixture の JSON 自体の SHA-256 は次である。

```text
d3c1708fbdd7cda82bb24cf50f1913cffc8bd7922053c8e9c71d12e9c32170bd
```

public DER は 294 bytes、DER SHA-256 は次である。

```text
73a95f05ef53be8cf5d0d150dc33d59036bfad3d7890a4f9075a545a8d05f19e
```

### Canonical body の確認結果

既存の official 26.2 `javap` artifacts と既存 compatibility docs を照合した。body は
次の順序である。

```text
int32_be(1)                         // PlayerChatMessage marker
sender UUID: 16 bytes
session UUID: 16 bytes
int32_be(link.index)
int64_be(salt)
int64_be(timestamp.epochSecond)
int32_be(raw argument UTF-8 byte length)
raw argument UTF-8 bytes
int32_be(last_seen count)
last_seen signatures: 256 bytes each, ordered
```

`PlayerChatMessage.updateSignature` は marker → `SignedMessageLink` →
`SignedMessageBody` を流す。したがって command 全文、argument name、typed value の再
シリアライズ、epoch milliseconds、raw 3-byte ACK bitsetは署名対象にしていない。

`ArgumentSignatures` は既存 artifact で次を確認できる。

- count decode 上限 `8`。
- entry name は `readUtf(16)` / `writeUtf(..., 16)`。
- entry は name と 256-byte `MessageSignature`。
- `signCommand` は `SignableCommand.Argument.value()` を signer に渡し、entry には
  `Argument.name()` を別フィールドとして保存する。
- `SignableCommand` は `SignedArgument` marker の argument だけを対象にし、
  `ParsedArgument` の original `StringRange` から raw substring を得る。
- list order は parsed argument list order。N=2 fixture の verification order は packet
  entry order とし、reorder では link index binding が崩れて reject する期待を記録した。

これは official 26.2 server JAR の static bytecode 照合結果であり、**vanilla runtime
capture ではない**。

## Migration / Investigation Notes

### Provenance and independence

- official 26.2 outer JAR: `60,894,273` bytes、SHA-1
  `823e2250d24b3ddac457a60c92a6a941943fcd6a`。
- official inner JAR: `24,952,681` bytes、SHA-1
  `86765a5899bd9c96461036a628796b4245715058`。
- canonical field order と `ArgumentSignatures`/`SignableCommand` の規則は、これらの
  JAR を実行せず既存 `javap` outputから確認した。
- public key/signature は OpenSSL 3.2.2 による固定 test-only key の独立生成物。
  Mojang public key、session private key、実ユーザー token、本番 key、vanilla packet
  captureではない。
- Rust implementationは canonical bytesやsignature expected値の生成に使っていない。
  private keyは生成作業後に削除し、repositoryにはpublic DER/signatureだけを保存した。
- `vanilla runtime capture: false`。この fixture は official layout の静的根拠と、独立
  RSA known-answer を結び付けるもので、vanilla server/client acceptance の証明ではない。

### Negative contract

| case | mutation | expected |
|---|---|---|
| payload tamper | raw UTF-8/content byteだけを変更し signatureを再利用 | reject / `signature_mismatch` |
| argument reorder | N=2 entryを `rest, first` に並べ替え、signatureを再利用 | reject / `signature_mismatch_after_entry_reorder` |
| index mismatch | valid signatureの body link indexを変更 | reject / `signature_mismatch` |
| key mismatch | canonical bytes/signatureを別RSA public keyで検証 | reject / `invalid_signature_key` |
| invalid ACK | offset/bit/checksumを変える | signature fixtureでは扱わず、`last-seen-ack.json` の reject contract |

positive は全6 argument bodyについて canonical length/hashを先に照合し、その後に
RSA-PKCS#1 v1.5/SHA-256を検証する。署名をRust内で再生成するテストではない。

### 利用手順

1. JSON の `crypto.public_key_der_hex` を DER bytes に戻す。
2. 各 `arguments[*].canonical_hex` を bytes に戻し、`canonical_length` と
   `canonical_sha256` を検査する。
3. 各 `arguments[*].signature_hex`（必ず256 bytes）を同じ public DERで
   `openssl dgst -sha256 -verify` 相当の verifierに渡す。
4. parser integrationでは `raw_value_text` を typed resultから再生成せず、同じ
   `raw_value_utf8_hex` と `entry_order`/link indexを使う。
5. ACKのpreview/commitは `last-seen-ack.json` を別に実行し、invalid ACKをsignature
   positive/negativeの代替にしない。

新しい framework、依存追加、Rust test code、private keyの再配布は不要である。

## Recommended Next Steps

1. 次の Rust担当はJSONを読み込むframeworkを増やさず、既存 signature verifierにこの
   fixtureの固定値を接続する。canonical hash一致をRSA verifyより先に確認する。
2. N=2では packet entry order、name-to-parser mapping、chain index `i..i+N-1` を別々に
   assertionし、reorder/index mismatchで execute/state commitしないことを固定する。
3. ACK preview/checksum/atomic rollbackは `last-seen-ack.json` の別テストとして実装し、
   signature fixtureのpositiveをinvalid ACKの代用にしない。
4. vanilla runtime round-trip未確認のため、正式実装の受入根拠をこのfixtureだけで
   「vanilla runtime capture」と表現しない。

## Rust state-path connection

`crates/pumpkin/src/net/chat/state.rs::signed_command_fixture_exercises_n2_atomicity_and_no_signable_ack`
reads the public DER, N=2 raw values, and fixed signatures from this file and calls
`verify_signed_command_and_commit`. It asserts valid chain links `41` and `42`, atomic
rollback/chain break on an invalid second signature, and a zero-entry ACK-only transaction.
The fixture remains test-only independent crypto evidence; this test does not prove vanilla
runtime acceptance.
