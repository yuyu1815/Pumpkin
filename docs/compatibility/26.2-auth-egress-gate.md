## Egress result details

The egress suite used production `PendingConnection` and loopback `TcpListener` /
`TcpStream` fixtures for normal flush, kick/disconnect, writer framing, peer write, and
peer flush paths. No external network was contacted.

Passing cases confirmed:

- successful writer flush is the only completion `Ok(())` path that passed;
- deferred close/cancel, closed receiver, frame error, and write error notify `Err(())`; the separate forced-flush-failure test unexpectedly observed `Ok(())` and is listed below;
- pending/reserved bytes return to `0` in the passing cases;
- repeated close does not leak accounting;
- the start-reconfiguration sender-close path was executed once.

Two existing egress tests remain review findings and are not hidden by this gate:

- `start_reconfiguration_sender_close_is_failure_and_releases_bytes` failed its
  `is_closed()` assertion (the fixture uses protocol `1`, so the configuration-state
  precondition returns before the sender-close branch).
- `closed_peer_flush_failure_releases_bytes_and_unblocks_waiter` received `Ok(())`
  rather than `Err(())`; a TCP peer shutdown did not force a flush failure on that run.

These are outside the owned type/import/compile correction and are returned to the
read-only review owner. No blanket assumption was made that reject paths must leave the
chain unchanged: the existing auth implementation's replay/old-timestamp/signature
reject paths may mark the chain broken as required by the contract.

## Auth coverage and limits

The unit/handler-adjacent runs exercised canonical RSA verification, parser argument-set
validation, empty signable-argument seam, ACK preview preservation, lifecycle/session
ownership, replay/old-timestamp checks, and protocol signed-command decoding. The current
suite does not provide a complete production-handler assertion for: N=2 successful
execution followed by a second-entry invalid signature with execution/ACK/state atomicity,
no-signable command ACK transaction, or offline unsigned execution policy. Those remain
review/implementation coverage gaps rather than compatibility claims.

No vanilla client/server runtime or external TCP compatibility round-trip was run. The
network evidence above is loopback-only test transport. No files were staged or committed.

## Final gate rerun

- `net::java::egress_accounting_tests`: **9 passed, 0 failed**. The suite covers normal TCP
  flush `Ok(())`, Drop/cancel/sender-close/frame/write errors `Err(())`, repeated close
  accounting, corrected start-configuration sender-close setup, and the real `try_kick`
  disconnect frame. A peer shutdown is not treated as a deterministic flush failure because
  the TCP stack may still flush successfully.
- `net::chat::state`: **15 passed**, including the independent fixture state-path test.
  N=2 atomicity, invalid second signature, and zero-entry ACK-only behavior are asserted
  through `verify_signed_command_and_commit`, not just RSA KAT.
- Security gate: **pass for the reviewed root-cause fixes; compatibility remains conditional**.
  Official ACK-first side effects, duplicate-entry runtime behavior, reports-disabled signed
  no-session behavior, and vanilla client/server round-trip remain unconfirmed and explicitly
  incomplete. Safe rejection is not called compatibility complete.
