# 26.2 attack/interact item guards

## Findings

対象は Java Edition 26.2 / protocol `776` / world data version `4903` の
`ServerGamePacketListenerImpl.handleAttack` と `handleInteract` である。公式一次資料は
既存の `C:/Temp/server-26.2.jar` と、そこから保存済みの `javap -c -p` 結果を
read-only で照合した。JARをリポジトリへコピーせず、ネットワーク取得も行っていない。

### 公式 item/feature semantics

- `handleAttack` は target の world border、AABB reach、self / ItemEntity /
  ExperienceOrb / attackable でない arrow の検査後、`ItemStack.isItemEnabled(level.enabledFeatures())`、
  `ServerPlayer.cannotAttackWithItem(mainHand, 5)`、`PIERCING_WEAPON` の順に検査し、最後にだけ
  `Player.attack(target)` を呼ぶ。
- `handleInteract` は target の world border と AABB reach の後、packet の hand の
  `ItemStack.isItemEnabled(level.enabledFeatures())` を検査し、最後に `interactOn` へ進む。
- `cannotAttackWithItem(item, 5)` は `MINIMUM_ATTACK_CHARGE` が正の場合、
  `(attackStrengthTicker + 5) / currentItemAttackStrengthDelay >= minimumCharge` を要求する。
  通常の attack 拒否では item、attack ticker、Used statistic、event、damage を変更しない。
- `PIERCING_WEAPON` の通常 `handleAttack` 拒否は正しい。これは全 item を拒否する処理ではなく、
  専用の `ServerboundPlayerActionPacket` 経路が `PiercingWeapon.attack` を所有するためである。
  したがって通常 attack を `Player.attack` に通してはならないが、entity interact 全体から
  PiercingWeapon を拒否してはいけない。
- attack range は item `AttackRange` の min/max/margin を使い、外側境界は inclusive。
  component がない場合は `ENTITY_INTERACTION_RANGE` が default range になる。entity interact は
  `entityInteractionRange + 3.0` の strict `<`。block range は混ぜない。
- packet handler 自体に block line-of-sight raycast はない。壁越しを距離内で拒否しないことは
  vanilla handler 相当であり、LOS policy は別のサーバー policy として扱う。

### 現行 Pumpkin model

- `ItemStack::get_data_component` は item定義とstack patchをread-onlyに検索でき、
  `AttackRangeImpl`、`PiercingWeaponImpl`、`MinimumAttackChargeImpl`、
  `AttributeModifiersImpl` が既に存在する。
- `Server::get_enabled_features` / `is_feature_enabled` は存在し、通常の feature 名は
  `minecraft:vanilla` と datapack由来の experimental flags に分離されている。
- しかし `pumpkin_data::item::Item` / generated item modelには、vanillaの各 item が要求する
  `FeatureFlagSet` を保持する `required_features` 相当がない。現生成 item は componentを持つが、
  componentの存在から experimental gatingを推測してはいけない。
- `World::get_entity_by_id` は現ツリーで Ender Dragon 本体の `parts` を id 走査して
  `EnderDragonPart` を返す。partは `can_hit() == true` で damageを本体へ委譲する。
  したがって `world/mod.rs` や dragon entity の変更はこの task の範囲に不要である。

## Migration / Investigation Notes

### 今回解消したもの

1. `can_attack_with_item` を `handle_attack` の `Player::attack` 前に追加した。
   `SInteract` の旧 attack action にも同じ guardを適用した。
2. `MinimumAttackChargeImpl` と既存 `Player::last_attacked_ticks`、既存 itemの
   `AttributeModifiersImpl` を再利用した。itemの patch、count、durability、componentを変更しない。
3. `PiercingWeaponImpl` の通常 attack拒否は公式根拠ありとして維持した。ただし interact actionでは
   blanket拒否していない。
4. interact の main/off handをpacketから検証し、選択された handの itemだけを event/use/mutationへ渡す。
   これにより無関係な main-hand itemを読む副作用を除いた。
5. target authority guardは event、damage、item mutationより前にある。self attackは両経路で
   event前に invalid entityとして処理する。world border、reach、removed、dead living、same-world、
   spectator attacker、dragon part lookupの現行経路を維持した。
6. 非有限 range、および square overflowを拒否する pure guardを追加した。

### 未解消のmust-fix / 正確な最小モデル変更パス

**item feature enabled は未解消である。** 現在の `Item` に required feature setがないため、
この taskで `minecraft:bundle` 等を item名から推測して拒否するのは独自推測であり、vanilla標準 itemを
誤拒否する。最小の正しい後続変更は次の通り。

1. generated `Item` に `required_features: &'static [&'static str]`（または interned feature-set）を追加。
2. item data/codegen入力から、vanilla `minecraft:vanilla` と experimental datapack featureの
   required setを保持する。component presenceやitem名から再構成しない。
3. `ItemStack::is_item_enabled(enabled_features)` を `Item` の required setに対して追加し、
   stack patchで required featureを上書きできないよう read-onlyにする。
4. handlerは公式順序で、attackなら target invalid checks → range → item enabled →
   cannotAttackWithItem → PiercingWeapon → event/damage、interactなら target checks → range →
   selected-hand item enabled → event/item interaction とする。
5. `minecraft:vanilla` は全標準 itemが有効な通常 feature、bundle/trade/minecart/redstone 等は
   experimental gatingとして別々に testする。experimental全体を一括拒否しない。

このモデル変更は指定された今回の所有範囲（attack.rs、interact.rs、mod.rsの既存export、compat doc）外で、
生成 data/codegenを触る必要があるため、今回の確実なcommit範囲に含めない。
