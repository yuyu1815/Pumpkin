# 26.2 Adventure `can_break` / `can_place_on` codec checkpoint

## Findings

- Before this change, `CanPlaceOnImpl` and `CanBreakImpl` consumed the wire
  predicate entries and returned `NbtTag::List(Vec::new())`; their serializers
  always wrote predicate count `0`. Predicate data was therefore silently lost.
- The codec now keeps the predicate in the existing `CanPlaceOnImpl::predicate`
  / `CanBreakImpl::predicate` raw-NBT field. No evaluator, player/action change,
  block registry change, or tooltip policy change is included.
- Preserved wire fields are block holder sets (registry IDs and tags), state
  property exact/range matchers, compound block-entity NBT, exact component
  values through the existing `DataComponentImpl` representations, partial
  component IDs, and `TooltipDisplay`'s `hide_tooltip` plus hidden-component
  IDs.
- Parser limits are 256 predicates, 256 block IDs, 256 state properties, and
  256 component matcher entries. Negative counts, duplicate exact fields,
  invalid registry/component IDs, malformed NBT, unknown component names, and
  unsupported raw-NBT shapes fail instead of being skipped.

- The same JAR class shows the wire model used by the implementation:

- `C:/Temp/data_component26_1.json` and `assets/data_component.json` both map

  the added 26.2 component is unrelated). This is the 26.1 data-shape anchor;
  numeric component IDs are still validated against the current 26.2 registry.
- `tools/compat-data/data/26.1/protocol-summary.json` records protocol `775`
  and the existing 26.1 protocol/data source. The current 26.2 protocol asset
  records protocol `776`; the official inner JAR is the authoritative source
  for the 26.2 predicate field layout.
- `C:/Temp/adventure.javap` confirms the owning 26.2 item-side object is a list
  of `BlockPredicate`s. This patch retains that list shape in the existing raw
  component value and does not implement its matching behavior.

## Remaining gap / next gate

This is data retention only. Adventure permission evaluation remains fail-closed
and unimplemented: `canBreakBlockInAdventureMode` / `canPlaceOnBlockInAdventureMode`
must still evaluate block state, block-entity NBT, and component matchers in the
item/data owner before any Adventure allow-path change. Exact matcher values use existing component codecs; any pre-existing codec
that does not model a value is still a separate codec gap, not silently fixed
here. In particular, this gate does not establish arbitrary-value fidelity for
lossy pre-existing component codecs such as placeholder implementations, and
it does not establish evaluator behavior. Adventure permission evaluation must
remain fail-closed until a separate owner evaluates block state, block-entity
NBT, and component matchers. Do not edit player, action, or block-registry code
in this gate.
