# Minecraft Java 26.2 chat sidecar production lifecycle

## Findings

This change connects the existing inbound secure-chat sidecar to the production
world removal lifecycle without changing `ChatSession`, entity persistence,
signed commands, or the outbound secure-chat format. `Player` gains only the
per-connection `ChatOwnerToken` capability required for lifecycle ownership.

The lifecycle contract is:

- `crates/pumpkin/src/net/chat/state.rs::reset_inbound_state` installs a
  session-owned chain. Repeating the same session update is idempotent; a new
  session UUID replaces the old chain at the already validated session-update
  boundary.
- `crates/pumpkin/src/world/mod.rs::World::remove_player` removes the exact
  `Arc<Player>` owner, not an arbitrary player with the same profile UUID.
  This prevents an old connection from removing a newer same-UUID login.
- A real disconnect (`PlayerRemovalReason::Disconnect`) retires the per-Player
  `ChatOwnerToken` and conditionally clears the sidecar with profile UUID,
  current chat session UUID, and token identity. A stale old-session/old-token
  cleanup is a no-op. If another same-UUID player is published in any server
  world, cleanup is skipped and the replacement owns the sidecar.
- A dimension transfer (`PlayerRemovalReason::DimensionTransfer`) does not clear secure-chat state.
  The same `Player`/connection continues across worlds, so its inbound chain is
  not a disconnect lifecycle.
- A broken chain is still removed on a matching disconnect; invalid chat never
  resets or repairs the chain during message validation.

The sidecar's session UUID is part of the session guard, and its owner is a
`Weak<ChatOwnerToken>` tied to the live `Player`. No historical UUID tombstone
or allocation-address generation map is retained. World ownership is guarded
by `Arc::ptr_eq`, and sidecar ownership by `(profile UUID, session UUID,
token identity)`.

## Migration / Investigation Notes

### Official lifecycle distinction

The existing 26.2 official-JAR investigation recorded the secure chat chain as
owned by the active remote chat session: session replacement establishes a new
chain, while a player changing dimension remains the same connected player.
That distinction is consistent with the local production callers:

- `World::respawn_player` at `crates/pumpkin/src/world/mod.rs` calls
  `remove_player(player, PlayerRemovalReason::DimensionTransfer)` before
  publishing the same `Arc<Player>` into the destination world.
- `Player::teleport_world` at `crates/pumpkin/src/entity/player.rs` uses the
  same `DimensionTransfer` path.
- `Player::remove` calls `remove_player(self, PlayerRemovalReason::Disconnect)`
  only for connection teardown.

Therefore profile UUID sidecar state must survive dimension transfer and must
be cleared on disconnect, not on every world-list detach. The old implementation
had only `clear_inbound_state(player_id)`, which was unsafe for an old
connection: a later same-UUID session could have installed state before the old
disconnect task ran.

### Race/ownership design

1. `World::remove_player` now matches `Arc::ptr_eq(p, player)`, not only the
   profile UUID. An old `Player` cannot remove a replacement `Player` from the
   world list.
2. For `PlayerRemovalReason::Disconnect`, the world checks all currently
   published worlds for another player with the same profile UUID. A published
   replacement keeps ownership and suppresses cleanup.
3. If no replacement is published, the removed player's current
   `ChatSession.session_id` and `ChatOwnerToken` are passed to
   `clear_inbound_state` after the token is retired under `chat_lifecycle`.
4. `clear_inbound_state` holds the sidecar mutex and removes only when the
   stored session UUID and token identity match. A newer session or same-session
   replacement therefore survives an old disconnect even when both connections
   use the same profile UUID.
5. `reset_inbound_state` does not rewind an entry when the session UUID is the
   same. This protects the idempotent same-session update contract even if the
   caller repeats the reset boundary; a successful packet then binds the
   sidecar to that owner token.

This is intentionally a narrow fix. It does not add fields to `Player`, change
server duplicate-login policy, or alter `World::add_player`. A future owner that
needs a connection-generation token independent of session UUID should add an
explicit player/session lifecycle field and pass that token through login,
world ownership, and cleanup as one change; this task does not interfere with
that proposal.

### Secure-chat state safety

`verify_and_commit` remains success-only for ACK/window, index, and timestamp
commit. Signature failure, replay/index failure, old millisecond timestamp,
checksum failure, and broken-chain rejection do not reset the state. The sticky
`broken` flag is cleared only by a validated new session installation or by the
matching disconnect cleanup. RSA known-answer/canonical tests and signed-chat
serialization were not changed.

### Tests added

The state module now covers these concrete transitions with isolated UUIDs:

- `same_session_reset_is_idempotent`: accepted state (`next_index=4`, broken)
  is not rewound by the same session update.
- `old_disconnect_cannot_clear_new_session_or_duplicate_login_state`: old
  session cleanup returns `false` and leaves the new session entry installed.
- `old_player_token_cannot_clear_same_session_replacement`: a stale
  same-session Player token cannot clear a state committed by a replacement.
- `broken_chain_is_removed_by_matching_disconnect_cleanup`: a sticky broken
  entry is still removed by its owning disconnect.

The existing pure tests continue to cover root/index advancement, millisecond
ordering, sticky chain rejection, Java signed-byte checksum, canonical hash,
and ACK preview rollback.
