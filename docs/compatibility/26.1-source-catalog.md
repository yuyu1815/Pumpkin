# 26.1 基盤候補: 既存データ／ツール適合性カタログ

- 調査目的: 26.1 を**比較用データ基盤**として再利用できる範囲を確定する。最終 server 対象は Java 26.2 のままであり、26.1 bot/client を 26.2 に直結できるとは扱わない。
- 調査時点: 2026-09-19、HEAD `1ac447f2918b7dec7d19a5836fa3673d4fe3c9f5`。
- 書込み所有: 今回は `tools/compat-data/` と今回の 26.1 docs。正式コード、assets、既存 `tools/compat-26_2/` harness は変更していない。
- 取得方針: pinned raw の version/protocol/items/blocks/recipes と小さい metadata のみ。合計は約 1.84 MBで20 MB上限内。JAR、npm install、cargo、pcap、実プレイ traceは取得していない。

## Findings

### 1. まず必要な最小 dataset と任意 dataset

| 区分 | dataset / 成功条件 | 26.1 の実在確認 | 26.2 への扱い |
|---|---|---|---|
| **必須** | `version.json`: Minecraft version、protocol version、release type | PrismarineJS `data/pc/26.1/version.json`: `minecraftVersion=26.1`, `version=775`, `releaseType=release` | 26.2の一次根拠にはしない。Pumpkin/公式26.2 `protocol=776` と別キーで管理する。 |
| **必須** | `protocol.json`: state、direction、packet id mapping、field codec/schema | 336,715 bytes。handshaking/status/login/configuration/play、各 state の packet type と ProtoDef field schema が存在。packet 数は serverbound/clientbound で順に `2/0, 2/2, 5/6, 10/20, 69/141`。 | framing、VarInt、option/array/container、同一操作の**形**の fixture に限定。26.2 packet ID/field/semantic の根拠は26.2一次資料必須。 |
| **調査済み／今回未保存** | login / initial state schema | pinned raw `loginPacket.json` は 695,059 bytes、top-level key 12であることを確認したが、今回の committed foundationには保存していない。 | Join Game の26.2 field順、registry、secure-chat semantic を26.1から補完しない。必要時は別sourceとして同じpin/hashを追加する。 |
| **必須（機械可読の範囲）** | blocks / items / recipes | 26.1 `blocks.json` 1,168 entries、`items.json` 1,506 entries、`recipes.json` top-level item-key 887（レシピ総数ではない）。 | 26.1の item/block/recipe fixture、数量保存、同名操作の入力生成に使う。26.2のID、component、recipe result、remainderは26.2 source/generated/実wireで再判定。 |
| **条件付き必須** | 26.2側の一次 dataset | 既存 `assets/packet/26_2_packets.json`、`assets/datapacks/26_2/`、generated source、公式 metadata/JAR hash記録 | 最終対象。packet ID、registry payload、component、recipe semantic、Known Packs はここを主根拠とする。 |
| **任意** | entities、biomes、effects、enchantments、particles、language、collision shapes、sounds/tints/materials | 26.1 directory に実在し、API directory listingでサイズとblob SHAを確認。 | entity mapping、初期fixture、衝突形状の候補に使えるが、26.2の存在・値・挙動を証明しない。 |
| **任意／不足** | registries、dimension codec、tags、known-packs payload、全 item component values、world/chunk NBT | 26.1 `minecraft-data` directory listingに独立 registry/dimension/tag datasetは確認できず、READMEの提供一覧にも registry payload はない。 | 26.2一次データ、Pumpkin assets/generated、公式 server/client境界で必ず別検証。26.1の空欄を26.2へ推測移植しない。 |

`minecraft-data` の README は「protocol を complete description」と説明するが、READMEは対応の宣言である。実データ確認では commit固定 raw の `version.json`、`protocol.json`、items/blocks/recipes（loginPacketは調査のみ）の存在・サイズ・内容まで確認し、READMEの文言だけを根拠にしていない。manifestの `data_path` / `artifact` は `data/pc/26.1/...` を明示し、logical namespace=`26.1` と physical source version=`26.1` を分離記録している。

### 2. Web/取得で確認した候補

#### PrismarineJS/minecraft-data

- source: <https://github.com/PrismarineJS/minecraft-data>
- 26.1 data pin: commit `20a0b0142d99d9a069aa8fec98512ec082b4f0a3`（`tools/compat-data/manifest.json` と同一の canonical pin）。logical namespace=`26.1`、physical source version=`26.1`、resolved data path は `data/pc/26.1/`。別版共有を仮定していない。
- 実確認 URL（commit固定）:
  - `data/pc/26.1/version.json`: content SHA-256 `cced5b9e15eaa84c15b229fe7d861894dc29ec21210a03ff3a1ba4da606dee10`、104 bytes、protocol `775`。
  - `protocol.json`: content SHA-256 `88bad867681214bfea6c59c9a705da4cc269f8131e9d3495bd03916275e7fa08`、336,715 bytes。
  - `loginPacket.json`: content SHA-256 `0c314bd063cfe41c783db0490f082508368e678267f336cf38cc07f42481523f`、695,059 bytes。
  - `blocks.json`: content SHA-256 `573e172619f3c1ca64e15d07799ab646e1fd9ad19d759d9ceca65ac4fc7440a9`、860,277 bytes。
  - `items.json`: content SHA-256 `0d085dbf8a6fa129b94f696b77286d65ce7b04476eab398492558ab03cc1c45e`、189,396 bytes。
  - `recipes.json`: content SHA-256 `3af5e2bf3f5a6cfe5d9fed34b33332f45bdfadd3af859cc71edfe7b72742dd54`、404,729 bytes。
- raw JSON は repo の配布物として保存しない。`py -3 tools/compat-data/compat_data.py fetch` が `tools/compat-data/.cache/` に `version`、`protocol`、`items`、`blocks`、`recipes` を再現し、manifest の cache path、bytes、SHA-256で検証する。`protocol.json` は packet schema そのもので、summaryだけではない。
- 26.2 negative check: `https://raw.githubusercontent.com/PrismarineJS/minecraft-data/20a0b0142d99d9a069aa8fec98512ec082b4f0a3/data/pc/26.2/version.json` は HTTP `404`、14 bytes。これは「26.2が存在しない」の証明ではなく、このpinに26.2 directory/dataが無いという限定結果。
- license: pinned READMEの License は `MIT` だが、同pinの root `LICENSE`/`NOTICE` はHTTP 404で、README自身が wiki.vg / minecraft.gamepedia.com 等からの抽出とsource別licenseの変動可能性を明記している。したがって全JSONを無条件にMITとして再配布せず、rawはignored cache-onlyとした。実文書と制限は `tools/compat-data/THIRD_PARTY_NOTICES.md` と `tools/compat-data/LICENSE-minecraft-data.txt` に保存し、Mojang data条件は `assets/NOTICE.md` と別管理する。

- 26.1 support commit: `404fb097e47244d366a6011bfe4f9d9d530f7ded`、`2026-08-15T23:58:47Z`、message `26.1 (#1469)`。

- 拒否範囲: 26.2 parser/oracle、26.2 field/IDの自動補正、vanilla clientの代替。

#### GeyserMC/MCProtocolLib

- source: <https://github.com/GeyserMC/MCProtocolLib>
- READMEの実確認: custom bot/client/server向け library、MIT license。READMEだけで版対応を断定しない。
- actual codec: commit `054bf35d236d07c091a184cf1849c96090bc0b1b`、`2026-04-04T06:30:05Z`。`MinecraftCodec.java` は `.protocolVersion(775)`、`.minecraftVersion("26.1")`。
- 実際の登録APIは `registerServerboundPacket` / `registerClientboundPacket`。configurationの Known Packs、Registry Data、Keep Alive、playの Level Chunk With Light、Login等の Java packet class登録が存在する。`ClientboundSelectKnownPacks` は namespace/id/version のString listをdecodeする。
- `protocol/build.gradle.kts` の確認値は version `26.1-SNAPSHOT`。current codec grepでは `26.1`あり、`26.2`なし。
- current master commit `19783c29ece24bc3f07f8ff08628549527e3de20`（`2026-07-08T09:02:34Z`）を確認したが、codecは依然26.1。GitHub API releases endpointはこの調査中HTTP `403`だったため、latest release名やrelease対応は主張しない。
- license: GitHub metadata/READMEともMIT。
- 採用範囲: Java codec API設計比較、26.1 packet fixture、bot/server test設計。
- 拒否範囲: 26.2 parser、26.2 server/client oracle、26.2 semanticの代用。

### 3. license と再利用境界

- `minecraft-data`: repository README `MIT`。データの由来別条件があり得るため、PumpkinのGPLv3へ自動的に吸収しない。
- `node-minecraft-protocol`: `BSD-3-Clause`。sourceをコピーする場合はBSD noticeを保持。今回コピーしていない。
- `mineflayer`: `MIT`。source/API参照と実行依存は別管理。
- `MCProtocolLib`: `MIT`。sourceをコピーせず、codec/packet classの比較資料として使う。
- 公式 Mojang 26.2 artifact、client/server、assetsは再配布しない。既存 `assets/NOTICE.md`のMojang/Microsoft EULA・attribution方針を優先し、URL、version、期待hash、取得日時だけを記録する。

### 4. pin方法と具体的な再利用パス

1. **data pin**: `minecraft-data` は repo commit `20a0b0142d99d9a069aa8fec98512ec082b4f0a3`、対象 artifact の content SHA-256、`version.json` の protocol `775`を記録する。取得は commit 固定 raw URL、または git mirror で同 commit を fetch し、ファイル hash を照合する。branch名やnpm caretだけをpinとしない。raw schema/data は `tools/compat-data/.cache/` にのみ取得し、再現不能な配布コピーは作らない。
2. **codec/tool pin**: node-minecraft-protocolは少なくとも `404fb...`、mineflayerは `aa8...`、MCProtocolLibは `054bf...` を比較基盤のbaselineとして記録する。current headを採用する場合はそれぞれ `0eb...` / `2084...` / `19783...`を別pinとして明示する。
3. **dependency lock**: npmなら package-lock、JavaならGradle lock/dependency verification、dataなら外部repo commit＋blob SHAを併用する。`^` dependency解決結果を26.1 datasetの同一性とみなさない。
4. **repository内の再利用**: 26.1 raw data は正式 `assets/` や generated sourceへ無断コピーしない。rawは ignored `tools/compat-data/.cache/` に pin/hash検証付きで取得し、後続比較ツールは source URL・commit・content SHAを結果へ埋め込む。配布対象は committed summary/contract と出典通知だけである。
5. **26.2 authoritative path**: packetは `assets/packet/26_2_packets.json`と26.2生成経路、registry/items/blocks/recipesは26.2 assets/datapack/generated source、版値は既存公式metadata/JAR hash記録を主根拠にする。

既存資料の「対応」はそのまま採用せず、上記のversion file、version array、codec literal、実ファイル directory listing、package licenseを分離して確認した。取得したのは小さい metadata/raw/APIと対象JSONで、JAR/pcap/実プレイtraceは新規取得していない。

### 確認しなかったもの

- 26.1/26.2 vanilla client起動、公式server起動、実プレイtrace、pcap、online-mode session。
- 公式JARの新規download、JAR内部の全packet/registry decompile。
- node/npm install、Gradle build、MCProtocolLibのartifact download。
- 26.1 toolがPumpkin 26.2へ直接接続できること。むしろ上記version guard/APIから直接接続を採用しない。

## Recommended Next Steps

1. 26.1を使う後続fixtureは、`protocol=775`、source commit、各blob SHA、tool commit、licenseをfixture metadataへ必ず埋める。
2. 26.2比較では、26.1 packet schemaを候補として読み込んでも、`packet ID / registry / item component / recipe semantic`を26.2一次証拠なしにpassへしない。
3. node-minecraft-protocol/mineflayerは26.1合法操作の synthetic generatorまたは補助botとして条件付き採用し、26.2接続試験の判定器にはしない。
4. MCProtocolLibはJava codec設計の比較資料として採用し、26.2対応がcodec literal/commitで確認できない限り parser dependencyにしない。
5. Via変換を試す場合は、`26.2 -> 26.1 -> tool` の変換層として別証拠を記録する。変換前後のpacket、registry remap、semantic invariant、失われた/合成された情報を別表にし、vanilla 26.2 client代替や26.2 server直結の主張を禁止する。
