# 26.2 command vanilla policy / block digging 独立仕様 review

## Findings

### 判定

**現状は merge 不可。** ACK/chain の一部と digging の基本拒否は静的に妥当だが、公式 26.2 と異なる必須経路がある。特に STOP の delayed destroy、採掘状態の world/tick 生命周期、signed command の parsed-context/duplicate 選択を直すまで、`26.2-command-vanilla-policy.md` と `26.2-digging-authority.md` の「公式順序に一致」「互換仕様」という表現は過大である。

### 一致している点

- `crates/pumpkin/src/net/java/play/chat_command.rs:237-263` は `apply_last_seen_update` を parse より前に呼ぶ。ACK の成功更新は後段の parse/signature failure で rollback しない。
- secure signed command の `crates/pumpkin/src/net/chat/state.rs:368-388` は packet entry 順に同じ `next_index` を使い、各成功 entry ごとに 1 link 進める。後続 signature failure では先行 link を残して chain を broken にする。公式 `ServerGamePacketListenerImpl.collectSignedArguments` の entry loop/map.put と `SignedMessageChain.Decoder.unpack` の順序に一致する。
- unknown entry の known prefix を先に検証してから `break_inbound_chain` する `chat_command.rs:295-340`、missing は entry decode 後に reject する `:378-391` は、公式の unknown=chain broken / missing=chain を直接 broken にしない挙動に沿う。
- empty entry の no-signable seam、reports-disabled の unsigned decoder 相当、secure mode の signable command に対する unsigned reject、session expiry/empty session の拒否は、少なくとも static branch として分離されている。
- `crates/pumpkin-protocol/src/java/server/play/chat_command_signed.rs:27-47` の argument signature 上限 `8`、negative count、wire-fit 検査は存在する。
- digging の reach と上限 y の拒否、START 無し/位置不一致の FINISH 拒否、`speed * (elapsed + 1) >= 0.7`、creative START の即時 break、rejected FINISH の block resync/sequence 更新は、意図した防御境界として存在する。

### Must-fix 1 — STOP の progress 不足を stop/reject して delayed destroy を消している

- **path / symbol:** `crates/pumpkin/src/net/java/play/player_action.rs:195-242`、`can_finish_digging` `:330-342`。
- **条件:** matching START/position があり、`speed * (elapsed + 1) < 0.7` の STOP。
- **公式証拠:** `C:/Temp/game_mode.javap` の `handleBlockBreakAction` STOP branch offset `487-641`。progress `0.7` 未満では `isDestroyingBlock=false`、`hasDelayedDestroy=true`、`delayedDestroyPos=pos`、`delayedTickStart=destroyProgressStart` を設定する。`tick` offset `10-78` は毎 tick `incrementDestroyProgress` を継続し、progress `>=1.0` で `destroyBlock` する。
- **現状:** `can_finish_digging` false で `player.stop_mining()`、block update、return。delayed state も tick owner も作られず、vanilla が後から破壊するブロックを破壊しない。
- **再現案:** hard block と低い break speed で START、STOP を `speed * (elapsed + 1) < 0.7` の tick に送る。その後 STOP/追加 action を送らず server tick を必要時間進める。vanilla は delayed destroy 完了、現状 Pumpkin は block を維持する。
- **最小修正:** `Player` の既存 `mining`/`mining_pos` と混ぜず、`delayed_destroy_pos`/`delayed_destroy_start`/有効 boolean を最小追加するか、既存 mining state を delayed mode として明示化する。Player tick に公式同等の delayed progress/update/`>=1.0` destroy を追加し、STOP mismatch/ABORT/air/world-change/切断で delayed state を確実に清掃する。`stop_mining()` だけで代用しない。

### Must-fix 2 — position mismatch の STOP が vanilla より強く state を消す

- **path / symbol:** `player_action.rs:218-242` と `can_finish_digging`。
- **条件:** START(A) 後に STOP(B) を送る場合。
- **公式証拠:** `game_mode.javap` STOP offset `494-630` は `pos.equals(destroyPos)` が false なら debug log のみで、`isDestroyingBlock` を clear しない。後で STOP(A) を受けられる。
- **現状:** B は predicate false で `stop_mining()`。A の state、stage、boolean も消えるため、後続 STOP(A) は START 無しとして reject される。
- **再現案:** slow block A で START → 別の reachable block B で STOP → A で STOP。vanilla は A の state を保持し得るが、現状は A を破棄する。
- **最小修正:** mismatch STOP は requested position の resync/sequence だけにし、active destroy state を消さない。delayed state がある場合も同じく別 owner を保持する。ABORT は公式どおり active state/progress を clear する。

### Must-fix 3 — shared tick と `mining` boolean の target/world 生命周期が分離していない

- **path / symbol:** `player_action.rs:101-160`、`crates/pumpkin/src/entity/player.rs:2761-2808,2882-2929`、dimension transfer `player.rs:3892-3907` / `world/mod.rs:4554-4557`。
- **条件 A:** 既に A を mining 中に、別 target B の START、creative START、または instant-break START を受ける。
- **現状:** Java START は既存 mining を先に `stop_mining()` せず `start_mining_time`/`mining_pos` を上書きし、instant/creative branch も active boolean を clear しない。共通 `Player::tick` は分離 boolean と現在の `mining_pos` だけを読み、古い progress packet や意図しない B/旧 state の継続処理を起こし得る。
- **条件 B:** mining 中に world/dimension move。
- **現状:** `teleport_world`/world respawn の detach→`change_world_chunks`→`set_world` に `stop_mining()` がない。次 tick の `player.world()` は新 world だが `mining=true`、旧座標、旧 start tick を持ち続ける。`stop_mining()` 自体も現在 world に Stop を送るため、移動後に呼ぶだけでは旧 world の progress cleanup にならない。
- **再現案:** slow block A で START → dimension teleport、または START(A) → START(B) → 旧 world/new target の tick を数える。`BlockBreakingProgress::Update` の送信先、`mining_pos`、破壊位置を観測する。切断は world list から消えるため mutation は止まるが、progress cleanup/fields の明示 reset は未実装。
- **最小修正:** target を変更する全 caller の共通入口で、旧 world を参照した `stop_mining()` を先に実行する。instant/creative/新 START/ABORT/FINISH の state transition を一か所で清算し、world transfer 前に boolean/stage/speed/position を reset する。delayed destroy は active mining と別 boolean のまま world-bound cleanup を持つ。

### Must-fix 4 — duplicate の chain 消費はあるが、公式の「最後の map value」を実行へ渡していない

- **path / symbol:** `crates/pumpkin/src/net/java/play/chat_command.rs:92-111,343-391`、`execute_authenticated_chat_command:177-224`。
- **公式証拠:** `C:/Temp/javap-ServerGamePacketListenerImpl.txt:4567-4661` の `collectSignedArguments` は packet order で `Map.put(name, decoded)` するため、同名 duplicate は許可され、最後の entry が map value になる。その map を `CommandSigningContext.SignedArguments` として parse result に map して `Commands.performCommand` へ渡す。
- **現状:** duplicate は `HashSet` で reject しなくなり、`contents`/`signatures` は duplicate ごとに chain を進めるので auth side は概ね一致する。しかし Pumpkin は map/last-value を作らず、`dispatcher.execute(parsed)` に signed argument context を注入していない。コメントで「last entry で上書き」と宣言するだけで、選択結果が command execution に存在しない。
- **再現案:** 同じ signable name を 2 entry 送り、first/last の署名 body を異なる known fixture にする。chain index が 2 消費されることと、command executor がどの decoded value を参照するかを観測する。現状は後者の context API 自体がない。
- **最小修正:** core command execution に vanilla 相当の signed/unsigned argument context を最小追加し、packet-order `Map::insert` の最後の value を `parsed` の source/context に map してから execute する。context を実装しない間は「duplicate selection compatible」と記載しない。

### Must-fix 5 — no-session unsigned seam が accepted path で command を再 parse している

- **path / symbol:** `chat_command.rs:177-224`、特に `:215-216`。
- **条件:** `authenticated == false` の empty-entry/no-signable、または reports-disabled entry path。
- **公式証拠:** `handleSignedChatCommand` は ACK 後に parse、`collectSignedArguments`（empty entries は `collectUnsignedArguments`）後、同じ parse result を `Commands.performCommand(parsed, packet.command)` へ渡す。再 parse はない。
- **現状:** first parse 済みの `parsed` を受け取っているのに、`authenticated == false` では `dispatcher.handle_command(source, &command)` を呼び、command tree を再 parse する。plugin/event の間に tree/permission が変わる場合、公式の parse/execute identity と一致しない。また signed command の no-session/no-signable を通常 raw command path と同一視している。
- **再現案:** parse 後から execute 前に command tree/permission を変更する plugin hook、または parse result と再 parse の redirect/argument path が異なる command を用いる。公式は最初の parse result、現状は二度目の parse resultになる。
- **最小修正:** accepted signed-command path は secure/unsigned decoder を問わず、渡された `parsed` を execute する。event を許すなら command text mutation を拒否する現在の防御を維持し、unsigned decoded argument context は別途 no-signature context として注入する。

### Must-fix 6 — timestamp field の単位 fallback が混在している

- **path / symbol:** `crates/pumpkin/src/net/chat/state.rs:58-59,93-96,103-113`。
- **条件:** `last_timestamp_epoch_millis == None` かつ `last_timestamp_epoch_second == Some(x)` の state。
- **現状:** comparison input は wire epoch-millis だが、`.or(last_timestamp_epoch_second)` で epoch-second を同じ比較値として使う。通常の現行 constructor/`advance_at` は両 field を同時に設定するため、この状態の production reproduction は未確認だが、field meaning は明確に不正で、future state migration/partial initialization で誤判定する。
- **最小修正:** order check は millis field だけで行う。epoch-second は canonical signed body/diagnostic 専用にし、fallback しない。`last_timestamp_epoch_millis=None` state を作る unit test と、`1_001ms` 後に `1_000ms` を reject する test を分離する。

### Defensive strict と vanilla compatibility を分けるべき点

- **Adventure digging:** 公式 `C:/Temp/javap-Player.txt:181-224` の `blockActionRestricted` は spectator を拒否するが、Adventure 相当で `mayBuild=false` でも main-hand `ItemStack.canBreakBlockInAdventureMode(BlockInWorld)` が true なら通す。`player_action.rs:35,210` の `!player.may_build()` は全 Adventure mutation を拒否するため、predicate が未実装なら安全な fail-closed ではあるが vanilla compatibility ではない。
- **Adventure placement:** `crates/pumpkin/src/block/registry.rs:621-623` は `may_build` だけで shared placement mutation boundary を拒否する。公式 `C:/Temp/itemstack.javap` offset `14-47` は `mayBuild=false` のとき `canPlaceOnBlockInAdventureMode` を評価する。Java/Bedrock caller の共通 boundary を閉じる security fix としては merge 候補だが、`can_place_on` evaluator 完成までは compatibility pass と記載しない。
- **START official preconditions:** `game_mode.javap` START offset `76-251` には spawn protection、`ServerLevel.mayInteract`、`blockActionRestricted` がある。現 handler では reach/high/may_build/item `can_mine` は見るが、spawn protection/mayInteract と Adventure `canBreak` の公式判定は再現していない。これは今回の diff が新規に作った欠落とは限らないため、既存 gap と今回変更の blocker を分けて記録する。

### Float / zero divisor / air

- `crates/pumpkin/src/block/mod.rs:~520-536` の `calc_block_breaking` は `mining_speed / hardness / i` を直接計算する。`player_action.rs:229` は air を先に除外せず FINISH ごとに計算し、`speed.is_finite()` で inf/NaN の結果を reject するだけである。
- 現状は mutation 前に reject するため即時の block-break bypass は確認できないが、公式 STOP は air なら destroy branch に入らず、zero hardness/zero speed は domain として明示されるべきである。最小修正は `state.is_air()` の先行 branch、hardness `<= 0`/非有限 speed の明示的 reject、共通 tick `continue_mining` 側にも同じ guard を置くこと。`continue_mining` の `tick_counter - starting_time`（`player.rs:2889`）も world/state reset 後の負値・overflowを別 test にする。
