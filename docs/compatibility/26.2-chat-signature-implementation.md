# 26.2 chat signature: first implementation

## Scope and evidence

This patch implements only the evidence-backed, stateless part of the first
chat-signature step. The 26.2 canonical byte order was taken from static
analysis of `C:/Temp/minecraft-26_2-server.jar` (outer SHA-1
`823e2250d24b3ddac457a60c92a6a941943fcd6a`, 60,894,273 bytes), specifically
`PlayerChatMessage.updateSignature`, `SignedMessageLink.updateSignature`,
`SignedMessageBody.updateSignature`, and `LastSeenMessages.updateSignature`.
The JAR was not executed.

The implemented bytes are:

```text
int32_be(1)
sender UUID (16 bytes)
session UUID (16 bytes)
int32_be(link index)
int64_be(salt)
int64_be(timestamp epoch seconds)
int32_be(content UTF-8 byte length)
content UTF-8 bytes
int32_be(last_seen count)
last_seen signatures, 256 bytes each, in order
```

The serverbound `SChatMessage.timestamp` is treated as epoch milliseconds and
converted with floor division by 1000. The implementation does not use Java
UTF-16 length, VarInt lengths, epoch milliseconds in the signed bytes, or the
packet's raw 3-byte acknowledgement bitset as `last_seen`.

The signature verifier reuses the existing `rsa`/`sha2` dependencies and
performs RSA PKCS#1 v1.5 with SHA-256 over the canonical bytes. This is distinct
from the existing Mojang session-certificate RSA/SHA-1 verification.

## Independent known-answer fixture

The empty-`last_seen` vector is:

- sender `00000000-0000-0000-0000-000000000001`
- session `00000000-0000-0000-0000-000000000002`
- index `0`
- salt `0x0102030405060708`
- wire timestamp `1700000000000` ms, signed timestamp `1700000000` s
- content `hi`
- canonical length `66`
- canonical SHA-256
  `6ca6cc185f024bc125cd5beec691bf4541541dfc73c6d8322801276a01387d10`

A fixed 2048-bit RSA public DER key and 256-byte signature are embedded in the
module tests. The signature was generated independently with OpenSSL 3.2.2
using a private key that was not stored in the repository. The Rust tests do
not generate or re-sign any fixture. They cover the valid signature plus
content, salt, timestamp, session, index, `last_seen`, wrong-key, zero-byte,
and wrong-length mutations.

## Why the handler does not enforce verification yet

The current handler has no trustworthy inbound signed-chain index. Its
`ChatSession::messages_sent` is an outbound broadcast counter and must not be
substituted for the client chain index. The current `MessageCache` also does
not expose an atomic, current-packet `last_seen` result suitable for signing;
its existing `last_seen` is not that result. Therefore this patch does **not**
reject or secure-broadcast based on this new verifier. Enabling that would
make an apparently safe implementation verify the wrong bytes and would be a
compatibility and safety regression.

The existing secure-mode checks remain unchanged, including the existing
policy boundary. Offline/unsigned chat is not newly rejected by this patch;
`online_mode=false` with reports disabled remains an unsigned/system-chat
configuration. The independent signature tests are not vanilla client/server
round-trip evidence.

Still incomplete and intentionally not hidden:

- inbound session chain state: next index, last timestamp, broken-chain state,
  and advance only after successful verification;
- atomic `LastSeenMessages.Update` reconstruction and Java signed-byte
  checksum semantics;
- session-key expiry integration with message verification;
- signed-command argument signatures, command chain, and removal of the
  signed-to-unsigned command fallback;
- vanilla 26.2 client/server interoperability and report UI behavior.
