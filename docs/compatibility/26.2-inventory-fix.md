# 26.2 inventory fix round 1/3 — INV-01 検証結果

## Findings

- **判定: INV-01 のアイテム増殖は、許可された実処理 fixture では再現しなかった。候補を反証したため、本番ロジックの修正は行わない。**
- 対象は Java 26.2 / protocol `776` の inventory crafting shift-click である。26.1 data foundation は今回の判定に不要だったため使用していない。26.2 の最終対象は維持した。
- 検証した実処理は、テスト内に `quick_move` / `insert_item` / craft 消費ロジックを作り直さず、次の既存経路を直接実行した。
  - `ScreenHandler::on_slot_click`
  - `PlayerScreenHandler::quick_move`
  - `CraftingTableScreenHandler::quick_move`
  - `ScreenHandler::insert_item`
  - `ResultSlot::refill_output`
  - `ResultSlot::on_take_item`
  - `ScreenHandler` の QuickMove 内部反復
- oak log 1個の実レシピ結果は oak planks 4個であり、材料消費、recipe output 倍率、cursor/result/drop/player inventory の状態を操作前後で観測した。
- 部分 stack で残った output は、空きがない場合は drop に、空きがある場合は空き slot に移動した。result preview は craft 後に消え、cursor は空のままだった。
- 複数材料を同じ grid stack に置いた場合、1回の shift-click が既存の `ScreenHandler` 内部反復で craft 可能な回数を処理する。2 log → 4 planks × 2 = 8 planks となり、増殖ではない。
- full inventory では材料を消費せず、result preview 4個を保持した。これは「搬送不能なのに消費する」経路の反証である。
- stack limit は全 fixture で main inventory の各 stack が item max 以下（oak planks は最大64）だった。
- **remainder は別候補 INV-03 として未修正・未確定のまま残した。** `ResultSlot::on_take_item` は各 input から1個を除去するだけで、`pumpkin_data::recipe_remainder::get_recipe_remainder_id` をこの crafting path で使っていない。cake/milk bucket の runtime fixture をこの INV-01 修正へ混ぜると別候補の修正になるため、今回の増殖判定の証拠には採用していない。

## Migration / Investigation Notes

### Fixture と保存則

テスト fixture は `PlayerScreenHandler`（2x2 inventory crafting）と `CraftingTableScreenHandler`（3x3 crafting table）の両方で同じ意味の操作を実行した。材料は slot 1 に直接配置した後、既存 `ScreenHandler::update_to_client` を通して実際の `ResultSlot` listener から result を生成した。shift-click は `handler.on_slot_click(0, 0, SlotActionType::QuickMove, &player)` で実行した。

result slot の stack は「まだ取得されていない preview」であり、所有済み output の保存則には操作前の preview を加えない。従って所有済み output は次で数えた。

```text
player main inventory の oak planks
+ cursor stack の oak planks
+ drop callback で記録した oak planks
```

result slot、cursor、grid input は別々に assert した。これにより、preview の表示を実アイテムとして二重計上しない。

| ケース | 初期状態 | 実行結果 | 判定 |
|---|---|---|---|
| 満杯 + partial stack | inventory slot 0 = planks 62、残り35 slot = cobblestone 64、grid = oak log 1、result preview = planks 4 | inventory planks 64、drop planks 2、result empty、grid empty、cursor empty。所有済み output は `62 + 4 = 66` のまま | 増殖なし。stack max 64 |
| partial stack + 空き slot | slot 0 = planks 62、slot 35 = empty、その他は cobblestone 64、grid = oak log 1 | inventory slot 0 = 64、空き slot = planks 2、drop 0、result/grid/cursor empty。所有済み output は `62 + 4 = 66` | 増殖なし。部分空きの搬送も保存 |
| 完全満杯 | 全36 main slot = cobblestone 64、grid = oak log 1、result preview = planks 4 | planks inventory 0、drop 0、input log 1、result preview 4、cursor empty | 搬送不能時に材料を消費しない |
| 複数回 craft | grid の oak log stack = 2、player inventory empty | 1回の QuickMove 内部反復で2回 craft、inventory planks 8、input/result/cursor/drop は empty。その後の再QuickMoveは no-op | `2 × output 4 = 8`、増殖なし |

各ケースを player inventory screen と crafting table の両方で実行した。fixture の `DropRecorder` は drop callback の実引数を記録するだけで、搬送処理を再実装していない。

### 失敗 test → fixture の狭い修正 → 成功

最初の複数回 craft test は「1回の QuickMove は1 recipeだけ」と仮定していた。既存 `ScreenHandler::internal_on_slot_click` の次の反復を考慮していなかった。

```text
while moved_stack != empty
  && slot stack == moved_stack {
    moved_stack = self.quick_move(...)
}
```

- 初回の試行: 28 tests 中 26 passed / 2 failed、終了コード `101`。
- 失敗値: `left: 8`, `right: 4`。
- 失敗箇所: 初期テストの「2 log なら1回の shift-click で4 planks」という期待値。
- 判断: production code の増殖を示す失敗ではなく、既存 QuickMove の「残材料がある限り反復 craft」という仕様を test が誤っていた。
- 狭い変更: production source は変更せず、test の期待値を「2 recipe を処理して8 planks」に修正し、2回目の no-op と材料消費を明示した。
- 修正後の targeted run: 6 tests passed / 0 failed、終了コード `0`。

### 未確認事項・限界

- vanilla Java 26.2 client GUI、実 TCP packet、server process、packet capture、再接続は実行していない。従って「vanilla client との完全互換」を主張しない。
- remainder runtime（milk bucket/cake 等）、component transfer、transmute、recipe-book max-stack は INV-03 の範囲であり、このラウンドでは未修正・未確定である。静的に `on_take_item` が remainder registry を呼ばないことは確認したが、INV-01 の増殖確定とは扱っていない。
- drop は test double の callback 記録であり、world entity の tick、pickup、永続化までは検証していない。ただし shift-click が callback に渡した count は保存則へ含めた。
- 2x2/3x3 の通常 shaped recipe と output count 4 を対象にした。special/dynamic recipe、component 付き result、stack size 1 item は対象外。
- `ScreenHandler::next_revision`、stale click、hopper 境界、equipment broadcast、close window id は INV-02/04/05 の別候補であり変更していない。

## Recommended Next Steps

1. **INV-01 は本ラウンドで修正不要。** 今回の証拠では、静的に疑われた `set_stack` → `refill_output` 経路は、`on_take_item` と `on_quick_move_crafted`、および QuickMove の反復を通過した後に、output の二重所有を残さなかった。
2. 次ラウンドで remainder を扱う場合は、INV-03 として別 fixture を作る。cake の milk bucket、満杯時の remainder の player inventory/drop、component/transmute を分離し、失敗 test が INV-01 と混ざらないようにする。
3. 複数回 craft の期待値は今回の test のように「1 click = 可能な回数を内部反復」として明示する。1 recipe 単位の検査が必要な場合は、grid input count と result preview の遷移を別に記録する。
4. vanilla 26.2 client を利用できる隔離環境が整った場合のみ、partial stack、部分空き、満杯、複数 craft の GUI trace と final inventory/drop state を Pumpkin と比較する。
5. 最終報告の結論は **再現なし / production 修正なし / local regression tests 8件追加 / remainder 等は残課題** とする。
