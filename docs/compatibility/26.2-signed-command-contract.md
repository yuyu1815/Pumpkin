# 26.2 `SChatCommandSigned` 認証契約と fallback 調査

## 調査境界と開始 snapshot

対象は Java Edition 26.2 / protocol 776 の signed command だけである。通常の
serverbound chat message の canonical signature bytes を signed command 全体へ流用
しない。正式 Rust source、protocol source、既存 fixture、chat state は変更していない。
この調査で書いたファイルは本ファイルだけである。

開始時 snapshot:

- `HEAD`: `0361670fb89e3d3df450151ca78275c991f265f4`
  (`test(compat): expose TCP harness baseline failures`)
- `git status --short --branch`: `master...origin/master [ahead 10]`
- 開始時の未追跡領域: `.pi/` と複数の既存 `docs/compatibility/26.2-*.md`
  （他 agent の chat/state 作業を含む）。これらを本調査の変更とは数えない。
- `docs/compatibility/26.2-signed-command-contract.md` は開始時には存在しなかった。

以降の観察はこの開始 snapshot と区別する。並行 agent の作業を reset、clean、stage、
commit していない。

## Findings

### 1. 現在の Pumpkin fallback は署名認証ではない

`crates/pumpkin/src/net/java/mod.rs` の
`handle_play_packet` にある `SChatCommandSigned` 分岐は、現在次の動作をする。

1. `SChatCommandSigned::read` が成功すると `signed.command` だけを `String` にコピーする。
2. `timestamp`、`salt`、argument signature の名前と 256-byte 値、message-count/ack、
   checksum は捨てる。
3. `SChatCommand` を新たに構築して `JavaClient::handle_chat_command` へ渡す。
4. `SChatCommandSigned::read` が失敗すると、同じ payload を通常の
   `SChatCommand::read` で読み直し、先頭の command 文字列を実行する。

従って、成功 packet は署名 metadata を無検証で通常 command に降格し、malformed
signed packet は signed decode failure を理由に拒否されず、通常 command fallback に
入る。どちらも 26.2 の signed-command 認証契約ではない。

`crates/pumpkin/src/net/java/play/chat_command.rs::JavaClient::handle_chat_command` は
spam check、`PlayerCommandSendEvent`、`server.command_dispatcher` の permission / parse /
execute を行う。しかし入力は既に command text だけであり、signed command の
session、chain index、timestamp、salt、last-seen、argument attribution は到達しない。
このため現状でも「signed packet が player の権限を直接 op に昇格させる」とは断定しない。
permission dispatcher は別の authorization gate として残っている。一方、invalid signed
packet が同じ通常 execution path に入るため、auth failure、chain state、secure command
reporting が欠落している。

### 2. 公式 26.2 packet と argument signature の一次契約

静的 oracle は repository 外の Mojang 26.2 server JAR
`C:/Temp/minecraft-26_2-inner.jar`（outer JAR は
`C:/Temp/minecraft-26_2-server.jar`）である。JAR は実行せず、repository にコピーも
再配布していない。対象 class は次の通り。

- `net.minecraft.network.protocol.game.ServerboundChatCommandSignedPacket`
- `net.minecraft.commands.arguments.ArgumentSignatures`
- `net.minecraft.commands.arguments.ArgumentSignatures$Entry`
- `net.minecraft.network.chat.SignableCommand`
- `net.minecraft.network.chat.SignedMessageChain`
- `net.minecraft.network.chat.SignedMessageChain$Decoder`
- `net.minecraft.network.chat.SignedMessageLink`
- `net.minecraft.network.chat.SignedMessageBody`
- `net.minecraft.network.chat.LastSeenMessages` / `$Update`
- `net.minecraft.network.chat.MessageSignature`
- `net.minecraft.server.network.ServerGamePacketListenerImpl`

`ServerboundChatCommandSignedPacket` の 26.2 record fields は次である。

```text
String command
Instant timeStamp
long salt
ArgumentSignatures argumentSignatures
LastSeenMessages.Update lastSeenMessages
```

wire の last-seen update は `VarInt offset + fixed 20-bit acknowledged + byte checksum`
である。26.2 official class には、Pumpkin の `message_count` という名前の独立した
inbound signed-message index はない。Pumpkin の
`SChatCommandSigned::message_count` はこの wire の `Update.offset` として扱う値であり、
署名 chain の `SignedMessageLink.index` ではない。

`ArgumentSignatures` は次を固定する。

- argument signature count の decode 上限は `8` (`MAX_ARGUMENT_COUNT`)
- entry name は `readUtf(16)` / `writeUtf(..., 16)`
- `MessageSignature` は常に `256` bytes (`MessageSignature.BYTES`)
- entry は `name` と raw signature bytes だけを持つ
- name は signed body の bytes に入る値ではなく、parsed signable argument と entry を
  対応付ける key である

`ArgumentSignatures.signCommand(SignableCommand, Signer)` は
`SignableCommand.arguments()` の各 argument に対し、`Argument.value()` だけを signer
へ渡す。返る entry は `Argument.name()` とその signature である。signature payload
に argument name や typed value を別途連結する処理は公式 bytecode にない。

### 3. parse result から signable args を決める公式規則

公式 `ServerGamePacketListenerImpl.performSignedChatCommand` は、command text を
player の command source で `parseCommand` し、得られた Brigadier `ParseResults` から
`SignableCommand.of(ParseResults)` を生成する。

`SignableCommand.of` / `ArgumentVisitor` の規則は以下である。

1. parsed command path の `ArgumentCommandNode` と `ParsedArgument` を巡回する。
2. argument node の `ArgumentType` が `net.minecraft.commands.arguments.SignedArgument`
   を実装するものだけを採用する。
3. `ParsedArgument.getRange()` で command original string の raw substring を取り、
   `SignableCommand.Argument.value` にする。
4. name は node の `getName()`、つまり command tree 上の argument name にする。
5. typed parse result、正規化後の UUID/selector、再シリアライズした数値などを signature
   input に置き換えない。
6. `hasSignableArguments(ParseResults)` は、この抽出 list が空でないかだけを返す。

したがって、署名対象の content は `/command` 全体ではなく、各 signable argument の
raw text である。例えば parser が `target` と `message` を signable とした場合、
packet の `argument_signatures` はこの二つの name/value を別々に対応付け、各 signature
を同じ packet timestamp、salt、last-seen と別々の chain link に対して検証する。

公式 signed-command verification の body は、各 entry について次の構造になる。

```text
SignedMessageLink(current chain link)
SignedMessageBody(
    content = parsed signable argument raw substring,
    timeStamp = packet.timeStamp,
    salt = packet.salt,
    lastSeen = reconstructed packet last-seen
)
```

その body を `SignedMessageChain.Decoder.unpack(entry.signature, body)` に渡す。通常の
chat message の body helper は field order の参考にはなるが、command 全体を content に
したり、argument name を content に足したりして流用してはいけない。

### 4. message index / timestamp / salt / last-seen の関係

公式 `ServerGamePacketListenerImpl` には次の state が分離して存在する。

- `signedMessageDecoder`: current player/session の inbound signed chain decoder
- decoder 内の `SignedMessageChain.nextLink`: sender UUID、session UUID、current index
- decoder 内の `lastTimeStamp`: 前回 accepted signed body の timestamp
- `lastSeenMessages`: 20-message acknowledgement window
- `nextChatIndex`: recipient へ送る outbound `ClientboundPlayerChatPacket` 用 index

`nextChatIndex` は inbound signed command の message index ではない。Pumpkin の
`ChatSession.messages_sent`、world broadcast count、packet の `message_count` も
`SignedMessageLink.index` の代用品にしてはいけない。

`SignedMessageChain$Decoder.unpack` の静的に確認できる順序は次である。

1. signature が null なら secure profile decoder では `MISSING_PROFILE_KEY`。
2. profile key expiry を確認する。
3. `body.timeStamp` が chain の last timestamp より古ければ `OUT_OF_ORDER_CHAT` とし、
   `setChainBroken()` する。
4. `PlayerChatMessage(link, signature, body, ...)` を作って public-key signature を検証する。
5. invalid signature なら `setChainBroken()` して `INVALID_SIGNATURE`。
6. success 後に current link を `advance()` する。argument signature が複数あれば、
   それぞれが順番に link index を一つ消費する。

よって、signed command packet に wire 上の「command message index」はないが、
argument signature ごとの verification は通常 chat と同じ inbound chain を進める。
valid signed command の次に chat message を検証する場合、次の expected index は command
内で検証に成功した argument 数だけ増えていなければならない。

timestamp は `Instant` として body に渡され、salt は `long` として body に渡される。
公式 26.2 の chat canonical helper と同様、署名 bytes へ入る timestamp は
`Instant.epochSecond` であり、wire millisecond をそのまま int64 に書く設計にしない。
last-seen は raw 3-byte bitsetではなく、`LastSeenMessages.Update` を tracked window に
適用して得た順序付き signature list である。同じ packet の last-seen list が各 argument
body に渡される。

公式 command handler の入口は `handleSignedChatCommand` →
`unpackAndApplyLastSeen(update)` → `tryHandleChat(command, true, runnable)` である。
ack update が失敗したときは runnable は呼ばれず、command は実行されない。Pumpkin の
signed-command 分岐はこの入口を持たず、ack を signed command の auth と結合していない。

### 5. parse、argument mismatch、permission、unsigned variant

`performSignedChatCommand` の公式処理は次である。

- packet command を player command source で parse する。
- parsed result から signable args を抽出する。
- `argument_signatures` が非空なら、packet entry の順序で各 entry name が parsed signable
  list に存在するか確認し、signature をその raw value に対して検証する。name は対応付け
  keyであり、chain index の消費順は実際に検証した entry 順である。
- すべての parsed signable arg が entry に対応しているか確認する。余分な unknown name
  または不足する expected name は `SignedMessageChain.DecodeException` とし、unknown
  name の場合は decoder を chain-broken にする。
- mismatch / invalid signature では `Commands.performCommand` に進まない。
- success 後、signing context を command source へ付けて `Commands.performCommand` を
  呼ぶ。

permission は署名の代替ではない。parse は player source の requirements で行われ、
execution も同じ player identity/permission を保持する。valid argument signature が
あっても `/op` 等の permission を与えない。無権限 player の valid signed command と、
permission failure の test を別々に検証する。

公式 unsigned の境界は signed command と混ぜない。

- 通常の `ServerboundChatCommandPacket` は parse 後、`enforceSecureProfile=true` かつ
  `SignableCommand.hasSignableArguments(parseResults)=true` のときだけ unsigned command
  rejection (`INVALID_COMMAND_SIGNATURE`) の対象になる。
- signable args が **ない command** は、secure profile enforcement が有効でも、この
  signable-argument guard だけを理由に拒否してはいけない。
- `enforceSecureProfile=false` / offline policy では ordinary unsigned command は unsigned
  command として合法であり、secure identity の証明とは見なさない。
- signed-command の `argument_signatures` が空で、parsed signable args も空なら、署名
  argument の verification を要求する理由はない。command 自体の packet/ack/parse/
  permission policy は別に満たす必要がある。
- parsed signable args がある secure session で signature entry を空にした場合は、公式
  `collectUnsignedArguments` が `SignedMessageBody.unsigned(value)` を作るものの、secure
  `signedMessageDecoder.unpack(null, body)` は missing profile key として失敗する。これを
  「署名不要な command」と誤って許可しない。
- unsigned variant は `SignedMessageBody::unsigned` / `PlayerChatMessage::unsigned` として
 扱う data model であり、normal chat の RSA body verifierへ通すものでも、signed command
  を通常 `SChatCommand` へ降格する理由でもない。

### 6. 既存 Rust parser にあるもの / 足りないもの

#### あるもの

`crates/pumpkin-protocol/src/java/server/play/chat_command_signed.rs::SChatCommandSigned`
は次の wire data を保持している。

- `command`
- `timestamp`
- `salt`
- `argument_signatures: Vec<ArgumentSignature { name, signature }>`
- `message_count`（last-seen offset 相当）
- `acknowledged: &[u8]`（固定 3 bytes）
- `checksum`

name の 16-byte bound、signature の 256-byte read、negative count の rejection、wire
remaining-byte fit guard は存在する。`crates/pumpkin-command/src/node/dispatcher.rs`
には `CommandDispatcher::parse_input` / `parse` と `ParsingResult` があり、
`crates/pumpkin-command/src/context/command_context.rs::ParsedArgument` は typed result と
`StringRange { start, end }` を保持する。`StringRange::substring_slice` により、parse
result の元 command string から raw argument text を取り出す材料はある。

`crates/pumpkin-command/src/node/tree.rs::Tree::can_use` と
`CommandDispatcher::parse_nodes` は requirements を parse 中に評価するため、既存の
permission gate は利用できる。`crates/pumpkin/src/net/java/play/chat_command.rs` は通常
command の event、dispatcher、permission execution を既に一箇所へ集約している。

#### 足りないもの

1. **公式 count 上限**: `SChatCommandSigned::read` は remaining bytes に収まるかだけを
   見ており、公式 `ArgumentSignatures.MAX_ARGUMENT_COUNT=8` を semantic bound として
   固定していない。9 entries が wire fit する場合を拒否する証拠がない。
2. **signable marker**: Pumpkin の `AnyArgumentType` / `ArgumentType` に公式の
   `SignedArgument` 相当 marker がない。argument node metadata にも signable flag がない。
   `grep` で `SignedArgument` の実装は確認できなかった。
3. **parse result extraction**: typed `ParsedArgument` と raw range はあるが、どの argument
   node が signable かを区別できない。argument name のみから signable と推測してはいけない。
4. **command-specific signature body**: current `net/chat/signature.rs` は
   `SignedMessageBody` 全体を chat content として canonicalize する helper であり、
   signable argument value ごとの body/link sequence を持たない。
5. **inbound command chain**: `ChatSession` / sidecar state の signed chat chain と
   `SChatCommandSigned` が接続していない。特に command 内の N argument signatures が N 個の
   chain index を消費することを current dispatch は表現しない。
6. **signed-command ack transaction**: current signed branch は ack/offset/checksum を
   handler に渡さない。`handle_chat_ack` の offset-only path も signed command body auth
   とは別である。
7. **no-fallback dispatch**: malformed signed decode を ordinary `SChatCommand::read` へ
   fallback させない dedicated path がない。
8. **signed execution context**: `PlayerCommandSendEvent` は command text しか持たず、
   argument signature context を持たない。ただし permission check 自体は現 dispatcher
   の player source を再利用すべきで、署名成功を permission bypass に変えてはいけない。

### 7. 既存 fixture の独立性と今回の扱い

`tools/compat-26_2/chat-fixtures/` は既存 fixture set として独立している。本調査では
変更していない。

- `signed-command.json` は wire/parser/policy の contract であり、argument canonicalization
  unknown を `deferred` として保持していた。今回の JAR static evidence により、raw parsed
  substring + packet timestamp + salt + reconstructed last-seen + chain link という構造は
  `SignableCommand` / `collectSignedArguments` まで確定した。ただし fixture の
  test-only signature label を Mojang signature として昇格させない。
- `canonical-empty-last-seen.json` / `signature.rs` の RSA fixture は normal chat body の
  独立 known-answer であり、signed command argument の known-answer ではない。
- `chain-state.json` と `last-seen-ack.json` は inbound state/ack の independent inputs と
 して再利用できるが、signed command は一 packet = 一 chain index ではないため、argument
  signature 数を chain event 数として追加する必要がある。
- positive fixture は implementation が自分で生成した signature を自分で検証するだけに
 しない。外部 oracle の固定 public key/signature、または明確な licensed upstream/official
  bytecode との layout 比較を使う。
- negative は valid fixture を一箇所だけ改変する。unknown argument name、missing expected
  argument、duplicate/mismatched set、content raw substring mutation、timestamp、salt,
  last-seen、link index/session、signature/replay を別 case とする。invalid signatureを
  Rust signer で都合よく再生成しない。

### 8. 必須 acceptance / rejection matrix

| case | expected result | verification method |
|---|---|---|
| valid signed command, no signable args, valid ack, allowed permission | execute once; no argument signature required | parse result signable list is empty; ack preview succeeds; ordinary dispatcher permission/execution counter is 1 |
| valid signed command with one signable arg | verify raw argument value, timestamp, salt, reconstructed last-seen and current link; then execute | external known-answer signature; assert next chain index `+1` |
| valid signed command with N signable args | verify N independent entries in packet-entry order with parsed-name mapping; require the parsed set to be complete; consume N chain links; then execute | assert each body uses same packet timestamp/salt/last-seen and indexes `i..i+N-1` in verification-entry order |
| unknown signature name | reject; no execute; chain broken/fail-closed | mutate only entry name; assert dispatcher and command event are untouched |
| missing expected signature entry | reject in secure signed path; no execute | omit one parsed signable arg entry; assert no permission/executor side effect |
| argument raw text changed after signing | reject | preserve name/timestamp/salt/last-seen, mutate only `StringRange` source bytes |
| timestamp/salt/last-seen/link session/index changed | reject; no chain advance | mutate one body field at a time; assert expected index/timestamp remain unchanged or chain is sticky-broken per policy |
| replay / wrong next chain index | reject; no command execution | resend valid signature with old/current link; assert `index_not_next` and no fallback |
| invalid ACK offset/bit/checksum/unknown entry | reject before command execution | preview `LastSeenMessages.Update`; snapshot validator before/after; assert no command event/executor |
| malformed signed packet | reject signed packet; never call `SChatCommand::read` fallback | malformed count/entry/trailing input; spy on dispatcher/event |
| ordinary unsigned command with no signable args | legal under official boundary | `SignableArguments.is_empty`; secure-profile guard must not reject solely for unsignedness |
| offline / reports-disabled ordinary unsigned command | legal unsigned execution policy; no secure attribution claim | `allow_chat_reports=false` / offline policy fixture, separate from secure signature test |
| valid signature but insufficient permission (`/op`, etc.) | reject/command error from normal permission path; no privilege gain | execute with player command source and permission level unchanged |
| normal chat body sent as signed command argument | not accepted as a substitute | command-specific body content is argument raw value; never pass whole command to `net/chat/signature.rs` |

## Migration / Investigation Notes

### Recommended next 70-turn implementation: one responsibility only

次の実装単位は、暗号・chat broadcast・permission redesign を同時に行わず、まず
**command parser が official の signable argument set と raw value を losslessly 出せる
ようにする一責務**へ絞る。

対象は以下だけにする。

1. `pumpkin-command` の argument node metadata/builder に opt-in の `signable` 属性を追加する。
2. `ParsingResult` から、parse 成功した順序で
   `(argument name, raw StringRange value, node identity)` を抽出する pure helper を追加する。
3. `StringRange` の元 command string slice を signature input に使い、typed parse result
   を再シリアライズしない。
4. `signable list empty` を first-class result とし、commands without signable args を
   legitimate case として test する。
5. same parser/source の permission rejection、malformed parse、unknown argument、raw
   Unicode/quote/greedy range の unit test だけを追加する。

この単位では `net/java/mod.rs` の fallback、RSA verifier、last-seen state、world broadcast、
`SChatCommandSigned` の execution を変更しない。これにより parser classification と
signed-command cryptographic validation を別責務として review できる。

その次の小単位で初めて `SChatCommandSigned` dispatch を dedicated handler へ移す。
その変更の不変条件は次である。

- signed decode error は `SChatCommand::read` へ fallback しない。
- full packet metadata を dedicated validator へ渡す。
- signable list が空の valid command は ordinary permission path で実行できる。
- signable list が非空の secure command は全 entry/body/link/ack/chain checks 成功後だけ
  ordinary dispatcher へ渡す。
- signed validation failure は `PlayerCommandSendEvent` と executor の前に止める。
- offline unsigned ordinary command の合法性は secure signed path へ混ぜない。

### 変更してはいけない境界

- normal `SChatMessage` canonical helper を command whole-text signature に流用しない。
- `PlayerChatMessage::unsigned` を signed-command failure の fallback representation にしない。
- `ChatSession.messages_sent`、outbound `nextChatIndex`、`message_count`/ack offset を
  signed inbound link index と混同しない。
- signature が valid でも permission dispatcher を省略しない。
- `allow_chat_reports=false`、offline unsigned、commands without signable args を「署名が
 ないので常に reject」へ単純化しない。
- argument signature の name を署名 bytes に足す、typed parse result を stringify する、
  `/command` 全文を content にする、という推測実装をしない。
