# 26.2 chat lifecycle runtime duplicate-login / bounded-owner validation

## Findings

- 対象は Java Edition `26.2` / protocol `776`。実行条件は Rust `1.97.1`、`CARGO_TARGET_DIR=C:/Temp/pumpkin-target-26_2-next`、`CARGO_INCREMENTAL=0`、dev debug `0`、jobs `2`、`--locked`。
- `13eeb3e42` の UUID-keyed `retired_generations` tombstone 設計は、接続ごとに履歴を保持するため memory bounded ではない。今回の最小修正では tombstone map を削除し、`Player` ごとの `ChatOwnerToken` (`Arc` owner + `AtomicBool active`) に置き換えた。
- `InboundChatState` は owner の `Weak<ChatOwnerToken>` だけを保持する。disconnect または duplicate-login supersession で owner を retire すると、遅延 session update / verify は state store に再登録・commitできない。replacement は別 token を持つため、古い token の退役情報を UUID ごとに永久保持しない。
- `Server::add_player` の実 publish 成功後に同 UUID の既存 `Player` token を retire する。したがって delayed old session update が validation の await 後に lifecycle lock を取得しても拒否される。
- `World::remove_player` は引き続き `Arc::ptr_eq` で exact Player を除去する。disconnect は token retire → current `ChatSession.session_id` 読み出し → matching state clear の順で行う。dimension transfer は retire/clear せず、chain を保持する。
- same-UUID old disconnect は replacement が全 server worlds のいずれかに残っていれば `EntityTracker` の player observer cleanup、tab-list remove、`CachedStatus` decrement を replacement に適用しない。

## Migration / Investigation Notes

### Runtime fixture and production conditions

- fixture は `Server::new`、一時 world、`Server::add_player`、`World::add_player`、`World::remove_player`、`EntityTracker`、`Server::remove_player`、`CachedStatus` を実際に通る。
- transport は loopback TCP pair から作った `JavaClient::from_pending` を test-only client として使用。packet harness、外部認証、Mojang key fetch、vanilla client は使用しない。`allow_chat_reports=false` のため fixture は session certificate/RSA validationを主張せず、production state boundary (`reset_inbound_state` / `verify_and_commit`) と real ownership lifecycle を検証する。
- 同じ `GameProfile.id` の old/new `Player` を同じ実 `Server` に順番に publish。new publish 後に old token が inactive になることを確認。
- old の delayed session update 相当 (`reset_inbound_state` with old token) は `false`。old の delayed secure verify (`SChatMessage` with 256-byte signature placeholder) は RSA 到達前に `LifecycleMismatch`。new state の session UUID は保持される。
- new を実 world list から `DimensionTransfer` reason で detach し、Nether world list に再 publish。transfer 後の same-session reset は `true` で、state chain owner/session が維持される。
- old の disconnect は exact old Arc だけを除去し、Nether にいる new Arc を残す。`EntityTracker` old entity entry は除去され、`CachedStatus.players.online` は `1` のまま。new disconnect 後は state が消え、online は `0`。
- 同一 UUID の add/install/disconnect を **32 cycles** 繰り返し、各 cycle 後に state store に当該 UUID が存在しないことを確認。永久 tombstone の件数増加は実装上存在しない。memory bounded の上限は「active Player/state と live async owner graph」に限定され、過去接続数に比例しない。

### Global store / lock / await audit

- global lifetime は `OnceLock<Mutex<InboundStateStore>>` の process lifetime。ただし store は active/current `states` のみを保持し、retired owner history map は持たない。
- owner token は `Player` が強く保持し、state は `Weak` のみを保持する。Player が drop されると state が accidental に残っても owner weak は upgrade できず、次の同 UUID install/lookup で stale state を置換できる。通常 disconnect path は先に明示 clear する。
- lock order は secure-message path で `Player::chat_lifecycle` → `ChatSession` → global inbound state → `signature_cache`。session update は lifecycle lock 下で global state install の後に ChatSession を更新するが、global guard は function return 時に解放されるため global と ChatSession を同時保持しない。disconnect は lifecycle → ChatSession read → global clear で、global guard 下に await はない。
- `verify_and_commit` は sidecar mutex を ack preview と RSA verify の間保持するが、その区間に `.await` はない。これは同一 inbound index の二重 commit 防止の既存 transactional contract。`handle_chat_session_update` の async validation は lifecycle lock の取得前に完了する。session update は global lockを解放してから ChatSession mutex を取るため、global → ChatSession の同時保持を作らない。
- `Server::retire_duplicate_chat_owners` と `World::remove_player` の lifecycle guard 下にも await はない。world RCU/ArcSwap guards は packet broadcast や event await の前に解放される。
- 注意点: RSA verify 中の global mutex hold は latency/blocking の既存 trade-off。今回の bounded-owner修正では lock 粒度を広げていない。clippy/performance review では別論点として扱う。
