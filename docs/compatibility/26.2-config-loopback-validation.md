### Harness changes and unit evidence

`tools/compat-26_2/protocol776_harness.py` に次を追加した。

- `ConfigurationRegressionTracker`: direction、packet id、framed length、payload bytes、compression、state event を記録。
- `parse_disconnect_reason`: disconnect の String field と trailing bytes を厳密 decode。
- `_login_to_configuration` / `run_configuration_regression`: 共通 login prefix の後、独立 TCP connection ごとに deterministic order を制御。
- `early_finish_ack`: server の `select_known_packs` packet を観測してから、server の `finish_configuration` 前に空の Finish Configuration ack を送る。server の request 前に競合 packet を投げる race ではない。
- `duplicate_known_packs`: valid な空 Known Packs を送り、server response の実 packet を1つ観測してから duplicate を送る。最初の request と duplicate の順序を socket read/write で確定する。
- first chunk の block-entity は NBT の wire envelope だけを bounded skip する。NBT の意味、registry、block entity semantics は decode/pass claim しない。
- synthetic client の Client Information view distance は `2` に固定し、world/chunk生成量を bounded にした。packet frame/data upper bounds は既存の `2 MiB` / `8 MiB` / VarInt 5-byte checksを維持した。

### Ordered negative case 1: Finish Configuration before server Finish

独立 connection `compat_early` で、server の clientbound `select_known_packs` (`packet_id=14`) を受信した後、clientbound `finish_configuration` (`packet_id=3`) がまだ観測されていない状態で、serverbound empty Finish Configuration (`payload_bytes=0`) を送った。

観測要点:

```text
clientbound select_known_packs: packet_id=14, framed_length=23, payload_bytes=21
serverbound early_finish_configuration: body_is_empty=true, payload_bytes=0
clientbound disconnect: packet_id=2, framed_length=111, payload_bytes=109
```

- harness exit code: `0`
- `server_disconnect=true`
- exact disconnect reason: `Error while reading incoming packet Received finish configuration acknowledgment before finish configuration`
- result: `expected_configuration_disconnect`
- server `finish_configuration` は early ack 前に観測されていない。

### Ordered negative case 2: duplicate Known Packs

独立 connection `compat_duplicate` で、server の Known Packs request を観測し、空の valid Known Packs (`payload_bytes=1`, count `0`) を送った。その後、server の Registry Data response (`packet_id=7`, compressed, first response `framed_length=16017`, decoded payload `169866` bytes) を1 frame観測してから、同じ空 Known Packsを duplicate送信した。

観測要点:

```text
clientbound select_known_packs: packet_id=14
serverbound known_packs: payload_bytes=1, body_is_empty=false
clientbound registry response: packet_id=7, compressed=true
serverbound duplicate_known_packs: payload_bytes=1
clientbound finish_configuration: packet_id=3, payload_bytes=0
clientbound disconnect: packet_id=2, payload_bytes=90
```

server は既に queue 済みの Registry Data / Finish packet を送ることがあるため、duplicate 後に `finish_configuration` frame が観測されたことだけでは正常遷移と判定していない。raw disconnect field を読み、最終的な disconnect を期待値と照合した。

- harness exit code: `0`
- `server_disconnect=true`
- exact disconnect reason: `Error while reading incoming packet Received known packs without a pending server request`
- result: `expected_configuration_disconnect`
- duplicate は server response の観測後に送っており、初期 request と競合する race 投入ではない。

- shutdown action: `redirected-stdin-stop`

## Migration / Investigation Notes

- 既存 docs の normal flow は `Login Success → Login Acknowledged → Client Information → Known Packs request/reply → Registry/Tags/Finish → empty Finish ack → Play`。この順を strict control で実 packet 観測した。
- early Finish は Known Packs request後かつ server Finish前に送った。Known Packs duplicate は valid response後かつ duplicateを送る前に server responseを readした。
- `configuration_packets=35` は server が送る configuration frames の数であり、Registry Data の値意味論や vanilla acceptanceを意味しない。
- duplicate case で `packet_id=7` payload を opaque として記録したが、Registry DataのNBT値・Known Packs tupleの意味・unknown payloadの意味は検証していない。
- `MAX_PACKET_SIZE=2,097,152`、`MAX_PACKET_DATA_SIZE=8,388,608`、VarInt 5 byte bound、compression threshold `256` の既存制約を維持した。実観測最大 decoded configuration payload は `169,866` bytesで上限内。
- configuration fix の Rust pure testsは既存 evidenceとして4件すべて exit `0`。本担当では Cargoを実行せず、harness全unit testsを最終状態で19件 exit `0`確認した。
- binaryは source/config fix 後の既存 build evidenceに基づいて選択した。ただし binary内部のsource commit埋込みや完全なreproducible buildは未確認。

## Unconfirmed / Limitations

- graceful server shutdown の exit code `0` は未達。`0xC00000FD` stack overflowの根因特定・修正は未実施。
- vanilla Java 26.2 clientの起動・接続・画面・client-side decodeは未実施。
- registry data、update tags、Known Packs tuple/subset semantics、block-entity NBT semantics、chunk section palette、resource pack、chat signingは未確認。
- online-mode、encryption、Bedrock、telemetry外部送信、公式 launcher、EULA代理同意は未実施。
- unsolicited Known Packsをserver requestより前に送る、というケースは packet orderをraceなしに保証できないため実施・主張していない。今回の順序外検査は early Finish と duplicate Known Packs に限定した。
- first chunkのNBTは envelopeをskipしただけで、unknown payloadの意味を検証していない。

## Recommended Next Steps

1. `0xC00000FD` が `Starting worlds` の shutdown saveで再現する原因を、world/shutdown担当の専用調査として切り出す。今回の configuration pass判定と混ぜない。
2. graceful shutdown修正後、同じ binary/source/hash/run config/evidence contractで strict normal、early Finish、duplicate Known Packsを再実行し、server exit `0`、`Completed save!`、`The server has stopped.`を確認する。
3. 次段でKnown Packs tuple/subsetのsemantic decoderを別担当範囲として追加する。opaque packet観測をsemantic passへ昇格させない。
4. vanilla client validationは、既存のlegal/EULA gateとJava 25/client artifact条件を満たした別試験で実施する。
