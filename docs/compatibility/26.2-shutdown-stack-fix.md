# 26.2 Windows graceful-shutdown stack overflow fix

- Target: Java Edition `26.2`, protocol `776`
- Source baseline: `ba266a5e3` + `9dd4c6137`
- Original binary: `C:/Temp/pumpkin-target-26_2-next/debug/pumpkin.exe`, SHA-256 `c9101d43c409a0b303a9ea60c8b3351338971c0f84eeddcf92edd6b799878b43`, 233,593,856 bytes
- Fixed binary used for validation: SHA-256 `115b2f48d55cda22a54936723cf829a8a30a6c4620a003c70c08c1de9b5d4e8d`, 233,558,016 bytes

## Findings

The original failure was a real Windows process failure, not a hidden or forced stop:

- `server.stderr.log`: `thread 'main' (...) has overflowed its stack`
- process exit: `3221225725` / `0xC00000FD`
- port closed and the server process was not left running
- status/strict login passed, but graceful lifecycle exit `0` did not

A fresh isolated no-client idle run did **not** reproduce the failure: exit `0`.
A fresh isolated login -> disconnect -> stdin `stop` run reproduced it: harness exit `0`, then server exit `3221225725`. The strict peer observed protocol `776`, `configuration_packets=35`, `known_pack_reply=true`, `position_syncs=1`, `teleport_confirms_sent=[1]`, and `result=first_playable_strict`.

Instrumentation separated the suspected causes:

- the chunk/DAG cancellation path is iterative (`DAG::fast_drop_node`, `drop_edge_chain`, `terminal_cancel_nodes`); no recursive DAG drop was reached;
- the world shutdown entity snapshot contained roughly 36--45 live entities after a player run, while idle contained none;
- the player disconnect cleanup had already saved/evicted many entity chunks, but the live `World::entities` index could still retain entities whose entity chunk was no longer resident;
- `World::shutdown -> save_entity` then called `Level::get_entity_chunk`, which re-entered the asynchronous entity-saver load path for those evicted chunks during shutdown. The crash was reproducibly reached after a live entity save, while the no-client path never entered this path;
- increasing a Windows thread stack was not used. The evidence points to shutdown-time re-entry/race through the entity-chunk saver, not a finite legitimate frame requirement or an intentional infinite recursion in entity NBT serialization.

## Fix

`crates/pumpkin/src/world/mod.rs` now makes shutdown entity persistence use only a resident entity chunk. Entity chunks are written before eviction; a live entity whose chunk is already evicted is therefore already persisted. Shutdown no longer reloads that chunk through `get_entity_chunk` while the entity saver and level shutdown are being drained. It emits a warning identifying the entity/chunk instead of entering the recursive async load path.

After entity serialization, shutdown also clears the live entity index, entity tracker, and spawn-state index before tearing down the level. This is a bounded cleanup of runtime ownership references and prevents entity/world/tracker retention during final destruction; it does not remove the serialized NBT from the owning chunk.

`crates/pumpkin/src/world/entity_tracker.rs` adds `EntityTracker::clear`, used only by world shutdown.

## Limits

The synthetic protocol peer is not a vanilla-client acceptance test. The fix validates the requested local lifecycle and shutdown path; it does not claim full world/entity semantic compatibility. The warning path should be followed up by a separate entity-index/eviction consistency investigation so that a live entity is never retained after its chunk has been evicted, even though shutdown now preserves the already-written chunk data and exits cleanly.
