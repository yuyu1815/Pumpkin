# 26.2 Fattack / interact 残 feature metadata 契約調査

対象は Java Edition `26.2`、protocol `776`、world data version `4903`。この調査で書き込むのは本ファイルだけで、Rust source、generated source、assets、datapack、JAR、world、log、stage/commit は変更しない。

## Findings

### 結論

- 公式 26.2 の `handleAttack` / `handleInteract` は、`ItemStack.isItemEnabled(level.enabledFeatures())` を副作用の前に要求する。攻撃だけはさらに `cannotAttackWithItem(mainHand, 5)` と `PIERCING_WEAPON` 拒否がある。
- 現行 Pumpkin は `can_attack_with_item` と通常攻撃の `PiercingWeapon` 拒否を既に `Player::attack` 前へ置いている。しかし `Item` に required feature metadata がなく、`ItemStack.is_item_enabled` 相当は未実装である。`interact.rs` もこの欠落を明記したまま標準生成 item を通している。
- **「feature metadata がないから全 item を安全に許可できる」または「不足分を全 item 拒否で埋める」はどちらも契約にならない。** 26.2 built-in itemについては、確認できた公式登録 bytecode と local item dataから、通常 itemは `minecraft:vanilla` だけを要求するのが根拠付きの結論である。一方、custom registry / 将来の experimental item を安全に扱う表現が現行 modelにない。
- 公式 26.2 の feature universe は `vanilla`、`trade_rebalance`、`redstone_experiments`、`minecart_improvements` の4つで、`bundle` は存在しない。現行 `DatapackManager::resolve_enabled_features` とその test は `minecraft:bundle` を追加しており、これは別の小さな feature-config 修正候補である。bundle itemをexperimental itemと推測して拒否してはならない。
- したがって最小実装は、全 item data の再生成でも全 item 拒否でもなく、(1) 公式 feature universeを型付きで扱う、(2) generated `Item` に明示的 required feature setを追加する、(3) `ItemStack` と attack/interact handlerでその setを read-only照合する、の3点である。26.2 built-in itemの現行入力は default `minecraft:vanilla` として保持し、非vanilla overrideが一次資料で確認された itemだけを小さい明示 manifestで追加する。

### 公式 26.2 の一次 code 契約

既存の repository 外 artifact `C:/Temp/server-26.2.jar` と保存済み `C:/Temp/javap-ServerGamePacketListenerImpl.txt`、`C:/Temp/javap-Player.txt` を read-only で照合した。

#### `handleAttack`

`ServerGamePacketListenerImpl.handleAttack` の実順序は次のとおり。

1. `hasClientLoaded()` と attacker の `isSpectator()` を確認。
2. 同じ `ServerLevel` の `getEntityOrPart(entityId)` で target を解決。
3. target が無い、または target の `blockPosition()` が world border 外なら return。
4. main hand item と target AABBを取り、`isWithinAttackRange(item, AABB, 3.0D)` を確認。item `AttackRange` があれば min/max/margin、無ければ player の interaction-range attributeを使う。公式の attack range outer boundary は inclusive。
5. main hand `PIERCING_WEAPON` component があれば return。これは通常の `Player.attack` 経路を使わせず、専用 piercing weapon 経路に任せるための拒否である。
6. `ItemEntity`、`ExperienceOrb`、自分自身、attackableでない arrow は invalid entity として disconnect/return。
7. `mainHand.isItemEnabled(level.enabledFeatures())` を確認。
8. `player.cannotAttackWithItem(mainHand, 5)` を確認。
9. ここまで通った場合だけ `player.attack(target)`。

保存済み bytecode の要点は `PIERCING_WEAPON` が bytecode offset `108`、`isItemEnabled` が `193`、`cannotAttackWithItem` が `207`、`attack` が `221` に現れること、また target border/range に `3.0D` が使われることである。

#### `handleInteract`

`ServerGamePacketListenerImpl.handleInteract` は次の契約である。

1. `hasClientLoaded()` を確認。
2. 同じ `ServerLevel` の `getEntityOrPart(entityId)` で target を解決。
3. target が存在する場合、world border内を確認。
4. target AABBに対して `isWithinEntityInteractionRange(AABB, 3.0D)` を確認。これは `entityInteractionRange + 3.0` の **strict `<`**。
5. packetで指定された hand の itemを取得し、その itemだけに `isItemEnabled(level.enabledFeatures())` を適用。
6. `interactOn(target, hand, location)` に進む。

`handleInteract` は `cannotAttackWithItem` を呼ばず、`PIERCING_WEAPON` を理由に entity interaction 全体を拒否しない。公式 packet handlerには block line-of-sight raycastもないため、LOSをこの feature契約へ追加しない。

#### `isItemEnabled` と required feature

公式 `ItemStack.isItemEnabled(FeatureFlagSet)` bytecodeは、empty stackなら `true`、non-emptyなら `getItem().isEnabled(enabled)` の結果を返す。公式 `FeatureElement.isEnabled` は次の判定である。

```text
item.requiredFeatures().isSubsetOf(level.enabledFeatures())
```

公式 `Item` は `requiredFeatures` fieldを保持し、`Item.Properties` の defaultは `FeatureFlags.VANILLA_SET`。`Item.Properties.requiredFeatures(...)` で明示的な flag setだけを上書きできる。つまり component presence、item name、recipe、tagから required featureを再構成する仕様ではない。

#### `cannotAttackWithItem`

保存済み `javap-Player.txt` の `Player.cannotAttackWithItem(ItemStack, int)` は次の式である。

```text
minimum = item.getOrDefault(MINIMUM_ATTACK_CHARGE, 0.0f)
strength = (attackStrengthTicker + offset) / getCurrentItemAttackStrengthDelay()
reject iff minimum > 0.0f && strength < minimum
```

packet handlerの offsetは `5`。`getCurrentItemAttackStrengthDelay()` は `20.0 / player ATTACK_SPEED attribute`（公式 bytecode上は `1.0 / attribute * 20.0`）である。従って、通常 itemに `minecraft:minimum_attack_charge` が無ければこの guardは要求なし、componentが `1.0` の spear等では tickerと現在の attack speedから thresholdを満たすまで通常 attackを拒否する。拒否は item、ticker、Used statistic、event、damageを更新してはならない。

公式標準 dataでは minimum charge は `minecraft:wooden_spear`、`stone_spear`、`copper_spear`、`iron_spear`、`golden_spear`、`diamond_spear`、`netherite_spear` に存在し、各値は `1.0`。同じ7 itemが `minecraft:piercing_weapon` も持つ。これは **experimental feature itemの証拠ではなく、通常 vanilla itemの combat component** である。

### 公式 feature universe と standard item の判定

公式 `net.minecraft.world.flag.FeatureFlags` の `javap -p/-c` 結果は次の4 flagだけである。

| 公式 flag | defaultで有効か | 26.2 item metadata調査での扱い |
|---|---:|---|
| `minecraft:vanilla` | yes (`VANILLA_SET`, `DEFAULT_FLAGS`) | 全 built-in itemの default required set |
| `minecraft:trade_rebalance` | no | optional experimental flag。item名から要求を推測しない |
| `minecraft:redstone_experiments` | no | optional experimental flag。item名から要求を推測しない |
| `minecraft:minecart_improvements` | no | optional experimental flag。item名から要求を推測しない |

`FeatureFlags` に `BUNDLE` / `minecraft:bundle` は無い。公式 `Items` の static registration bytecodeでは `requiredFeatures` 呼び出しは block itemを作る共通 `registerBlock` helperから blockの required setをコピーする箇所だけで、直接 itemを experimental flagへ割り当てる呼び出しは確認できない。公式 `Blocks` の保存済み bytecodeには `requiredFeatures` 呼び出しが無かった。

このため、今回確認した 26.2 built-in itemについては「全標準 itemは vanilla setで許可される」という限定結論を採る。

- local `assets/items.json`: 1,537 item entries。
- `minecraft:bundle`: item id `1065`、generated `Item::BUNDLE` として存在。
- `minecraft:minecart`: item id `882`、generated `Item::MINECART` として存在。
- `minecraft:wooden_spear`: item id `1326`、generated `Item::WOODEN_SPEAR` として存在。
- `assets/datapacks/26_2/data/minecraft/recipe/bundle.json` と、bundle 17色分を含む `17` recipe files、`tags/item/bundles.json` が存在する。

ただしこれは「将来/custom itemも全て安全」という結論ではない。公式 Item API自体が required feature setを持ち、server enabled feature setとの subset 判定を実装しているため、non-vanilla itemの表現能力は必要である。現 repository内にその metadataを持つ custom/generated Item entryは見つからなかったため、disabled-feature fixtureは現行 vanilla itemを偽って使わず、明示的な synthetic metadata fixtureとして定義する。

### 現行 F 実装との境界

- `attack.rs::can_attack_with_item` は公式の minimum charge条件を read-onlyでミラーし、`can_use_ordinary_attack_item` は `PiercingWeaponImpl` を通常 `Player::attack`から除外する。
- `interact.rs` は packet handを main/off handへ検証し、選択 handの itemを使う。ただし現コードコメントどおり Item modelに required feature metadataがないため、feature guardは未完である。
- 現行 `server.get_enabled_features` / `is_feature_enabled` が存在することは、`ItemStack.isItemEnabled` が実装済みであることを意味しない。feature name listとitem required setの結合が欠けている。
- 現在の built-in vanilla itemについて許可結果が公式と一致し得ることと、unknown/custom experimental itemを安全に通してよいことを同一視しない。

## Migration / Investigation Notes

### 最小実装契約

1. **Typed feature universeを先に固定する。** 26.2の許可値は `vanilla` と公式3 optional flag。現行 `minecraft:bundle` は公式 `FeatureFlags` に無いため、bundle itemを保護する目的で残さない。未知の feature nameは item判定時に黙って許可せず、config load時に reject/diagnoseする。
2. **generated `Item` に required feature setを追加する。** 既存全 itemを再生成する前に、codegen inputの契約を追加する。26.2 built-in dataでは default `minecraft:vanilla` を共有 static setとして使い、公式一次 dataで non-vanilla required setが確認された entryだけ明示 overrideする。component presence、item name、tag、recipeから推測しない。
3. **`ItemStack::is_item_enabled` を read-onlyで追加する。** emptyはtrue。non-emptyは base `Item.required_features` が server enabled setの subsetかを判定する。stack component patchは required feature setを変更できない。これを実装してから handlerを接続する。
4. **handler接続は既存 F guardと独立に行う。** attackは公式順序の target/world-border/range → piercing → invalid target → selected main-hand feature → minimum charge → side effect。interactは target/world-border/range → packet selected-hand feature → event/item interaction。interactへ attack-only `cannotAttackWithItem` や piercing blanket rejectを入れない。
5. **recipe/tag/packet全再生成は不要。** item feature guardは registry item metadataと enabled feature setの判定で完結する。`CFeatureFlags` は typed enabled feature listを送るための別境界、tags/recipesは既存 source/packetの境界として維持する。recipe packet送信 gapをこの修正の依存にしない。

### fixture 契約

fixtureは decision、side effect counters、stack before/after、selected hand、feature setを記録する。`observed: false` の synthetic testは vanilla runtime traceと呼ばない。

| fixture | 入力 | 期待 decision / invariants |
|---|---|---|
| 通常 item | `minecraft:diamond_sword`（id `964`）、main hand、enabled=`[minecraft:vanilla]`、range内 target | item enabled。attackなら charge thresholdが無いので通常 guardを通る。valid時だけ event/damage/statが進み、reject時は全て `0`。bundle/minecart/spearを通常 itemの代用にしない |
| disabled feature | synthetic `Item` metadataに `required_features=[minecraft:minecart_improvements]`、server enabled=`[minecraft:vanilla]`。同じ fixtureを flag有りでも再実行 | flag無しでは attack/interact とも item side effect `0`、stack/cooldown/stat unchanged。flag有りでは target/range等の他条件を満たせば進む。これは 26.2 built-in itemの主張ではなく metadata modelの negative contract |
| creative | `Item::WOODEN_SPEAR` または `AttackRange`付き synthetic item、creative player。creative min/max reachを使い、通常の entity attribute/block rangeを混ぜない | official AttackRangeの creative min/max/margin と player creative entity range bonus `+2.0` を使う。attack outerは inclusive、interact outerは strict。feature guardの有無と reach判定を別 assertionにする |
| cooldown | selected hand itemに `UseCooldown`、cooldown active/inactiveを分ける。main hand itemと off hand itemを入れ替えて確認 | active中は item behavior、mutation、Used/Broken stat、break statusを増やさない。inactiveでは通常 interaction。cooldown groupは item metadataに従い、required feature guardと混同しない。既存 `ItemRegistry::use_on_entity` の cooldown pathと packet selected handを結ぶ integration fixtureが必要 |
| piercing | `minecraft:wooden_spear`（id `1326`）または `stone_spear`（id `1327`）、feature vanilla、range内 target | ordinary `handleAttack` は `Player::attack`、damage、event、stat、item mutationを `0`。これは item feature disabledではない。`handleInteract` は piercingを理由に blanket rejectせず、selected handの item interaction契約を別に確認 |

minimum chargeの境界は spearで `attackStrengthTicker+5` が current delay以上/未満になる2ケースを別に固定する。creative、cooldown、piercingを1つの expected booleanへ畳み込まない。

### 安全なコミット単位と依存順

現行 F の authority / charge / piercing修正は、required feature metadataが未実装でも他修正と独立した安全なコミット単位として扱える。ただし「公式26.2 item feature guard完了」とは記載しない。

推奨順序:

1. **調査/doc**: 本契約のみ。この回の書込み範囲。
2. **feature universe fix**: `DatapackManager` の公式4 flag整合（特に bundle誤追加）と focused config test。F attack/interact sourceとは別 commit。
3. **metadata model**: codegen input、generated `Item`、typed feature set、`ItemStack::is_item_enabled`。巨大な全 data再生成を避け、default static set + explicit override manifestを優先。
4. **handler integration**: `attack.rs` / `interact.rs` の item-enabled callと副作用前 order。existing F guardの独立差分として reviewする。
5. **fixtures**: 通常、synthetic disabled feature、creative、cooldown、piercingを別ケースで追加。compile/testはこの後。
6. **recipe/tag/packet**: item feature guardの必須依存にはしない。必要なら `CFeatureFlags` の typed serializationだけを別検証する。

候補 commit分割は次のとおり。

- `docs(compatibility): define 26.2 item feature contract`（本ファイル）
- `fix(protocol): align 26.2 feature universe`（bundle誤追加を含む configのみ）
- `feat(data): preserve item required feature metadata`（codegen/generated/metadata model）
- `fix(protocol): gate attack and interact items by enabled features`（handler接続とfixturesは別または同owner）
