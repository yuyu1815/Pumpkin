# 26.2 Gchat lifecycle / E実TCP 独立レビュー

対象は、現在の共有 worktree にある G（secure-chat inbound sidecar lifecycle）と E（Play -> Configuration -> Play real TCP test）の read-only review である。結論は **現状のままの merge は不可**。G には same-UUID replacement の world/index/tracker/listing cleanup と、disconnect 後の非同期 task が sidecar を復活させる P1 がある。E には CI で実行不能になり得る Python launcher と、EOF 成功判定が server 観測ではなく client 自己申告になっている P1 がある。

## Findings

### 判定サマリ

| 対象 | 判定 | merge 判定 | 阻害事項 |

| G: `World::remove_player` の caller / transfer distinction | caller audit は merge 可 | **部分 merge 可、G lifecycle 全体は不可** | 現 source の `true/false` caller は期待どおりだが、`fire_event: bool` は型で disconnect を表現せず、same-UUID replacement cleanup は sidecar 以外を保護しない。 |

### G: `World::remove_player` caller audit と `fire_event` semantics

全 repository の `World::remove_player` callerを確認した。

| caller | path / symbol | flag | 判定 |
|---|---|---:|---|
| connection teardown | `crates/pumpkin/src/entity/player.rs:1033-1066::Player::remove` | `true` | Java/Bedrock の実 disconnect path。 |
| respawn dimension transfer | `crates/pumpkin/src/world/mod.rs:4548::World::respawn_player` | `false` | cross-dimension transfer。same-world respawnではこの detach pathを通らない。 |
| explicit teleport dimension transfer | `crates/pumpkin/src/entity/player.rs:3885::Player::teleport_world` | `false` | cross-dimension transfer。 |

追加の `World::remove_player` callerは `grep`で発見できなかった。したがって **現在の source では dimension transfer以外の `false` disconnect は確認されない**。`lib.rs:618`/`724` の `server.remove_player(&player)`は別の `Server::remove_player`であり、world detach flagではない。

ただし `fire_event`は「PlayerLeaveEventを発火するか」という既存のboolであり、型名・enumでdisconnect/transferを強制していない。現 caller auditの結論は merge可だが、将来callerが意味を取り違える余地は残る。

### G P1-1: same-UUID replacement は sidecar以外の active owner を壊す

具体条件:

1. old `Player A`（UUID `U`）が world にいる。
2. `Server::add_player` / `World::add_player` が同じ UUID `U` の `Player B`を拒否せず、`World::players`へ appendする（`server/mod.rs:640`、`world/mod.rs:5142`）。
3. A の disconnect が `World::remove_player(A, true)`へ到達する。
4. `world/mod.rs:5205-5220` の `replacement_is_present`はBを検出するので inbound sidecarのclearだけは抑制する。
5. しかしその前後で以下は抑制されない。

- `world/mod.rs:5195-5196` の `entity_tracker.remove_entity(A)`。
- `world/mod.rs:5250` の UUID `U`に対する `CRemovePlayerInfo` broadcast。
- `world/mod.rs:5252-5255` の old entity remove broadcast。
- `world/entity_tracker.rs:37` の `TrackedEntity.seen_by: DashSet<Uuid>` と `remove_player`（334-336）。observer identityがUUIDだけなので、A/Bを同一ownerとして区別できない。
- listener終了後の `lib.rs:618`/`724` -> `Server::remove_player(A)` -> `server/connection_cache.rs:142-152::CachedStatus::remove_player`。`CachedStatus`はadd時に同UUIDをdeduplicateする一方、remove時はUUIDだけでsampleから削除し、online countを減らす。

結果として、Bが`World::players`/`get_player_by_uuid`に残っていても、server-list status/sampleはBがいるのに消える。さらにUUID keyed trackerはBのtracking relationshipをold disconnectのcleanupで消し得る。UUID `U`のtab-list remove broadcastもreplacementの表示を巻き込む。これは「old connectionがnew stateを消さない」というsidecar単体の保証を超えて、active replacementの可視性/indexを壊すためP1と判定する。

最小修正候補:

- 直近のonline count破壊だけなら `Server::remove_player` / `CachedStatus::remove_player`を、UUIDだけでなく現在の server-owned `Arc<Player>`と照合し、同UUID replacementが存在する場合はlisting removeをskipする。
- 正しい replacement semanticsを維持するなら、duplicate UUIDを`Server::add_player`でpublish前に拒否/旧ownerを原子的に退場させるか、`TrackedEntity.seen_by`とremove/broadcast経路をArc owner/entity-generationで識別する。単にsidecar clearをskipするだけでは不十分。
- replacementが存在する場合の `CRemovePlayerInfo(U)`は送らない。old entity idのremoveはold entityだけを対象にしたtracker identity設計と一体で扱う。

必要なtest:

- A/Bを同一UUIDで同一worldにpublishし、Aを`World::remove_player(A, true)`した後、Bだけが`get_all_players`/`get_player_by_uuid`に残ること。
- `CachedStatus`のonline count/sampleが1/Bのままであること。
- Bのclient queueに、A cleanup由来のUUID tab-list removeやBのtracking state消失が発生しないこと。
- 実 `World::remove_player`を呼び、helper mapだけで判定しないこと。

### G P1-2: disconnect後の非同期 session update / chat verify が sidecarを復活・破損させる

`crates/pumpkin/src/net/java/mod.rs:1563-1568`の`SPlayerSession`処理は、reader taskから `server.spawn_task(async move { client.handle_chat_session_update(...) })`を起動する。chat messageも同様に別 taskへ渡される。一方、connection reader終了後の`lib.rs:617-624`/`719-728`は、server taskの完了を待たずに`player.remove()`とworld cleanupを進める。

race例:

1. old Aのsession update taskまたはvalid chat taskが未完了のまま残る。
2. `Player::remove` -> `World::remove_player` -> `clear_inbound_state`でUUID `U`のstateを消す。
3. 遅れて`handle_chat_session_update`が`ChatSession`を更新して`reset_inbound_state(U,S)`を呼び、stateを再作成する。
4. または遅れて`verify_and_commit(A,S,...)`が`states.get(U).cloned().unwrap_or_else(InboundChatState::new)`を通り、disconnect後にold stateを新規insertする。
5. replacement Bが同じUUIDで既にstate `S_B`を持つ場合、old Aのsession mismatch path（`state.rs:185-191`）が`broken=true`をBのstateへinsertする可能性がある。

`owner_generation`は成功commit時だけ`state.rs:233`で設定される。`reset_inbound_state`はPlayer ownerを受け取らず、new stateのgenerationは`None`である。さらに`verify_and_commit`はmissing stateをvalidな初期stateとして作る。したがって、clear後の再作成と、replacement stateへのold mismatch mutationを防げていない。P1である。

最小修正候補:

- `reset_inbound_state`、`verify_and_commit`、`clear_inbound_state`の全production APIに同じPlayer/connection generationを渡し、reset時点からownerを記録する。
- `verify_and_commit`は「stateがない」場合に新規作成せず拒否する。session mismatchやowner mismatchのold taskは既存replacement stateを`broken`にも変更しない。
- session updateは、更新とsidecar resetを同一 lifecycle lock/transactionで行う。少なくとも`chat_session` guardを保持したままsidecar resetを実行し、`ChatSession`とsidecarが一時的に別sessionにならないようにする。
- disconnectはactive ownerを無効化してからclearし、遅延taskがそのownerでcommit/resetできないことを確認する。server world membershipのcheckだけではcheck後にremoveが起こるため、epoch/owner tokenの原子的判定が必要。

必要なtest:

- Aのdelayed session updateをclear後に完了させ、mapが再作成されないこと。
- Aのdelayed valid/invalid messageをBのsame-UUID session後に完了させ、Bのstate/session/broken/indexが変わらないこと。
- clear直後のmissing stateに対して`verify_and_commit`がstateを自動作成しないこと。
- 実`handle_chat_session_update`、実`verify_and_commit`、実`World::remove_player`を使うintegration/production-call test。

### G P1-3: ChatSessionとsidecar resetのlock/state mutation順序がatomicでない

`chat_message.rs:207-225`は次の順で動く。

1. `player.chat_session`をlock。
2. fieldsを比較し、違えば`*chat_session = ChatSession::new(...)`。
3. `drop(chat_session)`。
4. `reset_inbound_state(player_id, session_id)`で別Mutexをlock。

`SPlayerSession`ごとにasync taskがspawnされるため、validation完了順がpacket arrival順と一致しない。さらにA/B taskが以下の順に走ると、`ChatSession`とsidecarが不一致になる。

- AがChatSessionを`S_A`へ変更してdrop。
- BがChatSessionを`S_B`へ変更してsidecarを`S_B`へreset。
- Aが遅れてsidecarだけを`S_A`へreset。

その後のmessageはChatSession `S_B`とsidecar `S_A`のmismatchになり、sidecarがbroken化する。session updateの「same session no-op」はこのraceを防がない。

lock orderそのものについては、確認できたproduction pathでは概ね `chat_session -> inbound sidecar -> signature_cache`であり、逆順の確実なdeadlock pathは今回確認できなかった。しかしlock orderが一致していても、現状は二つのstate mutationを別critical sectionにしているためatomicityがない。上記P1-2と併せて修正が必要。

### G generation / pointer ABA / ownership評価

`owner_generation = Some(player as *const Player as usize)`は、現在の`World::remove_player` call chainでold `Arc<Player>`が`remove_player`引数として保持されている間に実行される。したがって、そのstrong `Arc`が生きている間に同じallocation addressを新Playerが再利用するlive ABAは確認できなかった。allocation addressの再利用はold Arcがdropされた後にしか起きず、その後にold `remove_player`を呼ぶことはできないためである。

ただしこれは明示的なgeneration/ownership tokenではない。

- reset時は`owner_generation=None`で、clearの`.is_none_or(...)`がwildcardになる。
- production testsは実Player pointerを使わず、`1/11/22`の整数を手動でstateへ設定している。
- pointerを`usize`へ落とす設計は、将来のowner lifecycleを型で強制しない。

よって「現在のlive ABAは反証されたが、production ownership proofではない」と分けて記録する。P1の本質はABAより、missing-stateの再作成、遅延task、UUID keyed stateのowner未登録である。

### G testsの証拠境界

`crates/pumpkin/src/net/chat/state.rs`の10 testsは、次のpure/helper範囲である。

- `reset_inbound_state`のsame-session idempotence。
- `clear_inbound_state`のsession/generation比較。
- `InboundChatState`のbroken/index/timestamp/checksum。
- 直接lockしたHashMapのmutation。

次は呼ばれていない。

- `JavaClient::handle_chat_session_update`。
- `JavaClient::validate_chat_message`からの実`verify_and_commit` production call。
- `World::remove_player`の`fire_event`分岐。
- `Player::remove`、`World::respawn_player`、`Player::teleport_world`。
- `Server::add_player` / duplicate UUID、`CachedStatus`、`EntityTracker`。
- delayed task / concurrent session update ordering。

したがって「10 tests pass」は、仮に実行できてもhelper invariantの証拠であり、production lifecycleの証拠とは扱わない。今回の制約でRust testは再実行していない。

### E: real server / tick / timing の実体

E testは `crates/pumpkin/tests/java_reconfiguration_tcp.rs:256`の`java_reconfiguration_over_real_tcp_preserves_player_state`で、次を使う。

- `PumpkinServer::new`（`crates/pumpkin/src/lib.rs`）。`new`はreal `Server`、OSのloopback `TcpListener`、`Ticker::run`の`Server-Ticker` threadを作る。
- test内の`run_listener` -> real `PumpkinServer::unified_listener_task` accept loop。
- real `PendingConnection`/`JavaClient`/`Player`/`World`。
- OS assigned `127.0.0.1:0` port。
- client baselineはreal Play packets、`JavaClient::last_packet_time`、`pending_bytes`、Python harnessのactual keep-alive echoを使う。

従って **TCP、network reader/writer、server ticker、keep-alive timingは本物**で、pure fake state machineだけではない。ただし、`JavaClient::start_reconfiguration`を呼ぶのは`java_reconfiguration_tcp.rs:305/337/414`のtest本体であり、production server tickやcommand/event callerではない。証明範囲は「real serverに対するtest-owned trigger」までで、production trigger reachabilityは未確認・現状callerなしである。

### E normal 2 cycles / state preservation assertion

server-sideで確認している点:

- cycle 1後に`get_player_by_name(TEST_USERNAME)`が返すArcと`Arc::ptr_eq(&player, ...)`（`java_reconfiguration_tcp.rs:331-334`）。
- cycle 2後にも同じArcがserver-ownedであること（`java_reconfiguration_tcp.rs:355-359`）。
- Rust側のexact `Player::entity_id`、`Player::position`、`Arc<World>`、main inventory 36 slot snapshot（`java_reconfiguration_tcp.rs:288-302`, `377-397`）。
- server-owned `JavaClient::connection_state`がConfig -> Playへ戻ること、duplicate triggerがfalseになること。

このため、normal 2 cyclesのstate preservationは単なるPythonの`same_entity`/`same_position`自己申告だけではない。**server-owned Arc/entity/position/world/inventory比較がある点はmerge可の強い証拠**である。

一方、次はharness側のself-observationである。

- `events`のpacket count（Start 2、ack 2、Finish 2、Join Game 1）。
- `same_entity`/`same_position` JSON booleans。
- exact body emptyのassertはRust testで`events`の`body_is_empty`を検証していない。client codeが`b""`を生成していることには依存するが、captured event fieldのassertではない。
- Configuration Registry Data / Update Tags / chunk section / NBT/resource-pack payloadの意味論。

### E EOF P1: `client_eof`はserver比較ではない

`tools/compat-26_2/protocol776_harness.py:1614-1622`は、Configuration中に

```python
stream.shutdown(socket.SHUT_RDWR)
return {"server_disconnect": "client_eof", ...}
```

と即時returnする。serverからEOF後のpacketをreadしていない。Rust test `java_reconfiguration_tcp.rs:425-430`はこのJSONと、`eof_java.connection_state != ConnectionState::Play`だけを確認するが、後者はtrigger直後からConfigのままでも成立する。

したがって現在のEOF passは、次を証明しない。

- Pumpkin readerがOS EOFを観測した。
- `JavaClient::progress_player_packets`が終了した。
- `close_token`がcancelされた。
- `Player::remove`/world cleanupが実行された。
- serverがConfigurationからPlayへ戻らなかったことをserver-side lifecycle eventで確認した。

最小修正候補は、harnessのlocal shutdown後にRust側で `eof_java.is_closed()`/reader終了相当をwaitし、さらに `get_player_by_name(EOF_USERNAME)`が消えることをbounded timeoutで確認すること。より強い実装はtest-only observer/TaskTrackerを使い、EOF原因とcleanup完了をserver側で記録してからJSONを判定すること。単にPythonの`server_disconnect`文字列を信頼してはいけない。

### E opaque packet acceptance の弱点

`tools/compat-26_2/protocol776_harness.py`は明示的に未知packet IDを拒否するが、既知mapping内の大部分をopaqueとして受理する。

- `ConfigurationRegressionTracker`/`run_reconfiguration`はKnown Packs以外のConfiguration payload（Registry Data、Update Tags等）を`opaque_configuration`として記録するだけ。
- test adapter `crates/pumpkin/tests/protocol776_reconfiguration_client.py`は`_configuration_ids`のknown setに**全Play clientbound packet IDs**をunionする。したがってConfiguration reader中に既知Play IDのframeが出ても、payloadを検証せずopaqueとして通る。
- `StrictPlayTracker`はJoin Game、Player Position、最初のchunk envelope、keep-alive/pingを検証するが、その他Play frameはmapping IDとframe boundsだけでopaque扱いする。

これは queued Play frame raceを許容するための意図的なtest adapterであり、normal lifecycleの限定証拠としては説明可能。しかし成功条件を弱めていることは明記が必要で、**任意payloadの意味論が正しいこと、Play/Configuration state boundaryに誤packetがないこと、vanilla clientがdecodeできることは証明しない**。特にConfiguration中の既知Play packet ID unionは、誤ったstate packetを隠す可能性がある。最小修正は、opaqueを必要な公式packet名のallowlistに限定し、critical packetはpayload/end-of-bodyを必ずparseし、opaque count/IDを結果とRust assertへ出すこと。

### E env / Python / timeout / port / temp / cwd / cleanup

- **Python launcher（P1）**: `PYTHON_LAUNCHER = "py"`、args `-3`。Windowsの現環境では`py -3 --version`が `Python 3.11.9`を返したが、Linux/macOSのCIでこのlauncher名と`-3`仕様は保証されない。`.github/workflows/rust.yml`の`build_and_test`は5 OS matrixで`cargo nextest run --verbose`を実行し、このintegration testを自動的に拾う。CI側のPython install/resolverなしではLinux等でspawn panicになる。
- **port**: `127.0.0.1:0`でOS assigned。固定port衝突は避けており、通常は安全。
- **temp**: `tempfile::TempDir`をworld rootに使い、成功時はtest末尾まで保持。Python scriptは`__file__`からabsoluteにrepo assets/toolsを解決するためcwd依存は小さい。
- **timeout**: Python socketのper-read/connect timeoutは60秒。ただしRustの`wait_for_harness(Child)`はprocess-level timeoutを持たず、`wait_with_output()`を無期限で待つ。2048/512 packet loopの各read timeoutに依存する。
- **cleanup**: normal/EOFとも最後のassertが全て通った時だけ`stop_server()`、listener await、`Server::shutdown()`へ到達する。途中panicではchildに`kill_on_drop`がなく、listener/ticker/child cleanupが保証されない。Windows CIでtest failure後の子process/port/resource leakが残る可能性がある。
- **global state**: `STOP_INTERRUPT`はprocess-globalなone-shot cancellation token。現在test binaryにこのtestは1件だが、同一binaryへ別server testが追加されると順序依存になる。
