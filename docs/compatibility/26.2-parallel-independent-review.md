### attack / interact: 公式条件との差

公式一次資料として repository 外の既存 `C:/Temp/server-26.2.jar` を `javap -c -p` で静的確認した。`net.minecraft.server.network.ServerGamePacketListenerImpl.handleAttack` / `handleInteract` は、概ね次の順である。

- `hasClientLoaded`。attack は attacker `isSpectator` も拒否。
- packet を同じ `ServerLevel` の `getEntityOrPart` で解決。
- target block position が world border 内であることを確認。
- target AABB と eye position の距離を使い、検証用 `3.0D` を加える。
- interact は `entityInteractionRange + 3.0` の **strict `<`**。
- attack は item `AttackRange` の min/max/margin と **inclusive `>=` / `<=`**。component がない場合は attribute を default range に使う。
- attack にはさらに self、ItemEntity、ExperienceOrb、attackable でない arrow、item feature enabled、piercing weapon、`cannotAttackWithItem` の guard がある。
- これらの packet handler 自体に block LOS raycast はない。よって壁越し拒否を vanilla 26.2 handler の必須条件とはしない。

現行 `crates/pumpkin/src/net/java/play/attack.rs::valid_entity_interaction`（119行付近）と `interact.rs::JavaClient::handle_interact`（39行付近）は、AABB最近点・same-world・removed・finite値・reach・attack spectator を副作用前に検査している。これは不正入力の安全性を上げるが、次の差分を残す。

1. **world border がない（must-fix）**。公式は attack/interact とも target の `blockPosition` を world border で検査する。Pumpkin の `World::worldborder` / `Worldborder::contains` は存在するが、両handlerから呼ばれていない。border外targetを入力に、`valid_entity_interaction`、期待 `false`、修正は target block position を border lock の `contains` 相当で拒否すること。attack と interact の両方に同一テストを追加する。
2. **attack item/feature guard がない（must-fix）**。`valid_entity_interaction` は `AttackRangeImpl` を読むだけで、公式の `ItemStack.isItemEnabled`、piercing weapon、`cannotAttackWithItem` を見ない。特に piercing weapon は公式 handler が無条件 return する。入力は enabled/disabled item、piercing component、cannot-attack item、期待は `Player::attack`・plugin event・damage counter すべて0。修正位置は `handle_attack` の `player.attack` 前、または共通validatorの attack-only branch。
3. **entity part の解決がない（must-fix）**。公式は `getEntityOrPart` だが `World::get_entity_by_id`（`crates/pumpkin/src/world/mod.rs:4819`付近）は `entities` と players の本体だけを走査する。`EnderDragonPart` は `can_hit=true` でも本体indexへ委譲されず、Java attack packet の正当な part target を見失う。入力は dragon part runtime id、期待は本体への damage path、修正は part index を world lookup/tracker に登録するか、`get_entity_by_id` 相当で part を解決すること。
4. **interaction に attack-only でない拒否が混ざる（互換性上の要修正）**。共通 `valid_entity_target_state` は `target.is_spectator()` と living health `<=0` を attack 以外にも拒否する。公式 `handleInteract` はこの二条件を packet-handler guard として要求せず、range/feature後に `interactOn` へ進む。安全 policy と vanilla decisionを同一関数で表現しないこと。少なくとも dead living target、spectator target、spectator attacker の各々について、公式相当の no-op/camera/event結果を決め、`valid_entity_interaction` の `attack` 引数で明示的に分離する。
5. **自分自身のattackの順序が経路間で不一致**。`handle_attack` は validator 前に self-idをkickする一方、`handle_interact` の ActionType::Attack は event発火後に self-idを検査する。入力 self id、期待は両経路で event/damage 0かつ公式相当の disconnect/no-opを固定する。上位側ガードの順序を統一する。

rangeについては、公式 `Player.isWithinEntityInteractionRange(AABB, 3.0D)` の AABB最近点、strict `<`、`AttackRange.isInRange` の inclusive境界、item componentの creative min/max/margin、attribute default を現行 pure testが部分的に再現している。creative `+2.0` は現コードが `gamemode == Creative` で手動加算しているため、この経路の期待値は 3→5、検証上限は 8。block range 4.5/creative 5.0を entity rangeへ混ぜていない点は **merge可**。ただし world border/item/partの未実装を埋めない限り、全体を「公式整合」とは呼ばない。

LOSについては、`Entity::has_line_of_sight` が存在しても packet handlerの公式条件ではない。壁越しを距離内で拒否しないことは **vanilla handler相当**、安全上LOSを必須にすることは別policyであり、互換性証明に混ぜない。

### chat: state transition、owner/session/index/last-seen、rollback/replay

接続は確認できる。`crates/pumpkin/src/net/java/play/chat_message.rs::validate_chat_message`（161行付近）が secure policy、署名長、現在時刻範囲、session id/key/expiry を確認し、`state::verify_and_commit` を呼ぶ。その戻り後にのみ `handle_chat_message` の spam/plugin event と `World::broadcast_secure_player_chat`（`world/mod.rs:1128`付近）へ進む。reports disabled では署名なしを system chat として通す既存policyであり、reports enabled では署名なし/空sessionを拒否する。この接続自体は **merge可の方向**。

ただし以下は **must-fix / 完成判定不可**。

1. **official chain-break と現行 rollback の意味が逆**。公式 `SignedMessageChain$1.unpack` は、timestampが古い場合に `setChainBroken()`、signature failure の場合にも `setChainBroken()` を実行する。現行 `state::verify_and_commit`（112行付近）は `Signature` / `OutOfOrderTimestamp` 失敗時に sidecar index/timestamp を一切変更せず、次の message を通常継続可能にする。単発の失敗を安全側に捨てる設計としては説明できるが、vanilla 26.2 chain state とは一致しない。入力 `valid index0 → invalid signature index0 → replay valid index0`、期待は公式なら chain broken後に再受理なし、現行は replayが通り得る。修正は session-owned state に `broken` を持たせ、公式と同じ失敗種別で broken に遷移するか、少なくとも再送を絶対受理しないこと。rollbackを採用するなら「vanilla互換ではなく fail-closed policy」と文書化する。
2. **timestamp比較が秒単位で精度不足（must-fix）**。`timestamp_epoch_second = chat_message.timestamp.div_euclid(1_000)` と `last_timestamp_epoch_second` を比較している。公式 chain は `Instant.isBefore`、すなわち wire millisecond timestampの順序を比較する。入力 `last=1000ms, current=999ms` は現行では同じepoch secondとして通り得るが、公式は reject + chain break。stateを `i64` epoch milliseconds（または Instant相当）で保持し、`same-second backward` testを追加する。
3. **同一session updateの再送でstateをresetする（must-fix）**。`handle_chat_session_update` は証明書検証後、同じ `SPlayerSession` でも `ChatSession::new` と `reset_inbound_state`（215行付近）を毎回行う。公式 `handleChatSessionUpdate` は既存 profile-key dataと同一なら returnし、`resetPlayerChatState`しない。入力 `session S → valid message index0 → 同じSPlayerSession再送 → index0 replay`、期待は再送update no-opか replay reject、現行は sidecar index0へ戻り replay acceptedの可能性がある。old/new session replacementだけをresetし、同一sessionはidempotentにする。
4. **signed command は未接続**。`crates/pumpkin/src/net/java/mod.rs` の `SChatCommandSigned` branchは signed packetを `signed.command.to_string()` にして通常 `SChatCommand`へ降格し、decode failureも通常command readへ fallbackする。公式は `handleSignedChatCommand`で last-seenを適用し、argument signatureを `SignedMessageBody`として検証し、失敗時は実行しない。これは本taskのchat完成を否定する範囲であり、少なくとも「未実装/deferred」を明記し、signed commandを安全/互換完了に数えない。
5. **session-owned sidecarのlifecycleがない**。`INBOUND_STATE: OnceLock<Mutex<HashMap<Uuid, InboundChatState>>>` は player UUIDだけで、disconnect cleanupがない。新session updateで通常上書きされるが、永続増加・UUID再利用・Player交替の境界が未定義。ownerは Player/session lifecycleにcleanupまたは接続単位keyを追加する。
6. **独立fixtureが実在しない**。`26.2-chat-state-validation.md` と `26.2-chat-chain-fixtures.md` は `tools/compat-26_2/chat-fixtures/` をfixture sourceとして記載するが、今回 `find` では該当ファイル0件だった。`state.rs::nonempty_last_seen_matches_fixture_hash` は入力をtest内で生成し、期待SHAを同じsourceに固定した self-generated expected であり、独立vanilla fixtureではない。`signature.rs` のOpenSSL known-answerはRSA helperの独立値だが、official chat traceではない。fixture provenanceを修正し、外部生成・固定入力・expected・source hashを別ファイルで分離するまで、last-seen state evidenceは中以下とする。
7. **integration testがない**。現行 `state.rs` testsは `InboundChatState`、checksum、`preview_last_seen`、canonical hashを対象とし、実 `Player`を通る `verify_and_commit`、session reset、signature success/failure後のcache/sidecar、broadcast前のstate transitionを呼んでいない。`chat_message.rs`にもhandler testがない。最小testは次のとおり。
   - secure reports enabled + valid session + independent signature: `verify_and_commit`成功、ack validator/index/timestampが1回だけ進み、その後 broadcast spyが呼ばれる。
   - unsigned with reports disabled: system broadcastのみ、secure attributionなし。
   - unsigned/missing session/expired key/invalid DER/wrong signature: broadcast 0、original ack/index/timestampの期待値、公式互換を選ぶなら broken=true。
   - ack unknown/repeated/checksum mismatch: `preview_last_seen`とproduction cacheを比較し、failure後のrollbackまたは公式commit-before-signature policyを明示。
   - replay、same-session update replay、old millisecond timestamp、session mismatch、index 0→1 sequence。

`World::broadcast_secure_player_chat` は inbound verified linkをそのまま送らず、`messages_sent` と `Uuid::nil()` sessionで outbound objectを作る。これは既存 outbound semanticsの別問題で、今回の「検証helper→broadcast前state transition」がつながったこととは別に記録する。recipient側のsecure attributionをvanillaと同じと主張しない。

### entity persistence E2E の証拠強度

`crates/pumpkin/src/world/mod.rs::tests::world_entity_persistence_e2e_spawn_move_stop_reopen`（7810行付近）は、要求された経路をかなり満たす。

- `TempDir`上の実 `World`/`Level`を `test_world`で生成。
- `crate::entity::r#type::from_type(&EntityType::ARMOR_STAND, ...)`で実 concrete entity factoryを通す。
- `World::spawn_entity_non_save`でlive world indexへ登録。
- live `Pos`と`Entity::custom_data` markerを変更。
- 初回save後、entityをchunk 0からchunk 2へ移動。
- 初回snapshotのないchunk 5へ2体目をspawnし、save→shutdown。
- 別 `World`/`Level`を同じTempDirから作り、`Level::receive_entity_chunks`で実storage loaderを通る。
- 旧chunk empty、移動先/new-spawn chunk count=1、UUID/type/Pos/`PumpkinCustomData.marker`を比較し、2 chunk内UUID重複を検査。

この範囲のE2Eは **条件付き merge可**。`crates/pumpkin-world/src/level.rs::save_entity_nbt`（788行付近）の同UUID置換、cached他chunkからのstale UUID除去、実disk reopenの回帰としては十分に強い。既存 lower-level tests `entity_save_load_reopen_preserves_live_and_existing_nbt`、corrupt bytes保持、missing chunk snapshot保護も補助証拠になる。

ただし証拠の上限は次のとおり。

- `save_entity_nbt` が stale UUIDを除去するのは `loaded_entity_chunks` 内だけ。旧chunkがdisk上に存在するがcacheにない状態で移動saveした場合、全entity regionを走査していない。入力 `old chunk file exists, old chunk not cached, live entity moves to new chunk`、期待は旧disk copy 0/new copy 1、現状testにはない。これを追加するまで「全disk duplicate除去」とは言わない。
- reopen後はNbt recordを比較しており、reopened NBTを再び concrete entity factoryでinstantiateしてlive entityのUUID/type/pos/markerを比較する試験ではない。今回のstorage contractには十分だが、「実entity再生成後も保持」は未検証。
- UUID uniquenessは移動先とnew-spawnの2 chunkだけ。全region scanではない。old/source assertionはあるため、今回のcached boundary regressionは観測できるが、任意の別chunkに残る重複は除外できない。
- docs `26.2-entity-persistence-e2e.md` に記載された clean detached worktreeのcargo結果は、本独立レビューが再実行した証拠ではない。現shared worktreeは chat/attack/interact変更を含み、当レビューではcargoを禁止しているため、現HEADのcompile/test passは未確認。

### 公式と安全性の分離

- **安全性として妥当**: same-world、removed、finite、AABB reach、attack spectator、secure chatのmissing session/expiry/signature拒否、ack previewのclone、entity stale cached snapshot除去。
- **vanilla整合としてまだ不足**: world border、attack item/feature guard、entity part、interaction target dead/spectatorのexact semantics、official chat broken state/idempotent session update/millisecond ordering、signed command verifier、全disk stale scan。
- したがって「不正入力を拒否する安全側修正」と「Java 26.2 vanillaと同じ受理/拒否」を同じpass表現にしない。
