# 26.2 signed-command 認証: 独立 review と最小次タスク

## Findings

### 現在の gate は fail-closed だが、互換完成ではない

対象 HEAD は `e2081473b` (`fix(net): make Java egress accounting single-owner`)、直前は
`a82884045` (`fix(command): gate signed command dispatch`)。現在の実装は次を正しく固定している。

- `SChatCommandSigned::read` は argument signature 数を公式上限 `8`、name を `16`、signature を `256` bytes として読み、`handle_play_packet` は trailing body を拒否する。
- signed decode failure は `SChatCommand::read` へ fallback しない。
- `pumpkin-command::ParsingResult::signable_arguments` は permission-filtered な同じ parser/source から、signable node の元 command UTF-8 byte range を返す。typed value の再シリアライズはしていない。
- `Some(Vec::new())` かつ signature entry 空の command は通常 permission/event/dispatcher path へ進む。
- signable argument がある packet は現在すべて reject され、RSA、session、chain、last-seen/ACK はまだ検証されない。

これは安全側の暫定 gate であり、**公式 offline/unsigned の ordinary command が合法であること、または signable signed-command の実認証が完了したことを示さない**。特に `handle_signed_chat_command` の no-signable 分岐は `message_count`、3-byte ACK、checksum、session/expiry を検証せず通常実行へ進むため、認証実装ではここを先に transaction 化する。

### 再利用境界と実装契約

- parser: `dispatcher.parse_input(&packet.command, &player_source)` → `ParsingResult::signable_arguments()` → `SignableArgument::raw_value(&packet.command)` をそのまま使う。name は node 名、署名 content は raw substring。command 全文、typed result、argument name の連結は使わない。
- crypto: `net/chat/signature.rs::verify_chat_message_signature` / `canonical_bytes` は、各 argument の raw value を `SignedMessageBody::content` にした一件ごとの検証に再利用できる。normal chat の whole-command/whole-message fallback にはしない。
- ACK: `net/chat/state.rs::preview_last_seen` と `last_seen_checksum` を再利用する。preview は `MessageCache.last_seen_validator` の clone に対して実行し、reject 時は original cache を変更しない。
- state: `net/chat/state.rs::verify_and_commit` は `SChatMessage` 一件・chain index 一つを前提にしているため、signed command に直接呼ばない。代わりに同じ sidecar、`chat_lifecycle`、owner/session checks、cache lock ordering を使う N-argument transaction が必要。
- session/permission: `Player::chat_session` の validated public key、key signature、expiry、session UUID を確認した後も、dispatch は従来の player `CommandSource`/permission pathを通す。署名成功を permission bypass にしない。

### N argument transaction 契約

1. parser 完全成功、signable list、packet entry の unknown/duplicate/missing name set を side effect 前に確定する。検証順は packet entry order、対応する raw value は parser list から name で引く。
2. 同じ packet の `timestamp`、`salt`、ACK preview 結果を各 entry に使う。`message_count` は ACK offset であり chain index ではない。
3. state の `next_index + i`、sender UUID、session UUID で `SignedMessageLink` を作り、`verify_chat_message_signature` を各 signature に適用する。N entries は N links を消費する。
4. ACK preview、session/expiry/timestamp policy、全 RSA signatures が成功した後だけ、cache、`next_index += N`、last timestamp を一括 commitする。失敗時は execute、`PlayerCommandSendEvent`、ACK/state commit のいずれも起こさない。replay/old timestamp/chain-broken policy は `chain-state.json` の reject ID に固定する。
5. commit 後のみ既存 `handle_chat_command` 相当の spam/event/permission/execute を呼ぶ。signable list empty の合法ケースも ACK transaction を経由させ、ordinary unsigned `SChatCommand` の offline/reports-disabled policy と混同しない。

## Migration / Investigation Notes

### 必須指摘: egress completion は success/failure を区別しない

`crates/pumpkin/src/net/java/mod.rs::OutgoingPacket::Drop` は、deferred close、frame error、write error、flush error、正常 flush の全経路で `oneshot::Sender<()>` に同じ `()` を送る。従って `start_reconfiguration` の `completion_rx.await` は writer failure 後にも成功扱いになり得る。`pending_bytes` の Drop 減算自体は単一 owner になったが、completion は送信成功の証明ではない。

これは signed-command とは独立した must-fix task。最小修正は completion を `success/failure`（または同等の error result）にし、**flush 成功後だけ success、frame/write/flush/cancel/drop 経路は failure** を返すこと。`send_packet_now_data` も同じ結果を観測できる focused test を追加する。

`try_reserve_pending_bytes` は `MAX_PENDING_BYTES = 67,108,864` (64 MiB) 超過を CAS で拒否できている。一方 `checked_add(...).expect(...)` と `checked_sub(...).expect(...)` は overflow/所有権不整合を panic にする。通常上限下では overflow は観測されないが、raw `Bytes` 境界の error handling としては、reservation overflow を reject/close へ落とし、release underflow は二重 Drop 回帰 test で invariant を固定する小タスクを別 owner にする。
