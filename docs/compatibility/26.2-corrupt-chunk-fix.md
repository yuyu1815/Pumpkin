# 26.2 WLD-02 破損チャンクの Missing 降格防止

- 対象: Java Edition 26.2 / protocol `776` / world data version `4903`
- 対象ID: WLD-02
- 判定: **最小の安全修正を実装。Missing は生成へ進めるが、payload/region read error は terminal load failure として明示し、Proto/generation/save へ流さない。**
- 実ワールド: 不使用。破損データ fixture の作成、ユーザー world 操作、server 起動は実施していない。
- Cargo/rustup/build/test: 実施していない（inventory/build担当へ委譲）。

## Findings

### 症状の根拠

`crates/pumpkin-world/src/chunk_system/worker_logic.rs` の従来の `io_read_work` は、次の二つを同じ match arm で処理していた。

- `LoadedData::Missing(pos)` — Anvil slot が未生成
- `LoadedData::Error((pos, error))` — region read、compression、NBT decode などの失敗

両方を空の `ProtoChunk::new(...)` に変換するため、存在した chunk の payload 破損が「未生成」と同じ扱いになり得た。後続の generation、unload、shutdown save がその chunk を通常保存へ渡すと、原本 slot を上書きできる制御フローだった。

加えて `crates/pumpkin-world/src/chunk/io/file_manager.rs::ChunkFileManager::fetch_chunks` は、region serializer の初期化失敗を batch の先頭座標へ一件だけ送る。一方、旧 `io_read_work` は batch 件数分の応答を待つため、region open/parse error の場合に残りの pending request が応答なしになる経路もあった。このファイルは所有範囲外のため変更していない。

### 最小修正の方針

1. **Missing のみ** `ProtoChunk::new(x, z, ...)` を生成し、既存の正常 generation 経路へ渡す。
2. **Error は** `RecvChunk::LoadFailure { pos, error }` へ変換する。
3. scheduler は load failure をログへ明示し、失敗 chunk の holder/task を破棄する。失敗 payload から `Chunk::Proto`/`Chunk::Level` を作らないため、dirty/save queue へ流れない。
4. 失敗 chunk の read area に依存する非 in-flight graph task も terminal cancel する。これにより、生成を単に飛ばして dependency/pending request を無期限に待たせない。後の明示的な level transition は再試行可能な入口として残す。
5. `fetch_chunks` を worker 側で座標単位に呼び、各 scheduled coordinate に必ず一つの結果を割り当てる。region 不在は channel close 後に Missing として扱い、region read error は該当 coordinate の LoadFailure として上位へ届く。

## Migration / Investigation Notes

### 状態寿命と呼出し順

正常系は次の順序を維持する。

1. `GenerationSchedule::work` が Empty stage の IO task を graph に登録し、`running_task_count` を増やす。
2. `io_read_work` が座標ごとに `Level::chunk_saver.fetch_chunks` を呼ぶ。
3. `LoadedData::Loaded` は payload座標と要求座標を照合し、一致時だけ `process_loaded_chunk` を経て `RecvChunk::IO` へ進む。不一致も破損相当の `LoadFailure` とする。
4. `LoadedData::Missing` は worker 内で `ProtoChunk::new` を作り、`RecvChunk::IO(Chunk::Proto(...))` へ進む。これは従来と同じ生成入口で、正常 load の処理を変更しない。
5. `LoadedData::Error` は `RecvChunk::LoadFailure` になり、scheduler の terminal branch で holder/tasks を解放する。Proto は生成せず、`Chunk::Level`/`Chunk::Proto` は `io_write_work` に送られない。
6. `RecvChunk` 処理の末尾で `running_task_count -= 1` が実行されるため、failure 後に IO task 数が残らない。
7. unload/save/shutdown の `process_unload_queue` / `save_all_chunk` は holder の `chunk` が `None` の failure chunkを save batchへ入れない。失敗原本は読み取りのみで、今回の変更からは rename/delete/quarantine しない。

### 依存 task の terminal 処理

破損 chunkを単に `return` すると、隣接 stage の read area が `chunk.is_some()` を待ち続けるため不十分である。`cancel_tasks_affected_by_load_failure` は失敗座標を read radius に含む非 in-flight graph nodeを集め、`waiting_for_chunks`、holder task slot、DAG nodeを解放する。実行中の generation taskは安全に強制停止しない。現行 graph の pre-validation により、失敗 chunkが未提供のまま依存 taskが新たに in-flight になることは避ける。

失敗した holder の `target_stage` は外部 `LevelChannel` の old-stage contractを壊さないため保持する。内部 task/chunk は terminal として空にし、明示的な unload/update が来たときに通常の lifecycle へ戻す。failure の再試行 policy、quarantine/backup、上位 caller への structured error API は今回の所有範囲外であり、別作業が必要である。

### static 仮説の反証・未採用修正

- 既存 Anvil の sector offset `< 2`、length underflow拒否は upstream `334b37ade` 相当として既に存在するため、再修正しなかった。
- `AnvilChunkFile::get_chunks` は payload単位の `LoadedData::Error` を返しており、ErrorがMissingに落ちる原因は worker/scheduler policyであることを確認した。
- region serializer 初期化 errorについては、batchの一件だけ送信する file manager 自体を変更せず、workerを座標単位 fetch にすることで pending 未応答を避けた。これは安全性優先の最小変更だが、同一 region に対する fetch 呼出し回数が増えるため、後続で region-batch response contract を file manager側に追加する余地がある。
- corruption payloadの quarantine、region entry単位 salvage、NBT shape validation、Windows region replacement、fsyncはWLD-02以外の未解決項目であり、勝手に変更していない。
