# 26.2 outbound signed chat / `MessageArgument` consumer: minimum connection plan

## Findings

### 1. Scope and conclusion

This is an independent, read-only investigation for Java Edition 26.2 / protocol
776. Only this document is being added. Rust source, protocol source, fixtures,
`.pi/`, world data, staging, and commits are out of scope.

The minimum useful first patch is **one outbound consumer: `/msg` only**. It must
consume the already authenticated `message` argument and send the existing
`PlayerChatMessage` through the existing per-recipient egress/cache path. It
must not turn `/msg` into another system-message call. `/say`, `/me`, and
`/teammsg` remain separate follow-up consumers.

This is not a claim that signed-command compatibility is complete. The current
code has authentication/state work, but the verified argument does not yet
carry enough metadata to construct a recipient-correct outbound message.

### 2. Current Pumpkin path and the concrete gap

#### Command signing context

`pumpkin-command` currently stores the following in
`CommandSigningContext`:

- `Signed`: parsed node identity, original raw argument text, and signature bytes.
- `Unsigned`: parsed node identity and original raw argument text, with no signature.
- `from_signed_entries` uses map insertion by argument name. A duplicate name
  therefore leaves the **last** packet entry in the consumer map, matching the
  documented vanilla `Map.put` behavior.

The context does **not** currently carry:

- sender UUID;
- chat session UUID;
- the assigned inbound chain index for this argument;
- packet timestamp and salt;
- the reconstructed ordered last-seen signatures;
- a distinction between the last duplicate's assigned link and earlier duplicate
  links.

`JavaClient::handle_signed_chat_command` does verify entries in packet order and
advances the inbound state for each entry, but the state function currently
returns only `Result<()>`. The assigned indexes are therefore consumed and then
lost before the executor/consumer boundary.

`validate_signed_command_arguments` permits duplicate names and checks unknown
and missing names. Consequently, for a duplicate `message` entry:

1. every duplicate is authenticated in packet order and consumes one chain index;
2. the signing map exposes only the last entry to `MessageArgument` consumers;
3. the outbound consumer must use the **last entry's** signature and assigned
   link index, not the first entry's index or a newly allocated index;
4. the raw value, timestamp, salt, and reconstructed last-seen list are otherwise
   the same parsed/packet values.

The current context can represent the last signature, but not the last entry's
link/session/body metadata. This is the specific reason it cannot yet produce a
correct outbound `CPlayerChatMessage`.

#### Existing plain outbound calls are disguised/system output

The current command consumers do not preserve signed attribution:

- `commands/msg.rs` validates the signing-context name/node/raw binding, then
  converts the argument to `TextComponent` and calls `Player::send_message` for
  the source and each target.
- `Player::send_message` sends `CDisguisedChatMessage`. It has no sender UUID,
  signed index, signature, signed timestamp, salt, previous-message list, or
  recipient ACK window update.
- `commands/say.rs` and `commands/me.rs` call `Server::broadcast_message`, which
  reaches `World::broadcast_message` and also sends `CDisguisedChatMessage`.
- `commands/teammsg.rs` creates a translated `TextComponent` and calls
  `send_system_message`; it does not send a player-chat packet.

This plain path is valid for deliberately unsigned/system output, but it is not
an outbound signed `MessageArgument` consumer. Replacing only the `/msg` call
with a system message, or adding a chat type to `CDisguisedChatMessage`, would
not provide signature compatibility.

#### Existing secure player-chat path has a separate attribution defect

`World::broadcast_secure_player_chat` constructs a `PlayerChatMessage` from an
inbound `SChatMessage`, but currently builds its link from:

- `sender.chat_session.messages_sent`, which is an outbound counter; and
- `Uuid::nil()` as the session UUID.

Those values are not the inbound signed chain link. The existing inbound state
has the real session UUID and next index, but the secure broadcast function does
not receive them. This must not be copied into the command consumer. A signed
command argument must use the verified `(sender, session, assigned index)` from
the inbound chain result.

### 3. Real `CPlayerChatMessage` and cache information already present

`CPlayerChatMessage` already has the complete clientbound wire model:

- `global_index`: recipient-local outbound sequence;
- `sender`: sender UUID;
- `index`: sender chain index;
- optional 256-byte `message_signature`;
- raw signed `message`;
- signed timestamp and salt;
- recipient-relative `previous_messages`;
- optional `unsigned_content` component;
- recipient filter type;
- chat type registry index;
- sender display name and optional target display name.

Its codec already writes these fields in the existing packet order. No new codec
or chat framework is needed.

`OutgoingChatMessage::send_to_player` already performs the important
recipient-specific work for a non-system `PlayerChatMessage`:

1. applies the recipient's filter mask;
2. skips a fully filtered message;
3. uses the message link index as clientbound `index`;
4. reads the recipient's `ChatSession.messages_received` as `global_index`;
5. converts the sender's `signed_body.last_seen` through
   `MessageCache::last_seen.indexed_for(recipient)`;
6. sends `CPlayerChatMessage` with chat type, sender name, and target name;
7. adds the signature to the recipient's cache and pending ACK validator;
8. caches the message's last-seen signatures for non-senders; and
9. increments the recipient-local `messages_received` counter.

The two counters must remain separate:

| value | meaning | valid for the outbound packet |
|---|---|---|
| verified inbound chain index | sender's signed-message link index | `CPlayerChatMessage.index` |
| `ChatSession.messages_received` on recipient | packets sent to that recipient | `CPlayerChatMessage.global_index` |
| `ChatSession.messages_sent` on sender | Pumpkin's current outbound counter | **not** a substitute for inbound link index |
| signed command `message_count` | last-seen ACK offset | **not** a chain index |

The recipient's `previous_messages` list and its later ACK tracking are already
implemented in `MessageCache` / `LastSeenMessagesValidator`. The missing part is
feeding the correct signed argument body into this existing path.

### 4. Official 26.2 `MessageArgument` behavior from the JAR

Primary static oracle: `C:/Temp/minecraft-26_2-inner.jar`. It was inspected with
`javap`; it was not executed or copied into the repository.

`MessageArgument.resolveChatMessage(context, name, consumer)` does the following:

1. resolves the parsed `Message` into a component first. Entity selectors are
   resolved only when the source has selector permission; otherwise the original
   literal text remains. The resolved component is not the signed body text.
2. obtains `CommandSourceStack.getSigningContext()` and calls
   `getArgument(name)`.
3. when a signed `PlayerChatMessage` exists, attaches the resolved component as
   `unsignedContent` using `withUnsignedContent`, then resolves the signed path.
4. when no signed argument exists, creates `PlayerChatMessage.system(text)`,
   attaches the resolved component as unsigned content, and resolves the
   disguised/system path.

The signed path then:

- filters only when the source is a player and the message has a signature from
  that same player;
- sends the signed raw content to the source text filter;
- decorates `PlayerChatMessage.decoratedContent()` through the server
  `ChatDecorator`;
- applies the resulting `FilterMask` to the message before invoking the consumer;
- never replaces the signed raw content with the decorated component.

`withUnsignedContent` stores no component when the resolved component is exactly
literal signed content. It stores a component only when selector resolution,
decoration, or another transformation differs from the signed literal. This
field is display metadata, not a new signed payload.

The official command classes use the same consumer shape:

- `SayCommand`: `MessageArgument` -> `PlayerList.broadcastChatMessage` with
  `ChatType.SAY_COMMAND`.
- `MsgCommand`: `MessageArgument` -> one `OutgoingChatMessage`, source with
  `MSG_COMMAND_OUTGOING`, each target with `MSG_COMMAND_INCOMING` and target name.
- `TeamMsgCommand`: `MessageArgument` -> team members; sender uses
  `TEAM_MSG_COMMAND_OUTGOING`, other members use `TEAM_MSG_COMMAND_INCOMING`,
  and the team display name is the target name.
- Pumpkin's `me` source was also inspected; it currently uses a signable greedy
  string and disguised broadcast. The official registry has `EMOTE_COMMAND`,
  but this plan does not change `/me` in the first patch.

The official `ChatType` bootstrap confirms the relevant registry decorations:

- `chat` -> `chat.type.text`;
- `say_command` -> `chat.type.announcement`;
- incoming/outgoing message -> `commands.message.display.incoming/outgoing`;
- incoming/outgoing team message -> `chat.type.team.text/sent`;
- emote -> `chat.type.emote`.

A chat type is therefore display/routing metadata passed alongside the signed
message. It does not create, repair, or replace a signature.

### 5. Signed, unsigned, offline, and secure-session policy must stay separate

The first consumer needs an explicit three-way policy:

| input state | permitted first-patch output | attribution claim |
|---|---|---|
| verified signed command argument with valid session/link/body | existing `OutgoingChatMessage::Player` -> `CPlayerChatMessage` | signed sender/session/index/body are preserved |
| explicit unsigned command context or reports-disabled path | existing system/disguised output, or `PlayerChatMessage::system` through `OutgoingChatMessage::create` | no secure player attribution |
| offline/no valid secure session | unsigned/system output only | profile name/identity is not cryptographically proven |

Do not use `PlayerChatMessage::unsigned(non_nil_sender, ...)` as a shortcut for a
secure packet: the current `OutgoingChatMessage::create` treats any non-system
sender as a player message, which would send a `CPlayerChatMessage` without a
valid signature/session attribution. That is a separate policy decision and not
part of the minimum signed connection.

A valid signature also does not bypass command permissions. The existing parse,
permission, command event, and executor path remains the authorization gate.

## Migration / Investigation Notes

### Minimum handoff shape

The smallest safe handoff is not a new crypto or chat abstraction. It is a
transport-neutral authenticated argument record produced by the existing signed
command/state owner and consumed by the existing chat owner. Its required data
is:

```text
argument name
parsed node identity and original raw value
sender UUID
session UUID
assigned inbound chain index
signature bytes
packet timestamp
packet salt
ordered reconstructed last-seen signatures
```

The state owner should return one record per successfully verified packet entry,
in packet order. The context builder can then retain the final record for each
argument name, preserving the official last-duplicate lookup behavior. For the
final duplicate exposed to `/msg`, the record's `index` must be the final
consumed link index. No consumer should allocate a new index or read
`messages_sent`.

The chat consumer can construct the existing `PlayerChatMessage` from that record:

```text
SignedMessageLink(index, sender, session)
SignedMessageBody(raw_value, timestamp, salt, last_seen)
signature = record.signature
unsigned_content = resolved display component only when it differs from raw text
filter_mask = existing pass-through/recipient filter result
```

Then it calls existing `OutgoingChatMessage::create(...).send_to_player(...)`
for the selected recipients. Recipient-specific `previous_messages`, global
index, cache insertion, and pending ACK state remain in `send_to_player`.

This handoff should not place `PlayerChatMessage`, RSA, or recipient cache types
inside `pumpkin-command`; that would create a dependency cycle and duplicate
ownership. The command crate needs only an opaque/plain authenticated record, or
the network layer can keep the record beside the parsed context and expose a
narrow lookup to the Pumpkin executor.

### First 70-turn patch: one responsibility

**Responsibility:** authenticated plain `/msg` argument -> existing signed
recipient egress.

Include only:

1. return/preserve verified per-entry link metadata from the existing command
   state path;
2. retain the final duplicate-by-name record in the signing context;
3. change `MsgExecutor` to reject a missing/mismatched authenticated record in
   secure mode, build the existing `PlayerChatMessage`, and send it to the
   source/targets through `OutgoingChatMessage::send_to_player`;
4. keep the existing `MSG_COMMAND_OUTGOING` and `MSG_COMMAND_INCOMING` chat type
   values, sender name, and target name routing;
5. keep unsigned/offline execution on the existing disguised/system path;
6. add only focused tests for field preservation, duplicate-last selection,
   recipient cache/ACK effects, and no system-packet substitution.

Do not include in this patch:

- a chat framework or new routing abstraction;
- a new crypto implementation or signer;
- changes to `/say`, `/me`, or `/teammsg`;
- changes to the protocol codec;
- a second parser or typed-value reserialization;
- selector/decorator/filter framework work beyond passing the already available
  resolved display component;
- vanilla runtime/client installation or a server run;
- broad changes to `World::broadcast_message`.

The selector/decorator/filter portion must be a later explicit step if Pumpkin's
current `StringArgumentType` cannot produce the official `MessageArgument`
component. A plain `TextComponent::text(raw)` happy path is not evidence that
full `MessageArgument.resolve` compatibility exists.

### Exact signed-command map/duplicate rule for the recipient

The map lookup and chain consumption have different cardinalities:

- chain/state: one verified record per packet entry, including every duplicate;
- context lookup: one record per argument name, with the last duplicate replacing
  the earlier value;
- outbound recipient: at most one `CPlayerChatMessage` for the resolved
  `message` argument, using the final record's signature/index/body metadata.

For example, packet entries `message=A, message=B` consume indexes `41` and `42`.
The consumer must send `B` with index `42`; it must not send `A`, use index `41`,
use `messages_sent`, or send both messages. If duplicate policy is later changed
to reject duplicates, that is a separate compatibility decision and must not be
silently mixed into this outbound patch.

### Recipient ACK details to preserve

For a target whose cache lacks one of the sender's `last_seen` signatures,
`indexed_for` emits `PreviousMessage { id: 0, signature: Some(full) }`. If the
recipient already has it, it emits a positive cache ID with no full signature.
This is per recipient, so one shared pre-encoded `CPlayerChatMessage` cannot be
used for all targets.

After a signed packet is queued, the existing recipient cache adds the message
signature and marks it pending in `LastSeenMessagesValidator`. A later inbound
ACK applies to that recipient's window. The sender's `last_seen` list is the
body context being sent; the recipient's pending validator is the ACK state.
They must not be collapsed into one global list.

### Owner / test contract

| owner | minimum contract | focused check |
|---|---|---|
| signed command/state owner | return sender/session/index/signature/timestamp/salt/ordered-last-seen for every verified entry; preserve packet order | one entry and duplicate `message` entries; final duplicate index is the one delivered |
| command consumer owner | resolve by name/node/raw range; use final map value; preserve permission/event path | altered raw range or missing context does not execute or send |
| chat egress owner | construct existing `PlayerChatMessage`; route with existing `OutgoingChatMessage::send_to_player` | packet is `CPlayerChatMessage`, not `CDisguisedChatMessage`; sender/index/signature/body fields match |
| recipient cache owner | keep per-recipient previous-message ID/full-signature selection and pending ACK updates | cache miss/hit produce different `PreviousMessage` encodings; `messages_received` increments per recipient |
| unsigned policy owner | no valid secure record means disguised/system output only | reports-disabled/offline/no-session path has no secure attribution claim |

Suggested focused tests, without a framework or new fixture generator:

- one verified `/msg` record preserves sender UUID, session UUID in the internal
  link, chain index, signature, raw content, timestamp, salt, and last-seen list;
- duplicate entries consume successive indexes but only the final map record is
  delivered;
- source gets outgoing chat type and each target gets incoming chat type plus
  target name;
- recipient cache miss sends full previous signature and cache hit sends an ID;
- signed send marks recipient pending ACK and increments only that recipient's
  outbound global index;
- unsigned/offline/no-session path remains disguised/system and does not invent
  a nil-session signed player packet;
- invalid/missing/changed name-node-raw binding stops before executor and egress.

A self-generated fixture, even if it passes the Rust codec and its own signer,
is not vanilla client/server evidence. Existing RSA/canonical fixtures prove
fixed test vectors only; there is no existing real 26.2 client outbound
`MessageArgument` packet capture or recipient-ACK round trip. Mark that gap
explicitly until a separately authorized vanilla run or independent packet oracle
exists.

## Recommended Next Steps

1. Implement only the per-entry authenticated record return and `/msg` signed
   egress consumer described above. Reuse `signature.rs`, `state.rs`,
   `PlayerChatMessage`, `CPlayerChatMessage`, `OutgoingChatMessage`, and
   `MessageCache`; add no dependency and no framework.
2. Keep `/say`, `/me`, and `/teammsg` on their current unsigned/system behavior
   until each has an explicit official `MessageArgument` component/filter/target
   contract. Do not call the system path “signed compatibility.”
3. In a later patch, implement selector resolution, decorator, text-filter result,
   and recipient-specific filter masks if the current command model lacks them.
   Keep those display transformations in `unsigned_content`/`filter_mask`; never
   mutate the signed raw content.
4. Separately repair `World::broadcast_secure_player_chat` so it receives the
   actual verified inbound session/index instead of nil session plus
   `messages_sent`. This is not part of the first `/msg` patch.
5. After focused tests, run only the permitted project checks in a separate owner
   task. This investigation ran no cargo/server/install/download command.
