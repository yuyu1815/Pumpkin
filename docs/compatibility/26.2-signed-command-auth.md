# 26.2 signed-command auth

## Findings

- `SChatCommandSigned` now has a dedicated authentication path. It never falls back to
  `SChatCommand` after decode, parse, ACK, session, chain, or RSA failure.
- Parsing uses the existing player `CommandSource` and `ParsingResult::signable_arguments()`.
  Permission filtering therefore remains before signature lookup; execution still uses the
  existing permission/event dispatcher after authentication.
- Packet signature entries are matched by argument name, but verification order is packet entry
  order. Each entry uses the parsed argument's original UTF-8 byte substring, not the typed value,
  argument name, or whole command.
- The state transaction previews the ACK window on a clone, verifies every entry at successive
  `next_index` values, and commits ACK state plus chain cursor only after all entries verify.
  A signable-empty command still passes the same session/ACK/checksum transaction with zero chain
  entries. A signable command with missing, unknown, or duplicate entries is rejected.
- A valid chat session is required for signed packets: non-nil session UUID, validated public key
  and key certificate, and unexpired profile key. Ordinary unsigned commands remain legal when
  `allow_chat_reports=false`; when secure reports are enabled, ordinary commands with signable
  arguments are rejected before event/execute and are not treated as secure attribution.

## Official 26.2 bytecode confirmation

Primary artifact: `C:/Temp/minecraft-26_2-inner.jar` (static inspection only; no runtime
round-trip). Rechecked with `C:/Program Files/Java/jdk-21/bin/javap.exe`.

- `ArgumentSignatures` limits entries to `8`; entry names use UTF-8 length `16`; signatures are
  fixed `256` bytes. `signCommand` signs `SignableCommand.Argument.value()` and stores the node
  name separately.
- `SignableCommand` visits parsed argument nodes and signs only the `SignedArgument` marker
  types. Its value is `ParsedArgument.getRange()` applied to the original command string.
- `ServerGamePacketListenerImpl.handleSignedChatCommand` applies the last-seen update before
  dispatch, then `performSignedChatCommand` parses with the player source and checks packet
  entries by name. Unknown or missing argument names fail; empty entries for a signable argument
  go through the unsigned decoder and fail when a secure profile is required.
- For each packet entry, the decoder consumes one link in packet-entry order. The next link uses
  `index`, sender UUID, and session UUID; the body uses the same packet timestamp, salt, and
  reconstructed last-seen list. The official link index is not the wire `message_count`.
- `SignedMessageBody.updateSignature` order is `salt`, timestamp `Instant.getEpochSecond()`,
  UTF-8 content length/content, then last-seen signatures. The existing Rust canonical helper
  already supplies the outer version/link prefix and this body order.
- The official decoder rejects a missing/expired profile key, rejects timestamps older than the
  previous accepted body, and marks the chain broken on out-of-order or invalid RSA signature.
  Server-expiry is logged by vanilla after successful verification rather than used as a hard
  rejection. Pumpkin retains the existing profile-key expiry gate and chain policy.

## Migration / Investigation Notes

- `message_count` is treated only as the last-seen ACK offset. It is never used as a chain index.
  N verified arguments consume `next_index .. next_index + N - 1`. A checksum byte of `0` is the
  official `IGNORE_CHECKSUM` sentinel; non-zero checksums are verified against the preview result.
- The shared normal-chat state now stores the comparison timestamp as epoch seconds, matching the
  signed body and official `Instant` semantics; wire timestamps remain epoch milliseconds in the
  body canonicalization.
- Invalid ACK/checksum/session/lifecycle input does not commit the cloned validator. Invalid
  signature, replay, old timestamp, session mismatch, or signed argument name-set mismatch makes
  the inbound chain fail closed; it does not advance the cursor or execute the command.
- No new dependency, fallback, or abstraction was added. `net/java/mod.rs`, egress, protocol
  decoding, and independent fixture tooling were not changed by this owner.
- The independent `tools/compat-26_2/chat-fixtures/signed-command-independent.json` fixture is
  now present. Rust now also consumes its N=2 vectors through `verify_signed_command_and_commit`
  in `signed_command_fixture_exercises_n2_atomicity_and_no_signable_ack`; this is state-path
  evidence, not vanilla runtime capture. An independent Node/OpenSSL-compatible verification checked all 6 vectors: byte
  lengths `69, 334, 335, 596, 590, 585`, recorded SHA-256 values, and RSA verification `6/6`.
  This proves the fixed test-only canonical vectors, not vanilla runtime acceptance. Production
  wiring is implemented, but full compatibility acceptance is still **not claimed** until the
  fixture is connected to Rust integration coverage and a vanilla round-trip is observed.

## Recommended Next Steps

1. Add an independent known-answer signed-command fixture (one entry and N=2) and assert the
   exact Rust canonical bytes/signatures; do not generate the signing key/signature in the test.
2. Run focused `pumpkin` state/handler tests plus protocol and command tests under the mandated
   toolchain/target. Treat a compile-only result as insufficient for production compatibility.
3. Keep vanilla runtime positive/negative cases separate: ACK mutation, raw argument mutation,
   replay, chain broken, session expiry, permission failure, and no-signable ACK-only execution
   remain unconfirmed outside the Rust state-path test. Do not call safe rejection “compatibility
   completed.”

## Final implementation follow-up

`handle_signed_chat_command` now executes the authenticated parse result directly and rejects a
command event mutation. The signed branch is inline in `handle_play_packet`, while ACK handling
uses the same `chat_lifecycle` lock. The project policy remains atomic preview/commit rather than
official ACK-first mutation. Reports-disabled ordinary unsigned commands are still a separate
policy path; the secure signed path's no-session rejection remains an explicit compatibility gap,
not a pass claim.
