# 26.2 Configuration state transition fix (NET-CONFIG)

- Target: Minecraft Java Edition 26.2 / protocol `776`
- Scope: `crates/pumpkin/src/net/java/pending.rs`, Java login/configuration flow, and the existing Play `configuration_acknowledged` handler.
- Explicitly out of scope: protocol decoder, chat, entity, world, generated packet data, manifest changes, dependency changes, server startup, and Cargo/build commands.
- Status: source-level fix and local regression tests added; compilation/test execution is intentionally deferred because the world担当 currently owns the Cargo/build lane.

## Findings

### Primary specification evidence

The repository's existing connection evidence records the official 26.2 server artifact as:

- `C:/Temp/minecraft-26_2-server.jar`
- size `60,894,273` bytes
- SHA-1 `823e2250d24b3ddac457a60c92a6a941943fcd6a`
- embedded version metadata: `id=26.2`, protocol `776`, world version `4903`, Java major `25`

The already-read official-JAR/source cross-check in `docs/compatibility/26.2-connection.md` identifies the relevant packet classes (`ClientboundFinishConfigurationPacket`, `ClientboundSelectKnownPacks`, `ServerboundFinishConfigurationPacket`, `ServerboundSelectKnownPacks`, and the resource-pack configuration packets). The repository packet source and mapping audit record these 26.2 IDs:

- clientbound configuration `finish_configuration=3`, `select_known_packs=14`
- serverbound configuration `select_known_packs=7`, `finish_configuration=3`
- play clientbound `start_configuration=118`; play serverbound `configuration_acknowledged=16`

The normal first configuration sequence is:

1. Login Success (`login_finished`), then client Login Acknowledged.
2. Server enters Configuration and sends branding/links and, when enabled, the configuration resource-pack offer.
3. Server sends enabled features and `select_known_packs`; for a resource pack, this waits until the valid resource-pack response advances the flow.
4. Client sends `select_known_packs` (the response may be a legal subset; it is decoded but not semantically compared here).
5. Server sends Registry Data, Update Tags, and Finish Configuration.
6. Client sends the empty Finish Configuration acknowledgment.
7. Server enters Play.

For reconfiguration, the official protocol has a serverbound Play `configuration_acknowledged` response to a server-issued clientbound `start_configuration`. This repository has the `CStartConfiguration` codec, but no server send call site was found. Therefore this change does **not** invent a reconfiguration sender or reject any existing legal reconfiguration flow: it rejects the response while no server-issued reconfiguration is pending. A future sender must move the shared phase to `ReconfigurationAwaitingAck` before sending `CStartConfiguration`.

### Confirmed defects and minimum corrections

1. `PendingConnection::handle_config_packet` accepted Finish Configuration before `CFinishConfig` had been sent, and after duplicate/incorrect sequences. It now requires `ConfigurationPhase::AwaitingFinishAck` and requires an empty packet body.
2. The Known Packs handler ignored the packet body, so the existing `SKnownPacks::read` bound (`0..=64` plus bounded strings) was bypassed. It now decodes the packet, allows any valid client selection, rejects trailing bytes, and only accepts it in `AwaitingKnownPacks`.
3. Resource-pack responses were accepted without a phase guard, and the pending handler did not verify the configured pack UUID. It now requires `AwaitingResourcePack`, verifies the UUID derived from the configured URL, disconnects an invalid/unknown response without advancing, and preserves the existing selective response behavior: `Accepted` remains pending; downloaded/success/discarded/optional decline/failure advances to Known Packs; forced decline/failure and invalid/reload-failed responses still kick.
4. A Play `configuration_acknowledged` packet unconditionally changed `JavaClient::connection_state` to Config even though Pumpkin has no `CStartConfiguration` sender. It now parses the empty packet body and kicks unsolicited acknowledgments without changing state. The handler permits the future `ReconfigurationAwaitingAck` phase and then moves the shared configuration phase to `AwaitingKnownPacks`.

## Migration / Investigation Notes

### Shared phase state

`ConfigurationPhase` is an enum, not a collection of independent booleans:

| Phase | Legal inbound transition |
|---|---|
| `NotInConfiguration` | no configuration response |
| `AwaitingResourcePack` | valid configured resource-pack status; `Accepted` stays here |
| `AwaitingKnownPacks` | one valid `select_known_packs` packet |
| `AwaitingFinishAck` | one empty `finish_configuration` packet |
| `Play` | no initial-configuration response; duplicate Finish Ack is rejected by the pending path and cannot promote again |
| `ReconfigurationAwaitingAck` | one empty Play `configuration_acknowledged` packet; no current sender sets this phase |

The same `AtomicCell<ConfigurationPhase>` is moved by `JavaClient::from_pending`, so the phase is not copied into a second independent flag during Login → Configuration → Play handoff. `connection_state` remains the coarse dispatcher state; `ConfigurationPhase` is the single source for configuration sub-phase ordering.

A disconnect while resource-pack or Known Packs pending does not advance this phase: the existing `get_packet` close/EOF path returns `None`, and no response handler is called. A malformed or out-of-phase packet returns `ReadingError`; the existing pending loop sends a disconnect and closes the connection. This preserves the existing disconnect guard without adding a timeout or a second pending boolean.

## Recommended Next Steps

1. Keep the four pure tests as the regression floor. Add a permitted stateful TCP regression later for: Finish Ack before Finish Config, duplicate Finish Ack, Known Packs before request, malformed Known Packs count/truncated string, valid subset Known Packs, Accepted resource-pack response followed by Downloaded, wrong resource-pack UUID, and disconnect before response.
2. When reconfiguration is implemented, make its sender the only code path that changes `Play → ReconfigurationAwaitingAck` and sends `CStartConfiguration`; then route the subsequent Configuration packets through the same phase owner rather than adding booleans or a parallel dispatcher.
3. Keep vanilla-client evidence separate from synthetic framing: the existing `play_frame_observed`/`known_pack_reply=true` records do not prove registry semantics, resource-pack acceptance, or Java 25 client compatibility.
