# Java 26.2 inventory crafting: remainder / transmute investigation

## Findings

- 対象は Java Edition **26.2** の既存データと実装経路であり、26.1 のデータは使用していない。既存記録の protocol は `776`、world/data version は `4903` である。
- 先行 `INV-01` の oak log → oak planks の通常 recipe、部分 stack、満杯 inventory、内部反復 craft は再調査していない。今回の新規対象は次の **2 シナリオ**だけに絞った。
  1. cake の残容器（milk bucket → bucket）を、通常の result pickup と close/cursor return で検査する。
  2. map-cloning transmute の材料倍率、filled map の `map_id` component、input/material の厳密な組合せを検査する。
- 既存の `ResultSlot::on_take_item` は input を1個ずつ消費するだけで、残容器 registry を使わず、通常 pickup 後に result preview を明示的に再計算していなかった。これは cake の milk bucket が消える候補を、実 handler path で示せる欠陥として最小修正した。
- transmute は従来、2つの occupied slot が `input` または `material` のどちらかに一致すれば通っていた。そのため `filled_map + filled_map` のような input/input も result を生成し得た。input 1個と material 1個の順序を厳密に確認するよう最小修正した。
- transmute result は従来 `ItemStack::new` で新規作成され、source input の patched component を引き継がなかった。map cloning の `map_id` を source input から result に移すようにした。
- 26.2 datapack の `map_cloning.json` は `add_material_count_to_result: true` を定義している一方、生成された Rust の `CraftingTransmute` model はこの flag を保持していない。handler 内では、input=`filled_map` / material=`map` / result=`filled_map` のこの vanilla recipe に限り、blank map stack count を result count に加える。
- 26.2 datapack の `map_extending.json` は `crafting_special_mapextending` であり、現行の `CraftingRecipeTypes` match には一般化された special recipe 実装がない。今回ここを「実装済み」とは扱わず、仕様不明・範囲外の未解決事項として残した。

## Migration / Investigation Notes

### 実際に使った handler path

テストは recipe matcher や quick-move の再実装を作らず、既存 screen handler を直接操作する。

```text
ScreenHandler::update_to_client
  -> ResultSlot listener / ResultSlot::refill_output
ScreenHandler::on_slot_click
  -> SlotActionType::Pickup
  -> ResultSlot::try_take_stack_range / ResultSlot::on_take_item
PlayerScreenHandler::on_closed または CraftingTableScreenHandler::on_closed
  -> default cursor return
  -> crafting grid drop/offer path
```

map の invalid ケースは同じ handler に grid input を置き、`update_to_client` 後の result preview と no-op QuickMove を確認する。oak/planks の INV-01 shift-click path は今回再利用・再判定していない。

### 保存則

- cake は1 recipe あたり、3 milk bucket input が消費され、cake 1個が cursor に出て、3個の empty bucket が grid に残る。close 時に cursor の cake と grid の bucket が player inventory または drop へ移る。preview slot 自体は所有済み output に加えない。
- map cloning の最小ケースは filled map 1個 + blank map 1個 → filled map 2個。input の `map_id=42` component が result へ移り、input 2 slot は消える。これは 26.2 datapack の `add_material_count_to_result` に対応する。
- invalid transmute は filled map 2個では result を生成しない。したがって input/material の組合せが成立しない場合、材料消費・生成物・cursor/drop の副作用は発生しない。

### 最小修正

1. `ResultSlot::recipe_remainder` は現行 generated item constants だけを使い、次の remainder を作る。`pumpkin-data` の `recipe_remainder` module は feature-gated で、今回の所有範囲では manifest を変更できないため、generated item IDの二重管理ではなく既存 `Item` constants の identity を使う最小経路に留めた。
   - milk bucket → bucket
   - mushroom stew / rabbit stew / beetroot soup / suspicious stew → bowl
   - potion / honey bottle → glass bottle
2. `ResultSlot::on_take_item` は input 1個を消費した後、slot が空なら remainder を同じ crafting slot に戻す。残りの input stack がある場合は `offer_or_drop_stack` に渡し、勝手に捨てない。最後に `refill_output` を呼ぶため、通常 pickup 後の stale preview を残さない。
3. transmute は occupied slot 2個を input/material の順序付き pair として確認する。valid pair の input slotを `copy_components_from` に記録し、result stack の patched component をコピーする。
4. map cloning だけは 26.2 datapack の倍率 flag が generated Rust model にないため、item identity が一致する限定分岐で material count を result count に加える。全 transmute に倍率を推測適用していない。

## Recommended Next Steps

1. remainder の full inventory / partial destination を別ケースで検査する。特に `offer_or_drop_stack` が bucket component を保存し、drop callback/world entity と合計保存則を満たすかを確認する。
2. map cloning は blank map を複数 occupied slot に置く 2..8 ケースを別シナリオで検査する。現行 matcher は occupied slot 数を `count` とし、`on_take_item` は各 slot を1個だけ消費するため、stacked material と複数 slot の仕様を混同しない。
3. `map_extending.json`、decorated pot、special/dynamic recipe、recipe-book use-max、component transform の vanilla 26.2 oracle 比較は未確認である。これらを実装済みと断定せず、公式 26.2 client/server の隔離 differential test を後続で行う。
4. 26.1 data は今回使用していない。26.2との差分を一次資料で再確認できない限り、26.1の recipe semantics を補助根拠として流用しない。
