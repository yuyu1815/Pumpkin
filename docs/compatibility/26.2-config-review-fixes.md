# Minecraft Java 26.2 configuration residual fixes

- Target: Java Edition `26.2` / protocol `776` / world data version `4903`
- Scope: configuration state only. Inventory, close/window-id, chat, generated packet data, dependencies, Cargo/build, and server startup are out of scope.
- Ownership: `crates/pumpkin/src/net/java/pending.rs`, `net/java/login/`, `net/java/config/`, configuration-state portions of `net/java/mod.rs`, and this document.
- Status: **CFG-T1 and CFG-T2 source fixes plus local regression tests added. CFG-T3 reconfiguration remains intentionally incomplete.**

## Findings

### CFG-T1: resource-pack status is terminal only at the official boundary

The official 26.2 artifact is `C:/Temp/minecraft-26_2-server.jar`, SHA-1
`823e2250d24b3ddac457a60c92a6a941943fcd6a`; the extracted inner artifact used
for bytecode inspection is `C:/Temp/minecraft-26_2-inner.jar`.

`net.minecraft.network.protocol.common.ServerboundResourcePackPacket$Action.isTerminal()`
returns false only for `ACCEPTED=3` and `DOWNLOADED=4`. Therefore `Downloaded`
is an intermediate notification, not permission to advance the configuration task.
`DownloadSuccess=0` is the successful terminal result. The implementation now
shares this matrix between `PendingConnection` and the reserved JavaClient
configuration handler. The official `ServerCommonPacketListenerImpl` bytecode
has an explicit required-pack disconnect only for `Declined`; other non-wait
statuses are terminal and let the configuration task continue:

| Result | Optional pack | Required pack | State effect |
|---|---|---|---|
| `Accepted=3` | wait | wait | remain `AwaitingResourcePack` |
| `Downloaded=4` | wait | wait | remain `AwaitingResourcePack` |
| `DownloadSuccess=0` | complete | complete | send Known Packs once |
| `Declined=1` | complete | kick | official required-decline policy |
| `DownloadFail=2` | complete | complete | official terminal result; no wait |
| `Discarded=7` | complete | complete | terminal |
| invalid/reload/unknown | complete | complete | terminal; no second wait |

UUID verification remains mandatory: only the UUID derived from the configured
resource-pack URL is accepted. A mismatch kicks and does not advance. Once a
terminal result advances the phase, a duplicate response is out of phase and is
rejected; this prevents a second Known Packs request.

### CFG-T2: Known Packs is an exact ordered comparison, not an exact-only rejection

The official 26.2 `net.minecraft.server.network.config.SynchronizeRegistriesTask`
bytecode performs `List.equals` against the request. On equality it passes
`Set.copyOf(requestedPacks)` to registry serialization; on mismatch it passes
`Set.of()`. Both branches call registry serialization and then continue to the
next configuration task. Thus subset, empty, unknown, reordered, or duplicate
replies are **not rejected as malformed** when their count and strings are
wire-valid. They select the fallback/empty known-pack set and still reach Finish.

The implementation now:

1. stores the actual serialized request as owned `(namespace, id, version)` tuples
   before sending `CKnownPacks`;
2. compares the response to that stored list with length, tuple values, and order;
3. classifies only a complete ordered match as `KnownPacksSelection::Exact`;
4. classifies subset, empty, unknown, reordered, duplicate, and missing-request
   cases as `KnownPacksSelection::Fallback`;
5. continues to Registry Data, Update Tags, and Finish for both classifications;
6. deliberately keeps every registry packet and entry payload because Pumpkin's
   generated registry table has no per-entry Known Pack ownership metadata. It
   does not incorrectly omit registry data merely because the response selected
   the official empty set. Safe per-entry omission requires that missing metadata
   to be added by a separate registry-data task.

The same request state is moved from `PendingConnection` to `JavaClient`, so the
initial path and the reserved future configuration path do not maintain separate
request copies.

### CFG-T3: reconfiguration is deliberately deferred

`ReconfigurationAwaitingAck` remains reserved and its dead-code warning is not
suppressed. This task does not add a `CStartConfiguration` sender, a Play-to-Config
inbound dispatcher, Config-to-Play return path, or a stateful reconfiguration test.
The next dedicated task must implement these as one unit:

1. the sole guarded sender transitions `Play -> ReconfigurationAwaitingAck` before
   sending `CStartConfiguration`;
2. the empty Play `configuration_acknowledged` body is checked and admitted only
   for that pending phase;
3. inbound Configuration packets are routed to the shared configuration owner;
4. Known Packs exact/fallback selection, Registry Data, Tags, and Finish are
   processed through the same stateful path;
5. Finish acknowledgment returns to Play exactly once, with duplicate, mixed-state,
   trailing-body, and disconnect cases covered.

The current change therefore fixes initial configuration and prepares shared state
for that work; it does **not** claim reconfiguration compatibility.

## Validation limits

- No vanilla 26.2 client acceptance or stateful TCP loopback was performed.
- Registry payload semantic equality with the official per-entry Known Pack
  ownership metadata remains unverified; this change intentionally uses the safe
  full-payload fallback rather than omitting data.
- The official listener bytecode used here establishes terminal status and Known
  Packs selection behavior; it does not by itself establish a UUID-mismatch
  rejection policy. The UUID rejection is Pumpkin's retained configured-pack
  identity guard and is covered by the local pure test.
- Inventory, close/window-id, and chat were not modified.
