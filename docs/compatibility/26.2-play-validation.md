# 26.2 first playable 縦断検証

## Findings

- 既存の `play_frame_observed` は維持し、`tools/compat-26_2/protocol776_harness.py` に opt-in の `--strict-play` を追加した。strict の成功条件は、単なる Play frame の受信ではなく、次の同一接続上の縦断成立である。
  1. protocol `776` の status/login/configuration state 遷移。
  2. configuration の Known Packs 応答と Finish Configuration。
  3. Play の Join Game (`minecraft:login`) を 26.2 の既存 codec 順序で完全消費。
  4. Player Position (`minecraft:player_position`) の座標・速度・rotation・relative flags・teleport id を完全消費し、同じ id の Accept Teleportation を送信。
  5. 最初の Level Chunk With Light (`minecraft:level_chunk_with_light`) の外側構造を完全消費。
  6. Play Keep Alive (`minecraft:keep_alive`) を i64 echo して少なくとも一回応答。
- strict の実 Pumpkin 接続は成功した。`strict_play_validation: "pass"`、`result: "first_playable_strict"` を返すが、`real_client_compatibility: "not_claimed"` は意図的に残している。
- packet ID は新規推測せず、`assets/packet/26_2_packets.json` を runtime に読み、`verify_critical_mapping()` で state/direction/ID を検査する。今回の必須 ID は以下。

## Migration / Investigation Notes

### strict の検証範囲

- Join Game は 26.2 の `CLogin` 実装に合わせ、entity id、hardcore、dimension list、max/view/simulated distance、game mode、dimension id/name、seed、debug/flat、death position option、portal cooldown、sea level、26.2 online mode、secure chat までを読み、trailing bytes を拒否する。
- Player Position は finite な座標/速度/rotation と teleport id を読み、受信した teleport id を `accept_teleportation` packet として同じ compression state で返す。strict の `teleport_confirms_sent` はサーバーへ送った確認値であり、vanilla client が画面表示まで受理したことを意味しない。
- First chunk は chunk x/z、26.2 heightmap 3件（key `1,4,5`、各37 longs）、opaque section-data length、block entity count、4つの light BitSet、sky/block light array lengths と bytes の境界を検証する。section palette、biome、block state、light の意味論はデコードしていない。
- block entity count が非ゼロの場合は、NBT を解読したふりをせず strict failure にする。今回の fresh world の最初の chunk は `block_entities=0` だった。
- Known Packs には空リストを返す。これは pack registry の同一性を確認した結果ではなく、未知の pack identifier を推測していないだけである。Registry Data、Update Tags、resource pack、chat signing、その他大半の Play payload は ID/framing のみ検査または opaque のままである。

## Recommended Next Steps

1. **vanilla 26.2 client の実接続** — Java 25 と利用権限/EULA を別途準備し、公式 client のログ・受信 packet acceptance をこの synthetic harness の結果と分離して取得する。ここが「本物 client 互換」を主張するための第一ブロッカーである。
2. **configuration registry / known packs** — 空 Known Packs 応答のままでは registry の同一性を主張できない。公式 26.2 の既知 pack registry と server の `Registry Data` / `Update Tags` を payload 単位で比較する。
3. **chunk semantic acceptance** — 現 strict は first chunk の外側境界と light array 境界だけで、section palette/biome/block state/light semantics/非空 block-entity NBT は未検証である。非空 block entity fixture と、公式 client が実際に chunk を受理した証拠が必要。
4. **longer gameplay trace** — `move_player_pos` など serverbound の通常移動、tick、追加 chunk、respawn、resource pack、chat signing、online-mode/encryption は未検証。first playable は gameplay 完了の pass ではない。
5. **固定 binary の扱い** — 今回は cargo build を禁止されたため、`C:/Temp/pumpkin-target-26_2-next/debug/pumpkin.exe` の再利用結果である。strict harness の変更を binary に組み込んだ再ビルドは、所有範囲と build 許可が得られた別作業で行う。
